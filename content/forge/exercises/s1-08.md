# S1-08 · Recuperación y diseño reversible

Banco de la celda: predecir qué pierde una restauración, escribir la consulta que verifica una migración, operar un incidente de migración fallida, distinguir los tres «revertir», escribir un plan de recuperación verificable y transferirlo a dos versiones de la aplicación conviviendo.

## Restaurar el respaldo de las 02:00
type: prediccion
id: s1-08-pred-restaurar
rol: prediccion
escala: 50 70 90

La migración en sitio empezó a las 02:00 y falló a las 02:40. Entre tanto se hicieron 41 reservas y el trabajo de recordatorios envió 300 SMS. Restauras el respaldo de las 02:00. Predice el estado después de restaurar.

### Opciones
- [x] La tabla vuelve a estar consistente, pero se pierden las 41 reservas y los 300 SMS siguen enviados: hay que recuperar las reservas por otra vía y compensar los SMS.
- Todo queda como a las 02:00, incluidos los SMS, que el proveedor cancela al detectar la restauración.
- La tabla queda consistente y las 41 reservas se conservan, porque la restauración sólo deshace la migración.
- Nada cambia hasta reiniciar la aplicación.
### Justificación
Restaurar devuelve los datos a un instante: todo lo escrito después, migración incluida, desaparece, y eso incluye reservas legítimas. Una restauración no distingue entre los cambios de la migración y los de los usuarios. Los efectos que ya salieron del sistema (los SMS) no se deshacen restaurando una base: se compensan con otra acción, y para eso hay que saber a quién se enviaron.

## La consulta que verifica la migración
type: sql
id: s1-08-sql-verificar
orden: no

La migración rellena `inicio_utc_min` a partir de `inicio_local_min` y del desfase de la sede (`utc = local - desfase_min`; por ejemplo, la sede Norte está en UTC−6, `desfase_min = -360`). Escribe la consulta de verificación que debe devolver **cero filas** cuando la migración terminó bien: lista las citas sin `inicio_utc_min` o cuyo valor no corresponde al de su sede. Una columna: `cita_id`.

### Esquema
```sql
CREATE TABLE sede (sede_id TEXT PRIMARY KEY, desfase_min INTEGER NOT NULL);
CREATE TABLE cita (
  cita_id          TEXT PRIMARY KEY,
  sede_id          TEXT NOT NULL REFERENCES sede(sede_id),
  inicio_local_min INTEGER NOT NULL,
  inicio_utc_min   INTEGER
);
```
### Datos
```sql
INSERT INTO sede VALUES ('NORTE', -360), ('SUR', -300);
INSERT INTO cita VALUES
  ('C-1', 'NORTE', 480, 840),
  ('C-2', 'NORTE', 540, 900),
  ('C-3', 'SUR', 600, 900);
```
### Fixtures
```sql
-- fixture: completa
UPDATE cita SET inicio_utc_min = inicio_utc_min WHERE cita_id = 'C-1';
```
```sql
-- fixture: lote-pendiente
INSERT INTO cita VALUES ('C-4', 'NORTE', 660, NULL);
```
```sql
-- fixture: signo-invertido
UPDATE cita SET inicio_utc_min = inicio_local_min - 360 WHERE cita_id = 'C-2';
```
### Solución
```sql
SELECT c.cita_id
FROM cita c
JOIN sede s ON s.sede_id = c.sede_id
WHERE c.inicio_utc_min IS NULL
   OR c.inicio_utc_min <> c.inicio_local_min - s.desfase_min
```
### Ingenua
```sql
SELECT c.cita_id
FROM cita c
WHERE c.inicio_utc_min IS NULL
```

## Tres maneras de «revertir»
type: multiple_choice
id: s1-08-choice-revertir
rol: recuperacion

Sin volver al libro: un despliegue cambió el cálculo de precios, migró la columna `precio` a centavos y envió 120 facturas por correo con montos equivocados. ¿Qué combinación describe bien la vuelta atrás?

### Opciones
- [x] Redesplegar el código anterior es barato; volver la columna a su forma anterior exige una migración o una restauración (y puede perder lo escrito después); las 120 facturas no se deshacen: se compensan con facturas de corrección enviadas desde el registro de envíos.
- Con redesplegar el código anterior basta, porque el código anterior vuelve a calcular todo bien.
- Restaurar el respaldo de antes del despliegue deshace las tres cosas.
- Se borran las facturas del servidor de correo y así nadie las ve.
### Justificación
Son tres cosas distintas. El código vuelve atrás con un despliegue. Los datos ya migrados no vuelven solos: el código viejo leería centavos como pesos. Y lo que salió del sistema (las facturas en los buzones de los clientes) sólo se compensa con otra acción, para la que hace falta saber qué se envió y a quién. Restaurar no alcanza buzones ajenos, y borrar del servidor propio no retira lo ya entregado.

## Un plan de recuperación verificable
type: production
id: s1-08-prod-plan

Tienes que cambiar `paciente.nombre` (una sola columna) por `nombre` y `apellidos`. Escribe el plan para hacerlo de forma reversible, con la vuelta atrás de cada paso y la comprobación que decide si se sigue.

### Modelo
1. Respaldo y restauración de prueba en una copia; se registran conteo de filas y suma de verificación. Vuelta atrás: no aplica. 2. Expandir: agregar `nombre_pila` y `apellidos` nulas; la aplicación sigue leyendo `nombre`. Vuelta atrás: borrar las columnas nuevas. 3. Rellenar por lotes idempotentes con tabla de progreso; los casos que la regla de partición no resuelve (un solo nombre, partículas) van a una lista de revisión en vez de adivinarse. Vuelta atrás: ninguna, `nombre` sigue intacta. 4. Verificar: cero filas sin rellenar fuera de la lista de revisión, y `nombre_pila || ' ' || apellidos = nombre` en todas las filas resueltas. 5. Escribir en ambas formas y cambiar lecturas detrás de un interruptor, primero en un porcentaje pequeño. Vuelta atrás: apagar el interruptor. 6. Contraer tras semanas sin lecturas de `nombre`: quitarla. Vuelta atrás: restaurar desde el respaldo, el único paso caro.
### Regla
Un cambio es reversible si cada paso tiene una vuelta atrás conocida y barata, y si la columna vieja vive hasta que una verificación objetiva dice que la nueva es correcta.
### Rúbrica
- Respaldo verificado por restauración antes de empezar.
- Expandir antes de contraer, con la columna vieja intacta mientras se verifica.
- Lotes idempotentes y reanudables, con tratamiento explícito de los casos que no se pueden convertir.
- Una consulta de verificación con criterio objetivo para avanzar.
- La vuelta atrás de cada paso, señalando cuál es la cara.

## El lote 37
type: prediccion
id: s1-08-pred-lote
rol: prediccion

El relleno de `inicio_utc` corre por lotes de 5,000 con una tabla de progreso, y cada lote sólo toca filas con `inicio_utc` nula. El lote 37 de 60 falla por horas ambiguas en una sede. La columna vieja `inicio` sigue intacta y la aplicación todavía la lee. Predice qué conviene hacer.

### Opciones
- [x] Corregir el cálculo de las horas ambiguas y reanudar desde el lote 37: los lotes 1 a 36 ya están bien, y como cada lote es idempotente no se repite ni se salta ninguna fila.
- Restaurar el respaldo y empezar de cero, porque una migración que falla nunca se reanuda.
- Repetir los 60 lotes desde el primero para estar seguros.
- Borrar la columna nueva de inmediato, porque los usuarios ya ven datos corruptos.
### Justificación
El diseño reversible hizo barata esta falla: la columna vieja sigue siendo la fuente que lee la aplicación, así que nadie ve datos a medio convertir y no hay nada que restaurar. Los lotes idempotentes con tabla de progreso permiten reanudar donde se quedó. Restaurar perdería lo escrito desde el respaldo sin necesidad; repetir todo es seguro pero desperdicia trabajo; borrar la columna nueva no hace falta porque todavía no se lee.

## Giro: dos versiones de la aplicación a la vez
type: giro
id: s1-08-giro
rol: transferencia

La clínica no acepta ventana de mantenimiento: durante una semana conviven la versión vieja de la aplicación (que lee y escribe `inicio` en hora local) y la nueva (que usa `inicio_utc`), en sedes distintas. ¿Cómo cambia tu plan de migración? Explica cómo mantienes las dos columnas coherentes mientras ambas versiones escriben y qué verificas antes de apagar la versión vieja.

### Rúbrica
- Reconoce que ambas versiones escriben y que la migración por lotes ya no basta: hace falta escritura doble o una sincronización entre columnas.
- Define cuál columna es la fuente de verdad durante la convivencia y cómo se resuelven diferencias.
- Mantiene la verificación objetiva (cero diferencias entre columnas) como condición para avanzar.
- Explica qué pasa con los recordatorios y otros lectores durante la semana.
- Preserva la vuelta atrás barata hasta el paso de contraer.
