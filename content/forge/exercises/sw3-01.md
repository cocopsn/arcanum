## Antes de leer: once bytes en ocho
type: prediccion
id: prediccion-once-en-ocho
rol: prediccion
tiempo: 2

Un flujo de bytes vacío tiene capacidad 8. El escritor empuja `hello world` (11 bytes). ¿Qué pasa?

### Opciones
- [x] Entran los primeros 8 bytes (`hello wo`) y el flujo informa que aceptó 8; los 3 restantes no se guardan y el escritor debe reintentarlos cuando haya lugar.
- Entran los 11, porque la capacidad es una recomendación.
- No entra nada, porque el mensaje no cabe completo.
- Entran los últimos 8 bytes, porque el flujo descarta lo más viejo.
### Justificación
La capacidad es un límite de memoria: el flujo acepta lo que cabe y dice cuánto aceptó. Rechazar todo desperdiciaría el lugar disponible y castigaría a los mensajes grandes; aceptar todo rompería el límite. Descartar los bytes más viejos cambiaría el contenido del flujo, que debe entregar los bytes en el orden en que se escribieron. Lo que no entró es responsabilidad del escritor.

## Simula el flujo de bytes
type: code
id: codigo-flujo-bytes
tiempo: 15

Implementa el contrato del flujo de bytes del libro como una función que procesa operaciones en orden y devuelve el resultado de cada una.

### Especificación
`flujo(capacidad, operaciones)`:
- `capacidad ≥ 1`. El buffer empieza vacío y abierto.
- `["push", texto]`: agrega al final los primeros caracteres de `texto` que quepan en la capacidad disponible y responde **cuántos** entraron. Si el flujo está cerrado, no agrega nada y responde `0`.
- `["peek"]`: responde el contenido completo del buffer, sin consumirlo.
- `["pop", n]`: consume y responde los primeros `min(n, en buffer)` caracteres.
- `["capacidad"]`: responde la capacidad disponible (`capacidad − en buffer`).
- `["close"]`: cierra el flujo y responde `"ok"`.
- `["fin"]`: responde `true` si el flujo está cerrado **y** el buffer vacío; si no, `false`.
- Devuelve la lista de resultados, en orden. Los textos son ASCII: un carácter es un byte.

### Solución
```javascript
function flujo(capacidad, operaciones) {
  let buffer = "";
  let cerrado = false;
  const salida = [];
  for (const op of operaciones) {
    if (op[0] === "push") {
      if (cerrado) {
        salida.push(0);
        continue;
      }
      const entra = op[1].slice(0, capacidad - buffer.length);
      buffer += entra;
      salida.push(entra.length);
    } else if (op[0] === "peek") {
      salida.push(buffer);
    } else if (op[0] === "pop") {
      const sale = buffer.slice(0, op[1]);
      buffer = buffer.slice(sale.length);
      salida.push(sale);
    } else if (op[0] === "capacidad") {
      salida.push(capacidad - buffer.length);
    } else if (op[0] === "close") {
      cerrado = true;
      salida.push("ok");
    } else {
      salida.push(cerrado && buffer.length === 0);
    }
  }
  return salida;
}
```
```python
def flujo(capacidad, operaciones):
    buffer = ""
    cerrado = False
    salida = []
    for op in operaciones:
        if op[0] == "push":
            if cerrado:
                salida.append(0)
                continue
            entra = op[1][: capacidad - len(buffer)]
            buffer += entra
            salida.append(len(entra))
        elif op[0] == "peek":
            salida.append(buffer)
        elif op[0] == "pop":
            sale = buffer[: op[1]]
            buffer = buffer[len(sale):]
            salida.append(sale)
        elif op[0] == "capacidad":
            salida.append(capacidad - len(buffer))
        elif op[0] == "close":
            cerrado = True
            salida.append("ok")
        else:
            salida.append(cerrado and len(buffer) == 0)
    return salida
```

### Pistas
- `push` acepta como máximo la capacidad disponible y dice cuánto aceptó; lo demás no se guarda.
- `pop` de más es válido: consume lo que hay.
- «Terminó» exige las dos cosas: cerrado y buffer vacío.

## Cerrado no es terminado
type: multiple_choice
id: cerrado-no-terminado
tiempo: 3

El escritor empuja 1,000 bytes, que caben, y cierra el flujo. El lector todavía no leyó nada. ¿Qué responde `¿terminó?` en este momento y qué debe hacer el lector?

### Opciones
- [x] Responde que no: el flujo está cerrado pero quedan 1,000 bytes; el lector sigue consumiendo y sólo se detiene cuando la respuesta es sí.
- Responde que sí, porque el escritor ya cerró y no vendrán más bytes.
- Responde que sí y el flujo descarta los 1,000 bytes, porque el cierre vacía el buffer.
- Lanza un error, porque no se puede cerrar un flujo con datos sin leer.
### Justificación
Cerrar es una decisión del escritor sobre el futuro (no empujará más); terminar es una observación del lector sobre el presente (no queda nada por leer y no vendrá nada). Con datos en el buffer, el flujo está cerrado y no terminado. Si el lector se detuviera al ver el cierre, perdería los 1,000 bytes. El cierre no borra nada y no es un error cerrar con datos pendientes: es lo normal al final de una transferencia.

## Los contadores después de una traza
type: trace
id: traza-contadores
tiempo: 3

Un flujo de capacidad 4 recibe en orden: `push("abcdef")`, `pop(3)`, `push("gh")`, `pop(10)`. ¿Cuánto valen al final los bytes empujados, los consumidos y los que quedan en el buffer?

### Opciones
- [x] 6 empujados, 6 consumidos y 0 en el buffer: entran `abcd`, salen `abc`, entran `gh` (había lugar para 3), y `pop(10)` consume `dgh`.
- 8 empujados, 6 consumidos y 2 en el buffer, porque se empujaron 8 caracteres en total.
- 6 empujados, 13 consumidos y 0 en el buffer, porque se pidieron 13.
- 4 empujados, 6 consumidos y 0 en el buffer, porque la capacidad es 4.
### Justificación
`push("abcdef")` acepta 4 (capacidad), así que se empujaron 4. `pop(3)` consume `abc` y deja `d`. `push("gh")` encuentra lugar para 3 y acepta los 2: van 6 empujados y el buffer es `dgh`. `pop(10)` consume lo que hay, 3 bytes: van 6 consumidos y el buffer queda vacío. Los contadores cuentan lo aceptado y lo entregado, no lo que se intentó; y lo consumido nunca puede superar lo empujado.

## Demuestra el contrato con trazas
type: production
id: produccion-contrato-flujo
tiempo: 12

La defensa de esta celda pide demostrar el contrato del flujo con trazas pequeñas. Escribe el contrato de `push`, `pop` y `¿terminó?` (precondición, postcondición y casos borde) y tres trazas de a lo sumo cinco operaciones que, juntas, cubran capacidad agotada, cierre con datos pendientes y lectura parcial.

### Modelo
*`push(texto)`:* sin precondición sobre el tamaño. Postcondición: si el flujo está cerrado, no cambia nada y devuelve 0; si no, agrega al final los primeros `min(|texto|, disponible)` bytes, devuelve esa cantidad y suma lo mismo a «empujados». Borde: texto vacío devuelve 0.
*`pop(n)`:* precondición `n ≥ 0`. Postcondición: quita y devuelve los primeros `min(n, en buffer)` bytes y suma esa cantidad a «consumidos». Borde: con el buffer vacío devuelve vacío.
*`¿terminó?`:* verdadero si y sólo si el flujo está cerrado y el buffer vacío.
*Invariante:* `0 ≤ en buffer = empujados − consumidos ≤ capacidad`.
*Traza 1 (capacidad agotada, capacidad 3):* `push("abcd") → 3`, `capacidad → 0`, `push("x") → 0`, `pop(1) → "a"`, `push("x") → 1`.
*Traza 2 (cierre con datos, capacidad 4):* `push("ab") → 2`, `close`, `¿terminó? → no`, `pop(2) → "ab"`, `¿terminó? → sí`.
*Traza 3 (lectura parcial, capacidad 8):* `push("hola") → 4`, `pop(10) → "hola"`, `pop(1) → ""`, `push("") → 0`.

### Regla
Un contrato de flujo se demuestra con su invariante y con trazas mínimas que recorren cada borde: aceptación parcial, escritura tras el cierre, cierre con datos pendientes y lecturas mayores que lo disponible.

### Rúbrica
- Escribe postcondiciones que dicen cuánto se acepta o se consume, no sólo qué devuelve la función.
- Distingue cerrado de terminado en el contrato.
- Escribe el invariante que relaciona contadores, buffer y capacidad.
- Las trazas son cortas, concretas y cubren los tres bordes pedidos.
- Incluye al menos un caso de escritura después del cierre o de texto vacío.

## Giro: el lector lento al otro lado de la red
type: giro
id: giro-lector-lento-red
rol: transferencia
tiempo: 15

El escritor ya no es tu propio código: es la red, que entrega datos a 1 Gbps desde otra máquina, y el lector es una aplicación que procesa a 10 Mbps. El flujo sigue teniendo capacidad fija. Rediseña: qué hace el receptor con los bytes que no entran, cómo se entera el emisor remoto de que debe frenar, qué se preserva del contrato del flujo y qué deja de estar en tus manos.

### Rúbrica
- Mantiene el contrato del flujo: acepta lo que cabe, nunca crece sin límite y entrega en orden.
- Explica que el receptor no puede «pedirle a la red» que espere: necesita anunciar al emisor su capacidad disponible para que éste no envíe más de lo que cabe (la ventana de recepción de TCP).
- Distingue descartar bytes que no caben (el emisor tendrá que retransmitirlos) de no haberlos recibido, y explica el costo de cada caso.
- Declara qué deja de controlar (el ritmo del emisor, las pérdidas de la red) y qué garantiza todavía (orden y límite de memoria).
- Conecta con SW3-02 (bytes fuera de orden) o SW3-03 (control de flujo) sin mezclar sus garantías con las del flujo en memoria.
