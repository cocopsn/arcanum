## Antes de leer: mil corridas verdes
type: prediccion
id: prediccion-mil-corridas
rol: prediccion
tiempo: 2

Una función de transferencia toma el lock de la cuenta de origen y después el de destino. La prueba que lanza dos transferencias cruzadas a la vez (Ana a Beto y Beto a Ana) pasó 1,000 veces seguidas. ¿Qué concluyes?

### Opciones
- [x] Nada definitivo: el bloqueo mutuo necesita que los dos threads tomen su primer lock antes de que cualquiera tome el segundo, y esa ventana puede ser rara en la máquina de pruebas y frecuente bajo carga real.
- Que el código no se bloquea, porque mil corridas son una muestra suficiente.
- Que el código se bloquea siempre, pero la prueba no lo detecta porque usa tiempos de espera.
- Que el bloqueo mutuo sólo ocurre con más de dos threads.
### Justificación
El bloqueo mutuo depende de una intercalación concreta: T1 toma `lock(ana)`, T2 toma `lock(beto)`, y entonces cada uno espera el del otro. Si en la máquina de pruebas un thread casi siempre termina antes de que el otro empiece, la ventana casi nunca se abre. Mil corridas verdes miden esa máquina, no el diseño. El argumento correcto es estructural: con dos órdenes de adquisición distintos existe un ciclo posible. Dos threads bastan.

## ¿Quién está en el ciclo?
type: code
id: codigo-en-ciclo
tiempo: 18

Implementa la detección sobre el grafo de espera: devuelve los threads que forman parte de algún ciclo, es decir, los que están en un bloqueo mutuo.

### Especificación
`enCiclo(esperas)`:
- `esperas` es una lista de pares `[a, b]`, que significan «el thread `a` espera un recurso que tiene el thread `b`». Puede haber pares repetidos.
- Un thread está en un ciclo si, siguiendo las esperas desde él, se puede volver a él. Un thread que se espera a sí mismo (`[a, a]`) está en un ciclo.
- Un thread que espera a alguien que está en un ciclo, pero desde el cual no se vuelve a él, **no** está en el ciclo (está bloqueado por arrastre, que es otra cosa).
- Devuelve la lista de threads en algún ciclo, sin repetidos, ordenada de forma ascendente como cadenas.

### Solución
```javascript
function enCiclo(esperas) {
  const ady = new Map();
  for (const [a, b] of esperas) {
    if (!ady.has(a)) ady.set(a, new Set());
    if (!ady.has(b)) ady.set(b, new Set());
    ady.get(a).add(b);
  }
  const vuelve = (inicio) => {
    const vistos = new Set();
    const pila = [...ady.get(inicio)];
    while (pila.length > 0) {
      const n = pila.pop();
      if (n === inicio) return true;
      if (vistos.has(n)) continue;
      vistos.add(n);
      for (const m of ady.get(n)) pila.push(m);
    }
    return false;
  };
  return [...ady.keys()].filter(vuelve).sort();
}
```
```python
def en_ciclo(esperas):
    ady = {}
    for a, b in esperas:
        ady.setdefault(a, set())
        ady.setdefault(b, set())
        ady[a].add(b)

    def vuelve(inicio):
        vistos = set()
        pila = list(ady[inicio])
        while pila:
            n = pila.pop()
            if n == inicio:
                return True
            if n in vistos:
                continue
            vistos.add(n)
            pila.extend(ady[n])
        return False

    return sorted(n for n in ady if vuelve(n))
```

### Pistas
- Un thread está en un ciclo si alguno de los que espera lo alcanza de vuelta: basta un recorrido desde sus sucesores.
- Marca los visitados para no recorrer para siempre un ciclo que no te incluye.
- Ordena como cadenas: `"T10"` va antes que `"T2"`.

## La condición que rompe el orden global
type: multiple_choice
id: condicion-orden-global
tiempo: 3

Para eliminar el bloqueo mutuo en las transferencias, el equipo hace que todo thread tome los locks de las cuentas en orden ascendente de id. ¿Cuál de las cuatro condiciones del bloqueo mutuo rompe esa regla?

### Opciones
- [x] La espera circular: un ciclo exigiría que algún thread esperara un lock de id menor que uno que ya tiene, y el orden ascendente lo prohíbe.
- La exclusión mutua: con el orden, dos threads pueden tener el mismo lock.
- Retener y esperar: con el orden, ningún thread retiene un lock mientras espera otro.
- La falta de expropiación: con el orden, el sistema le quita el lock al thread de id mayor.
### Justificación
Con el orden global los threads siguen reteniendo un lock mientras esperan el siguiente, y los locks siguen siendo exclusivos y sin expropiación. Lo que desaparece es la posibilidad de un ciclo: recorriendo cualquier cadena de esperas, los ids crecen, y una cadena de valores siempre crecientes no puede cerrarse sobre sí misma. Como el bloqueo mutuo necesita las cuatro condiciones juntas, romper una basta.

## Los dos threads demasiado educados
type: trace
id: traza-livelock
tiempo: 4

T1 transfiere de Ana a Beto y T2 de Beto a Ana. Cada uno toma su primer lock, intenta el segundo durante 10 ms y, si no lo obtiene, suelta el primero y reintenta **de inmediato**. Los dos threads arrancan en el mismo instante y corren a la misma velocidad. ¿Qué pasa?

### Opciones
- [x] Un livelock: en cada ronda los dos toman su primer lock, fallan el segundo, sueltan y vuelven a empezar al mismo tiempo; los dos están activos y ninguno transfiere.
- Un bloqueo mutuo clásico: los dos quedan esperando para siempre el lock del otro.
- Nada malo: el tiempo de espera garantiza que en la segunda ronda uno de los dos gana.
- T1 siempre gana porque empezó primero en la lista de threads.
### Justificación
El tiempo de espera rompe «retener y esperar»: nadie espera para siempre con un lock en la mano, así que no hay bloqueo mutuo. Pero si los dos ritmos coinciden, cada ronda repite la misma intercalación: los dos ceden a la vez y vuelven a chocar. Están activos, consumen CPU y no avanzan: es una falla de vivacidad que un monitoreo de threads bloqueados no ve. Nada garantiza que la segunda ronda sea distinta; por eso los reintentos llevan una pausa aleatoria, o mejor, se usa un orden global.

## Lo que garantiza tu diseño y lo que no
type: production
id: produccion-garantias-progreso
tiempo: 12

Para la transferencia con orden global del libro, escribe la defensa que pide la ficha: qué garantiza la corrección del diseño, qué depende del planificador y del lock, y qué pasaría con una transferencia de una cuenta a sí misma.

### Modelo
*Garantiza (seguridad):* el saldo total no cambia y ninguna transferencia ve un estado intermedio, porque los dos locks se toman antes de mover el monto y se sueltan después.
*Garantiza (ausencia de bloqueo mutuo):* con cualquier planificador, porque todos los threads toman los locks en orden ascendente de id, y una cadena de esperas con ids siempre crecientes no puede formar un ciclo.
*Depende del planificador y del lock:* que **cada** transferencia termine. Si el lock no es equitativo y hay mucha contención sobre una cuenta, una transferencia concreta puede esperar indefinidamente mientras otras le ganan (inanición). También depende de que el planificador dé tiempo de CPU a los threads que tienen locks.
*Caso borde:* `transferir(ana, ana, 10)` pediría el mismo lock dos veces; con un lock no reentrante, el thread se bloquea consigo mismo. La especificación lo rechaza como error declarado (`misma-cuenta`) antes de tomar ningún lock.

### Regla
Una defensa de concurrencia separa seguridad («nunca pasa algo malo») de vivacidad («algo bueno termina pasando»), y dentro de la vivacidad separa lo que el diseño garantiza para cualquier planificador de lo que depende de la equidad del lock y del planificador.

### Rúbrica
- Separa explícitamente propiedades de seguridad y de vivacidad.
- Argumenta la ausencia de ciclos con el orden global, no con pruebas que pasaron.
- Distingue bloqueo mutuo de inanición y dice de qué depende la segunda.
- Trata el caso de la transferencia a la misma cuenta.
- No afirma que «toda transferencia termina» sin condiciones.

## Giro: el lote con una cuenta remota
type: giro
id: giro-lote-remoto
rol: transferencia
tiempo: 15

Las transferencias ahora son lotes: un pago de nómina toca hasta 200 cuentas locales, y una de ellas puede ser una cuenta de otro banco a la que se accede por un servicio externo que a veces tarda 30 segundos o no responde. Rediseña la adquisición de recursos: cómo evitas el bloqueo mutuo entre lotes que se solapan, qué haces con el recurso remoto, cuánto retienes cada lock y qué garantía de progreso puedes dar.

### Rúbrica
- Mantiene un orden global para los locks locales del lote (por ejemplo, ordenar las 200 cuentas por id antes de tomar ninguna).
- No retiene locks locales mientras espera al servicio externo, o declara y justifica un plazo máximo de retención.
- Trata la parte remota como una operación con resultado desconocido (plazo, idempotencia y reconciliación), no como un lock más.
- Separa la garantía de ausencia de bloqueo mutuo (diseño) de la garantía de que el lote termine (depende del servicio externo y de los plazos).
- Considera el costo de retener 200 locks a la vez y propone cómo reducir la contención (por ejemplo, partir el lote).
