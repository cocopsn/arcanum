## Antes de leer: write() devolvió «listo»
type: prediccion
id: prediccion-write-listo
rol: prediccion
tiempo: 2

Tu programa llama a `write()` sobre un archivo y la llamada termina sin error. Medio segundo después, la máquina pierde la energía. ¿Qué puedes afirmar del dato?

### Opciones
- [x] Nada seguro: `write()` normalmente devuelve cuando el dato está en la memoria del sistema operativo, y sin un `fsync()` posterior que haya terminado, puede no haber llegado al disco.
- Que está en el disco, porque `write()` no devuelve hasta escribirlo.
- Que se perdió, porque toda escritura de menos de un segundo se pierde en un corte.
- Que está en el disco si el archivo es pequeño.
### Justificación
`write()` copia el dato a la caché del sistema operativo y devuelve; el sistema lo lleva al disco cuando le conviene. Si el proceso termina, el dato sobrevive; si se cae la máquina, puede perderse. Para saber que llegó al almacenamiento hay que esperar a que termine `fsync()`, y aun entonces la garantía depende del disco y del entorno. No hay una regla de «menos de un segundo» ni de tamaño: el dato pudo escribirse o no.

## Recupera el log
type: code
id: codigo-recuperar-log
tiempo: 18

Implementa la recuperación de un log de sólo agregar con registros enmarcados, como el del libro, usando enteros para los bytes.

### Especificación
`recuperar(bytes)`:
- `bytes` es una lista de enteros entre 0 y 255: el contenido del archivo de log.
- Cada registro es: un byte `L` (longitud del contenido, 0 a 255), un byte `S` (suma de verificación) y `L` bytes de contenido.
- Un registro es **válido** si están todos sus bytes y `S` es igual a la suma de su contenido módulo 256.
- La recuperación lee registros desde el principio y se detiene en el **primer** registro incompleto (faltan bytes de cabecera o de contenido) o inválido; no intenta saltarlo.
- Devuelve `{ "registros", "valido_hasta" }`: la lista de contenidos de los registros válidos, en orden, y la posición en `bytes` donde termina el último registro válido (donde se truncaría el archivo).

### Casos
```json
[
  { "input": [[]], "expected": { "registros": [], "valido_hasta": 0 } },
  { "input": [[2, 3, 1, 2]], "expected": { "registros": [[1, 2]], "valido_hasta": 4 } },
  { "input": [[2, 3, 1, 2, 1, 5, 5]], "expected": { "registros": [[1, 2], [5]], "valido_hasta": 7 } },
  { "input": [[2, 3, 1, 2, 3, 9, 1, 2]], "expected": { "registros": [[1, 2]], "valido_hasta": 4 } },
  { "input": [[2, 4, 1, 2, 1, 5, 5]], "expected": { "registros": [], "valido_hasta": 0 } },
  { "input": [[0, 0]], "expected": { "registros": [[]], "valido_hasta": 2 } },
  { "input": [[2, 3, 1, 2, 7]], "expected": { "registros": [[1, 2]], "valido_hasta": 4 } },
  { "input": [[2, 44, 200, 100, 1, 9, 8]], "expected": { "registros": [[200, 100]], "valido_hasta": 4 }, "hint": true }
]
```

### Solución
```javascript
function recuperar(bytes) {
  const registros = [];
  let i = 0;
  while (i + 2 <= bytes.length) {
    const largo = bytes[i];
    const suma = bytes[i + 1];
    if (i + 2 + largo > bytes.length) break;
    const contenido = bytes.slice(i + 2, i + 2 + largo);
    if (contenido.reduce((a, b) => a + b, 0) % 256 !== suma) break;
    registros.push(contenido);
    i += 2 + largo;
  }
  return { registros, valido_hasta: i };
}
```
```python
def recuperar(bytes_):
    registros = []
    i = 0
    while i + 2 <= len(bytes_):
        largo = bytes_[i]
        suma = bytes_[i + 1]
        if i + 2 + largo > len(bytes_):
            break
        contenido = bytes_[i + 2:i + 2 + largo]
        if sum(contenido) % 256 != suma:
            break
        registros.append(contenido)
        i += 2 + largo
    return {"registros": registros, "valido_hasta": i}
```

### Pistas
- Un registro necesita al menos dos bytes de cabecera; si no están, la lectura termina ahí.
- La suma de verificación se compara módulo 256: 200 + 100 = 300 se guarda como 44.
- `valido_hasta` es la posición después del último registro válido, no la del primero inválido más uno.

## Reemplazar un archivo sin perderlo
type: multiple_choice
id: reemplazo-atomico
tiempo: 3

Tu servicio guarda una instantánea de su estado en `agenda.snap` cada hora. ¿Qué secuencia garantiza que, tras una caída en cualquier punto, `agenda.snap` contenga la instantánea vieja completa o la nueva completa?

### Opciones
- [x] Escribir en `agenda.tmp` en el mismo directorio, `fsync()` de `agenda.tmp`, renombrar `agenda.tmp` a `agenda.snap` y `fsync()` del directorio.
- Abrir `agenda.snap` truncando, escribir la instantánea nueva y hacer `fsync()`.
- Borrar `agenda.snap`, escribir la nueva con el mismo nombre y hacer `fsync()`.
- Escribir en `agenda.tmp` en otro disco y renombrarlo a `agenda.snap`.
### Justificación
Mientras el archivo nuevo no esté completo y persistido, el nombre definitivo debe seguir apuntando al viejo. Escribir el temporal, persistirlo, renombrar (atómico dentro de un mismo sistema de archivos) y persistir el directorio cumple eso. Truncar o borrar el original abre una ventana en la que una caída deja el archivo vacío, a medias o inexistente. El renombrado entre sistemas de archivos distintos no es atómico: en realidad es copiar y borrar.

## El archivo después de la caída
type: trace
id: traza-caida-reescritura
tiempo: 4

Un servicio guarda su estado con `writeFileSync("agenda.json", texto)`, que abre el archivo truncándolo y luego escribe el texto nuevo, sin `fsync()`. La máquina se cae justo después de que el archivo se abrió truncado y antes de que se escribiera nada del contenido nuevo. ¿Qué encuentra el servicio al arrancar?

### Opciones
- [x] Con toda probabilidad, un archivo vacío o con contenido incompleto: el truncado ya ocurrió y el contenido nuevo no llegó, así que se perdió el estado viejo y el nuevo.
- El estado viejo intacto, porque `writeFileSync` no modifica nada hasta terminar.
- El estado nuevo completo, porque el sistema operativo termina las escrituras pendientes al reiniciar.
- Un error del sistema de archivos que impide arrancar, que se resuelve reparando el disco.
### Justificación
Abrir truncando cambia el archivo de inmediato: el estado viejo deja de existir antes de que exista el nuevo. Si la caída ocurre en esa ventana, lo que quede depende de qué alcanzó a llegar al disco, y en el peor caso es un archivo vacío o un JSON a medias que el servicio no puede leer. Nada termina las escrituras de una máquina que perdió la energía. No es un problema de reparación del disco: el sistema de archivos está bien; el contenido es el que no sirve. Por eso se reemplaza con temporal y renombrado.

## Declara tus supuestos
type: production
id: produccion-supuestos-durabilidad
tiempo: 12

Para el log de reservas del libro, escribe la sección «Supuestos de atomicidad y durabilidad» de su documento de diseño: qué supones del sistema operativo, del sistema de archivos y del disco, qué protege cada mecanismo del diseño contra la violación de cada supuesto, y cuáles comprobaste y cuáles quedan sin comprobar en el entorno de producción.

### Modelo
*Supuestos:* (1) `fsync()` sobre el log no devuelve hasta que sus datos llegaron al almacenamiento persistente del entorno; (2) el renombrado dentro del mismo sistema de archivos es atómico; (3) `fsync()` del directorio persiste el renombrado; (4) no supongo atomicidad de una escritura de varios bytes ni orden entre escrituras sin `fsync()` intermedio.
*Protecciones:* la suma de verificación y la longitud de cada registro detectan escrituras parciales (supuesto 4) y la recuperación trunca en el primer registro inválido; responder «listo» sólo después de `fsync()` hace que lo confirmado dependa sólo del supuesto 1; la instantánea usa temporal, `fsync()`, renombrado y `fsync()` del directorio (supuestos 2 y 3).
*Comprobado:* recuperación con escrituras interrumpidas en varios puntos (truncando el archivo a mano en cada posición) en el entorno de pruebas.
*Sin comprobar:* que el disco del proveedor de nube cumpla el supuesto 1 con su caché de escritura; queda declarado como supuesto no verificado y como riesgo, con la prueba pendiente de cortar la energía de una máquina de prueba del mismo tipo.

### Regla
Un diseño persistente declara qué supone de cada capa (sistema operativo, sistema de archivos, disco), qué mecanismo protege contra la violación de cada supuesto y qué está comprobado en el entorno real; lo no comprobado se declara como tal, no se extrapola.

### Rúbrica
- Enumera supuestos concretos y separados por capa.
- Para cada supuesto, dice qué mecanismo del diseño depende de él o lo protege.
- No supone atomicidad de escrituras de varios bytes ni orden sin `fsync()`.
- Distingue lo comprobado de lo no comprobado en el entorno de producción.
- Propone cómo comprobaría lo que queda sin comprobar.
