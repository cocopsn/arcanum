# S1-03 · Índices y almacenamiento

Banco de la celda: contar páginas antes de medir, encontrar la entrada que rompe una búsqueda binaria casi correcta, escribir un rango que respete el orden de la codificación, elegir estructura según la consulta y transferir el índice a una tabla con escrituras continuas.

## Mil páginas o cuatro
type: prediccion
id: s1-03-pred-paginas
rol: prediccion
escala: 50 70 90

Una tabla de 100,000 citas guarda 100 citas por página. Hay un árbol B+ sobre `cita_id` con unas 100 llaves por nodo. Predice cuántas lecturas de página necesita, aproximadamente, encontrar **una** cita por su `cita_id` usando el índice.

### Opciones
- [x] Unas 4: tres niveles del árbol y la página de datos.
- Unas 17, una por cada paso de una búsqueda binaria sobre 100,000 llaves.
- Unas 500, la mitad de la tabla en promedio.
- Una sola, porque el índice guarda la fila completa.
### Justificación
Con 100 llaves por nodo, un nivel distingue 100 valores, dos niveles 10,000 y tres niveles 1,000,000: tres nodos bastan para llegar a la hoja, y una lectura más trae la página de la fila. Las 17 comparaciones de una búsqueda binaria ocurren, pero casi todas dentro de las mismas páginas del árbol: lo que cuesta son las páginas. La mitad de la tabla es el costo promedio de un escaneo. Un índice secundario guarda la ubicación de la fila, no la fila.

## La búsqueda binaria casi correcta
type: contraejemplo
id: s1-03-contra-primera-posicion

`primeraPosicion(claves, objetivo)` debe devolver el **menor** índice `i` tal que `claves[i] >= objetivo` (o `claves.length` si no existe), sobre un arreglo de enteros ordenado de menor a mayor. Es la operación que usa un índice para empezar un rango. La versión «casi correcta» pasa muchas pruebas. Da unos argumentos que respeten el contrato y en los que su resultado difiera del de la referencia.

### Firma
```javascript
function primeraPosicion(claves, objetivo) {
  // claves: enteros en orden no decreciente; objetivo: entero
}
```
### Precondición
```javascript
function pre(claves, objetivo) {
  if (!Array.isArray(claves) || claves.length > 1000 || !Number.isInteger(objetivo)) return false;
  for (let i = 0; i < claves.length; i++) {
    if (!Number.isInteger(claves[i])) return false;
    if (i > 0 && claves[i - 1] > claves[i]) return false;
  }
  return true;
}
```
### Casi correcta
```javascript
function primeraPosicion(claves, objetivo) {
  let lo = 0;
  let hi = claves.length - 1;
  while (lo <= hi) {
    const mid = (lo + hi) >> 1;
    if (claves[mid] === objetivo) return mid;
    if (claves[mid] < objetivo) lo = mid + 1;
    else hi = mid - 1;
  }
  return lo;
}
```
### Referencia
```javascript
function primeraPosicion(claves, objetivo) {
  let lo = 0;
  let hi = claves.length;
  while (lo < hi) {
    const mid = (lo + hi) >> 1;
    if (claves[mid] < objetivo) lo = mid + 1;
    else hi = mid;
  }
  return lo;
}
```

```json

```

## Citas del RM-2 en una ventana
type: sql
id: s1-03-sql-ventana
orden: si

Devuelve las citas del equipo `RM-2` que empiezan entre las 08:00 y las 10:00 (inclusive) del 2026-11-10, ordenadas por inicio. Una columna: `cita_id`. La tabla guarda el inicio dos veces: `inicio` en ISO (`2026-11-10T09:30`) y `hora_local` como la escribe recepción (`9:30`). Sólo una de las dos tiene un orden de texto que respeta el orden del tiempo.

### Esquema
```sql
CREATE TABLE cita (
  cita_id    TEXT PRIMARY KEY,
  equipo_id  TEXT NOT NULL,
  inicio     TEXT NOT NULL,
  hora_local TEXT NOT NULL
);
CREATE INDEX cita_equipo_inicio ON cita (equipo_id, inicio);
```
### Datos
```sql
INSERT INTO cita VALUES
  ('C-1', 'RM-2', '2026-11-10T08:00', '8:00'),
  ('C-2', 'RM-2', '2026-11-10T08:40', '8:40'),
  ('C-3', 'TC-1', '2026-11-10T08:50', '8:50'),
  ('C-4', 'RM-2', '2026-11-10T11:00', '11:00');
```
### Fixtures
```sql
-- fixture: solo-manana-temprano
UPDATE cita SET hora_local = hora_local WHERE cita_id = 'C-1';
```
```sql
-- fixture: nueve-y-media
INSERT INTO cita VALUES ('C-5', 'RM-2', '2026-11-10T09:30', '9:30');
```
```sql
-- fixture: diez-en-punto
INSERT INTO cita VALUES ('C-6', 'RM-2', '2026-11-10T10:00', '10:00');
```
### Solución
```sql
SELECT cita_id
FROM cita
WHERE equipo_id = 'RM-2'
  AND inicio BETWEEN '2026-11-10T08:00' AND '2026-11-10T10:00'
ORDER BY inicio
```
### Ingenua
```sql
SELECT cita_id
FROM cita
WHERE equipo_id = 'RM-2'
  AND inicio BETWEEN '2026-11-10T08:00' AND '2026-11-10T10:00'
ORDER BY hora_local
```

## Hash o árbol
type: multiple_choice
id: s1-03-choice-estructura
rol: recuperacion

Sin volver al libro: la consulta más frecuente del tablero es «citas del RM-2 entre dos horas» y la segunda es «la cita C-48213». Sólo puedes mantener un índice. ¿Cuál eliges?

### Opciones
- [x] Un árbol B+ sobre `(equipo_id, inicio)`, porque resuelve el rango por equipo; para la segunda consulta ya existe el índice de la llave primaria.
- Un índice hash sobre `(equipo_id, inicio)`, porque el hash siempre es más rápido que un árbol.
- Un índice hash sobre `inicio`, porque los rangos de tiempo se reparten bien en cubetas.
- Un árbol B+ sobre `(inicio, equipo_id)`, porque el tiempo es lo más selectivo.
### Justificación
El hash destruye el orden: responde igualdades, no rangos, así que no sirve para «entre dos horas». El árbol B+ conserva el orden, y con `equipo_id` primero, todas las citas de un equipo quedan contiguas y ordenadas por inicio: el rango es un recorrido de hojas consecutivas. Con `inicio` primero, las citas del RM-2 quedan mezcladas con las de los demás equipos dentro del rango y hay que filtrarlas. La búsqueda por `cita_id` la cubre el índice de la llave primaria.

## El orden de las columnas del índice
type: prediccion
id: s1-03-pred-compuesto
rol: prediccion

Existe un árbol B+ sobre `cita(equipo_id, inicio)`. Predice cuál de estas consultas **no** puede usar el orden del índice para acotar la búsqueda.

### Opciones
- [x] `WHERE inicio BETWEEN '2026-11-10T08:00' AND '2026-11-10T10:00'` (sin filtrar por equipo)
- `WHERE equipo_id = 'RM-2'`
- `WHERE equipo_id = 'RM-2' AND inicio >= '2026-11-10T08:00'`
- `WHERE equipo_id = 'RM-2' AND inicio = '2026-11-10T09:30'`
### Justificación
El índice ordena primero por equipo y, dentro de cada equipo, por inicio. Sin fijar `equipo_id`, las citas de las 08:00 a las 10:00 están repartidas entre todos los equipos: no forman un tramo contiguo del índice. Con el equipo fijado (con o sin condición de inicio), la búsqueda baja al tramo de ese equipo y recorre sólo lo necesario.

## Lectura, memoria, escrituras y mantenimiento
type: production
id: s1-03-prod-costos

La agenda recibe 5,000 inserciones por minuto en horario pico y el tablero consulta «citas del RM-2 entre dos horas» unas 50 veces por minuto. Escribe un párrafo que relacione el índice sobre `(equipo_id, inicio)` con lectura, memoria, escrituras y mantenimiento, y di qué medirías antes de aprobarlo.

### Modelo
Lectura: el índice convierte el rango en unas pocas lecturas de página por consulta, frente a recorrer la tabla. Memoria: sus nodos internos ocupan memoria intermedia que compite con las páginas de datos; los niveles altos se mantienen en memoria porque se usan siempre. Escrituras: cada una de las 5,000 inserciones por minuto también inserta en el índice y, a veces, divide una hoja; el costo es logarítmico, pero se suma a cada escritura y necesita candados internos con concurrencia. Mantenimiento: construirlo sobre la tabla viva exige una variante que no bloquee las escrituras, y con el tiempo conviene vigilar su tamaño. Mediría: latencia de las inserciones antes y después, páginas leídas por consulta del tablero, tamaño del índice y uso de la memoria intermedia, con las mismas condiciones de caché en ambas corridas.
### Regla
Un índice acelera lecturas selectivas a cambio de trabajo en cada escritura y de memoria; se aprueba con una medición que cubre las dos caras en condiciones comparables.
### Rúbrica
- Cubre las cuatro dimensiones: lectura, memoria, escrituras y mantenimiento.
- Explica el costo por escritura y su relación con la tasa de 5,000 por minuto.
- Menciona cómo construir el índice sin bloquear la operación.
- Propone métricas concretas y una condición de medición justa (misma caché).
