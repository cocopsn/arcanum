## Antes de leer: ¿qué agrupa primero?
type: prediccion
id: prediccion-precedencia
rol: prediccion
tiempo: 2

En el lenguaje de reglas de la clínica, `y` tiene más precedencia que `o`, igual que la multiplicación sobre la suma. ¿Cuánto vale `verdadero o falso y falso`?

### Opciones
- [x] `verdadero`, porque se agrupa como `verdadero o (falso y falso)`, que es `verdadero o falso`.
- `falso`, porque se evalúa de izquierda a derecha: `(verdadero o falso) y falso`.
- `falso`, porque `y` con un `falso` siempre da `falso`, sin importar el resto.
- No está definido: hacen falta paréntesis para que la regla sea válida.
### Justificación
La precedencia está escrita en la gramática: `termino := factor ( "y" factor )*` está un nivel por debajo de `expr := termino ( "o" termino )*`, así que `falso y falso` forma un solo término antes de que intervenga el `o`. Leer de izquierda a derecha ignora la gramática; es justo el error de un evaluador hecho con operaciones de cadena. El `falso` del `y` sólo afecta a su término, no a toda la regla. La regla es válida sin paréntesis precisamente porque la gramática no es ambigua.

### Solución
```javascript
function evaluar(texto) {
  const tokens = [];
  let i = 0;
  while (i < texto.length) {
    const c = texto[i];
    if (c === " ") {
      i++;
      continue;
    }
    if (c >= "0" && c <= "9") {
      let j = i;
      while (j < texto.length && texto[j] >= "0" && texto[j] <= "9") j++;
      tokens.push(Number(texto.slice(i, j)));
      i = j;
      continue;
    }
    if ("+-*()".includes(c)) {
      tokens.push(c);
      i++;
      continue;
    }
    return "error";
  }
  let p = 0;
  const fallo = {};
  const ver = () => tokens[p];
  function expr() {
    let v = termino();
    while (ver() === "+" || ver() === "-") {
      const op = tokens[p++];
      const d = termino();
      v = op === "+" ? v + d : v - d;
    }
    return v;
  }
  function termino() {
    let v = factor();
    while (ver() === "*") {
      p++;
      v = v * factor();
    }
    return v;
  }
  function factor() {
    const t = ver();
    if (t === "-") {
      p++;
      return -factor();
    }
    if (t === "(") {
      p++;
      const v = expr();
      if (ver() !== ")") throw fallo;
      p++;
      return v;
    }
    if (typeof t === "number") {
      p++;
      return t;
    }
    throw fallo;
  }
  try {
    const v = expr();
    return p === tokens.length ? v : "error";
  } catch (e) {
    if (e === fallo) return "error";
    throw e;
  }
}
```
```python
def evaluar(texto):
    tokens = []
    i = 0
    while i < len(texto):
        c = texto[i]
        if c == " ":
            i += 1
            continue
        if "0" <= c <= "9":
            j = i
            while j < len(texto) and "0" <= texto[j] <= "9":
                j += 1
            tokens.append(int(texto[i:j]))
            i = j
            continue
        if c in "+-*()":
            tokens.append(c)
            i += 1
            continue
        return "error"

    class Fallo(Exception):
        pass

    pos = [0]

    def ver():
        return tokens[pos[0]] if pos[0] < len(tokens) else None

    def expr():
        v = termino()
        while ver() == "+" or ver() == "-":
            op = tokens[pos[0]]
            pos[0] += 1
            d = termino()
            v = v + d if op == "+" else v - d
        return v

    def termino():
        v = factor()
        while ver() == "*":
            pos[0] += 1
            v = v * factor()
        return v

    def factor():
        t = ver()
        if t == "-":
            pos[0] += 1
            return -factor()
        if t == "(":
            pos[0] += 1
            v = expr()
            if ver() != ")":
                raise Fallo()
            pos[0] += 1
            return v
        if isinstance(t, int):
            pos[0] += 1
            return t
        raise Fallo()

    try:
        v = expr()
    except Fallo:
        return "error"
    return v if pos[0] == len(tokens) else "error"
```

### Pistas
- Una función por no terminal: `expr`, `termino` y `factor`, cada una consume sólo sus tokens.
- La asociatividad izquierda sale de un ciclo `while`, no de una llamada recursiva sobre «el resto».
- Al terminar, comprueba que consumiste todos los tokens: `1+2)` parsea un prefijo válido y deja basura.

```javascript
function sumarRestar(texto) {
  const m = texto.match(/^(\d+)([+-])(.*)$/);
  if (!m) return Number(texto);
  const izq = Number(m[1]);
  const der = sumarRestar(m[3]);
  return m[2] === "+" ? izq + der : izq - der;
}
```

### Referencia
```javascript
function sumarRestar(texto) {
  const partes = texto.match(/\d+|[+-]/g);
  let total = Number(partes[0]);
  for (let i = 1; i < partes.length; i += 2) {
    const n = Number(partes[i + 1]);
    total = partes[i] === "+" ? total + n : total - n;
  }
  return total;
}
```

## El árbol de una regla con «no»
type: trace
id: traza-arbol-no
tiempo: 4

Con la gramática del libro (`expr := termino ("o" termino)*`, `termino := factor ("y" factor)*`, `factor := "no" factor | comparacion | "(" expr ")"`), ¿qué árbol produce el parser para `no a == 1 y b == 2`?

### Opciones
- [x] `Y(No(a == 1), b == 2)`: el `no` se aplica a un `factor`, que es sólo la comparación `a == 1`; después `termino` consume el `y` y la segunda comparación.
- `No(Y(a == 1, b == 2))`: el `no` niega todo lo que viene a su derecha.
- `Y(a == 1, No(b == 2))`: el `no` se desplaza al último operando.
- El parser falla, porque `no` sólo puede aparecer antes de un paréntesis.
### Justificación
La regla `factor := "no" factor` hace que `no` tome exactamente un factor. Al leer `no`, `factor()` se llama a sí mismo y devuelve la comparación `a == 1`; ese resultado, negado, es el primer factor de `termino()`, que luego ve el `y` y lee `b == 2`. Para negar la conjunción completa hay que escribir `no (a == 1 y b == 2)`. Ninguna regla mueve el `no` de lugar, y la gramática permite `no` delante de cualquier factor, no sólo de un paréntesis.

## Por qué no traducir a eval
type: multiple_choice
id: por-que-no-eval
tiempo: 3

Un compañero propone implementar el lenguaje de reglas reemplazando `y` por `&&`, `o` por `||` y `no` por `!`, y pasando el resultado a `eval` del lenguaje anfitrión. «Es una línea y la precedencia ya está resuelta». ¿Cuál es la objeción más completa?

### Opciones
- [x] Quien escribe reglas podría ejecutar código arbitrario en el servidor, y además el significado queda atado a la precedencia y a las conversiones del lenguaje anfitrión, que no son las que el lenguaje de reglas define; los errores tampoco pueden señalar una posición de la regla.
- Sólo es más lento: `eval` compila en cada llamada, así que bastaría con guardar el resultado en caché.
- No hay objeción si se filtran las palabras `function` y `require` antes de llamar a `eval`.
- La única objeción es de estilo: un parser propio se ve más profesional en una revisión de código.
### Justificación
`eval` convierte cada regla en código ejecutable, así que el que escribe reglas obtiene el poder del lenguaje anfitrión: es un riesgo de seguridad, no de estilo. Filtrar palabras no basta, porque hay muchas formas de llegar a lo mismo. Además, el significado cambia sin que nadie lo decida: la precedencia y las conversiones de tipos pasan a ser las del anfitrión (por ejemplo, comparaciones entre texto y número), y un error dice algo sobre JavaScript, no sobre la regla. El costo de compilar es el menor de los problemas.

## Extiende la gramática con «en»
type: production
id: produccion-gramatica-en
tiempo: 12

Producto pide un operador de pertenencia: `pais en ["MX", "CO", "PE"]`. Escribe la gramática extendida en la notación del libro, di en qué nivel entra el operador nuevo y por qué, y explica cómo demuestras que las reglas existentes siguen significando exactamente lo mismo.

### Modelo
*Gramática:*
`expr := termino ("o" termino)*`
`termino := factor ("y" factor)*`
`factor := "no" factor | comparacion | pertenencia | "(" expr ")"`
`comparacion := CAMPO OPERADOR VALOR`
`pertenencia := CAMPO "en" "[" VALOR ("," VALOR)* "]"`
*Nivel:* `pertenencia` entra como alternativa de `factor`, al mismo nivel que `comparacion`, porque produce un booleano atómico; así `no pais en ["MX"]` niega la pertenencia y `pais en ["MX"] y edad >= 18` agrupa como cualquier comparación.
*Tokenizador:* `en`, `[`, `]` y `,` son tokens nuevos; `en` se vuelve palabra reservada, así que se comprueba que ningún campo existente se llame `en`.
*Compatibilidad:* ninguna regla vieja contiene el token `en` fuera de una cadena, así que su árbol no cambia; se demuestra parseando el corpus completo de reglas existentes con la gramática vieja y la nueva y comparando árboles y resultados sobre registros de muestra.

### Regla
Un operador nuevo se agrega en el nivel de la gramática que corresponde a lo que produce, sin cambiar las reglas existentes; la compatibilidad se demuestra con el corpus real de reglas, no con ejemplos nuevos.

### Rúbrica
- La gramática nueva es una extensión: las producciones viejas siguen ahí sin cambios.
- Justifica el nivel del operador nuevo por lo que produce y por cómo interactúa con `no`, `y` y `o`.
- Trata el impacto en el tokenizador, incluida la nueva palabra reservada.
- Propone comparar el corpus de reglas existentes con la gramática vieja y la nueva.
- Incluye al menos un error con posición para una pertenencia mal escrita.
