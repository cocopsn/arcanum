## Renombrar no es modelar
type: prediccion
id: renombrar-tabla
rol: prediccion
tiempo: 2

Para «migrar» a episodios de atención, alguien renombra el tipo de objeto `Cita` a `Episodio` sin cambiar sus propiedades, sus links ni sus acciones. Aplicas la prueba de tabla renombrada (¿qué decisión sirve?, ¿qué acción lo modifica?, ¿qué lógica lo alimenta?, ¿qué control lo protege?) a `Episodio`. Predice el resultado.

### Opciones
- [x] Falla: las respuestas son las de la cita; ninguna decisión, acción ni lógica es propia de un episodio, así que el cambio es sólo de nombre y además rompe el significado del historial.
- Pasa, porque el objeto conserva sus acciones y links.
- Pasa, porque «episodio» describe mejor el negocio.
- No aplica: la prueba sólo sirve para objetos nuevos.
### Justificación
Un cambio de dominio se justifica por decisiones nuevas (por ejemplo, asignar un médico responsable del episodio). Renombrar conserva las respuestas de la cita bajo otro nombre: las reasignaciones registradas pasarían a describir «episodios» que nunca se reasignaron. La salida correcta es agregar Episodio como objeto nuevo con un link 1:N a Cita y preservar todo lo anterior.

### Solución
```javascript
function reconstruir(eventos) {
  const pilas = new Map();
  const porId = new Map();
  const rechazadas = new Set();
  for (const e of eventos) {
    if (e.tipo === "asignar" || e.tipo === "reasignar") {
      porId.set(e.id, e);
      if (!pilas.has(e.cita)) pilas.set(e.cita, []);
      pilas.get(e.cita).push({ id: e.id, tipo: e.tipo, medico: e.medico });
    } else if (e.tipo === "revertir") {
      const ref = porId.get(e.ref);
      const pila = ref ? pilas.get(ref.cita) : null;
      const tope = pila && pila.length ? pila[pila.length - 1] : null;
      if (ref && ref.tipo === "reasignar" && tope && tope.id === e.ref && pila.length > 1) pila.pop();
      else rechazadas.add(e.ref);
    }
  }
  const citas = [...pilas.keys()].sort();
  return {
    asignacion: citas.map((c) => ({ cita: c, medico: pilas.get(c)[pilas.get(c).length - 1].medico })),
    rechazadas: [...rechazadas].sort(),
  };
}
```
```python
def reconstruir(eventos):
    pilas = {}
    por_id = {}
    rechazadas = set()
    for e in eventos:
        if e["tipo"] in ("asignar", "reasignar"):
            por_id[e["id"]] = e
            pilas.setdefault(e["cita"], []).append({"id": e["id"], "tipo": e["tipo"], "medico": e["medico"]})
        elif e["tipo"] == "revertir":
            ref = por_id.get(e["ref"])
            pila = pilas.get(ref["cita"]) if ref else None
            tope = pila[-1] if pila else None
            if ref and ref["tipo"] == "reasignar" and tope and tope["id"] == e["ref"] and len(pila) > 1:
                pila.pop()
            else:
                rechazadas.add(e["ref"])
    return {
        "asignacion": [{"cita": c, "medico": pilas[c][-1]["medico"]} for c in sorted(pilas)],
        "rechazadas": sorted(rechazadas),
    }
```

- Sólo se revierte la reasignación vigente: si después hubo otra, la reversión se rechaza.

## Agregar sin romper el historial

tiempo: 2

La dirección necesita «asignar un médico responsable del episodio de atención» y «ver todas las citas de un episodio». ¿Cuál es el cambio defendible?

### Opciones

- Renombrar Cita a Episodio y agregar una columna con el número de episodio.

### Justificación
Un cambio de dominio agrega lo que la decisión nueva necesita y preserva lo que ya registra decisiones pasadas. Renombrar cambia el significado del historial; borrar registros destruye la auditoría; copiar propiedades crea una tabla duplicada sin decisión propia.
