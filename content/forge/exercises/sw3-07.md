## Antes de leer: el panel verde
type: prediccion
id: prediccion-panel-verde
rol: prediccion
tiempo: 2

El panel del servicio de agenda muestra cero errores, latencia de 40 ms y CPU baja. Aun así, los usuarios reportan que la app les ofrece horarios que ya están ocupados. ¿Qué indicador falta con más probabilidad?

### Opciones
- [x] La frescura: el servicio responde rápido y sin errores, pero con datos viejos, porque algo dejó de actualizar la agenda que sirve.
- La disponibilidad: debe haber errores que el panel no cuenta.
- La latencia: 40 ms es demasiado rápido para ser real.
- La CPU: si está baja, el servicio está caído.
### Justificación
Responder sin errores y a tiempo no dice nada sobre si lo que se responde está al día. Si el proceso que actualiza la agenda se detuvo, el servicio sigue sirviendo con éxito una versión vieja: disponibilidad y latencia perfectas, frescura rota. La CPU baja es coherente con eso (hay menos trabajo), no una señal de caída. Un indicador de antigüedad del dato servido lo habría mostrado antes que el primer usuario.

## El presupuesto de error
type: code
id: codigo-presupuesto-error
tiempo: 15

Calcula el estado del presupuesto de error de un servicio a partir de sus peticiones.

### Especificación
`presupuesto(objetivoPorMil, umbralMs, eventos)`:
- `objetivoPorMil` es el objetivo en tanto por mil (por ejemplo, `995` para 99.5 %); `umbralMs` es la latencia máxima de una respuesta buena.
- `eventos` es una lista de `{ "codigo", "ms" }` con el código HTTP y la latencia de cada petición.
- Una petición es **buena** si su código es menor que 500 (los errores 4xx son del cliente y no cuentan contra el servicio) **y** su latencia es `≤ umbralMs`.
- `permitidas = ⌊total × (1000 − objetivoPorMil) / 1000⌋`, con aritmética entera.
- `restantes = permitidas − malas`, donde `malas = total − buenas` (puede ser negativo).
- `agotado` es verdadero si `malas > permitidas`.
- Devuelve `{ "total", "buenas", "permitidas", "restantes", "agotado" }`.

  return { total: 0, buenas: 0, permitidas: 0, restantes: 0, agotado: false };
}

### Solución
```javascript
function presupuesto(objetivoPorMil, umbralMs, eventos) {
  const total = eventos.length;
  const buenas = eventos.filter((e) => e.codigo < 500 && e.ms <= umbralMs).length;
  const permitidas = Math.floor((total * (1000 - objetivoPorMil)) / 1000);
  const malas = total - buenas;
  return { total, buenas, permitidas, restantes: permitidas - malas, agotado: malas > permitidas };
}
```
```python
def presupuesto(objetivo_por_mil, umbral_ms, eventos):
    total = len(eventos)
    buenas = sum(1 for e in eventos if e["codigo"] < 500 and e["ms"] <= umbral_ms)
    permitidas = (total * (1000 - objetivo_por_mil)) // 1000
    malas = total - buenas
    return {"total": total, "buenas": buenas, "permitidas": permitidas, "restantes": permitidas - malas, "agotado": malas > permitidas}
```

### Pistas
- Una respuesta rápida con error del servidor es mala; una respuesta correcta pero lenta también.
- Los códigos 4xx no cuentan contra el servicio: el cliente pidió algo inválido.
- Usa división entera para `permitidas`; con pocos eventos, el presupuesto puede ser cero.

## La señal que responde la pregunta
type: multiple_choice
id: senal-correcta
tiempo: 3

La latencia de `POST /reservas` subió de 80 ms a 2 s, y la petición pasa por cuatro servicios. Quieres saber en qué tramo de la cadena se va el tiempo. ¿Qué señal usas primero?

### Opciones
- [x] Una traza de una petición lenta: muestra el tiempo de cada tramo en cada servicio, y su identificador lleva después a los registros de ese tramo.
- La métrica de latencia agregada del servicio de entrada: ya dice que la petición tarda 2 s.
- Los registros de los cuatro servicios en el mismo intervalo, leídos en orden de hora.
- La CPU de cada máquina: la que esté más alta es la culpable.
### Justificación
La métrica agregada confirma el síntoma pero no dice dónde está. Leer los registros de cuatro servicios por hora sin un identificador común es buscar a ciegas entre miles de líneas. La CPU es una causa posible, no una medición del recorrido: un servicio puede tardar esperando a otro con la CPU en cero. La traza responde exactamente «¿en qué parte de la cadena se fue el tiempo?» y, con el identificador de petición, conecta con los registros del tramo culpable.

## ¿Esta alerta debe despertar a alguien?
type: multiple_choice
id: alerta-sintoma
tiempo: 3

¿Cuál de estas alertas debería enviar una notificación a la persona de guardia a las 3 de la mañana?

### Opciones
- [x] «La proporción de reservas buenas de la última hora consume el presupuesto de error de 28 días diez veces más rápido de lo sostenible.»
- «La CPU de una máquina pasó del 85 % durante 5 minutos.»
- «El disco de una réplica está al 70 %.»
- «Hubo un error 404 en el endpoint de reservas.»
### Justificación
Una alerta que despierta a alguien debe significar que los usuarios sufren o van a sufrir pronto y que hay algo que hacer. El gasto acelerado del presupuesto de error mide justo eso, sobre lo que el usuario experimenta. La CPU alta y el disco al 70 % son causas posibles que pueden no afectar a nadie: van al panel de diagnóstico o a un aviso de horario hábil. Un 404 suele ser un error del cliente y no dice nada del servicio.

## Una entrada de runbook
type: production
id: produccion-runbook
tiempo: 12

Escribe la entrada de runbook para la alerta «la agenda que ve la app tiene más de 10 minutos de atraso», con la forma del libro: qué significa, cómo confirmar, cómo localizar, qué hacer (empezando por lo reversible) y cuándo escalar. Supón que la agenda se alimenta de un proceso que lee los cambios de la base de reservas.

### Modelo
*Qué significa:* los usuarios ven horarios libres que pueden estar ocupados; las reservas nuevas pueden fallar con `traslape` al confirmar.
*Confirmar:* en el panel de frescura, la antigüedad del último cambio aplicado a la agenda supera 10 minutos; comparar el último cambio de la base con el último aplicado (una consulta de conteo por minuto, sin leer contenido de reservas).
*Localizar:* revisar si el proceso de actualización está corriendo; si corre, ver su atraso y su tasa de error; abrir los registros del último lote fallido por su identificador; revisar si hubo un despliegue o un cambio de esquema en la última hora.
*Qué hacer:* si hubo un despliegue reciente del proceso, volver a la versión anterior; si el proceso está detenido, reiniciarlo y vigilar que el atraso baje; mientras tanto, activar el aviso en la app de «disponibilidad en actualización» para que los usuarios sepan que pueden ver datos viejos.
*Escalar:* si el atraso no baja en 20 minutos, o si el proceso falla por un cambio de esquema, avisar al equipo dueño de la base de reservas.

### Regla
Una entrada de runbook responde a una alerta concreta con cinco partes (qué significa para el usuario, cómo confirmar, cómo localizar, cómo mitigar empezando por lo reversible y cuándo escalar), escritas para alguien que no conoce el sistema.

### Rúbrica
- Explica qué sufre el usuario, no sólo qué métrica cruzó un umbral.
- Da una forma concreta de confirmar la alerta con un panel o una consulta que no expone datos sensibles.
- Ordena la localización de lo más probable a lo menos probable.
- Empieza la mitigación por acciones reversibles y avisa al usuario si ve datos viejos.
- Define un criterio y un destino de escalada.
