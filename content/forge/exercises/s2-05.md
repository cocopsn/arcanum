# S2-05 · CDC, streams y datos tardíos

Banco de la celda: predecir qué revive un borrado sin marca, implementar la aplicación por versión, reconstruir el estado actual desde el registro de cambios con SQL, separar tiempo del evento y tiempo de procesamiento, decidir qué hacer con un rezagado, diseñar una reconstrucción verificable y transferirla a un origen que reinicia su numeración.

## La cita que revive
type: prediccion
id: s2-05-pred-revive
rol: prediccion
escala: 50 70 90

Para la cita C-9, el origen produjo `v1 insertar (09:00)`, `v2 actualizar (11:00)` y `v3 borrar`. Llegan en el orden `v1, v3, v2`. El consumidor aplica cada evento en el orden de llegada y borra la fila al recibir un borrado. Predice el estado final de C-9 en la proyección.

### Opciones
- [x] Existe, agendada a las 11:00: la actualización v2 llegó después del borrado y volvió a crear la fila.
- Borrada, porque el borrado siempre gana.
- Existe a las 09:00, porque v1 fue la primera.
- La proyección lanza un error porque v2 actualiza una fila inexistente.
### Justificación
Aplicar por llegada reproduce el orden del transporte, no el del origen. Al borrar la fila sin dejar marca, el consumidor olvida que existió una versión 3; cuando llega v2 no tiene contra qué compararla y la aplica. Nada hace que «el borrado gane» si no se guarda su versión. Muchos consumidores tratan una actualización sin fila como inserción (o así está escrito el código), por eso no hay error: hay un estado que el origen nunca tuvo.

## Aplicar por versión
type: code
id: s2-05-code-proyectar

Implementa `proyectar(eventos)`. Cada evento es `{ llave, version, op, valor }` con `op` igual a `"insertar"`, `"actualizar"` o `"borrar"`, y llegan en cualquier orden, a veces repetidos. Aplica un evento sólo si su `version` es mayor que la última guardada para su llave (también la de un borrado). Devuelve las llaves vivas al final como pares `[llave, valor]`, ordenados por llave.

### Firma
```javascript
function proyectar(eventos) {
  // devuelve [[llave, valor], ...] ordenado por llave, sin las borradas
}
```
### Casos
```json

  { "input": [[{ "llave": "C-9", "version": 1, "op": "insertar", "valor": "09:00" }, { "llave": "C-9", "version": 2, "op": "actualizar", "valor": "11:00" }]], "expected": [["C-9", "11:00"]] },
  { "input": [[{ "llave": "C-9", "version": 1, "op": "insertar", "valor": "09:00" }, { "llave": "C-9", "version": 3, "op": "borrar", "valor": null }, { "llave": "C-9", "version": 2, "op": "actualizar", "valor": "11:00" }, { "llave": "C-9", "version": 2, "op": "actualizar", "valor": "11:00" }]], "expected": [] },
  { "input": [[{ "llave": "C-9", "version": 1, "op": "insertar", "valor": "09:00" }, { "llave": "C-9", "version": 1, "op": "insertar", "valor": "09:00" }]], "expected": [["C-9", "09:00"]] },
  { "input": [[{ "llave": "C-1", "version": 1, "op": "insertar", "valor": "08:00" }, { "llave": "C-2", "version": 1, "op": "insertar", "valor": "09:00" }, { "llave": "C-1", "version": 2, "op": "actualizar", "valor": "08:30" }, { "llave": "C-2", "version": 2, "op": "borrar", "valor": null }]], "expected": [["C-1", "08:30"]] },
  { "input": [[{ "llave": "C-9", "version": 2, "op": "actualizar", "valor": "11:00" }, { "llave": "C-9", "version": 1, "op": "insertar", "valor": "09:00" }]], "expected": [["C-9", "11:00"]] },
  { "input": [[{ "llave": "C-9", "version": 1, "op": "insertar", "valor": "09:00" }, { "llave": "C-9", "version": 2, "op": "borrar", "valor": null }, { "llave": "C-9", "version": 3, "op": "insertar", "valor": "12:00" }]], "expected": [["C-9", "12:00"]] }
]
```
### Solución
```javascript
function proyectar(eventos) {
  const p = new Map();
  for (const e of eventos) {
    const actual = p.get(e.llave);
    if (actual && e.version <= actual.version) continue;
    p.set(e.llave, { version: e.version, borrado: e.op === "borrar", valor: e.op === "borrar" ? null : e.valor });
  }
  return [...p.entries()]
    .filter(([, v]) => !v.borrado)
    .map(([k, v]) => [k, v.valor])
    .sort((a, b) => (a[0] < b[0] ? -1 : a[0] > b[0] ? 1 : 0));
}
```
### Pistas
- Guarda el borrado como una entrada con su versión; fíltralo sólo al final.
- La comparación es contra la versión guardada, no contra el orden en que llegaron.

## El estado actual desde el registro de cambios
type: sql
id: s2-05-sql-estado-actual
orden: no

La tabla `cambios` es el registro crudo de la captura de cambios: llave, `version` de origen, operación, valor y `recibido_en` (orden de llegada al pipeline). Un duplicado repite exactamente el mismo cambio. Devuelve el estado actual: una fila por llave viva, con `llave` y `valor`, tomando para cada llave el cambio de **mayor versión de origen** y omitiendo las llaves cuyo último cambio es un borrado.

### Esquema
```sql
CREATE TABLE cambios (
  llave       TEXT NOT NULL,
  version     INTEGER NOT NULL,
  op          TEXT NOT NULL CHECK (op IN ('insertar', 'actualizar', 'borrar')),
  valor       TEXT,
  recibido_en INTEGER NOT NULL
);
```
### Datos
```sql
INSERT INTO cambios VALUES
  ('C-1', 1, 'insertar', '08:00', 1),
  ('C-1', 2, 'actualizar', '08:30', 2),
  ('C-2', 1, 'insertar', '09:00', 3);
```
### Fixtures
```sql
-- fixture: en-orden
UPDATE cambios SET valor = valor WHERE llave = 'C-1' AND version = 1;
```
```sql
-- fixture: borrado-adelantado
INSERT INTO cambios VALUES
  ('C-3', 1, 'insertar', '10:00', 4),
  ('C-3', 3, 'borrar', NULL, 5),
  ('C-3', 2, 'actualizar', '11:00', 6);
```
```sql
-- fixture: duplicado-tardio
INSERT INTO cambios VALUES
  ('C-2', 2, 'actualizar', '09:15', 7),
  ('C-2', 1, 'insertar', '09:00', 8);
```
### Solución
```sql
SELECT DISTINCT c.llave, c.valor
FROM cambios c
WHERE c.op <> 'borrar'
  AND NOT EXISTS (
    SELECT 1 FROM cambios d
    WHERE d.llave = c.llave AND d.version > c.version
  )
```
### Ingenua
```sql
SELECT DISTINCT c.llave, c.valor
FROM cambios c
WHERE c.op <> 'borrar'
  AND NOT EXISTS (
    SELECT 1 FROM cambios d
    WHERE d.llave = c.llave AND d.recibido_en > c.recibido_en
  )
```

## ¿Qué hora cuenta?
type: multiple_choice
id: s2-05-choice-tiempos
rol: recuperacion

Sin volver al libro: el tablero «citas atendidas por hora» agrupa por la hora en que el pipeline **procesó** cada evento. La red de la sede Norte se cortó de 09:05 a 09:35 y sus eventos de atención llegaron juntos al reconectar. ¿Qué muestra el tablero y qué debería hacer?

### Opciones
- [x] Muestra la hora de las 9 casi vacía para Norte y la de las 10 inflada; debería agrupar por la hora de atención registrada en el origen (tiempo del evento) y esperar un margen antes de cerrar cada hora.
- Muestra lo correcto, porque todos los eventos terminaron llegando.
- Muestra lo correcto si se deduplican los eventos al reconectar.
- Muestra la hora de las 9 duplicada, porque los eventos se reenvían dos veces.
### Justificación
Agrupar por tiempo de procesamiento mezcla la pregunta del negocio (cuándo se atendió) con un accidente del transporte (cuándo llegó el aviso). Que todos lleguen no arregla la hora en que se cuentan. Deduplicar evita contar dos veces, pero no mueve los eventos a su hora. La respuesta es agrupar por tiempo del evento y decidir cuánto esperar a los rezagados.

## Un rezagado de 40 minutos
type: prediccion
id: s2-05-pred-rezagado
rol: prediccion

La hora `[09:00, 10:00)` de «citas atendidas» se publica a las 10:15 (15 minutos de margen). A las 10:40 llega un evento de atención ocurrido a las 09:50. El pipeline está configurado para descartar en silencio lo que llega después del margen. Predice el efecto.

### Opciones
- [x] La hora de las 9 queda publicada con una cita menos, para siempre y sin aviso; el número es incorrecto y nadie sabe que lo es.
- El pipeline espera automáticamente hasta que lleguen todos los rezagados.
- La cita se cuenta en la hora de las 10, que es donde llegó.
- La hora publicada se corrige sola en la siguiente publicación.
### Justificación
Descartar después del margen es una decisión válida sólo si se declara y se mide. En silencio produce un número equivocado que parece correcto. Las alternativas defendibles son corregir la hora publicada con un registro de corrección, o mandar el rezagado a un circuito de reparación con aviso. Ningún pipeline sabe cuándo «llegaron todos», y contarla en la hora de llegada es volver al tiempo de procesamiento.

## Una reconstrucción que se puede verificar
type: production
id: s2-05-prod-reconstruccion

Diseña cómo verificas cada noche que la proyección de citas (alimentada por CDC) es correcta, y cómo la reparas si no lo es. Especifica qué guardas, qué comparas, cómo localizas una diferencia y cuáles son los límites del procedimiento.

### Modelo
Se guarda el registro crudo de cambios, sólo agregando, con llave, versión de origen, operación, valor y hora de llegada, durante 35 días. Cada noche se reconstruye la proyección completa desde ese registro con la misma regla (por llave, gana la mayor versión; los borrados son marcas) y se compara con la incremental: número de llaves vivas y una suma de verificación por cada bloque de 1,000 llaves. Si un bloque difiere, se listan sus llaves con valor distinto y se reprocesan desde el último punto de control en el que ese bloque coincidía. Límites: sólo se puede reconstruir lo que está en los 35 días de registro (lo anterior depende de una instantánea mensual del origen), la reconstrucción tarda unos 40 minutos y, mientras corre, la proyección incremental sigue sirviendo; una diferencia causada por un error del origen no se detecta así, porque ambas copias leen el mismo registro.
### Regla
Una proyección incremental se vuelve confiable cuando se puede reconstruir desde un registro crudo con la misma regla y compararse por partes; la reparación se hace reprocesando desde un punto de control, y los límites (retención, tiempo, errores del origen) se escriben.
### Rúbrica
- Guarda un registro crudo con el orden de origen y una retención declarada.
- La comparación es por partes (conteo y sumas por rango), de modo que localiza la diferencia.
- La reparación es un reproceso desde un punto de control, no una edición manual.
- Declara al menos dos límites, incluido lo que esta verificación no puede detectar.
