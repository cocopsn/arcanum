## Antes de leer: la cola sin límite
type: prediccion
id: prediccion-cola-sin-limite
rol: prediccion
tiempo: 2

Un servicio puede atender 100 peticiones por segundo y, durante diez minutos, le llegan 120 por segundo. Su cola no tiene límite y nunca rechaza nada. ¿Qué le pasa a la latencia?

### Opciones
- [x] Crece sin parar mientras dure la sobrecarga: cada segundo entran 20 peticiones más de las que salen, así que la espera en cola aumenta hasta que los clientes abandonan o el proceso se queda sin memoria.
- Se estabiliza en un 20 % más que lo normal, porque la sobrecarga es del 20 %.
- No cambia, porque la cola absorbe las peticiones extra.
- Baja, porque con más peticiones los trabajadores nunca están ociosos.
### Justificación
Si llegan más peticiones de las que se atienden, la cola crece a 20 por segundo: en diez minutos acumula unas 12,000, y la última espera dos minutos en cola. La latencia no se estabiliza porque el sistema no es estable: la ley de Little sólo describe un equilibrio que aquí no existe. La cola no absorbe nada, sólo pospone. Tener a los trabajadores siempre ocupados no reduce la espera de quien está al final de la fila.

## Simula la cola con rechazo y plazos
type: code
id: codigo-simular-cola
tiempo: 20

Simula un servicio con trabajadores, una cola acotada y plazos, y cuenta qué pasa con cada petición.

### Especificación
`simular(trabajadores, servicio, capacidad, plazo, llegadas)`:
- `trabajadores ≥ 1`; cada uno atiende una petición a la vez durante `servicio` ms. `capacidad ≥ 0` es el tamaño máximo de la cola. `plazo` es cuántos ms después de su llegada puede **empezar** a atenderse una petición. `llegadas` es la lista de instantes de llegada, en orden no decreciente.
- Al llegar una petición en el instante `t`: primero, todo trabajador libre en un instante `≤ t` toma peticiones de la cola en orden de llegada (ver abajo). Después, si hay un trabajador libre en `t` y la cola está vacía, la petición empieza en `t`; si no, entra a la cola si hay lugar; si no hay lugar, se **rechaza**.
- Un trabajador que queda libre en el instante `f` toma la primera petición de la cola. Si `f > llegada + plazo`, la petición está **vencida**: se descarta sin atenderla y el trabajador toma la siguiente. Si no, se **atiende** desde `f` hasta `f + servicio`.
- Cuando se elige trabajador, se toma el que queda libre antes (a igualdad, el de menor índice).
- Después de la última llegada, se vacía la cola con la misma regla.
- Devuelve `{ "atendidas", "rechazadas", "vencidas" }`.

### Solución
```javascript
function simular(trabajadores, servicio, capacidad, plazo, llegadas) {
  const libreEn = new Array(trabajadores).fill(0);
  const cola = [];
  const r = { atendidas: 0, rechazadas: 0, vencidas: 0 };
  const masLibre = () => {
    let w = 0;
    for (let i = 1; i < libreEn.length; i++) if (libreEn[i] < libreEn[w]) w = i;
    return w;
  };
  const avanzar = (hasta) => {
    while (cola.length > 0) {
      const w = masLibre();
      const f = libreEn[w];
      if (f > hasta) return;
      const llegada = cola.shift();
      if (f > llegada + plazo) {
        r.vencidas++;
        continue;
      }
      libreEn[w] = f + servicio;
      r.atendidas++;
    }
  };
  for (const t of llegadas) {
    avanzar(t);
    const w = masLibre();
    if (libreEn[w] <= t && cola.length === 0) {
      libreEn[w] = t + servicio;
      r.atendidas++;
    } else if (cola.length < capacidad) {
      cola.push(t);
    } else {
      r.rechazadas++;
    }
  }
  avanzar(Infinity);
  return r;
}
```
```python
def simular(trabajadores, servicio, capacidad, plazo, llegadas):
    libre_en = [0] * trabajadores
    cola = []
    r = {"atendidas": 0, "rechazadas": 0, "vencidas": 0}

    def mas_libre():
        return min(range(len(libre_en)), key=lambda i: libre_en[i])

    def avanzar(hasta):
        while cola:
            w = mas_libre()
            f = libre_en[w]
            if hasta is not None and f > hasta:
                return
            llegada = cola.pop(0)
            if f > llegada + plazo:
                r["vencidas"] += 1
                continue
            libre_en[w] = f + servicio
            r["atendidas"] += 1

    for t in llegadas:
        avanzar(t)
        w = mas_libre()
        if libre_en[w] <= t and not cola:
            libre_en[w] = t + servicio
            r["atendidas"] += 1
        elif len(cola) < capacidad:
            cola.append(t)
        else:
            r["rechazadas"] += 1
    avanzar(None)
    return r
```

### Pistas
- Guarda, por trabajador, el instante en que queda libre; la cola guarda sólo instantes de llegada.
- Antes de atender una llegada, deja que los trabajadores ya libres vacíen lo que puedan de la cola.
- Una petición que empieza exactamente en `llegada + plazo` todavía se atiende; vencida es sólo si empieza después.

## El plazo que llega a la tercera capa
type: trace
id: traza-plazo-propagado
tiempo: 3

El usuario espera la respuesta como máximo 1,000 ms. El servicio A gasta 200 ms antes de llamar a B y le propaga el presupuesto restante. B gasta 300 ms antes de llamar a C y también le propaga lo que queda. ¿Con qué presupuesto empieza C, y qué debe hacer si su consulta tarda 700 ms?

### Opciones
- [x] Con 500 ms; si su consulta tarda 700 ms, debe cancelarla al llegar a los 500, porque después de ese instante nadie va a usar la respuesta.
- Con 1,000 ms, porque cada capa tiene su propio tiempo de espera completo.
- Con 800 ms, porque sólo A descuenta lo que gastó.
- Con 500 ms, pero debe terminar la consulta de todos modos para guardar el resultado en caché.
### Justificación
El plazo es un instante absoluto: al llegar a C ya pasaron 200 + 300 = 500 ms de los 1,000. Darle a cada capa un segundo propio haría que C trabajara hasta 1.5 s después de que el usuario dejó de esperar. B no puede olvidar los 200 ms que gastó A. Terminar la consulta «para la caché» es trabajo zombi bajo sobrecarga: consume justo la capacidad que falta. Si un resultado vale la pena para la caché, eso es una decisión aparte con su propio presupuesto.

## El cliente que se fue
type: multiple_choice
id: cliente-desconectado
tiempo: 3

A mitad de una petición que ya lanzó una consulta lenta a la base de datos y una llamada a un servicio externo, el cliente cierra la conexión. ¿Qué debe hacer el servicio?

### Opciones
- [x] Propagar la cancelación: abortar la consulta y la llamada externa si todavía se puede, liberar la conexión, el trabajador y su lugar en la cola en sus bloques de limpieza, y registrar la cancelación; si alguna operación tenía efectos, dejarla en un estado que se pueda reconciliar.
- Terminar todo normalmente y descartar la respuesta, porque cancelar a mitad de camino es arriesgado.
- Reintentar la petición completa para que el cliente encuentre el resultado listo cuando vuelva.
- Matar el proceso para liberar los recursos de golpe.
### Justificación
Sin destinatario, el trabajo pendiente sólo consume capacidad, y bajo carga ese trabajo zombi es lo que tumba al servicio. Cancelar no es arriesgado si cada recurso se libera en un bloque que corre con éxito, error o cancelación, y si las operaciones con efectos quedan reconciliables (SW3-06). Reintentar por el cliente duplica el trabajo sin que nadie lo pida. Matar el proceso corta también las peticiones sanas de los demás clientes.

## Elige los límites con datos
type: production
id: produccion-limites-con-datos
tiempo: 12

Un servicio de búsqueda tiene 6 trabajadores; cada búsqueda tarda en promedio 60 ms y el objetivo de servicio es responder en menos de 400 ms. Calcula la capacidad, el tamaño de cola que propondrías y el tiempo de espera de la llamada a la dependencia, explica con qué mediciones los revisarías y qué cambia si la dependencia pasa a tardar 300 ms.

### Modelo
*Capacidad:* 6 / 0.060 s = 100 búsquedas por segundo.
*Cola:* una búsqueda puede esperar a lo sumo 400 − 60 = 340 ms en cola; a 100 por segundo se atienden 34 en ese tiempo, así que una cola de más de unas 34 posiciones sólo agrega búsquedas que van a llegar tarde. Propongo 30, con margen para la variación.
*Tiempo de espera de la dependencia:* el mínimo entre un percentil alto de su latencia medida (por ejemplo, el 99) más un margen y el plazo restante de la petición; nunca más que el presupuesto que queda.
*Mediciones:* tasa de llegada, latencia por percentiles de la dependencia y de la búsqueda completa, longitud de la cola, rechazos por cola llena y descartes por plazo vencido.
*Si la dependencia tarda 300 ms:* la capacidad cae a 6 / 0.3 = 20 por segundo, y la cola útil a 20 × (0.4 − 0.3) = 2 posiciones; con la cola de 30, la mayoría de lo encolado vencería. El límite debe bajar (o calcularse dinámicamente con la latencia observada), y conviene degradar o rechazar antes de encolar.

### Regla
La capacidad sale de trabajadores entre tiempo de servicio, y la cola útil, de cuántas peticiones caben en el tiempo de espera que permite el objetivo; los límites se recalculan cuando cambian las mediciones.

### Rúbrica
- Calcula la capacidad con trabajadores y tiempo de servicio.
- Deriva el tamaño de cola del objetivo de servicio, no de una cifra arbitraria.
- El tiempo de espera de la dependencia respeta el plazo restante.
- Nombra las mediciones que confirmarían o cambiarían los límites.
- Recalcula los límites con la dependencia lenta y propone qué hacer.
