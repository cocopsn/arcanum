# A2-04 · SQL técnico

Banco ligero de la ruta A2. La misión: agregaciones, joins y consultas sobre historial de estados, defendiendo nulos,
duplicados, clientes sin eventos y zona horaria. La agregación condicional está en OA-11. Dialecto: SQLite.

## Antes de leer: COUNT con LEFT JOIN
type: prediccion
id: a2-04-pred-count
rol: prediccion

`clientes` tiene a Dani, que no tiene ningún evento. Corres
`SELECT c.nombre, COUNT(*) FROM clientes c LEFT JOIN eventos e ON e.cliente_id = c.id GROUP BY c.id, c.nombre`.
¿Qué número sale para Dani?

### Opciones
- 0
- [x] 1
- NULL
- Dani no aparece

### Justificación
El LEFT JOIN conserva a Dani con una fila cuyas columnas de eventos son NULL. COUNT(*) cuenta filas, y hay una. Para contar
eventos hay que usar COUNT(e.id), que ignora los NULL y da 0. Dani sí aparece, porque es un LEFT JOIN sin filtro en el WHERE.

## Compras por cliente, sin perder a nadie
type: sql
id: a2-04-sql-compras
orden: no

Devuelve una fila por cliente con su nombre y su número de compras (eventos con tipo 'compra'), incluidos los clientes que
no compraron nada, con 0. Columnas: nombre, compras.

### Esquema
```sql
CREATE TABLE clientes (id INTEGER PRIMARY KEY, nombre TEXT NOT NULL);
CREATE TABLE eventos (id INTEGER PRIMARY KEY, cliente_id INTEGER NOT NULL, tipo TEXT, ts TEXT NOT NULL);
```

### Datos
```sql
INSERT INTO clientes (id, nombre) VALUES (1, 'Ana'), (2, 'Beto'), (3, 'Caro');
INSERT INTO eventos (id, cliente_id, tipo, ts) VALUES
  (10, 1, 'compra', '2026-10-30T10:00:00Z'),
  (11, 1, 'compra', '2026-10-30T11:00:00Z'),
  (12, 1, 'visita', '2026-10-30T12:00:00Z'),
  (13, 2, 'compra', '2026-10-31T09:00:00Z'),
  (14, 3, 'compra', '2026-10-31T10:00:00Z');
```

### Fixtures
```sql
-- fixture: base
```
```sql
-- fixture: sin-eventos
INSERT INTO clientes (id, nombre) VALUES (4, 'Dani');
```
```sql
-- fixture: solo-visitas
INSERT INTO clientes (id, nombre) VALUES (5, 'Eli');
INSERT INTO eventos (id, cliente_id, tipo, ts) VALUES (15, 5, 'visita', '2026-10-31T12:00:00Z');
```
```sql
-- fixture: tipo-nulo
INSERT INTO eventos (id, cliente_id, tipo, ts) VALUES (16, 2, NULL, '2026-10-31T13:00:00Z');
```

### Solución
```sql
SELECT c.nombre, COUNT(e.id) AS compras
FROM clientes AS c
LEFT JOIN eventos AS e ON e.cliente_id = c.id AND e.tipo = 'compra'
GROUP BY c.id, c.nombre
```

### Ingenua
```sql
SELECT c.nombre, COUNT(e.id) AS compras
FROM clientes AS c
LEFT JOIN eventos AS e ON e.cliente_id = c.id
WHERE e.tipo = 'compra'
GROUP BY c.id, c.nombre
```

## Estado vigente al corte
type: sql
id: a2-04-sql-vigente
orden: no

`historial` guarda cada cambio de estado de un pedido con su instante, a veces en UTC (Z) y a veces con desfase (−06:00).
Devuelve el estado vigente de cada pedido al corte 2026-11-01T00:00:00Z: el último cambio con instante menor o igual al
corte. Un pedido sin cambios antes del corte no aparece. Columnas: pedido_id, estado.

### Esquema
```sql
CREATE TABLE historial (pedido_id INTEGER NOT NULL, estado TEXT NOT NULL, ts TEXT NOT NULL);
```

### Datos
```sql
INSERT INTO historial (pedido_id, estado, ts) VALUES
  (1, 'creado', '2026-10-31T10:00:00Z'),
  (1, 'pagado', '2026-10-31T12:00:00Z'),
  (1, 'enviado', '2026-11-01T09:00:00Z'),
  (2, 'creado', '2026-10-31T15:00:00Z'),
  (3, 'creado', '2026-11-01T08:00:00Z');
```

### Fixtures
```sql
-- fixture: base
```
```sql
-- fixture: zona
INSERT INTO historial (pedido_id, estado, ts) VALUES
  (2, 'pagado', '2026-10-31T17:30:00-06:00'),
  (2, 'cancelado', '2026-10-31T20:00:00-06:00'),
  (4, 'creado', '2026-10-31T19:00:00-06:00');
```
```sql
-- fixture: duplicado
INSERT INTO historial (pedido_id, estado, ts) VALUES (1, 'pagado', '2026-10-31T12:00:00Z');
```

### Solución
```sql
WITH h AS (
  SELECT pedido_id, estado, datetime(ts) AS t FROM historial
),
ultimo AS (
  SELECT pedido_id, MAX(t) AS t
  FROM h
  WHERE t <= datetime('2026-11-01T00:00:00Z')
  GROUP BY pedido_id
)
SELECT DISTINCT h.pedido_id, h.estado
FROM h
JOIN ultimo AS u ON u.pedido_id = h.pedido_id AND u.t = h.t
```

### Ingenua
```sql
SELECT h.pedido_id, h.estado
FROM historial AS h
WHERE h.ts = (
  SELECT MAX(h2.ts) FROM historial AS h2
  WHERE h2.pedido_id = h.pedido_id AND h2.ts <= '2026-11-01T00:00:00Z'
)
```

## NULL en un filtro
type: multiple_choice
id: a2-04-mc-null
rol: recuperacion

Sin volver al libro: `pedidos` tiene 10 filas; 3 con estado 'cancelado', 5 con 'entregado' y 2 con estado NULL. ¿Cuántas
filas devuelve `SELECT * FROM pedidos WHERE estado <> 'cancelado'`?

### Opciones
- 7
- [x] 5
- 10
- 2

### Justificación
Comparar NULL con cualquier valor da desconocido, y WHERE sólo deja pasar lo verdadero, así que las 2 filas con NULL quedan
fuera junto con las 3 canceladas. Para incluirlas hay que decirlo: `WHERE estado <> 'cancelado' OR estado IS NULL`. 7 sería
el resultado si NULL se comportara como un valor más.

## La defensa de la consulta, por escrito
type: production
id: a2-04-prod-defensa

Defiende tu consulta de estado vigente en cuatro puntos: nulos, duplicados, pedidos sin cambios antes del corte y zona
horaria. Un renglón o dos por punto.

### Modelo
Nulos: estado y ts son NOT NULL en el esquema, así que no hay filas que el filtro descarte en silencio; si ts pudiera ser
nulo, esas filas quedarían fuera del MAX y lo diría. Duplicados: un cambio repetido (mismo pedido, estado e instante)
produciría dos filas iguales en el join; DISTINCT las une sin esconder nada, porque son el mismo hecho. Pedidos sin cambios
antes del corte: no tienen fila en ultimo y el join interno los deja fuera, como pide el enunciado. Zona horaria: comparo
datetime(ts), que convierte el desfase a UTC, contra el corte también normalizado; comparar texto pone 19:00 −06:00 del 31
antes de medianoche UTC cuando es la 01:00 del 1.

### Regla
Una consulta se defiende nombrando qué hace con nulos, duplicados, filas sin pareja y zona horaria; los datos de ejemplo sin
esos casos no prueban nada.

### Rúbrica
- Explica el tratamiento de nulos con el esquema a la vista.
- Distingue un duplicado del mismo hecho de una multiplicación por join.
- Dice qué pasa con los pedidos sin cambios antes del corte.
- Justifica la comparación como instante y no como texto, con un ejemplo concreto.

## Giro: el reporte corre mientras se escribe
type: giro
id: a2-04-giro-concurrencia
rol: transferencia

Cambia una restricción: el reporte de estado vigente ahora son tres consultas (vigentes, conteo por estado y total) que deben
cuadrar entre sí, y corre en PostgreSQL mientras el sistema sigue escribiendo cambios. Explica qué puede descuadrar y cómo lo
evitas.

### Rúbrica
- Explica que, en el aislamiento por omisión, cada sentencia ve su propia instantánea, así que tres consultas pueden ver momentos distintos.
- Propone correr las tres en una transacción con un aislamiento que fije la instantánea (por ejemplo REPEATABLE READ) o en una sola sentencia.
- Mantiene el corte como instante explícito en UTC para que el resultado no dependa de cuándo corre.
- Dice cómo comprobaría que cuadran (el total es la suma del conteo por estado).
