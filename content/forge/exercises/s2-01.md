# S2-01 · Requisitos y números antes del dibujo

Banco de la celda: convertir objetivos de disponibilidad en minutos, encontrar el pico real de una planta, reconocer el número que cambia la forma del diseño, leer dos lecturas de §08 con el protocolo de cinco preguntas y transferir la estimación a sensores de vibración.

## Noventa y nueve punto nueve
type: prediccion
id: s2-01-pred-disponibilidad
rol: prediccion
escala: 50 70 90

El camino de alertas tiene un objetivo de disponibilidad de 99.9 % medido sobre 30 días. Predice cuánto tiempo de caída permite al mes, sin calculadora.

### Opciones
- [x] Unos 43 minutos.
- Unas 7 horas.
- Unos 4 minutos.
- Unos 9 segundos.
### Justificación
30 días son 43,200 minutos; el 0.1 % de eso es 43.2 minutos. Siete horas corresponden a un 99 % (432 minutos); unos 4 minutos, a 99.99 %; y 9 segundos, a un 99.9999 %. Convertir el porcentaje a minutos es lo que permite discutir el objetivo con quien recibe las alertas.

## Presupuesto de error en minutos
type: code
id: s2-01-code-presupuesto

Implementa `presupuestoMinutos(slo, dias)`: los minutos de indisponibilidad que permite un objetivo `slo` (fracción entre 0 y 1, por ejemplo `0.999`) en una ventana de `dias` días, redondeados a una décima.

### Firma
```javascript
function presupuestoMinutos(slo, dias) {
  // minutos permitidos, redondeados a 0.1
}
```
### Casos
```json
[
  { "input": [0.999, 30], "expected": 43.2 },
  { "input": [0.9995, 30], "expected": 21.6 },
  { "input": [0.99, 7], "expected": 100.8 },
  { "input": [0.9999, 365], "expected": 52.6 },
  { "input": [1, 30], "expected": 0 },
  { "input": [0.95, 1], "expected": 72 }
]
```
### Solución
```javascript
function presupuestoMinutos(slo, dias) {
  const minutos = (1 - slo) * dias * 24 * 60;
  return Math.round(minutos * 10) / 10;
}
```
### Pistas
- Un día tiene 1,440 minutos.
- Redondea al final, no en cada paso.

## El pico que no es el doble
type: prediccion
id: s2-01-pred-pico
rol: prediccion

Una planta tiene 8,000 sensores a una lectura por segundo. Su pasarela guarda hasta 10 minutos de lecturas si pierde la red y, al reconectar, las reenvía todas en un minuto. Predice cuántas lecturas por segundo **adicionales** llegan durante ese minuto.

### Opciones
- [x] Unas 80,000 por segundo, diez veces el tráfico normal de la planta.
- Unas 16,000 por segundo, el doble del tráfico normal.
- Unas 8,000 por segundo, porque la pasarela no supera la tasa normal.
- Unas 1,333 por segundo, porque el reenvío se reparte en 10 minutos.
### Justificación
10 minutos son 600 segundos: 8,000 × 600 = 4.8 millones de lecturas guardadas que llegan en 60 segundos, 80,000 por segundo encima del tráfico normal. Dimensionar con «el doble del promedio» ignora el mecanismo del pico. Si la pasarela limitara su tasa de reenvío o lo repartiera en 10 minutos, el número sería otro, y por eso el mecanismo se escribe como supuesto con su fuente.

## El número que cambia la forma
type: multiple_choice
id: s2-01-choice-umbral
rol: recuperacion

Sin volver al libro: tu diseño de alertas evalúa reglas en la nube con un p99 de 5 s. ¿Cuál de estos cambios obliga a cambiar la **forma** del diseño y no sólo su tamaño?

### Opciones
- [x] Que las alertas pasen a ser de seguridad y deban actuar en menos de 200 ms.
- Que la cantidad de máquinas crezca un 20 %.
- Que la retención de agregados pase de 2 a 3 años.
- Que se agregue un turno de noche con los mismos sensores.
### Justificación
Con 200 ms ya no cabe el viaje a la nube, la evaluación y la vuelta: la regla tiene que correr en la planta y la nube pasa a registrar. Los otros cambios crecen el sistema en proporción (más ingestión, más almacenamiento, más horas de uso) sin cambiar qué componente hace qué. Encontrar los umbrales de forma es la parte valiosa de una estimación.

Después haz el trabajo propio de §08: define un indicador, un objetivo y una regla de respuesta ante degradación para el camino de alertas de planta.

### Modelo
Problema: decidir cuánta confiabilidad necesita un servicio y cómo saber si la cumple, sin perseguir el 100 %. Supuesto esencial: existe un indicador medible que refleja lo que el usuario vive, y el usuario tolera algo de falla. Mecanismo: indicadores (SLI), objetivos (SLO) sobre una ventana y un presupuesto de error con una política que dice qué cambia cuando se gasta. Fallo que evita: discutir la confiabilidad por impresiones y priorizar funciones mientras el servicio se degrada. Costo: medir bien (elegir el indicador correcto cuesta), y aceptar congelar cambios cuando el presupuesto se agota. Trabajo propio: SLI = proporción de lecturas fuera de rango cuya alerta llega a la pantalla del supervisor en ≤ 5 s; SLO = 99.9 % en 30 días; regla = con el presupuesto gastado se congelan los cambios del camino de alertas y la siguiente iteración se dedica a la causa principal del gasto.
### Regla

### Modelo
