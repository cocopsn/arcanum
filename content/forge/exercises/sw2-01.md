## Antes de leer: el puntero al bloque liberado
type: prediccion
id: prediccion-uso-tras-liberar
rol: prediccion
tiempo: 2

Un programa en C libera un bloque con `free(p)` y, más adelante, escribe en `p[0]`. ¿Qué es lo más probable?

### Opciones
- [x] Que no falle de inmediato: el comportamiento no está definido, y la escritura puede no hacer nada visible o corromper los datos de otro objeto que ya ocupa ese lugar.
- Que el programa se detenga de inmediato con un error que señala la línea.
- Que la escritura se ignore, porque la memoria liberada queda protegida.
- Que el sistema operativo vuelva a asignar el bloque a `p` automáticamente.
### Justificación
En C, liberar no borra ni protege la memoria: el bloque vuelve al asignador, que puede entregarlo a otra parte del programa. Escribir ahí es comportamiento indefinido: a veces no se nota, a veces corrompe otro objeto, y el síntoma aparece lejos de la causa. No hay comprobación automática salvo que uses herramientas que la agreguen. Nada vuelve a asignar el bloque a `p`.

## Un pool con manijas de generación
type: code
id: codigo-pool-generaciones
tiempo: 18

Implementa el pool de bloques del libro, que detecta la doble liberación y el uso de manijas viejas.

### Especificación
`pool(n, operaciones)`:
- El pool tiene `n` bloques, todos libres y con generación 0 al empezar.
- `["alloc"]`: toma el bloque libre de **menor índice**, lo marca ocupado y responde la manija `"indice:generacion"`; si no hay libres, responde `"lleno"`.
- `["free", manija]`: si la manija es válida, libera el bloque, **sube su generación en 1** y responde `"ok"`; si no, responde `"invalido"`.
- `["leer", manija]`: responde `"ok"` si la manija es válida y `"invalido"` si no.
- Una manija es **válida** si tiene la forma `"i:g"` con enteros, `i` es un bloque del pool, el bloque está ocupado y su generación actual es `g`.
- Devuelve la lista de respuestas, en orden.

### Solución
```javascript
function pool(n, operaciones) {
  const generacion = new Array(n).fill(0);
  const ocupado = new Array(n).fill(false);
  const indiceValido = (manija) => {
    if (typeof manija !== "string") return -1;
    const m = /^(\d+):(\d+)$/.exec(manija);
    if (!m) return -1;
    const i = Number(m[1]);
    const g = Number(m[2]);
    return i < n && ocupado[i] && generacion[i] === g ? i : -1;
  };
  const salida = [];
  for (const op of operaciones) {
    if (op[0] === "alloc") {
      const i = ocupado.indexOf(false);
      if (i === -1) {
        salida.push("lleno");
      } else {
        ocupado[i] = true;
        salida.push(i + ":" + generacion[i]);
      }
    } else if (op[0] === "free") {
      const i = indiceValido(op[1]);
      if (i === -1) {
        salida.push("invalido");
      } else {
        ocupado[i] = false;
        generacion[i] += 1;
        salida.push("ok");
      }
    } else {
      salida.push(indiceValido(op[1]) === -1 ? "invalido" : "ok");
    }
  }
  return salida;
}
```

```python
import re

def pool(n, operaciones):
    generacion = [0] * n
    ocupado = [False] * n

    def indice_valido(manija):
        if not isinstance(manija, str):
            return -1
        m = re.fullmatch(r"([0-9]+):([0-9]+)", manija)
        if not m:
            return -1
        i, g = int(m.group(1)), int(m.group(2))
        return i if i < n and ocupado[i] and generacion[i] == g else -1

    salida = []
    for op in operaciones:
        if op[0] == "alloc":
            if False in ocupado:
                i = ocupado.index(False)
                ocupado[i] = True
                salida.append(str(i) + ":" + str(generacion[i]))
            else:
                salida.append("lleno")
        elif op[0] == "free":
            i = indice_valido(op[1])
            if i == -1:
                salida.append("invalido")
            else:
                ocupado[i] = False
                generacion[i] += 1
                salida.append("ok")
        else:
            salida.append("invalido" if indice_valido(op[1]) == -1 else "ok")
    return salida
```

### Pistas
- La generación sube al **liberar**: así toda manija entregada antes queda vieja.
- Una manija con el bloque ocupado pero otra generación es de un dueño anterior: inválida.
- Valida la forma de la manija antes de usar el índice: `"abc"` o `"5:0"` en un pool de 2 no son manijas.

## Dos dueños para un bloque
type: multiple_choice
id: dos-duenos
tiempo: 3

Un módulo crea un búfer en el montón y se lo pasa a una función que lo guarda en una estructura para usarlo después. Al terminar, el módulo libera el búfer. ¿Cuál es el problema y cuál la corrección?

### Opciones
- [x] Hay un alias sin dueño claro: la estructura conserva un puntero a un bloque que otro liberó, y su próximo uso es un uso después de liberar. Se corrige fijando un solo dueño (o la estructura copia el búfer, o la propiedad pasa a la estructura y sólo ella lo libera).
- No hay problema, porque el módulo lo creó y por eso le toca liberarlo.
- El problema es una fuga: habría que liberar el búfer dos veces, una en cada lugar.
- El problema es de rendimiento: copiar el búfer sería más lento que compartirlo.
### Justificación
Crear un bloque no basta para ser su único dueño si otra parte se queda con una referencia. Cuando dos partes creen tener derecho a usarlo y sólo una lo libera, la otra queda colgando. Liberarlo dos veces es una doble liberación, no una corrección. La solución es decidir un dueño: copiar para que cada parte tenga el suyo, o transferir la propiedad con una regla explícita. El costo de copiar es una decisión aparte; primero va la corrección.

## La variable local que se escapó
type: trace
id: traza-variable-local
tiempo: 3

En C, `int* crear() { int x = 42; return &x; }`. El llamador hace `int* p = crear();`, luego llama a otra función `f()` que usa la pila, y después lee `*p`. ¿Qué lee?

### Opciones
- [x] Un valor no definido: `x` vivía en el marco de pila de `crear`, que murió al volver; `f()` reutilizó esa zona de la pila, así que `*p` puede leer cualquier cosa que `f` haya dejado ahí.
- 42, porque el valor se copió al montón al hacer `return &x`.
- 42, porque la pila no se reutiliza mientras haya un puntero apuntando a ella.
- El programa no compila, porque C prohíbe devolver direcciones de variables locales.
### Justificación
Las variables locales viven en el marco de pila de su función y mueren al salir; devolver su dirección deja un puntero colgante. La siguiente llamada (`f()`) usa la misma zona de la pila para sus propios datos, así que el valor al que apunta `p` cambia sin aviso. C no copia nada al montón por devolver una dirección y no rastrea qué punteros apuntan a la pila. La mayoría de los compiladores sólo emite una advertencia: compila.

## Dónde vive cada dato
type: production
id: produccion-donde-vive
tiempo: 12

Para el pool del libro, reconstruye lo que pide la defensa de esta celda: dónde vive cada dato (el arreglo de bloques, los contadores, las manijas que reciben los clientes), cuánto vive cada uno, quién puede modificarlo y qué error detecta o deja pasar el diseño.

### Modelo
*Bloques y contadores:* el arreglo de bloques, el arreglo de ocupados y el de generaciones viven en el montón, creados al construir el pool y liberados al destruirlo; su único dueño es el pool, y sólo sus operaciones los modifican.
*Manijas:* son valores pequeños (índice y generación) que los clientes copian libremente, en su pila o en sus estructuras; no dan acceso directo a la memoria: todo acceso pasa por `leer` y por las operaciones del pool, que validan la manija.
*Contenido de un bloque:* vive desde `alloc` hasta `free`; su dueño es quien recibió la manija, y sólo ese dueño debe liberarlo.
*Errores detectados:* doble liberación y uso de una manija vieja (la generación ya no coincide), manijas mal formadas o fuera de rango.
*Errores que deja pasar:* que un cliente copie su manija a otro y los dos la usen a la vez (alias de una manija válida); que un cliente nunca libere su bloque (fuga, visible sólo como pool lleno); y, si el pool entregara punteros al contenido, que se los guarde después de liberar.

### Regla
Defender un componente con memoria explícita es reconstruir, por dato, dónde vive, cuánto vive, quién es su dueño y quién puede modificarlo, y declarar qué errores detecta el diseño y cuáles deja pasar.

## Giro: el pool compartido entre threads
type: giro
id: giro-pool-threads
rol: transferencia
tiempo: 15

El pool ahora lo usan 8 threads a la vez: unos asignan y liberan bloques, otros leen con manijas que recibieron de los primeros. Aparecen lecturas que validan la manija y, un instante después, encuentran el bloque ya reasignado. Rediseña el pool para que siga detectando manijas viejas bajo concurrencia: qué carrera aparece, qué proteges, qué cambia en el contrato de `leer` y qué se preserva.

### Rúbrica
- Identifica la carrera: entre validar la manija y usar el bloque, otro thread puede liberarlo y reasignarlo (revisar y luego actuar, SW2-03).
- Hace atómica la validación junto con el uso (por ejemplo, un lock por bloque o un contador de uso que impide liberar mientras alguien lee) y justifica la elección.
- Cambia el contrato de `leer` para que el acceso al contenido ocurra dentro de una operación del pool (una función que recibe lo que hay que hacer con el bloque) en lugar de entregar una referencia que sobrevive a la validación.
- Conserva las generaciones y la detección de doble liberación.
- Propone una prueba concurrente que reproduzca la carrera con el diseño viejo y no con el nuevo.
