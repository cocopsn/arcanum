## Antes de leer: de cuatro a cinco servidores
type: prediccion
id: prediccion-hash-mod
rol: prediccion
tiempo: 2

Un servicio asigna cada llave al servidor `hash(llave) mod N`. Hoy hay 4 servidores y se agrega un quinto. Con hashes bien distribuidos, ¿qué fracción aproximada de las llaves cambia de servidor?

### Opciones
- [x] Alrededor del 80 %: una llave se queda en su servidor sólo si `h mod 4` y `h mod 5` coinciden, y eso pasa para uno de cada cinco valores en promedio.
- Alrededor del 20 %, la parte que le toca al servidor nuevo.
- Alrededor del 25 %, porque cada servidor viejo cede una cuarta parte.
- Ninguna, porque el hash de la llave no cambia.
### Justificación
Las llaves se reparten por `h mod N`; al cambiar N, cambia la cuenta para casi todas. Mirando `h mod 20`, los residuos módulo 4 y módulo 5 coinciden sólo para 4 de los 20 valores (0, 1, 2 y 3), así que se queda en su lugar un 20 % y se mueve un 80 %, cuando lo mínimo necesario sería un 20 %. Por eso se usan un número fijo de shards con una tabla de asignación o el hash consistente: sólo se mueve lo que tiene que moverse. El hash no cambia, pero el servidor que le toca sí.

## Rebalancear la tabla de shards
type: code
id: codigo-rebalancear
tiempo: 20

Implementa el rebalanceo del controlador: dada la asignación actual de shards y la lista nueva de grupos, devuelve una asignación pareja que mueva lo menos posible, con reglas de desempate fijas para que sea determinista.

### Especificación
`rebalancear(asignacion, grupos)`:
- `asignacion[s]` es el id del grupo responsable del shard `s` (entero positivo), o `0` si no tiene. `grupos` es la lista de ids de grupos activos (puede venir desordenada o con repetidos; se usa ordenada y sin repetidos).
- Si no hay grupos, todos los shards quedan en `0`.
- Los shards de grupos que ya no están (y los que estaban en `0`) quedan **libres**.
- **Meta de cada grupo:** con `S` shards y `G` grupos, `q = ⌊S / G⌋` y `r = S mod G`. Se ordenan los grupos por cantidad actual de shards (de mayor a menor) y, a igualdad, por id ascendente; los primeros `r` tienen meta `q + 1` y los demás `q`.
- Cada grupo con más shards que su meta libera sus shards de **número más alto** hasta llegar a la meta.
- Los shards libres, en orden ascendente, se reparten entre los grupos que están por debajo de su meta, recorriendo los grupos por id ascendente y llenando cada uno hasta su meta antes de pasar al siguiente.
- Devuelve la asignación nueva (un arreglo del mismo largo).

### Solución
```javascript
function rebalancear(asignacion, grupos) {
  const ids = [...new Set(grupos)].sort((a, b) => a - b);
  const S = asignacion.length;
  if (ids.length === 0) return asignacion.map(() => 0);
  const de = new Map(ids.map((g) => [g, []]));
  const libres = [];
  asignacion.forEach((g, s) => (de.has(g) ? de.get(g).push(s) : libres.push(s)));
  const q = Math.floor(S / ids.length);
  const r = S % ids.length;
  const orden = [...ids].sort((a, b) => de.get(b).length - de.get(a).length || a - b);
  const meta = new Map(orden.map((g, i) => [g, q + (i < r ? 1 : 0)]));
  for (const g of ids) {
    const lista = de.get(g);
    while (lista.length > meta.get(g)) libres.push(lista.pop());
  }
  libres.sort((a, b) => a - b);
  const out = asignacion.slice();
  for (const g of ids) for (const s of de.get(g)) out[s] = g;
  let k = 0;
  for (const g of ids) {
    while (de.get(g).length < meta.get(g)) {
      const s = libres[k++];
      de.get(g).push(s);
      out[s] = g;
    }
  }
  return out;
}
```
```python
def rebalancear(asignacion, grupos):
    ids = sorted(set(grupos))
    S = len(asignacion)
    if not ids:
        return [0] * S
    de = {g: [] for g in ids}
    libres = []
    for s, g in enumerate(asignacion):
        if g in de:
            de[g].append(s)
        else:
            libres.append(s)
    q, r = divmod(S, len(ids))
    orden = sorted(ids, key=lambda g: (-len(de[g]), g))
    meta = {g: q + (1 if i < r else 0) for i, g in enumerate(orden)}
    for g in ids:
        while len(de[g]) > meta[g]:
            libres.append(de[g].pop())
    libres.sort()
    out = list(asignacion)
    for g in ids:
        for s in de[g]:
            out[s] = g
    k = 0
    for g in ids:
        while len(de[g]) < meta[g]:
            s = libres[k]
            k += 1
            de[g].append(s)
            out[s] = g
    return out
```

### Pistas
- Primero decide las metas; después libera excedentes; al final reparte. Mezclar los pasos rompe el determinismo.
- Los grupos con más shards reciben primero el `q + 1`: así se mueve lo menos posible.
- Un grupo que sale libera todos sus shards; uno que entra empieza con cero.

## La tabla que se quedó atrás
type: multiple_choice
id: tabla-dedup-migra
tiempo: 3

En una mudanza del shard 4 de G1 a G3, G3 recibe todos los pares llave-valor del shard, pero no la tabla de deduplicación (el último id de petición atendido por cliente). Un cliente cuya petición `put(k4, 70)` con id 18 se aplicó en G1 justo antes del cambio, y cuya respuesta se perdió, reintenta en G3. ¿Qué pasa?

### Opciones
- [x] G3 no sabe que el id 18 ya se aplicó y lo aplica otra vez; con una operación no idempotente (por ejemplo, un `append`), el valor queda duplicado.
- Nada: el valor de `k4` ya es 70, así que aplicarlo otra vez no cambia nada en ningún caso.
- G3 rechaza la petición porque el cliente usa una configuración vieja.
- G1 intercepta el reintento porque todavía tiene los datos del shard.
### Justificación
La deduplicación depende de recordar qué peticiones se atendieron, y ese recuerdo pertenece al shard tanto como sus datos. Si no viaja, el grupo nuevo trata el reintento como una petición nueva. Con un `put` puro el daño puede no verse, pero con `append` o con un incremento el efecto se duplica, y aun con `put` una escritura posterior de otro cliente podría quedar sobrescrita por el reintento tardío. El cliente ya tiene la configuración nueva cuando reintenta, y G1 dejó de servir el shard al aplicar la configuración 6.

## El cliente con la configuración vieja

### Opciones
- [x] G1 responde «grupo equivocado»; el cliente pide la configuración y recibe la 6; G3 responde «espera» porque no tiene los datos; cuando G3 instala el shard, el reintento devuelve el valor.
- G1 devuelve el valor, porque todavía tiene los datos del shard 4.
- G3 devuelve «no existe», porque el shard todavía está vacío en G3.
- El controlador devuelve el valor, porque conoce la configuración vigente.
### Justificación
G1 dejó de servir el shard 4 en cuanto aplicó la configuración 6 en su log; conservar los datos para entregarlos no lo vuelve responsable. G3 es el responsable según la configuración 6, pero no puede responder hasta tener los datos: responder «no existe» con un shard vacío sería devolver un valor falso. El controlador sólo publica configuraciones; no guarda datos de los shards.

## El paper de Dynamo con el protocolo de cinco preguntas
type: production
id: produccion-paper-dynamo
tiempo: 20

Lee el paper de Dynamo y responde el protocolo de cinco preguntas del programa: problema, supuesto esencial, mecanismo, fallo que evita y costo que introduce. Como trabajo propio de la sección 08, describe un historial con dos versiones concurrentes de un dato y la política de reconciliación que usarías. Cierra diciendo por qué Dynamo del paper y DynamoDB actual no se tratan como equivalentes.

### Modelo
*Problema:* un almacén de llaves que acepte escrituras siempre, aun con fallas de nodos y particiones de red, para servicios donde rechazar una escritura (agregar al carrito) cuesta más que reconciliar después.
*Supuesto esencial:* la disponibilidad de escritura importa más que la consistencia inmediata; las aplicaciones pueden tolerar y reconciliar versiones divergentes; el entorno es confiable (sin nodos maliciosos).
*Mecanismo:* hash consistente con nodos virtuales; réplica en los siguientes N nodos del anillo; quórums configurables de lectura y escritura; quórum flexible con entrega diferida cuando un nodo responsable no responde; relojes vectoriales para detectar versiones concurrentes; reconciliación por la aplicación; y sincronización de réplicas en segundo plano.
*Fallo que evita:* que la caída de nodos o una partición de red impida escribir.
*Costo:* las lecturas pueden devolver varias versiones y la aplicación debe unirlas; la unión puede resucitar elementos borrados; los relojes vectoriales crecen y hay que podarlos; razonar sobre la consistencia es más difícil.
*Historial (trabajo propio):* el carrito `{leche}` se lee en dos dispositivos durante una partición; uno agrega `pan` y otro quita `leche`. Quedan dos versiones concurrentes, `{leche, pan}` y `{}`. Una unión por conjunto daría `{leche, pan}` y resucitaría la leche; registrar las operaciones (agregar y quitar con su identificador) en lugar del estado permite reconciliar a `{pan}`.
*No equivalencia:* el paper describe un sistema interno de un momento dado; un servicio actual con un nombre parecido tiene su propio modelo de consistencia y su propia documentación, y sus garantías se leen ahí, no en el paper.

### Regla
Un paper se lee con cinco preguntas (problema, supuesto esencial, mecanismo, fallo que evita y costo que introduce), y sus propiedades no se extrapolan a servicios modernos que compartan el nombre.
