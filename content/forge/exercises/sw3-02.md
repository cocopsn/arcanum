## Antes de leer: el trozo que llega primero
type: prediccion
id: prediccion-trozo-adelantado
rol: prediccion
tiempo: 2

Un reensamblador espera el byte 0 de un flujo. Llega primero el trozo «índice 4: `efgh`» y el flujo de salida tiene lugar de sobra. ¿Qué debe hacer?

### Opciones
- [x] Guardarlo sin escribir nada todavía: falta el hueco de 0 a 3, y los bytes 4 a 7 se escriben en cuanto ese hueco se llene.
- Escribirlo de inmediato en el flujo, porque es lo primero que llegó.
- Descartarlo, porque no empieza en el índice esperado.
- Escribirlo y rellenar los índices 0 a 3 con ceros.
### Justificación
El orden del flujo lo dan los índices, no la llegada. Escribir `efgh` ahora lo pondría antes de bytes que van primero. Descartarlo obligaría al emisor a retransmitir algo que ya llegó bien y cabía. Rellenar con ceros inventaría datos. Lo correcto es guardarlo dentro de la ventana y esperar a que el hueco se cierre.

## El reensamblador
type: code
id: codigo-reensamblar
tiempo: 20

Implementa el reensamblador sobre un flujo de bytes con capacidad fija. Para simplificar, el lector no consume durante la simulación, así que la ventana termina siempre en el índice `capacidad`.

### Especificación
`reensamblar(capacidad, trozos)`:
- `trozos` es una lista de `[inicio, datos, ultimo]`: el índice del primer byte del trozo, el texto (ASCII, un carácter es un byte) y si es el último trozo del flujo.
- **Ventana:** de `primero` (el primer índice sin ensamblar, al principio 0) hasta el índice `capacidad`, sin incluirlo.
- Por cada byte del trozo: si su índice es menor que `primero`, ya se escribió y se ignora; si es mayor o igual que `capacidad`, no cabe y se descarta; si no, se guarda (si ya estaba guardado, no cambia nada).
- Después de cada trozo, mientras el byte en `primero` esté guardado, se escribe en el flujo y `primero` avanza.
- Si el trozo es el último, el flujo termina en `inicio + longitud de datos` (aunque una parte se haya descartado).
- Devuelve `{ "ensamblado", "pendientes", "cerrado" }`: el texto escrito en el flujo, cuántos bytes quedan guardados sin escribir (cada índice cuenta una vez) y si el flujo está cerrado (se conoce su fin y `primero` lo alcanzó).

### Firma

function reensamblar(capacidad, trozos) {
  // TODO: bytes guardados por índice, primero sin ensamblar y fin del flujo
  return { ensamblado: "", pendientes: 0, cerrado: false };
}

### Solución
```javascript
function reensamblar(capacidad, trozos) {
  let ensamblado = "";
  const guardados = new Map();
  let fin = null;
  for (const [inicio, datos, ultimo] of trozos) {
    if (ultimo) fin = inicio + datos.length;
    for (let i = 0; i < datos.length; i++) {
      const indice = inicio + i;
      if (indice < ensamblado.length || indice >= capacidad) continue;
      if (!guardados.has(indice)) guardados.set(indice, datos[i]);
    }
    while (guardados.has(ensamblado.length)) {
      const c = guardados.get(ensamblado.length);
      guardados.delete(ensamblado.length);
      ensamblado += c;
    }
  }
  return { ensamblado, pendientes: guardados.size, cerrado: fin !== null && ensamblado.length === fin };
}
```
```python
def reensamblar(capacidad, trozos):
    ensamblado = ""
    guardados = {}
    fin = None
    for inicio, datos, ultimo in trozos:
        if ultimo:
            fin = inicio + len(datos)
        for i, c in enumerate(datos):
            indice = inicio + i
            if indice < len(ensamblado) or indice >= capacidad:
                continue
            if indice not in guardados:
                guardados[indice] = c
        while len(ensamblado) in guardados:
            ensamblado += guardados.pop(len(ensamblado))
    return {"ensamblado": ensamblado, "pendientes": len(guardados), "cerrado": fin is not None and len(ensamblado) == fin}
```

### Pistas
- Organiza lo guardado por índice de byte: así los solapamientos y los duplicados se resuelven solos.
- La ventana termina en `capacidad` porque el lector no consume; lo que cae fuera se descarta aunque el resto del trozo se guarde.
- Conocer el fin del flujo no basta para cerrarlo: hace falta que el primer índice sin ensamblar lo alcance.

## Cerrar demasiado pronto
type: multiple_choice
id: cerrar-pronto
tiempo: 3

Llega el trozo «índice 6: `gh`», marcado como el último del flujo, cuando sólo se han ensamblado los bytes 0 a 3. ¿Qué debe hacer el reensamblador con el cierre?

### Opciones
- [x] Anotar que el flujo termina en el índice 8, guardar `gh` si cabe en la ventana y cerrar el flujo de bytes sólo cuando el primer índice sin ensamblar llegue a 8.
- Cerrar el flujo de inmediato, porque ya llegó el último trozo.
- Ignorar la marca de último, porque llegó fuera de orden.
- Cerrar el flujo y descartar los bytes 4 a 7 cuando lleguen.
### Justificación
La marca de último dice dónde termina el flujo, no que todo haya llegado. Cerrar ahora entregaría un flujo «terminado» al que le faltan los bytes 4 y 5. Ignorar la marca dejaría al lector esperando para siempre, porque el trozo no se va a repetir necesariamente. Descartar los bytes del medio sería perder datos válidos. Hay que recordar el fin y esperar a que el hueco se llene.

## Los pendientes con solapamiento
type: trace
id: traza-pendientes
tiempo: 3

Capacidad 20, nada ensamblado. Llegan en orden: «índice 5: `fgh`», «índice 6: `ghij`» y «índice 2: `cd`». ¿Cuántos bytes pendientes hay al final y qué se escribió en el flujo?

### Opciones
- [x] 7 pendientes (índices 2, 3, 5, 6, 7, 8 y 9) y nada escrito: falta el byte 0, así que no se puede escribir ninguno.
- 9 pendientes, porque llegaron 3 + 4 + 2 bytes.
- 7 pendientes y `cd` escrito, porque `cd` forma un bloque completo.
- 0 pendientes, porque los trozos que se solapan se descartan.
### Justificación
Los pendientes se cuentan por índice, no por byte recibido: `fgh` guarda 5, 6 y 7; `ghij` agrega sólo 8 y 9 (6 y 7 ya estaban); `cd` guarda 2 y 3. En total, 7 índices distintos. Sumar 9 cuenta dos veces los solapados. Nada se escribe porque el flujo sólo avanza desde el primer índice sin ensamblar, el 0, que no ha llegado; un bloque completo en medio no sirve. Los solapamientos se combinan, no se descartan.

## Justifica memoria y progreso
type: production
id: produccion-memoria-progreso
tiempo: 12

La defensa de esta celda pide justificar la memoria, el progreso y el comportamiento de cada borde del reensamblador. Escribe esa justificación: cuánta memoria usa como máximo y por qué, cuándo garantiza que el flujo avanza, y qué hace en cada borde (duplicado, solapamiento, hueco, fuera de la ventana, último trozo adelantado).

### Modelo
*Memoria:* guarda sólo bytes dentro de la ventana, que va del primer índice sin ensamblar hasta ese índice más la capacidad disponible del flujo; como los bytes escritos en el flujo también ocupan capacidad, la suma de bytes en el flujo y bytes guardados nunca supera la capacidad. Cada índice se guarda una vez.
*Progreso:* el primer índice sin ensamblar avanza en cuanto llega el byte que le corresponde; si ese byte nunca llega, no hay progreso, y eso es correcto: el emisor debe retransmitirlo (SW3-03). Cuando el lector consume, la ventana se abre y caben más bytes.
*Bordes:* duplicado, se ignora porque su índice ya se escribió o ya está guardado; solapamiento, se guardan sólo los índices nuevos; hueco, los bytes posteriores esperan guardados; fuera de la ventana, se descarta lo que no cabe aunque el resto del trozo se guarde; último trozo adelantado, se anota el fin y se cierra sólo cuando el primer índice sin ensamblar lo alcanza.

### Regla
Un reensamblador correcto se justifica con su invariante de memoria (lo escrito más lo guardado no supera la capacidad), con la condición exacta de progreso (llega el siguiente byte esperado) y con una regla explícita para cada borde.

### Rúbrica
- Acota la memoria con la capacidad y explica por qué lo escrito también cuenta.
- Dice cuándo hay progreso y por qué no avanzar sin el byte esperado es correcto.
- Trata los cinco bordes pedidos con una regla cada uno.
- Explica el papel del emisor cuando se descartan bytes.
- No cierra el flujo con huecos pendientes.
