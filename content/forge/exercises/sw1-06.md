## Antes de leer: mil commits
type: prediccion
id: prediccion-bisect-mil
rol: prediccion
tiempo: 2

Una regresión apareció en algún punto de los últimos 1,000 commits. Tienes una prueba determinista que distingue un commit bueno de uno malo. Con búsqueda binaria sobre el historial, ¿cuántas pruebas necesitas como máximo para encontrar el commit culpable?

### Opciones
- [x] Unas 10, porque cada prueba descarta la mitad del rango que queda y 2¹⁰ = 1,024 ≥ 1,000.
- Unas 500, porque en promedio el culpable está a la mitad del historial.
- 1,000, porque hay que compilar cada commit para estar seguro.
- Unas 32, porque la raíz cuadrada de 1,000 es el número de bloques que hay que revisar.
### Justificación
La bisección es búsqueda binaria sobre un rango ordenado en el que todos los commits antes del culpable son buenos y todos los posteriores son malos. Cada prueba parte el rango a la mitad, así que bastan ⌈log₂ 1,000⌉ = 10. Quinientas sería una búsqueda lineal promedio; mil, una búsqueda lineal completa. La raíz cuadrada aparece en otras estrategias de bloques, no en la búsqueda binaria. La condición importante es que la prueba sea determinista: si falla al azar, la búsqueda se desvía.

## Los commits que prueba la bisección
type: trace
id: traza-bisect
tiempo: 4

Los commits se numeran del 1 al 16. El 1 es bueno y el 16 es malo; el culpable real es el 11. En cada paso pruebas el commit `⌊(bueno + malo) / 2⌋`, donde `bueno` es el último commit bueno conocido y `malo` el primer malo conocido, hasta que `malo = bueno + 1`. ¿Qué commits pruebas, en orden?

### Opciones
- [x] 8, 12, 10, 11: el 8 es bueno, el 12 malo, el 10 bueno y el 11 malo; como 11 = 10 + 1, el culpable es el 11.
- 8, 12, 11: al ver que el 12 es malo, el culpable tiene que ser el anterior.
- 9, 13, 11: se redondea hacia arriba en cada paso.
- 1, 2, 4, 8, 16: se duplica el salto hasta encontrar el primer malo.
### Justificación
Con bueno = 1 y malo = 16, el primer punto es ⌊17/2⌋ = 8, bueno, así que bueno = 8. Luego ⌊24/2⌋ = 12, malo, así que malo = 12. Luego ⌊20/2⌋ = 10, bueno, bueno = 10. Luego ⌊22/2⌋ = 11, malo, malo = 11. Ahora malo = bueno + 1 y el culpable es el 11. Saltar del 12 al 11 sin probar el 10 supone algo que nadie comprobó: el culpable podía ser el 9 o el 10. Redondear hacia arriba no es la regla del enunciado, y aun con esa regla la secuencia 9, 13, 11 se detiene antes de tiempo: faltaría probar el 10 para saber que el 11 es el primero malo. Duplicar el salto es otra estrategia, útil cuando no conoces un commit malo.

## Corrige el error con el cambio mínimo
type: code
id: codigo-paginar
tiempo: 12

El código de `paginar` llegó con un reporte: «la página 1 muestra lo que debería estar en la página 2». La firma trae el código tal como está hoy. Encuentra la causa y corrígela con el cambio mínimo que cumple la especificación.

### Especificación
`paginar(items, pagina, tamano)`:
- `items` es una lista; `pagina` y `tamano` son enteros.
- Las páginas se numeran desde 1: la página 1 contiene los primeros `tamano` elementos.
- Si `pagina < 1` o `tamano < 1`, devuelve una lista vacía.
- Una página más allá del final devuelve una lista vacía; la última página puede tener menos de `tamano` elementos.
- No modifiques `items`.

### Firma
```javascript
function paginar(items, pagina, tamano) {
  if (pagina < 1 || tamano < 1) return [];
  const desde = pagina * tamano;
  return items.slice(desde, desde + tamano);
}
```
```python
def paginar(items, pagina, tamano):
    if pagina < 1 or tamano < 1:
        return []
    desde = pagina * tamano
    return items[desde:desde + tamano]
```

### Casos
```json
[
  { "input": [["a", "b", "c", "d", "e"], 1, 2], "expected": ["a", "b"] },
  { "input": [["a", "b", "c", "d", "e"], 2, 2], "expected": ["c", "d"] },
  { "input": [["a", "b", "c", "d", "e"], 3, 2], "expected": ["e"] },
  { "input": [["a", "b", "c", "d", "e"], 4, 2], "expected": [] },
  { "input": [["a", "b", "c"], 0, 2], "expected": [] },
  { "input": [["a", "b", "c"], 1, 0], "expected": [] },
  { "input": [[], 1, 10], "expected": [] },
  { "input": [["a", "b", "c"], 1, 10], "expected": ["a", "b", "c"], "hint": true }
]
```

### Solución
```javascript
function paginar(items, pagina, tamano) {
  if (pagina < 1 || tamano < 1) return [];
  const desde = (pagina - 1) * tamano;
  return items.slice(desde, desde + tamano);
}
```
```python
def paginar(items, pagina, tamano):
    if pagina < 1 or tamano < 1:
        return []
    desde = (pagina - 1) * tamano
    return items[desde:desde + tamano]
```

### Pistas
- Reproduce primero: ¿qué devuelve el código actual para la página 1 con tamaño 2?
- La especificación numera las páginas desde 1; el índice del primer elemento de una página sale de restar uno.
- El cambio mínimo es una sola expresión. Si estás tocando más de una línea, para y vuelve a leer la causa.

## El parche que pasa el CI
type: multiple_choice
id: parche-cambia-contrato
tiempo: 3

Para el error de medianoche (`validarSolicitud([], 1380, 1440)` devuelve `"horario-invalido"` y debería devolver `"ok"`), un compañero propone quitar por completo la comprobación de `fin`, porque «el formulario ya no deja escribir valores fuera de rango». El parche también borra la prueba de `fin = 1441`, que ahora fallaría. El CI queda verde. ¿Qué haces en la revisión?

### Opciones
- [x] Rechazarlo: cambia el contrato (la frontera deja de comprobar la precondición), confía en un cliente que no controla y borra la prueba que lo delataba; pedir el cambio mínimo de `fin > 1439` a `fin > 1440` con la prueba de medianoche como regresión.
- Aprobarlo: el CI está verde y el formulario ya valida el rango, así que la comprobación es redundante.
- Aprobarlo si agrega un comentario explicando que el formulario valida el rango.
- Pedir que también reescriba la validación completa, ya que está tocando ese código.
### Justificación
Un CI verde dice que las pruebas que quedan pasan, no que el contrato se conserva; y aquí el parche borró justo la prueba que fallaba. La comprobación en la frontera existe porque la solicitud puede llegar de otro cliente que no es el formulario. La corrección mínima restablece el contrato con una línea y deja la prueba nueva como regresión. Un comentario no compensa quitar la protección. Pedir una reescritura dentro de una corrección urgente agranda el alcance y esconde la línea que importa.

## Causa, alcance y por qué no una reescritura
type: production
id: produccion-explicacion-parche
tiempo: 12

Escribe la descripción del pull request para la corrección del error de medianoche del libro. Debe explicar la causa, el alcance del cambio, la evidencia de que la corrección funciona y por qué no elegiste reescribir la validación. Máximo diez líneas.

### Modelo
*Causa:* el commit «endurece validación de horario» cambió `fin > 1440` por `fin > 1439` al querer rechazar `fin = 1441`; el contrato de `validarSolicitud` usa intervalos semiabiertos con `fin ≤ 1440`, así que 1440 es un fin válido.
*Cambio:* una línea, de vuelta a `fin > 1440`.
*Evidencia:* la prueba nueva `rechaza_reserva_valida_que_termina_a_medianoche` falla sin el cambio y pasa con él; la prueba existente de `fin = 1441` sigue pasando; bisección sobre 64 commits con `git bisect run` y la prueba nueva, 6 pasos, señaló ese commit.
*Alcance:* no cambia ningún error devuelto ni el orden de las comprobaciones; ningún consumidor tiene que hacer nada.
*Por qué no reescribir:* el error tiene una causa única y el contrato está escrito; una reescritura arriesgaría la precedencia declarada (`horario-invalido` gana) sin ninguna evidencia de que haga falta.

### Regla
Un cambio de corrección se defiende con la causa comprobada, una prueba que falla sin el cambio y pasa con él, y un alcance mínimo que no altera ningún contrato; una reescritura necesita su propia evidencia y su propio cambio.

### Rúbrica
- Nombra la causa en una frase comprobable, con el commit que la introdujo.
- Presenta una prueba que falla sin el parche y pasa con él.
- Declara el alcance y afirma explícitamente qué contrato no cambia.
- Justifica no reescribir con un riesgo concreto, no con preferencia.
- Cabe en diez líneas y no mezcla cambios ajenos a la corrección.

## Giro: el error que no se reproduce
type: giro
id: giro-no-reproduce
rol: transferencia
tiempo: 15

Un error nuevo: en producción, una de cada 10,000 reservas queda duplicada. No lo puedes reproducir en tu máquina, las pruebas pasan y el historial no muestra ninguna regresión clara: el código de reservas no cambió en tres meses, pero sí cambió la infraestructura (más réplicas del servicio). El equipo quiere un parche hoy. Diseña cómo llegas a una reproducción y a un cambio mínimo, qué no harías y qué evidencia pedirías antes de aprobar cualquier parche.

### Rúbrica
- Formula hipótesis comprobables que conectan el cambio de infraestructura con el síntoma (por ejemplo, dos réplicas que procesan la misma solicitud reintentada).
- Propone instrumentación mínima y segura para observar el caso en producción (identificador de solicitud, registros correlacionados), sin registrar datos sensibles.
- Busca una reproducción determinista fuera de producción (por ejemplo, forzar dos réplicas y un reintento) antes de corregir.
- Rechaza parches que oculten el síntoma (por ejemplo, borrar duplicados después) sin atacar la causa, o los marca como mitigación temporal declarada.
- Exige una prueba de regresión que reproduzca la concurrencia antes de aprobar.
