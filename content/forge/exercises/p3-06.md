## El efecto que modifica lo que vigila
type: prediccion
id: efecto-modifica
rol: prediccion
tiempo: 2

Una automatización tiene la condición «objetos modificados en el conjunto de alertas de prioridad alta» y el efecto «acción Escalar», que marca la alerta como escalada (una modificación). Se modifica una alerta alta. Predice qué pasa si nada más lo impide.

### Opciones
- [x] Rebota: la modificación que hace el efecto vuelve a cumplir la condición y la alerta se escala una y otra vez.
- Se escala una sola vez, porque Automate ignora los cambios hechos por sus propios efectos.
- No se escala, porque la condición sólo mira cambios de los datasets.
- Se escala una vez por hora, porque el monitoreo es programado.
### Justificación
La documentación de condiciones sobre conjuntos de objetos indica que los cambios pueden venir de datasets, de acciones o de aplicaciones externas: el cambio hecho por la acción del efecto también cuenta. Sin una guarda en la condición (por ejemplo, «y no escalada») o un efecto idempotente, la automatización se realimenta.

### Solución
```javascript
function simular(objetos, modificados, usar_guarda, max_ciclos) {
  const estado = new Map(objetos.map((o) => [o.id, { ...o }]));
  let actuales = [...new Set(modificados)].filter((id) => estado.has(id));
  let disparos = 0;
  let ciclos = 0;
  while (ciclos < max_ciclos) {
    const disparados = actuales.filter((id) => {
      const o = estado.get(id);
      return o.prioridad === "alta" && (!usar_guarda || o.escalada === false);
    });
    if (disparados.length === 0) return { disparos, ciclos, rebota: false };
    ciclos += 1;
    disparos += disparados.length;
    for (const id of disparados) estado.get(id).escalada = true;
    actuales = disparados;
  }
  return { disparos, ciclos, rebota: true };
}
```
```python
def simular(objetos, modificados, usar_guarda, max_ciclos):
    estado = {o["id"]: dict(o) for o in objetos}
    actuales = [i for i in dict.fromkeys(modificados) if i in estado]
    disparos = 0
    ciclos = 0
    while ciclos < max_ciclos:
        disparados = [i for i in actuales if estado[i]["prioridad"] == "alta" and (not usar_guarda or estado[i]["escalada"] is False)]
        if not disparados:
            return {"disparos": disparos, "ciclos": ciclos, "rebota": False}
        ciclos += 1
        disparos += len(disparados)
        for i in disparados:
            estado[i]["escalada"] = True
        actuales = disparados
    return {"disparos": disparos, "ciclos": ciclos, "rebota": True}
```
### Pistas
- Cada ciclo sólo mira lo que se modificó en el ciclo anterior.
- El efecto modifica a todos los disparados: sin guarda, vuelven a disparar.
- Termina por falta de disparos o por el tope de ciclos; sólo el tope cuenta como rebote.

## La guarda que sí corta el ciclo
type: multiple_choice
id: guarda-correcta
tiempo: 2

¿Cuál de estos cambios corta de verdad el ciclo de la automatización «Escalar alertas altas»?

### Opciones
- [x] Agregar a la condición «y escalada = falso», con un efecto que marca la alerta como escalada y no vuelve a modificarla si ya lo está.
- Pasar de monitoreo en vivo a monitoreo programado cada hora.
- Guardar en una variable en memoria del proceso las alertas ya escaladas.
- Desactivar las notificaciones del efecto.
### Justificación
La guarda tiene que estar en los datos que la condición evalúa: una alerta escalada sale del conjunto y no vuelve a disparar, aunque el proceso se reinicie. Programar la evaluación sólo hace el ciclo más lento; la memoria del proceso se pierde; y apagar las notificaciones esconde el ciclo sin cortarlo.

## Diseño de una automatización con recuperación
type: production
id: diseno-automatizacion
tiempo: 12

Diseña la automatización «Recordatorio de cita sin confirmar» para la clínica ficticia: 24 horas antes de una cita no confirmada, envía un recordatorio al paciente y, si 4 horas antes sigue sin confirmar, crea una tarea para recepción. Escribe condición y efecto de cada paso, la guarda que evita repetir recordatorios, el límite de repeticiones, la identidad de ejecución, si algo queda en revisión humana y la ruta de recuperación.

### Modelo
- **Paso 1:** condición de tiempo combinada con datos: citas programadas que empiezan en 24 h, `confirmada = falso` y `recordatorio_enviado = falso`. Efecto: acción «EnviarRecordatorio» que manda el mensaje y marca `recordatorio_enviado = verdadero` (idempotente: si ya está marcado, no hace nada).
- **Paso 2:** condición: citas que empiezan en 4 h, `confirmada = falso` y sin tarea abierta. Efecto: acción «CrearTareaRecepcion» sobre otro tipo de objeto (Tarea), que no modifica la cita.
- **Límites:** a lo sumo 1 recordatorio por cita y 1 tarea por cita; si la acción falla 3 veces, aviso a una persona.
- **Identidad:** una identidad de servicio con permiso sólo para esas dos acciones.
- **Revisión humana:** no para el recordatorio (bajo impacto); sí para cualquier cancelación automática, que no se automatiza.
- **Recuperación:** apagar la automatización; consultar el registro de recordatorios enviados; enviar un mensaje de corrección si se mandó por error (compensación, P2-06).
### Regla
Una automatización se diseña con su guarda en los datos, efectos idempotentes que llaman a acciones con criterios, límites de repetición con aviso humano, identidad de ejecución mínima, decisión explícita de revisión humana y una ruta de recuperación escrita antes de encenderla.
### Rúbrica
- Cada paso tiene condición y efecto definidos.
- Hay una guarda en los datos que impide repetir el recordatorio.
- El paso 2 escribe en otro tipo de objeto o no modifica la cita, para no rebotar.
- Define límites, identidad, revisión humana y recuperación.
