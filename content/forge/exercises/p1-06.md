## Eventos fuera de orden en un objeto respaldado por stream
type: prediccion
id: fuera-de-orden
rol: prediccion
tiempo: 3

Un tipo de objeto `Sensor` se indexa desde un stream. Para el sensor S-7 llegan, en este orden de llegada, dos eventos: primero «temperatura 81 °C a las 10:00:05» y después, con retraso de red, «temperatura 74 °C a las 10:00:01». El pipeline no reordena. Predice qué temperatura muestra el objeto S-7 después de indexar ambos.

### Opciones
- [x] 74 °C, el valor más viejo, porque la indexación aplica «la actualización más reciente gana» según el orden en que llegan las actualizaciones.
- 81 °C, porque la indexación compara las marcas de tiempo de los eventos y conserva el más reciente.
- Los dos valores, como dos versiones del mismo objeto.
- Ninguno: el pipeline de indexación rechaza eventos fuera de orden.
### Justificación
La página de Funnel streaming pipelines documenta que la indexación streaming trata cada stream como un changelog con «la actualización más reciente gana» y advierte que, si los eventos llegan fuera de orden, la Ontology termina con datos incorrectos. Si la fuente no garantiza orden, hay que resolverlo antes (por ejemplo, con la resolución por llave y orden de P1-04) o aceptar y declarar el riesgo.

### Solución
```javascript
function atribuir_latencia(eventos) {
  const def = [["ingesta", "publicado", "ingestado"], ["transformacion", "ingestado", "transformado"], ["indexacion", "transformado", "indexado"], ["presentacion", "indexado", "visible"]];
  const nulo = (v) => v === null || v === undefined;
  const pct = (xs, p) => xs[Math.ceil((p / 100) * xs.length) - 1];
  const tramos = [];
  const sin_medir = [];
  for (const [tramo, a, b] of def) {
    const xs = [];
    for (const e of eventos) {
      if (!nulo(e.t[a]) && !nulo(e.t[b])) xs.push(Math.round((e.t[b] - e.t[a]) * 10) / 10);
    }
    if (xs.length === 0) { sin_medir.push(tramo); continue; }
    xs.sort((x, y) => x - y);
    tramos.push({ tramo, n: xs.length, p50: pct(xs, 50), p95: pct(xs, 95) });
  }
  let dominante = null;
  let mejor = -Infinity;
  for (const t of tramos) if (t.p95 > mejor) { mejor = t.p95; dominante = t.tramo; }
  return { tramos, dominante, sin_medir };
}
```

```python
import math

def atribuir_latencia(eventos):
    defs = [("ingesta", "publicado", "ingestado"), ("transformacion", "ingestado", "transformado"),
            ("indexacion", "transformado", "indexado"), ("presentacion", "indexado", "visible")]
    def pct(xs, p):
        return xs[math.ceil(p / 100 * len(xs)) - 1]
    tramos = []
    sin_medir = []
    for tramo, a, b in defs:
        xs = []
        for e in eventos:
            ta, tb = e["t"].get(a), e["t"].get(b)
            if ta is not None and tb is not None:
                xs.append(round((tb - ta) * 10) / 10)
        if not xs:
            sin_medir.append(tramo)
            continue
        xs.sort()
        tramos.append({"tramo": tramo, "n": len(xs), "p50": pct(xs, 50), "p95": pct(xs, 95)})
    dominante = None
    mejor = -math.inf
    for t in tramos:
        if t["p95"] > mejor:
            mejor = t["p95"]
            dominante = t["tramo"]
    return {"tramos": tramos, "dominante": dominante, "sin_medir": sin_medir}
```

- Con el rango más cercano, el p95 de cinco valores o menos es el máximo.

## Promedio o percentil
type: multiple_choice
id: promedio-percentil
tiempo: 2

En un día, 950 eventos tardaron 3 s de extremo a extremo y 50 tardaron 300 s. ¿Qué reporte describe mejor lo que vivió la operadora?

### Opciones
- [x] «p50 3 s, p95 300 s, n = 1,000»: la mitad de los eventos llega en 3 s y el 5 % más lento tarda cinco minutos, que es lo que la operadora recuerda.
- «Promedio 17.85 s»: resume todo en un solo número comparable entre días.
- «Máximo 300 s»: el peor caso es el único que importa.
- «Mediana 3 s»: si la mayoría llega rápido, el sistema cumple.
### Justificación
El promedio (17.85 s) no le pasó a ningún evento: mezcla dos poblaciones. La mediana sola esconde la cola. El máximo solo no dice cuántos eventos la sufren. Los percentiles con el número de registros dicen cuánta gente vive qué experiencia, que es lo que una decisión de capacidad necesita.

## Un duplicado que parece retraso

id: duplicado-retraso
tiempo: 2

Al medir el tramo de ingesta aparece un evento con 600 s de retraso. Al revisarlo, el mismo `id` de evento ya había llegado 599 s antes con un retraso de 1 s. ¿Qué pasó y qué haces?

### Opciones
- [x] La ingesta tiene semántica de al menos una vez, así que el evento llegó dos veces; mides la latencia con la primera llegada por llave y cuentas los duplicados como una métrica aparte.
- Es un retraso real de 600 s y debe entrar al p95 de la ingesta.
- Es un error de reloj del sensor y hay que descartar todas sus marcas.
- Hay que borrar el stream y volver a sincronizar desde cero.
### Justificación
La página de Streams indica que el búfer caliente da semántica de al menos una vez en la ingesta. Un reintento produce un duplicado tardío; si no deduplicas por llave antes de medir, atribuyes a la ingesta un retraso que ningún usuario vivió. Los duplicados sí son un dato operativo, pero distinto.

## La pantalla que no se actualiza
type: multiple_choice
id: pantalla-sin-refresco
tiempo: 2

Los objetos `Sensor` se actualizan en la Ontology a los pocos segundos del evento, pero en una aplicación que no es Workshop la operadora ve el cambio hasta varios minutos después. ¿A qué tramo atribuyes ese retraso?

### Opciones
- [x] Presentación: según la documentación de Funnel streaming pipelines, fuera de Workshop las aplicaciones no refrescan en vivo; los datos ya estaban indexados y la pantalla no los pidió.
- Indexación: el pipeline de Funnel tarda minutos en escribir el objeto.
- Ingesta: el broker retiene los mensajes.
- Transformación: la lógica con estado acumula ventanas de varios minutos.
### Justificación
Si las marcas muestran el objeto actualizado en segundos, el retraso está después de la indexación. La documentación aclara que fuera de Workshop no hay refresco en vivo para objetos respaldados por streams; atribuirlo a otro tramo llevaría a gastar en el componente equivocado.

## Plan de medición con lo no medido
type: production
id: plan-medicion
tiempo: 12

Escribe el plan para medir la latencia de extremo a extremo de un flujo sintético: lecturas de 40 sensores publicadas en un broker, sincronizadas a un stream, transformadas por un pipeline de streaming, indexadas como objetos y vistas por una operadora en una aplicación con refresco por intervalo. Indica qué marca de tiempo agregas en cada frontera, qué estadísticas reportas, cómo tratas duplicados y relojes, y qué tramo no podrás medir directamente y cómo lo acotas.

### Modelo
- **Marcas:** `t_evento` en el sensor; `t_ingestado` al entrar al stream; `t_transformado` en la salida del pipeline; `t_indexado` estimado consultando el objeto; `t_visible` registrado por la aplicación al pintar el valor.
- **Estadísticas:** p50, p95 y p99 por tramo y de extremo a extremo, con `n` medidos por tramo; nunca sólo el promedio.
- **Duplicados:** deduplicar por id de evento y medir con la primera llegada; reportar la tasa de duplicados aparte.
- **Relojes:** medir el desfase entre el reloj de los sensores y el de la plataforma; un retraso negativo se reporta como desfase, no como latencia.
- **No medido:** la indexación por separado, porque no hay métricas para objetos respaldados por streams; se acota como la diferencia entre `t_transformado` y la primera lectura del objeto con el valor nuevo, con la resolución del sondeo.
### Regla
Una atribución de latencia es defendible si cada tramo tiene marcas en sus dos fronteras, se reporta como distribución con su `n`, se deduplica antes de medir y se declara explícitamente qué tramo no tiene marca propia y cuál es la incertidumbre de su estimación.
### Rúbrica
- Pone una marca de tiempo en cada frontera y define cada tramo como una resta.
- Reporta percentiles con `n`, no sólo promedios.
- Trata los duplicados de la semántica de al menos una vez y el desfase de relojes.
- Declara al menos un tramo no medido, con la razón y cómo lo acota.
