## Antes de leer: dos bajas de guardia
type: prediccion
id: prediccion-sesgo-escritura
rol: prediccion
tiempo: 2

Ana y Beto están de guardia y la regla exige al menos uno. Cada uno corre, al mismo tiempo, una transacción que cuenta a los **otros** médicos activos y, si hay al menos uno, se da de baja a sí mismo. La base usa aislamiento por instantánea. ¿Qué pasa?

### Opciones
- [x] Las dos transacciones confirman y no queda nadie de guardia: cada una vio una instantánea donde el otro seguía activo y escribió una fila distinta, así que no hubo conflicto de escritura.
- Una de las dos falla con un conflicto de escritura, porque las dos modificaron la tabla `guardia`.
- La segunda transacción espera a que la primera confirme y luego ve que ya no queda nadie, así que no se da de baja.
- Las dos fallan, porque el aislamiento por instantánea impide las lecturas concurrentes.
### Justificación
Es el sesgo de escritura. Con instantáneas, cada transacción lee los datos como estaban al empezar, y el conflicto que se detecta es el de dos escrituras a la **misma** fila. Ana escribe su fila y Beto la suya: no chocan, las dos confirman y la regla se rompe. No hay espera, porque las lecturas no bloquean. Para evitarlo hace falta el nivel serializable con reintento, materializar el conflicto o una restricción en la base.

## ¿Es serializable por conflictos?
type: code
id: codigo-serializable
tiempo: 18

Implementa la prueba de serializabilidad por conflictos con el grafo de dependencias.

### Especificación
`esSerializable(historia)`:
- `historia` es una lista de operaciones `[transaccion, operacion, dato]` en el orden en que ocurrieron; `operacion` es `"R"` (lectura) o `"W"` (escritura).
- Dos operaciones están en **conflicto** si son de transacciones distintas, tocan el mismo dato y al menos una es escritura.
- El grafo de dependencias tiene un nodo por transacción y una arista de Ti a Tj por cada par en conflicto en el que la operación de Ti ocurre antes que la de Tj.
- Devuelve `true` si el grafo no tiene ciclos y `false` si los tiene.
- Una historia vacía es serializable.

### Solución
```javascript
function esSerializable(historia) {
  const ady = new Map();
  for (const [t] of historia) if (!ady.has(t)) ady.set(t, new Set());
  for (let i = 0; i < historia.length; i++) {
    for (let j = i + 1; j < historia.length; j++) {
      const [ti, oi, xi] = historia[i];
      const [tj, oj, xj] = historia[j];
      if (ti !== tj && xi === xj && (oi === "W" || oj === "W")) ady.get(ti).add(tj);
    }
  }
  const estado = new Map();
  const hayCiclo = (n) => {
    estado.set(n, "visitando");
    for (const m of ady.get(n)) {
      if (estado.get(m) === "visitando") return true;
      if (!estado.has(m) && hayCiclo(m)) return true;
    }
    estado.set(n, "listo");
    return false;
  };
  for (const n of ady.keys()) if (!estado.has(n) && hayCiclo(n)) return false;
  return true;
}
```
```python
def es_serializable(historia):
    ady = {}
    for op in historia:
        ady.setdefault(op[0], set())
    for i in range(len(historia)):
        for j in range(i + 1, len(historia)):
            ti, oi, xi = historia[i]
            tj, oj, xj = historia[j]
            if ti != tj and xi == xj and (oi == "W" or oj == "W"):
                ady[ti].add(tj)
    estado = {}

    def hay_ciclo(n):
        estado[n] = "visitando"
        for m in ady[n]:
            if estado.get(m) == "visitando":
                return True
            if m not in estado and hay_ciclo(m):
                return True
        estado[n] = "listo"
        return False

    for n in list(ady.keys()):
        if n not in estado and hay_ciclo(n):
            return False
    return True
```

### Pistas
- Dos lecturas del mismo dato no están en conflicto; una lectura y una escritura, o dos escrituras, sí.
- La dirección de la arista la da el orden en la historia: de la transacción que operó primero a la que operó después.
- Para los ciclos basta un recorrido en profundidad que marque los nodos «visitando»: volver a uno de ellos es un ciclo.

## El detector de carreras limpio
type: multiple_choice
id: detector-limpio
tiempo: 3

El servicio de guardias pasa su suite con el detector de carreras de datos activado y sin ningún reporte. Un compañero concluye que la baja de guardia es correcta bajo concurrencia. ¿Qué le respondes?

### Opciones
- [x] Que el detector sólo encuentra accesos sin sincronizar a la misma memoria; el sesgo de escritura ocurre con transacciones bien sincronizadas dentro de la base, así que hace falta un historial adversarial contra el nivel de aislamiento declarado.
- Que tiene razón: si no hay carreras de datos, no puede haber anomalías transaccionales.
- Que el detector falló, porque toda anomalía transaccional es una carrera de datos en el motor de la base.
- Que basta con correr la suite más veces para que el detector encuentre el problema.
### Justificación
Una carrera de datos y una anomalía transaccional viven en niveles distintos. El motor de la base sincroniza correctamente sus accesos a memoria y entrega lo que promete su nivel de aislamiento; la regla de negocio se rompe porque ninguna transacción protegió las dos filas juntas. El detector no tiene nada que reportar y repetir la suite no cambia eso. La evidencia correcta es una historia elegida para provocar la anomalía, con el resultado esperado escrito antes de correrla.

## Materializar el conflicto
type: multiple_choice
id: materializar-conflicto
tiempo: 3

La base de la guardia usa aislamiento por instantánea y no puedes subirla a serializable este mes. ¿Qué cambio en la transacción de baja evita que Ana y Beto se den de baja a la vez?

### Opciones
- [x] Que ambas transacciones escriban la misma fila antes de contar (por ejemplo, un contador en la fila del turno): con instantáneas, la segunda en escribirla falla con un error de serialización y la aplicación reintenta la transacción completa, cuyo conteo ya ve la baja confirmada.
- Bajar el nivel a *read committed*, porque así cada transacción ve los cambios confirmados de la otra.
- Agregar un índice sobre la columna `activo`, para que la cuenta sea más rápida y la ventana más corta.
- Reintentar la transacción si tarda más de un segundo.
### Justificación
El sesgo de escritura ocurre porque las dos transacciones escriben filas distintas y ninguna toca lo que la otra escribe. Materializar el conflicto es hacer que las dos escriban un mismo dato, de modo que el motor tenga que ordenarlas; con instantáneas, sólo bloquear la fila sin escribirla no basta, porque la segunda seguiría contando sobre su instantánea vieja. Bajar a *read committed* sin más no da garantía: las dos lecturas pueden ocurrir antes de cualquier escritura. Un índice acorta la ventana pero no la cierra. Reintentar por tiempo no detecta nada, porque las dos transacciones confirman sin error.

## El paper de Spanner con el protocolo de cinco preguntas
type: production
id: produccion-paper-spanner
tiempo: 20

Lee Spanner y responde el protocolo de cinco preguntas del programa: problema, supuesto esencial, mecanismo, fallo que evita y costo que introduce. Como pide el trabajo propio de la sección 08, explica qué garantiza cada mecanismo y qué **no** puede suponerse en una aplicación ordinaria.

### Modelo
*Problema:* ofrecer transacciones con una garantía fuerte de orden sobre datos replicados y repartidos entre centros de datos de distintas regiones.
*Supuesto esencial:* existe un reloj con incertidumbre acotada y conocida (relojes atómicos y GPS en cada centro de datos), y cada partición de datos se replica con un protocolo de consenso.
*Mecanismo:* las particiones se replican con grupos de consenso; las transacciones de escritura usan locks y confirmación en dos fases entre grupos; cada transacción recibe una marca de tiempo del reloj con incertidumbre, y el commit espera a que esa incertidumbre pase antes de hacerse visible, de modo que el orden de las marcas respeta el orden real; las lecturas de sólo lectura pueden servirse con una instantánea a una marca dada sin locks.
*Fallo que evita:* que una transacción que empezó después de que otra confirmara vea un estado anterior a ella, aun entre regiones lejanas (consistencia externa), y la pérdida de datos por la caída de una réplica.
*Costo:* depende de una infraestructura de relojes especial; cada commit paga la espera de la incertidumbre; las transacciones entre regiones pagan viajes de red largos y la confirmación en dos fases.
*Lo que no se supone en una aplicación ordinaria:* sin un reloj con incertidumbre acotada y medida, ordenar transacciones por la hora del servidor no da esa garantía; los relojes comunes pueden desviarse sin aviso.

### Regla
Un paper se lee con cinco preguntas (problema, supuesto esencial, mecanismo, fallo que evita y costo que introduce), y se explica qué garantiza cada mecanismo y qué depende de supuestos que una aplicación ordinaria no tiene.

### Rúbrica
- Responde las cinco preguntas por separado y con palabras propias.
- El supuesto esencial nombra el reloj con incertidumbre acotada.
- El mecanismo conecta la marca de tiempo, la espera del commit y el consenso por partición.
- El costo incluye la espera de commit y la dependencia de infraestructura de relojes.
- Explica por qué ordenar por la hora de un servidor común no da la misma garantía.
