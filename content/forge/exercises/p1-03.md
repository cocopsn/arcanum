### Solución
```javascript
function cobro_neto(cobros) {
  const neto = new Map();
  const sin = [];
  for (const c of cobros) {
    if (c.cita_ref === null || c.cita_ref === undefined) {
      sin.push(c.folio);
      continue;
    }
    neto.set(c.cita_ref, (neto.get(c.cita_ref) || 0) + c.monto);
  }
  const llaves = [...neto.keys()].sort();
  return { neto: llaves.map((k) => ({ cita_ref: k, monto: neto.get(k) })), sin_referencia: sin.sort() };
}
```
```python
def cobro_neto(cobros):
    neto = {}
    sin = []
    for c in cobros:
        if c.get("cita_ref") is None:
            sin.append(c["folio"])
            continue
        neto[c["cita_ref"]] = neto.get(c["cita_ref"], 0) + c["monto"]
    return {
        "neto": [{"cita_ref": k, "monto": neto[k]} for k in sorted(neto)],
        "sin_referencia": sorted(sin),
    }
```

- Acumula por llave y ordena las llaves al final.
- Una cita con neto cero sigue siendo una fila del resultado.

## ¿Dónde vive la hora?
type: multiple_choice
id: hora-parametro
tiempo: 2

La regla «cobros de los últimos 30 días» necesita saber qué día es hoy. ¿Dónde debe obtenerse la fecha de corte para que la regla se pueda probar?

### Opciones
- [x] El adaptador la obtiene (o la recibe de la configuración del build) y se la pasa al núcleo como parámetro; la prueba llama al núcleo con una fecha fija.
- Dentro del núcleo, con `datetime.now()`, para que la regla siempre use la hora real.
- En la prueba, cambiando el reloj del sistema antes de llamar a la transformación.
- En ningún lado: las reglas de ventana de tiempo no se pueden probar con fixtures.
### Justificación
Un `datetime.now()` dentro del núcleo hace que la misma entrada dé salidas distintas según cuándo corre, y obliga a simular el reloj para probar. Con la fecha como parámetro, el núcleo es una función pura: el adaptador decide de dónde sale «hoy» y la prueba fija cualquier fecha, incluidos los bordes.

### Opciones
- [x] Que la regla produce los resultados esperados sobre los casos del fixture; no que el dataset real tenga ese esquema, ni que tengas permiso de leerlo, ni que la entrada cumpla los requisitos del modo incremental.
- Que el pipeline completo funciona en producción, porque las pruebas corrieron en la plataforma.

Además, la documentación aclara que estas pruebas aplican a pipelines por lotes, no a streaming.

## Fixture adversarial para una regla nueva
type: production
id: fixture-adversarial
tiempo: 10

La clínica agrega la regla «paciente frecuente»: un paciente es frecuente si tiene **3 o más citas atendidas en los 90 días anteriores a la fecha de corte**, contando una vez cada `cita_id`. Escribe la lista de casos de tu fixture (entrada resumida y esperado escrito a mano) que una implementación tiene que pasar antes de que confíes en ella. Mínimo seis casos.

### Modelo
1. Tres citas atendidas dentro de la ventana → frecuente.
2. Dos atendidas y una `no_asistio` → no frecuente (sólo cuentan atendidas).
3. Tres filas, pero dos son la misma `cita_id` repetida por el sync → no frecuente.
4. Tres atendidas, una exactamente en el día 90 antes del corte → define y prueba el borde (incluido o excluido, según la regla escrita).
5. Tres atendidas, una el día 91 → no frecuente.
6. Paciente sin citas → no aparece o aparece como no frecuente, según el contrato de salida, pero nunca como error.
7. Una cita a las 23:30 hora local del día del borde que en UTC cae en otro día → el esperado dice qué zona manda.
### Regla
Un fixture de reglas de datos se escribe desde el contrato y la cardinalidad, no desde la salida del código: cubre repeticiones de la llave, estados que no cuentan, bordes de ventana a ambos lados, el conjunto vacío y la zona horaria. Cada esperado se escribe antes de correr la implementación.
### Rúbrica
- Al menos seis casos con su esperado explícito.
- Incluye la repetición de `cita_id` y un estado que no cuenta.
- Prueba los dos lados del borde de 90 días y declara si el borde se incluye.
- Incluye el caso vacío y un caso de zona horaria.
- Ningún esperado depende de correr el código primero.
