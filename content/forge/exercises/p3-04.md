## Un permiso que la aplicación no declaró
type: prediccion
id: fuera-de-alcance
rol: prediccion
tiempo: 2

La aplicación «Agenda de reasignaciones» declara en su alcance los objetos Cita y Medico y la acción ReasignarCita. Un médico, que en la plataforma sí puede ver el tipo de objeto Paciente y sus datos, usa la aplicación y su código intenta cargar un Paciente. Predice el resultado.

### Opciones
- [x] Se deniega: el token de la aplicación está limitado a las entidades declaradas en su alcance, además de los permisos del usuario; Paciente no está en el alcance.
- Se permite, porque el médico tiene permiso sobre Paciente.
- Se permite sólo en modo lectura.
- Se permite, pero sin propiedades.
### Justificación
La documentación del Ontology SDK describe un token limitado a las entidades de la Ontology que la aplicación quiere usar, además de los permisos propios del usuario. Los permisos efectivos son la intersección de los dos: el permiso del médico no amplía el alcance de la aplicación.

## Permisos efectivos de una aplicación

id: permisos-efectivos

Escribe `evaluar_operaciones(alcance, usuario, operaciones)`. `alcance` es la lista de entidades que la aplicación declara (objetos y acciones). `usuario.permisos` es un objeto `entidad → lista de operaciones` (`ver`, `ejecutar`, …). ### Solución
```javascript
function evaluar_operaciones(alcance, usuario, operaciones) {
  const enAlcance = new Set(alcance);
  const permisos = (usuario && usuario.permisos) || {};
  return operaciones.map((op) => {
    if (!enAlcance.has(op.entidad)) return { id: op.id, permitido: false, razon: "fuera-de-alcance" };
    if (!(permisos[op.entidad] || []).includes(op.tipo)) return { id: op.id, permitido: false, razon: "sin-permiso" };
    return { id: op.id, permitido: true, razon: "ok" };
  });
}
```
```python
def evaluar_operaciones(alcance, usuario, operaciones):
    en_alcance = set(alcance)
    permisos = (usuario or {}).get("permisos") or {}
    out = []
    for op in operaciones:
        if op["entidad"] not in en_alcance:
            out.append({"id": op["id"], "permitido": False, "razon": "fuera-de-alcance"})
        elif op["tipo"] not in (permisos.get(op["entidad"]) or []):
            out.append({"id": op["id"], "permitido": False, "razon": "sin-permiso"})
        else:
            out.append({"id": op["id"], "permitido": True, "razon": "ok"})
    return out
```

## Lo que el SDK protege al leer
type: multiple_choice
id: proteccion-al-leer
tiempo: 2

Una política de filas oculta a la recepcionista las citas de otras sedes. Tu aplicación carga las citas con el token de la coordinadora y las guarda en un caché compartido que luego le sirve a la recepcionista. ¿Qué pasa?

### Opciones
- [x] La recepcionista ve citas de otras sedes: los controles de filas filtran lo que se lee por el SDK, pero no se extienden a la respuesta ni a lo que tu aplicación hace después con ella.
- La plataforma vuelve a filtrar el caché con los permisos de la recepcionista.
- El caché queda vacío para la recepcionista porque el token no es suyo.
- La aplicación falla al compilar porque el tipado detecta el caché compartido.
### Justificación
La documentación del Ontology SDK advierte que el cumplimiento de los controles de filas y columnas es al leer: nadie lee por el SDK lo que no está autorizado a ver, pero lo que la aplicación hace con la respuesta queda fuera de esos controles. Un caché compartido entre usuarios rompe esa protección.

## El tipado y el cambio de una propiedad
type: multiple_choice
id: tipado-cambio
tiempo: 2

Alguien renombra en la Ontology la propiedad `inicio` de Cita a `hora_inicio`. Tu aplicación usa el cliente TypeScript generado con el OSDK. Cuando regeneras el SDK, ¿dónde aparece el problema?

### Opciones
- [x] Al compilar: los tipos se generan desde la Ontology, así que el código que usaba `inicio` deja de compilar y se corrige antes de desplegar.
- En producción, como un campo vacío en la pantalla.
- En ningún lado, porque el SDK traduce los nombres viejos automáticamente.
- En la Ontology, que impide renombrar propiedades usadas por aplicaciones.
### Justificación
El OSDK genera tipos y funciones a partir del subconjunto de la Ontology relevante para la aplicación; con tipado fuerte, un nombre que ya no existe es un error de compilación. Es la ventaja de llevar el contrato al cliente: el error aparece donde es barato.

## Identidad, autenticación y permisos efectivos
type: production
id: identidad-permisos
tiempo: 12

Explica, para la aplicación sintética «Agenda de reasignaciones», quién es el usuario para la plataforma, cómo se autentica la aplicación, qué cuenta decide los permisos efectivos de cada operación y por qué la prueba con tu propio usuario no demuestra que la autorización funcione. Termina con tres reglas para el código de la aplicación.

### Modelo
- **Identidad:** la persona que usa la aplicación (coordinadora, recepcionista, médico), no quien la construyó ni una cuenta de servicio.
- **Autenticación:** la aplicación está registrada en Developer Console; el usuario inicia sesión y la aplicación recibe un token que actúa en su nombre.
- **Permisos efectivos:** intersección del alcance declarado de la aplicación (Cita, Medico, ReasignarCita) con los permisos del usuario sobre esos objetos y datos (incluidos los filtros de filas y columnas), y además los criterios de envío de cada acción.
- **Por qué tu usuario no prueba nada:** tiene más permisos que los usuarios reales; un éxito con él no demuestra que una recepcionista vea sólo lo suyo ni que un médico no pueda reasignar. Hay que probar con usuarios de cada rol.
- **Reglas de código:** no usar un token de servicio amplio para acciones del usuario; no compartir cachés de respuestas entre usuarios; declarar en el alcance sólo las entidades que la aplicación usa.
### Regla
En una aplicación con el OSDK, los permisos efectivos son la intersección del alcance de la aplicación con los permisos del usuario, más los criterios de cada acción; la protección es al leer, así que el código no debe reutilizar respuestas entre usuarios ni sustituir el token del usuario.
### Rúbrica
- Distingue identidad, autenticación y permisos efectivos.
- Escribe la intersección de alcance y permisos del usuario, más los criterios de envío.
- Explica por qué una prueba con un usuario con muchos permisos no es evidencia.
- Da tres reglas de código coherentes con la protección al leer.
