# S1-06 · API y evolución de contratos

Banco de la celda: predecir qué hace la paginación por desplazamiento bajo inserciones, implementar paginación por cursor con desempate, clasificar cambios compatibles, diseñar errores útiles, planear un cambio en paralelo y transferirlo a un socio que no puede actualizar.

## Exportar mientras llegan órdenes
type: prediccion
id: s1-06-pred-offset
rol: prediccion
escala: 50 70 90

Un socio exporta todas las órdenes con `?offset=0&limit=50`, luego `offset=50`, y así. Las órdenes se devuelven de la más nueva a la más vieja. Mientras exporta, entran 3 órdenes nuevas. Predice qué ve el socio.

### Opciones
- [x] Filas repetidas: las 3 órdenes nuevas empujan todo hacia atrás y las últimas 3 filas de una página reaparecen al principio de la siguiente.
- Filas saltadas: las 3 órdenes nuevas se intercalan y desplazan las filas hacia adelante.
- Nada raro: el desplazamiento se calcula sobre una copia fija de la tabla.
- Un error de la API, porque el total cambió durante la exportación.
### Justificación
Con orden de nuevo a viejo, cada inserción entra al principio. La posición 50 de la segunda petición es ahora la que antes era la 47, así que las filas 47 a 49 se entregan dos veces. (Con borrados, el efecto es el contrario: filas saltadas.) El desplazamiento se calcula sobre la tabla en el momento de cada petición, no sobre una copia, y la API no detecta que el total cambió: el error es silencioso.

## Paginación por cursor con desempate
type: code
id: s1-06-code-cursor

Implementa `paginar(filas, tamano, cursor)`. `filas` es una lista de `{ id, emitida }` (fecha ISO) en cualquier orden. El orden total es `emitida` ascendente y, a igual fecha, `id` ascendente. `cursor` es `null` (primera página) o el par `[emitida, id]` de la última fila entregada. Devuelve `{ ids, siguiente }`: los `id` de la página (a lo sumo `tamano`) y el cursor de su última fila si quedan filas después, o `null` si no queda ninguna.

### Firma
```javascript
function paginar(filas, tamano, cursor) {
  // devuelve { ids: string[], siguiente: [emitida, id] | null }
}
```
### Casos
```json
[

  { "input": [[{ "id": "O-5", "emitida": "2026-11-03" }, { "id": "O-4", "emitida": "2026-11-03" }, { "id": "O-6", "emitida": "2026-11-03" }], 2, ["2026-11-03", "O-5"]], "expected": { "ids": ["O-6"], "siguiente": null } }
]
```
### Solución
```javascript
function paginar(filas, tamano, cursor) {
  const cmp = (a, b) =>
    a.emitida < b.emitida ? -1 : a.emitida > b.emitida ? 1 : a.id < b.id ? -1 : a.id > b.id ? 1 : 0;
  const orden = [...filas].sort(cmp);
  const despues = cursor === null
    ? orden
    : orden.filter((f) => f.emitida > cursor[0] || (f.emitida === cursor[0] && f.id > cursor[1]));
  const pagina = despues.slice(0, tamano);
  const ultima = pagina[pagina.length - 1];
  const siguiente = despues.length > tamano ? [ultima.emitida, ultima.id] : null;
  return { ids: pagina.map((f) => f.id), siguiente };
}
```
### Pistas
- El cursor no es una posición: es «todo lo que va después de esta llave» en el orden total.
- Sin el desempate por `id`, dos órdenes de la misma fecha pueden repetirse o perderse entre páginas.

## ¿Compatible o no?
type: multiple_choice
id: s1-06-choice-compatible
rol: recuperacion

Sin volver al libro: ¿cuál de estos cambios a la respuesta de `GET /v1/ordenes` es compatible con todos los consumidores existentes, sin que cambien su código?

### Opciones
- [x] Agregar el campo opcional `sede` a cada orden, sin cambiar los demás.
- Renombrar `paciente` a `paciente_id`.
- Cambiar el orden por omisión de «más vieja primero» a «más nueva primero».
- Cambiar `emitida` de fecha ISO a número de milisegundos.
### Justificación
Un consumidor que ignora los campos que no conoce sigue funcionando si se agrega uno opcional. Renombrar es quitar un campo y agregar otro: quien leía `paciente` deja de encontrarlo. Cambiar el orden por omisión rompe a quien pagina o toma «la primera» como la más antigua. Cambiar el tipo rompe el parseo y cualquier comparación. Los tres últimos se hacen en paralelo (expandir, migrar, contraer) o en otra versión.

## Un enumerado que crece
type: prediccion
id: s1-06-pred-enum
rol: prediccion

La API agrega el valor `en_revision` al campo `estado` de las órdenes. El cliente de un socio hace `switch (orden.estado)` con un caso por cada valor conocido y lanza un error en el `default`. Predice qué pasa con la primera orden en revisión.

### Opciones
- [x] El cliente del socio lanza el error del `default` y falla, aunque el JSON sea válido: para él, el cambio fue incompatible.
- Nada, porque agregar un valor siempre es compatible.
- La API rechaza la orden porque el cliente no conoce el valor.
- El cliente la trata como `agendada`, el valor más parecido.
### Justificación
La compatibilidad depende de lo que el consumidor hace con el valor. Un `switch` exhaustivo que falla ante lo desconocido convierte un valor nuevo en una caída. Por eso el contrato debe decir si los enumerados pueden crecer y pedir a los clientes un caso «desconocido»; y el valor nuevo se publica con aviso y fecha. La API no sabe qué cliente lee, y ningún cliente adivina «el valor más parecido».

## Errores que se pueden usar
type: multiple_choice
id: s1-06-choice-errores

Un cliente recibe un error al crear una orden con `POST /v1/ordenes`. ¿Qué diseño de error le permite decidir bien sin leer el texto del mensaje?

### Opciones
- [x] Un código estable (`PACIENTE_NO_ENCONTRADO`), una categoría cerrada (`argumento`, `permiso`, `no_encontrado`, `conflicto`, `transitorio`) y un indicador de si reintentar; para `transitorio` en una escritura, la exigencia de una clave de idempotencia.
- Sólo el código HTTP, porque 4xx y 5xx ya dicen todo.
- Un mensaje detallado en español, para que la persona entienda qué pasó.
- Siempre 200 con `{ "ok": false }`, para que ningún cliente se caiga.
### Justificación
El cliente necesita qué pasó, de quién es la culpa y si conviene reintentar. El código HTTP no distingue «paciente no encontrado» de «orden no encontrada» ni dice si un 500 ocurrió antes o después de escribir. El mensaje es para personas y puede cambiar. Responder 200 con un indicador esconde los errores a la infraestructura (monitoreo, reintentos). Un error transitorio en una escritura no dice si la orden se creó: sin clave de idempotencia, reintentar puede duplicarla.

## Planear un cambio en paralelo
type: production
id: s1-06-prod-paralelo

Necesitas cambiar `emitida` de «fecha local sin zona» (`2026-11-02`) a «instante UTC» (`2026-11-02T15:30:00Z`), porque una sede nueva está en otra zona horaria. Escribe el plan para desplegarlo sin romper consumidores anteriores, con las condiciones que te dejan avanzar de un paso al siguiente.

### Modelo
Expandir: la versión 1.5 agrega `emitida_utc` junto a `emitida`, que se conserva sin cambiar su significado; la documentación y una cabecera de aviso marcan `emitida` como obsoleta con fecha. Migrar: se mide por cliente cuántas respuestas siguen leyendo `emitida` (o, si no se puede medir lectura, quién la usa en filtros y cursores) y se avisa a cada consumidor con su cuenta. Los filtros nuevos aceptan instantes; los viejos siguen aceptando fechas locales, interpretadas en la zona de la sede original. Contraer: cuando el uso de `emitida` llega a cero durante 4 semanas, o vence el aviso con los consumidores restantes notificados, se elimina en 2.0. Condición de retroceso: si la tasa de errores de cualquier consumidor sube tras 1.5, se retira la cabecera nueva y se revisa sin quitar nada.
### Regla
Un cambio incompatible se despliega en paralelo: lo nuevo convive con lo viejo, el avance de un paso al siguiente depende de una métrica de uso, y lo viejo conserva su significado mientras exista.
### Rúbrica
- Mantiene el campo viejo con su significado original durante la transición.
- Define una métrica concreta para decidir cuándo contraer.
- Incluye aviso a consumidores con fecha.
- Prevé el retroceso si algo se rompe.
