## Auditar la evidencia de los pasos
type: code
id: auditar-pasos
tiempo: 15

Escribe `auditar_pasos(pasos)`. `pasos` es la lista ordenada de pasos de un pipeline, cada uno con `id`, `entra`, `sale` (filas) y `declara`, que vale `conserva`, `reduce`, `filtra` o `expande`. Devuelve la lista de hallazgos `{ id, motivo }`, en el orden de los pasos, con estas reglas:

- `discontinuidad`: para todo paso que no es el primero, si `entra` es distinto del `sale` del paso anterior.
- `crece`: si el paso declara `conserva`, `reduce` o `filtra` y `sale > entra`.
- `pierde`: si el paso declara `conserva` o `expande` y `sale < entra`.

Si un paso tiene `discontinuidad` y otro hallazgo, la `discontinuidad` va primero.

### Solución
```javascript
function auditar_pasos(pasos) {
  const out = [];
  pasos.forEach((p, i) => {
    if (i > 0 && p.entra !== pasos[i - 1].sale) out.push({ id: p.id, motivo: "discontinuidad" });
    if (["conserva", "reduce", "filtra"].includes(p.declara) && p.sale > p.entra) out.push({ id: p.id, motivo: "crece" });
    if (["conserva", "expande"].includes(p.declara) && p.sale < p.entra) out.push({ id: p.id, motivo: "pierde" });
  });
  return out;
}
```
```python
def auditar_pasos(pasos):
    out = []
    for i, p in enumerate(pasos):
        if i > 0 and p["entra"] != pasos[i - 1]["sale"]:
            out.append({"id": p["id"], "motivo": "discontinuidad"})
        if p["declara"] in ("conserva", "reduce", "filtra") and p["sale"] > p["entra"]:
            out.append({"id": p["id"], "motivo": "crece"})
        if p["declara"] in ("conserva", "expande") and p["sale"] < p["entra"]:
            out.append({"id": p["id"], "motivo": "pierde"})
    return out
```
### Pistas
- Revisa primero la continuidad con el paso anterior y después la declaración del paso.
- «Reduce» y «filtra» pueden perder filas, pero nunca ganarlas; «expande» puede ganarlas, pero nunca perderlas.

### Corrección
```sql
-- paso: limpia
CREATE VIEW movs_limpios AS
SELECT DISTINCT mov_id, insumo_id, fecha, cantidad FROM movimientos;
-- paso: valora
CREATE VIEW mov_valorados AS
SELECT m.mov_id, m.insumo_id, m.fecha, m.cantidad, p.precio, m.cantidad * p.precio AS valor
FROM movs_limpios m JOIN precios p ON p.insumo_id = m.insumo_id
AND p.vigente_desde = (SELECT MAX(p2.vigente_desde) FROM precios p2 WHERE p2.insumo_id = m.insumo_id AND p2.vigente_desde <= m.fecha);
-- paso: resumen
CREATE VIEW resumen AS
SELECT insumo_id, SUM(cantidad) AS unidades, SUM(valor) AS valor
FROM mov_valorados GROUP BY insumo_id;
```

Tu equipo necesita (a) desarrollar durante dos semanas un cambio de esquema del dataset y del tipo de objeto sin afectar a los usuarios, y (b) llevar después ese cambio de desarrollo a prueba y a producción. ¿Qué herramienta corresponde a cada necesidad?

### Opciones
- [x] (a) una rama de Global Branching; (b) la gestión de versiones entre entornos (release management). Son complementarias, no alternativas.
- Las dos con Global Branching, porque una rama fusionada ya es una versión de producción.

### Justificación
La página de Global Branching separa los dos problemas: las ramas sirven para desarrollar y probar en aislamiento y fusionar a `main`; la gestión de versiones administra varias versiones de recursos en entornos distintos. La misma página propone usarlas juntas: desarrollar en una rama, fusionar en el entorno de desarrollo y luego desplegar a prueba y producción.

### Opciones

- Un README que describe el objetivo del producto.

Los commits ayudan después, para encontrar el cambio que lo introdujo.

## Manual de recuperación ensayable
type: production
id: manual-recuperacion
tiempo: 15

Escribe el manual de recuperación del producto «valor del inventario movido por insumo» para una persona de guardia que nunca vio el pipeline. Debe cubrir al menos dos síntomas («el valor se duplicó» y «el valor no cambió desde ayer»), y para cada uno: qué evidencia mirar primero, cómo localizar el paso, cómo contener, cómo volver atrás y cómo verificar. Termina con cómo ensayarías el manual.

### Modelo
- **Síntoma A: el valor se duplicó.** Mirar la unicidad de `mov_id` en la salida de `valora` y la tabla de conteos por paso del build de hoy contra el de ayer; el primer paso que declara «conserva» y crece es el sospechoso (típico: join con todas las versiones de precio). Contener: avisar a almacén por su canal que el valor de hoy no es confiable y marcar la salida. Volver atrás: revertir el cambio del paso o reconstruir desde la última versión buena. Verificar: expectativas de unicidad y conteo, y la comparación incremental contra completo.
- **Síntoma B: el valor no cambió desde ayer.** Mirar la frescura del contenido de `movimientos` (máximo de `fecha` contra el corte) y la cadena de conteos: una discontinuidad indica que un paso lee otra entrada (por ejemplo, un respaldo). Si la fuente no publicó, aplicar su contrato: dueño y canal de almacén; si el pipeline lee mal, revertir y reconstruir.
- **Dejar evidencia:** qué pasó, cómo se detectó, qué check faltó y qué falla sembrada se agrega.
- **Ensayo:** sembrar cada falla en una rama, pedir a alguien que no construyó el pipeline que siga el manual con un reloj, y corregir el manual donde se atore.
### Regla
Un manual de recuperación sirve si alguien que no construyó el producto puede seguirlo desde el síntoma hasta la verificación usando sólo la evidencia publicada, y si se ensayó con una falla sembrada. Contener (avisar y marcar) va antes de corregir, y nada se declara recuperado sin correr los checks.
### Rúbrica
- Cubre los dos síntomas con evidencia concreta para cada uno.
- Localiza el paso comparando declaración contra conteos, sin exigir leer código.
- Incluye contener, volver atrás y verificar, en ese orden.
- Usa el contrato de la fuente cuando el problema es de la fuente.
- Describe cómo se ensaya con una falla sembrada y con alguien que no construyó el pipeline.
