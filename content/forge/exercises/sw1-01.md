## Antes de leer: dos implementaciones, veinte pruebas
type: prediccion

rol: prediccion

Dos implementaciones de `reservar(agenda, solicitud)` pasan las mismas veinte pruebas de ejemplo, escritas por quien programó la primera. Sin leer más, ¿qué puedes afirmar con seguridad?

### Opciones
- [x] Sólo que coinciden en esos veinte casos; si cumplen el mismo contrato depende de que las pruebas cubran las particiones y los bordes que el contrato define.
- Que son intercambiables para cualquier cliente, porque veinte pruebas verdes son evidencia suficiente de equivalencia.
- Que el contrato está bien escrito, porque si estuviera mal alguna de las dos fallaría.
- Que la más rápida de las dos es la correcta y la otra debe retirarse.
### Justificación
Las pruebas de ejemplo muestran coincidencia en los puntos probados, no equivalencia. Si quien las escribió pensó desde su implementación y no desde el contrato, es fácil que falten particiones enteras: el bloque nuevo que contiene a uno ocupado, los bloques que sólo se tocan, el minuto 1440. El libro lo muestra con una implementación que pregunta por los extremos y pasa casi todo. Que ambas pasen tampoco dice nada sobre la calidad del contrato: dos implementaciones pueden compartir el mismo hueco. La velocidad es irrelevante para la corrección.

## ¿Cuál especificación es más fuerte?
type: multiple_choice
id: fuerza-de-especificacion
tiempo: 3

Especificación A de `reservar`: *pre* — la agenda llega ordenada por inicio y sin traslapes; *post* — devuelve una reserva o el error `traslape`. Especificación B: *pre* — la agenda llega sin traslapes, en cualquier orden; *post* — devuelve la reserva y la posición donde quedó en la agenda ordenada, o el error `traslape`. ¿Qué relación hay entre A y B?

### Opciones
- [x] B es más fuerte que A: su precondición es más débil (acepta agendas desordenadas) y su postcondición más fuerte (promete además la posición), así que toda implementación de B sirve a cualquier cliente de A.
- A es más fuerte que B, porque exige más al cliente y eso hace la operación más segura.
- Son incomparables, porque B devuelve un dato que A no devuelve y cambia la firma.
- Son equivalentes, porque las dos detectan los mismos traslapes.
### Justificación
La regla es: B es más fuerte que A si su precondición es igual o más débil y su postcondición igual o más fuerte. B acepta todo lo que A acepta y más; en esas entradas promete todo lo que A promete y además la posición. Un cliente escrito contra A ordena antes de llamar (B no lo necesita, pero tampoco le estorba) y no usa la posición (puede ignorarla). Exigir más al cliente hace la especificación más débil, no más segura. «Incomparables» confunde la firma con el contrato: un dato extra en la respuesta es una promesa adicional. Detectar los mismos traslapes no basta para ser equivalentes: difieren en lo que aceptan y en lo que prometen.

## El bloque que no tiene ningún extremo dentro
type: contraejemplo
id: contraejemplo-traslape-extremos
tiempo: 8

`libre(ocupados, inicio, fin)` decide si el bloque semiabierto `[inicio, fin)` se puede reservar. Contrato: `ocupados` es una lista de hasta 50 bloques `[a, b]` que representan `[a, b)`, con enteros `0 ≤ a < b ≤ 1440`; `inicio` y `fin` son enteros con `0 ≤ inicio < fin ≤ 1440`. Devuelve `true` si y sólo si `[inicio, fin)` no comparte ningún minuto con ningún bloque ocupado. La versión casi correcta pasó todas las pruebas del equipo. Da los argumentos `[ocupados, inicio, fin]` de una entrada que respete el contrato y en la que la casi correcta responda distinto de la referencia.

### Firma
```javascript
function libre(ocupados, inicio, fin) {
  // ocupados: [[a, b], ...] con 0 <= a < b <= 1440; inicio, fin enteros con 0 <= inicio < fin <= 1440
}
```

### Precondición
```javascript
function pre(ocupados, inicio, fin) {
  const minuto = (v) => Number.isInteger(v) && v >= 0 && v <= 1440;
  if (!Array.isArray(ocupados) || ocupados.length > 50) return false;
  for (const bloque of ocupados) {
    if (!Array.isArray(bloque) || bloque.length !== 2) return false;
    if (!minuto(bloque[0]) || !minuto(bloque[1]) || bloque[0] >= bloque[1]) return false;
  }
  return minuto(inicio) && minuto(fin) && inicio < fin;
}
```

### Casi correcta
```javascript
function libre(ocupados, inicio, fin) {
  for (const [a, b] of ocupados) {
    const inicioDentro = inicio >= a && inicio < b;
    const finDentro = fin > a && fin <= b;
    if (inicioDentro || finDentro) return false;
  }
  return true;
}
```

### Referencia
```javascript
function libre(ocupados, inicio, fin) {
  for (const [a, b] of ocupados) {
    if (inicio < b && a < fin) return false;
  }
  return true;
}
```

### Solución
```javascript
function validarSolicitud(agenda, inicio, fin) {
  const minuto = (v) => Number.isInteger(v) && v >= 0 && v <= 1440;
  if (!minuto(inicio) || !minuto(fin) || inicio >= fin) return "horario-invalido";
  for (const [a, b] of agenda) {
    if (inicio < b && a < fin) return "traslape";
  }
  return "ok";
}
```

```python
    def minuto(v):
        return isinstance(v, int) and not isinstance(v, bool) and 0 <= v <= 1440
    if not minuto(inicio) or not minuto(fin) or inicio >= fin:
        return "horario-invalido"
    for a, b in agenda:
        if inicio < b and a < fin:
            return "traslape"
    return "ok"
```

### Pistas
- Escribe primero la rama de `horario-invalido`: es la precedencia que el contrato declara.
- La prueba de traslape de dos semiabiertos `[x, y)` y `[a, b)` es `x < b && a < y`; con ella, tocar no es traslapar y contener sí lo es.
- La agenda puede venir desordenada: no supongas que basta con mirar al vecino.

## Lo que pertenece al contrato
type: multiple_choice
id: contrato-o-detalle
tiempo: 3

Al revisar el contrato de `reservar`, el equipo discute cuatro decisiones. ¿Cuál debe quedar **dentro** de la especificación y no como detalle interno?

### Opciones
- [x] Qué error se devuelve cuando la solicitud tiene a la vez un horario inválido y un traslape, porque el cliente decide qué mensaje mostrar según ese error.
- Si la agenda se guarda como lista o como árbol balanceado.
- En qué orden se recorren internamente los bloques al buscar traslapes.
- Si la implementación usa búsqueda binaria cuando la agenda está ordenada.
### Justificación
Lo que el cliente puede observar y sobre lo que va a tomar decisiones pertenece al contrato. Cuando fallan dos condiciones, el error devuelto es observable: un formulario que muestra «elige otro horario» o «la sala está ocupada» depende de cuál llega. Por eso el contrato del libro fija que gana `horario-invalido`. La estructura de datos, el orden del recorrido y el uso de búsqueda binaria no cambian ninguna respuesta: dejarlos fuera es lo que permite cambiar la implementación sin avisar a nadie.

## Escribe el contrato de cancelar
type: production
id: produccion-contrato-cancelar
tiempo: 12

Escribe la especificación de `cancelar(agenda, reservaId)` para la misma clínica: precondición, postcondición en éxito, errores declarados con nombre estable y lo que queda fuera del contrato. Indica cuál condición tratas como precondición y cuál como error declarado, y por qué, según quién llama.

### Modelo
*Precondición:* `agenda` es la agenda válida de una sala y un día (bloques semiabiertos sin traslapes); `reservaId` es una cadena no vacía. Como `reservaId` llega de la interfaz, su formato se comprueba en la frontera: si no es una cadena no vacía, `Error("id-invalido")`.
*Postcondición en éxito:* devuelve la reserva cancelada; la agenda resultante tiene exactamente los mismos bloques salvo ese, y ningún otro bloque cambia.
*Errores declarados:* `Error("no-existe")` si ninguna reserva tiene ese id en la agenda (puede ocurrir sin culpa del cliente: otra persona la canceló antes); `Error("ya-iniciada")` si la reserva empezó y la política no permite cancelar en curso. En ambos casos la agenda no cambia.
*Fuera del contrato:* cómo se busca el id (lista, índice), si la eliminación es física o con marca, y el orden interno de los bloques.
*Decisión defendida:* «la reserva ya no existe» es error declarado y no violación de precondición, porque con dos operadores concurrentes el cliente no puede garantizarlo; tratarlo como precondición haría el comportamiento indefinido justo en el caso más común de carrera.

### Regla
Un contrato distingue lo que el cliente puede garantizar (precondición) de lo que puede fallar aunque el cliente hizo su parte (error declarado, con nombre estable). Lo que el cliente no puede controlar no debe ser precondición.

### Rúbrica
- Escribe precondición, postcondición y errores por separado, sin mezclarlos.
- Cada error declarado tiene un nombre estable y dice en qué estado queda la agenda.
- Justifica con el criterio de quién puede garantizar la condición, y trata «ya no existe» como error declarado.
- Nombra al menos dos decisiones que quedan fuera del contrato.
- La postcondición dice qué no cambia, no sólo qué cambia.
