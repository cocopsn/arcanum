# A1-05 · Heaps, scheduling y Top-K

Banco ligero de la ruta A1. La misión: construir una cola de prioridades para trabajos de mantenimiento, defender el heap
frente a ordenar todo y explicar desempates y starvation. La estructura completa del heap está en ITC C5.

## Antes de leer: el heap del Top-K
type: prediccion
id: a1-05-pred-topk
rol: prediccion

Quieres las 10 lecturas más altas de un flujo de 10 millones, guardando sólo un heap de 10 elementos. ¿Qué heap usas?

### Opciones
- Un heap de máximos de tamaño 10: la raíz es la lectura más alta
- [x] Un heap de mínimos de tamaño 10: la raíz es la más baja de las 10 que llevas
- Un heap de máximos con los 10 millones, y extraes 10 veces
- Da igual el tipo mientras el tamaño sea 10

### Justificación
Al llegar una lectura nueva hay que decidir si entra al Top-10, y eso se decide contra la **más débil** de las que llevas. Un
heap de mínimos la tiene en la raíz: si la nueva es mayor, reemplaza la raíz en O(log 10). Con un heap de máximos de tamaño
10 la más débil queda enterrada. Guardar los 10 millones funciona, pero gasta memoria O(n) y O(n log n) de trabajo.

## Cola de mantenimiento, desvanecida
type: desvanecido
id: a1-05-desv-cola
lang: javascript

Completa `ordenDeAtencion(trabajos)`: cada trabajo es `[id, prioridad]` en orden de llegada (menor número = más urgente).
Devuelve los ids en el orden en que se atienden, con un heap binario y desempate por llegada.

### Pasos
1. Define cuándo un trabajo va antes que otro: menor prioridad y, si empatan, menor llegada.
2. Al insertar, sube el elemento mientras vaya antes que su padre.
3. Al extraer, baja la nueva raíz cambiándola por el hijo que va antes, mientras alguno vaya antes que ella.
4. Extrae la raíz hasta vaciar el heap: mueve el último elemento a la raíz y bájalo.
5. El desempate por llegada hace el orden determinista y atiende por orden de llegada entre iguales, pero no evita la starvation entre prioridades distintas: para eso hace falta envejecimiento.

### Plantilla
```javascript
function ordenDeAtencion(trabajos) {
  const h = [];
  // <paso 1>
  const antes = (x, y) => x[1] < y[1] || (x[1] === y[1] && x[2] < y[2]);
  // </paso 1>
  const subir = (i) => {
    // <paso 2>
    while (i > 0) {
      const p = (i - 1) >> 1;
      if (!antes(h[i], h[p])) break;
      [h[i], h[p]] = [h[p], h[i]];
      i = p;
    }
    // </paso 2>
  };
  const bajar = (i) => {
    // <paso 3>
    while (true) {
      const l = 2 * i + 1;
      const r = l + 1;
      let m = i;
      if (l < h.length && antes(h[l], h[m])) m = l;
      if (r < h.length && antes(h[r], h[m])) m = r;
      if (m === i) break;
      [h[i], h[m]] = [h[m], h[i]];
      i = m;
    }
    // </paso 3>
  };
  trabajos.forEach(([id, prioridad], llegada) => {
    h.push([id, prioridad, llegada]);
    subir(h.length - 1);
  });
  const out = [];
  // <paso 4>
  while (h.length) {
    out.push(h[0][0]);
    const ultimo = h.pop();
    if (h.length) {
      h[0] = ultimo;
      bajar(0);
    }
  }
  // </paso 4>
  return out;
}
```

### Solución
```javascript
function topK(a, k) {
  const h = [];
  const subir = (i) => {
    while (i > 0) {
      const p = (i - 1) >> 1;
      if (h[p] <= h[i]) break;
      [h[p], h[i]] = [h[i], h[p]];
      i = p;
    }
  };
  const bajar = (i) => {
    for (;;) {
      const l = 2 * i + 1;
      const r = l + 1;
      let m = i;
      if (l < h.length && h[l] < h[m]) m = l;
      if (r < h.length && h[r] < h[m]) m = r;
      if (m === i) return;
      [h[m], h[i]] = [h[i], h[m]];
      i = m;
    }
  };
  for (const x of a) {
    if (h.length < k) {
      h.push(x);
      subir(h.length - 1);
    } else if (k > 0 && x > h[0]) {
      h[0] = x;
      bajar(0);
    }
  }
  return h.sort((x, y) => y - x);
}
```
```python
import heapq

def top_k(a, k):
    h = []
    for x in a:
        if len(h) < k:
            heapq.heappush(h, x)
        elif k > 0 and x > h[0]:
            heapq.heapreplace(h, x)
    return sorted(h, reverse=True)
```

### Pistas
- La raíz del heap de mínimos es el umbral de entrada al Top-K.
- k = 0 no guarda nada: cuida que el reemplazo no lea una raíz que no existe.

## Un trabajo que nunca se atiende
type: multiple_choice
id: a1-05-mc-starvation
rol: recuperacion

Sin volver al libro: una válvula de prioridad baja lleva tres días en la cola porque cada hora llegan trabajos urgentes. El
heap funciona bien. ¿Qué está pasando y qué lo corrige?

### Opciones
- Es un error del heap; se corrige reconstruyéndolo con heapify.
- Es un interbloqueo entre trabajos; se corrige con un candado.
- [x] Es starvation; se corrige con envejecimiento: la prioridad efectiva mejora con la espera hasta que el trabajo se atiende.
- Se corrige ordenando la cola completa en cada llegada.

### Justificación
El heap hace exactamente lo que promete: entrega siempre lo más urgente. El problema es de política, no de estructura: con
llegadas urgentes continuas, lo menos urgente nunca llega a la raíz. El envejecimiento cambia la llave con el tiempo de
espera. Reconstruir el heap u ordenar todo produce el mismo orden, y no hay recursos bloqueados entre sí que justifiquen un
candado.

## Heap frente a ordenar, por escrito
type: production
id: a1-05-prod-defensa

Defiende, en cinco a siete líneas, por qué la cola de mantenimiento usa un heap y no un arreglo que se ordena en cada
llegada. Incluye costos y una situación en la que ordenar sí sería razonable.

### Modelo
Los trabajos llegan mientras se atienden otros. Ordenar en cada llegada cuesta O(n log n) por evento, o O(n) si se inserta
en su lugar dentro de un arreglo ordenado, porque hay que desplazar elementos. El heap cobra O(log n) por insertar y por
extraer el más urgente, y no ordena lo que no hace falta. Ordenar sí es razonable si el conjunto es fijo y se va a recorrer
completo en orden, por ejemplo el plan de un turno ya cerrado: un solo O(n log n) y luego O(1) por elemento.

### Regla
Una estructura se elige por las operaciones que se repiten: con llegadas y extracciones intercaladas gana el heap; con un
conjunto estático recorrido completo, ordenar una vez basta.

### Rúbrica
- Da el costo por evento de las dos opciones.
- Explica que el heap sólo mantiene el mínimo en la raíz y no el orden total.
- Da un caso concreto donde ordenar una vez es la mejor opción.

## Construir el heap de una vez
type: multiple_choice
id: a1-05-mc-heapify

Al iniciar el turno ya tienes los n trabajos pendientes. ¿Cuánto cuesta construir el heap con todos ellos de una vez, bajando
cada nodo interno desde el último hasta la raíz?

### Opciones
- O(n log n), porque cada uno de los n nodos puede bajar log n niveles
- [x] O(n): la mayoría de los nodos está cerca de las hojas y baja muy poco; la suma de alturas es lineal
- O(log n), porque sólo se ajusta la raíz
- O(n²), porque cada bajada puede recorrer todo el arreglo

### Justificación
Cerca de la mitad de los nodos son hojas y no bajan nada, un cuarto baja a lo sumo un nivel, un octavo a lo sumo dos, y así.
La suma de esas alturas es O(n). Insertar uno por uno sí cuesta O(n log n) en el peor caso, y por eso construir de una vez es
mejor cuando ya tienes todos los trabajos.
