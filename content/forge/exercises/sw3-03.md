## Antes de leer: TCP y la reserva duplicada
type: prediccion
id: prediccion-tcp-reserva
rol: prediccion
tiempo: 2

Una app envía reservas por HTTP sobre TCP. Un compañero afirma: «TCP garantiza que no hay duplicados, así que una reserva nunca se creará dos veces». ¿Es cierto?

### Opciones
- [x] No: TCP no duplica bytes dentro de una conexión, pero si la conexión se cae después de que el servidor aplicó la reserva y el cliente la reenvía por otra conexión, para TCP es un mensaje nuevo y la reserva se crea dos veces.
- Sí, porque TCP numera los bytes y descarta los repetidos.
- Sí, siempre que se use HTTPS en lugar de HTTP.
- No, porque TCP duplica segmentos con frecuencia y la aplicación ve bytes repetidos.
### Justificación
La garantía de TCP es sobre bytes de una conexión mientras existe. El reenvío del cliente tras un resultado desconocido viaja por otra conexión, con su propia numeración: TCP no tiene forma de saber que es la misma operación. HTTPS cifra, pero no cambia esa semántica. Y dentro de una conexión TCP sí descarta los segmentos repetidos: la aplicación nunca ve bytes duplicados. La protección contra la reserva doble es una clave de idempotencia en la aplicación.

## Lo que confirma y anuncia el receptor
type: code
id: codigo-receptor-tcp
tiempo: 18

Calcula, después de cada segmento recibido, la confirmación y la ventana que anunciaría un receptor como el del curso, usando índices absolutos (sin números de secuencia ni su vuelta).

### Especificación
`receptor(capacidad, segmentos)`:
- `segmentos` es una lista de `[inicio, datos]`: el índice del primer byte y el texto (ASCII). La aplicación receptora no lee durante la simulación.
- Los bytes se reensamblan como en SW3-02: se guarda cada byte cuyo índice está entre el primer índice sin ensamblar y `capacidad` (sin incluir `capacidad`), y se escriben en orden en cuanto no hay hueco antes.
- Después de cada segmento, la **confirmación** es el primer índice sin ensamblar y la **ventana** es `capacidad − bytes ensamblados` (los bytes guardados sin ensamblar no ocupan la ventana).
- Devuelve la lista de pares `[confirmacion, ventana]`, uno por segmento.

### Solución
```javascript
function receptor(capacidad, segmentos) {
  let ensamblado = 0;
  const guardados = new Set();
  const salida = [];
  for (const [inicio, datos] of segmentos) {
    for (let i = 0; i < datos.length; i++) {
      const indice = inicio + i;
      if (indice >= ensamblado && indice < capacidad) guardados.add(indice);
    }
    while (guardados.has(ensamblado)) {
      guardados.delete(ensamblado);
      ensamblado += 1;
    }
    salida.push([ensamblado, capacidad - ensamblado]);
  }
  return salida;
}
```
```python
def receptor(capacidad, segmentos):
    ensamblado = 0
    guardados = set()
    salida = []
    for inicio, datos in segmentos:
        for i in range(len(datos)):
            indice = inicio + i
            if ensamblado <= indice < capacidad:
                guardados.add(indice)
        while ensamblado in guardados:
            guardados.remove(ensamblado)
            ensamblado += 1
        salida.append([ensamblado, capacidad - ensamblado])
    return salida
```

### Pistas
- La confirmación sólo avanza cuando se cierra el hueco desde el primer índice sin ensamblar.
- Los bytes que llegan adelantados no achican la ventana hasta que se ensamblan.
- Lo que no cabe (índice mayor o igual que la capacidad) se descarta; el emisor lo retransmitirá cuando la ventana se abra.

## El temporizador que se duplica
type: trace
id: traza-rto
tiempo: 3

Un emisor con tiempo de espera inicial de 500 ms envía un segmento en t = 0. La red pierde el segmento y sus dos primeras retransmisiones; la tercera retransmisión llega y su confirmación vuelve 20 ms después. Cada retransmisión consecutiva duplica el tiempo de espera. ¿En qué instantes se retransmite y cuánto vale el tiempo de espera después de la confirmación?

### Opciones
- [x] Se retransmite en 500, 1,500 y 3,500 ms; la confirmación llega en 3,520 ms y el tiempo de espera vuelve a 500 ms.
- Se retransmite en 500, 1,000 y 1,500 ms, porque el tiempo de espera es fijo; después de la confirmación sigue en 500 ms.
- Se retransmite en 500, 1,500 y 3,500 ms; después de la confirmación queda en 4,000 ms, porque la red mostró pérdidas.
- Se retransmite en 500, 2,000 y 6,000 ms, porque el tiempo de espera se triplica.
### Justificación
El primer vencimiento ocurre a los 500 ms y la espera pasa a 1,000: la siguiente retransmisión es en 1,500 y la espera pasa a 2,000; la tercera es en 3,500 y la espera pasa a 4,000. Esa tercera llega y se confirma en 3,520. Una confirmación de datos nuevos devuelve el temporizador a su valor inicial, 500 ms. Un tiempo fijo reintentaría demasiado rápido en una red congestionada; conservar 4,000 tras la confirmación haría lenta la recuperación de la siguiente pérdida; la regla es duplicar, no triplicar.

## La conexión que se cayó a mitad
type: multiple_choice
id: conexion-caida
tiempo: 3

El servidor recibió por completo el `POST /reservas`, guardó la reserva y, antes de que la respuesta llegara al cliente, la conexión se reinició. ¿Qué sabe el cliente y qué debe hacer?

### Opciones
- [x] No sabe si la reserva se creó; debe reenviarla con la misma clave de idempotencia por una conexión nueva, para que el servidor devuelva el resultado guardado si ya la había aplicado.
- Sabe que la reserva no se creó, porque TCP no entregó la respuesta.
- Sabe que la reserva se creó, porque TCP confirmó los bytes de la petición.
- Debe esperar a que TCP retransmita la respuesta por la conexión reiniciada.
### Justificación
Que la conexión se reiniciara antes de la respuesta deja el resultado desconocido: la petición pudo procesarse o no. Que TCP confirmara los bytes de la petición sólo dice que llegaron al sistema operativo del servidor, no que el servidor los aplicó. Una conexión reiniciada no retransmite nada: su estado se perdió. La única forma segura de reintentar es con la misma clave de idempotencia, que hace que el servidor reconozca la operación.

## Qué garantiza el transporte y qué no
type: production
id: produccion-limites-transporte
tiempo: 12

La defensa de esta celda pide explicar qué garantiza el transporte y por qué una reserva todavía necesita invariantes. Escríbelo para un revisor que propone «confiar en TCP» para las órdenes del sistema: qué da TCP, qué no da y qué pone la aplicación encima, con un ejemplo de falla para cada límite.

### Modelo
*Lo que da TCP:* bytes en orden, sin huecos ni duplicados, entre dos extremos mientras la conexión vive; retransmisión de lo perdido; control de flujo con la ventana del receptor; control de congestión.
*Lo que no da, con su falla:* (1) que la aplicación procesó los datos: los bytes pueden estar confirmados y el servidor caerse antes de guardar; (2) nada después de un reinicio de conexión: el servidor guardó la orden y la respuesta se perdió, y el reenvío por otra conexión la duplicaría; (3) semántica de negocio: dos órdenes idénticas son, para TCP, dos mensajes distintos; (4) garantías a través de intermediarios: un proxy que confirma al cliente y falla antes de reenviar al servidor.
*Lo que pone la aplicación:* claves de idempotencia por operación lógica, estados explícitos para resultados desconocidos con reconciliación, invariantes de negocio validados en el servidor (la reserva no traslapa, el turno no queda vacío) y transacciones con el aislamiento declarado.
*Conclusión:* TCP es la base fiable para mover bytes; la garantía de «esta reserva existe una vez y es válida» es de punta a punta y vive en la aplicación.

### Regla
La garantía del transporte es sobre bytes de una conexión entre dos extremos; las garantías sobre operaciones de negocio (una sola vez, válidas, conciliadas) se implementan de punta a punta en la aplicación.

### Rúbrica
- Enumera con precisión lo que garantiza TCP, sin exagerarlo.
- Da al menos tres límites, cada uno con una falla concreta.
- Distingue bytes confirmados de operación aplicada.
- Propone los mecanismos de la aplicación (idempotencia, reconciliación, invariantes) y dice qué límite cubre cada uno.
- No atribuye al transporte garantías de negocio.
