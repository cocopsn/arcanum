# S1-05 · Modelado de estados e invariantes

Banco de la celda: predecir qué protege un botón deshabilitado, implementar la única puerta de transiciones, encontrar la secuencia que una versión casi correcta acepta, ubicar cada invariante y transferir el modelo a un sistema externo que escribe estados por su cuenta.

## El botón deshabilitado
type: prediccion
id: s1-05-pred-boton
rol: prediccion
escala: 50 70 90

En la interfaz, «Cancelar» está deshabilitado para las órdenes `informada`. La API de órdenes acepta `PATCH /ordenes/{id}` con cualquier `estado`. Predice si la regla «una orden informada no se cancela» está protegida.

### Opciones
- [x] No: cualquier cliente que llame a la API (un script, una importación, otro servicio) puede cancelarla; el botón sólo evita el error en un cliente.
- Sí, porque los usuarios sólo usan la interfaz.
- Sí, porque la API hereda las reglas de la interfaz.
- Depende del navegador del usuario.
### Justificación
Una regla vive donde ningún cliente pueda saltarla. La interfaz es un cliente entre varios; la API acepta el cambio sin comprobar la transición, así que todo lo que no pase por el botón puede violar la regla. Las reglas no se heredan de la interfaz a la API: van en la operación de escritura (y, si se puede, en el esquema).

## La única puerta de transiciones
type: code
id: s1-05-code-transicionar

Implementa `transicionar(estado, evento)` para la orden de estudio. Devuelve el estado destino si la transición es válida, o la cadena `"rechazada"` si no lo es (incluidos estados o eventos desconocidos). Transiciones válidas: `emitida` + `agendar` → `agendada`; `emitida` + `cancelar` → `cancelada`; `agendada` + `iniciar` → `en_estudio`; `agendada` + `cancelar` → `cancelada`; `agendada` + `agendar` → `agendada`; `en_estudio` + `informar` → `informada`. Ninguna más.

### Firma
```javascript
function transicionar(estado, evento) {
  // devuelve el estado destino o "rechazada"
}
```
### Casos
```json
[
  { "input": ["emitida", "agendar"], "expected": "agendada" },
  { "input": ["agendada", "iniciar"], "expected": "en_estudio" },
  { "input": ["en_estudio", "informar"], "expected": "informada" },
  { "input": ["agendada", "agendar"], "expected": "agendada" },
  { "input": ["emitida", "cancelar"], "expected": "cancelada" },
  { "input": ["informada", "cancelar"], "expected": "rechazada" },
  { "input": ["en_estudio", "cancelar"], "expected": "rechazada" },
  { "input": ["cancelada", "agendar"], "expected": "rechazada" },
  { "input": ["emitida", "informar"], "expected": "rechazada" },
  { "input": ["archivada", "agendar"], "expected": "rechazada" },
  { "input": ["emitida", "toString"], "expected": "rechazada" }
]
```
### Solución
```javascript
function transicionar(estado, evento) {
  const tabla = {
    emitida: { agendar: "agendada", cancelar: "cancelada" },
    agendada: { iniciar: "en_estudio", cancelar: "cancelada", agendar: "agendada" },
    en_estudio: { informar: "informada" },
    informada: {},
    cancelada: {},
  };
  if (!Object.prototype.hasOwnProperty.call(tabla, estado)) return "rechazada";
  const fila = tabla[estado];
  if (!Object.prototype.hasOwnProperty.call(fila, evento)) return "rechazada";
  return fila[evento];
}
```
### Pistas
- Escribe la tabla como datos y consulta la tabla; no encadenes `if` por estado.
- Un objeto literal hereda propiedades como `toString`: comprueba que la llave sea propia.

## La versión que acepta de más
type: contraejemplo
id: s1-05-contra-terminal

Esta versión de `transicionar` pasa las pruebas del camino feliz. Da un par `(estado, evento)` con valores conocidos de la orden en el que su resultado difiera del de la referencia.

### Firma
```javascript
function transicionar(estado, evento) {
  // devuelve el estado destino o "rechazada"
}
```
### Precondición
```javascript
function pre(estado, evento) {
  const estados = ["emitida", "agendada", "en_estudio", "informada", "cancelada"];
  const eventos = ["agendar", "iniciar", "informar", "cancelar"];
  return estados.includes(estado) && eventos.includes(evento);
}
```
### Casi correcta
```javascript
function transicionar(estado, evento) {
  if (evento === "cancelar") return "cancelada";
  if (estado === "emitida" && evento === "agendar") return "agendada";
  if (estado === "agendada" && evento === "agendar") return "agendada";
  if (estado === "agendada" && evento === "iniciar") return "en_estudio";
  if (estado === "en_estudio" && evento === "informar") return "informada";
  return "rechazada";
}
```
### Referencia
```javascript
function transicionar(estado, evento) {
  const tabla = {
    emitida: { agendar: "agendada", cancelar: "cancelada" },
    agendada: { iniciar: "en_estudio", cancelar: "cancelada", agendar: "agendada" },
    en_estudio: { informar: "informada" },
    informada: {},
    cancelada: {},
  };
  const fila = tabla[estado] || {};
  return Object.prototype.hasOwnProperty.call(fila, evento) ? fila[evento] : "rechazada";
}
```

```json
["informada", "cancelar"]
```

## ¿Dónde vive «informada tiene informe»?
type: multiple_choice
id: s1-05-choice-lugar
rol: recuperacion

Sin volver al libro: la regla es «toda orden en estado `informada` tiene un informe asociado». Las órdenes cambian de estado por la acción de la aplicación, por una importación nocturna y por un script de soporte. ¿Cuál es la combinación más sólida?

### Opciones
- [x] Que la operación de escritura exija el informe para pasar a `informada`, cerrar la escritura directa del script y la importación (que pasen por la operación) y un reconciliador que reporte cualquier `informada` sin informe.
- Ocultar el estado `informada` en la interfaz mientras no haya informe.
- Confiar en que la importación nocturna traiga siempre el informe.
- Revisar a mano cada semana una muestra de órdenes informadas.
### Justificación
La regla tiene tres clientes y debe vivir donde los tres pasen: la operación de escritura. Los caminos que hoy la saltan (script e importación) se cierran o se obligan a usar la operación, y el reconciliador acota cuánto dura una violación que entre por un camino no previsto. Ocultar en la interfaz no protege a los otros dos clientes; confiar en la importación es suponer, no proteger; una muestra semanal detecta tarde y de forma incompleta.

## Dos clientes a la vez
type: prediccion
id: s1-05-pred-concurrencia
rol: prediccion

La operación lee el estado de la orden, comprueba la transición y escribe el estado nuevo, sin condición en la escritura. A la vez llegan `cancelar` (de recepción) e `iniciar` (del técnico) para una orden `agendada`. Predice qué puede pasar.

### Opciones
- [x] Las dos comprobaciones pasan, porque ambas leen `agendada`, y el estado final es el de la escritura que llegue última: una orden «cancelada» con estudio en curso, o «en estudio» que recepción cree cancelada.
- La tabla de transiciones lo impide, porque `cancelar` desde `en_estudio` está prohibido.
- Siempre gana `cancelar`, porque los rechazos tienen prioridad.
- La base rechaza la segunda escritura porque el estado ya cambió.
### Justificación
La tabla sólo protege si la comprobación y la escritura ven el mismo estado. Leer, comprobar y escribir en pasos separados deja una ventana: las dos comprobaciones ven `agendada`. La protección es una escritura condicionada (`UPDATE … SET estado = 'cancelada' WHERE id = … AND estado = 'agendada'`, que afecta 0 filas si alguien llegó antes) o un candado sobre la orden. La base no rechaza nada por sí sola si no se le pidió.

## Defender el lugar de cada invariante
type: production
id: s1-05-prod-defensa

Para la orden de estudio, toma dos invariantes: «de `informada` no se sale» y «una orden `agendada` tiene exactamente una cita activa». Para cada una, di dónde vive, qué cliente puede intentar violarla y cómo lo detectarías si lo logra.

### Modelo
«De `informada` no se sale» es de transición: vive en la operación de escritura (la tabla de transiciones) y además en el esquema, con una escritura condicionada al estado leído. Pueden intentar violarla un script de soporte que actualiza la base, una importación que reescribe estados y un reintento tardío de `cancelar`. Detección: un reconciliador que compara el historial de cambios con la tabla y reporta cualquier salida de un estado terminal. «Una `agendada` tiene exactamente una cita activa» es entre entidades: vive en la operación que agenda (crea la cita y cambia el estado en la misma transacción) y, en el esquema, con una restricción de unicidad parcial sobre las citas activas por orden. Pueden violarla dos agendamientos simultáneos o la cancelación de la cita sin cambiar la orden. Detección: una consulta periódica de órdenes agendadas con 0 o con 2 o más citas activas.
### Regla
Un invariante vive donde todos los clientes que escriben tengan que pasar; lo que no se puede prevenir ahí se detecta con un reconciliador, que acota la duración del error.
### Rúbrica
- Clasifica cada invariante (de estado, de transición, entre entidades).
- Ubica cada una en la operación de escritura o el esquema, no en la interfaz.
- Nombra al menos dos clientes concretos que podrían intentar violarla.
- Propone una detección verificable (consulta o reconciliador) para lo que entre por fuera.

## Giro: un sistema externo marca estudios como informados
type: giro
id: s1-05-giro
rol: transferencia

El sistema de imagen (PACS) empieza a avisar por webhook cuando un estudio queda informado. Los avisos pueden llegar repetidos, fuera de orden (un «informado» antes de que tu sistema registre «iniciado») o para órdenes que recepción canceló hace un minuto. ¿Cómo cambia tu máquina de estados y dónde viven ahora las invariantes? Explica qué haces con un aviso que tu tabla rechazaría.

### Rúbrica
- Trata el aviso externo como un evento más que pasa por la misma puerta de transiciones, no como una escritura directa del estado.
- Hace la transición idempotente para avisos repetidos (mismo aviso, mismo resultado).
- Define qué pasa con un aviso fuera de orden o sobre una orden cancelada: se registra, no se aplica a ciegas, y va a revisión o a reconciliación.
- Preserva los estados terminales y el historial de cambios.
- Explica cómo detectaría y mediría las discrepancias entre su estado y el del sistema externo.
