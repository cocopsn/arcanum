# S1-02 · SQL, cardinalidad y planes

Banco de la celda: contar filas antes de ejecutar, corregir un reporte que multiplica por el join, desactivar la trampa de `NOT IN` con `NULL`, explicar por qué un índice no ayuda y transferir el razonamiento a datos con sesgo. Las consultas se comprueban en tu dispositivo con SQLite; los planes no se comparan (límite declarado del corredor).

## Tres citas, dos pagos
type: prediccion
id: s1-02-pred-fanout
rol: prediccion
escala: 50 70 90

La paciente P-7 tiene 3 citas y 2 pagos de 500 cada uno. Se ejecuta `SELECT COUNT(*), SUM(g.monto) FROM cita c JOIN pago g ON g.paciente_id = c.paciente_id WHERE c.paciente_id = 'P-7'`. Predice el resultado antes de calcularlo con calma.

### Opciones
- [x] 6 filas y 3,000: cada cita se combina con cada pago.
- 3 filas y 1,000: el join toma un pago por cita.
- 5 filas y 2,500: se suman las filas de ambas tablas.
- 2 filas y 1,000: el join se queda con la tabla más pequeña.
### Justificación
Un join por una llave que no es única en ninguno de los dos lados produce el producto de las filas que comparten el valor: 3 × 2 = 6. La suma recorre esas 6 filas y cada pago aparece 3 veces: 3 × 1,000 = 3,000. No hay ninguna regla que empareje «un pago por cita»; para eso haría falta una llave que los relacione (por ejemplo, `pago.cita_id`).

## Pagado y citas por paciente, sin inflar
type: sql
id: s1-02-sql-sin-inflar
orden: no

Devuelve, para **cada** paciente (incluidos los que no tienen citas o pagos), tres columnas: `paciente_id`, `citas` (número de citas) y `pagado` (suma de sus pagos, 0 si no tiene). Cuidado con unir dos relaciones 1:N por la misma llave.

### Esquema
```sql
CREATE TABLE paciente (paciente_id TEXT PRIMARY KEY);
CREATE TABLE cita (cita_id TEXT PRIMARY KEY, paciente_id TEXT NOT NULL REFERENCES paciente(paciente_id));
CREATE TABLE pago (pago_id TEXT PRIMARY KEY, paciente_id TEXT NOT NULL REFERENCES paciente(paciente_id), monto INTEGER NOT NULL);
```
### Datos
```sql
INSERT INTO paciente VALUES ('P-1'), ('P-2'), ('P-3');
INSERT INTO cita VALUES ('C-1', 'P-1'), ('C-2', 'P-2');
INSERT INTO pago VALUES ('G-1', 'P-1', 500), ('G-2', 'P-2', 300);
```
### Fixtures
```sql
-- fixture: uno-a-uno
UPDATE pago SET monto = monto WHERE pago_id = 'G-1';
```
```sql
-- fixture: cronico
INSERT INTO cita VALUES ('C-3', 'P-1'), ('C-4', 'P-1');
INSERT INTO pago VALUES ('G-3', 'P-1', 500);
```
```sql
-- fixture: sin-pagos
INSERT INTO cita VALUES ('C-5', 'P-3');
```
### Solución
```sql
WITH ci AS (SELECT paciente_id, COUNT(*) AS citas FROM cita GROUP BY paciente_id),
     pa AS (SELECT paciente_id, SUM(monto) AS pagado FROM pago GROUP BY paciente_id)
SELECT p.paciente_id, COALESCE(ci.citas, 0) AS citas, COALESCE(pa.pagado, 0) AS pagado
FROM paciente p
LEFT JOIN ci ON ci.paciente_id = p.paciente_id
LEFT JOIN pa ON pa.paciente_id = p.paciente_id
```
### Ingenua
```sql
SELECT p.paciente_id, COUNT(c.cita_id) AS citas, COALESCE(SUM(g.monto), 0) AS pagado
FROM paciente p
LEFT JOIN cita c ON c.paciente_id = p.paciente_id
LEFT JOIN pago g ON g.paciente_id = p.paciente_id
GROUP BY p.paciente_id
```

## Citas atendidas sin pago
type: sql
id: s1-02-sql-sin-pago
orden: no

Cobranza quiere las citas en estado `atendida` que no tienen ningún pago asociado. Un pago puede no estar ligado a una cita (los anticipos tienen `cita_id` en `NULL`). Devuelve una columna: `cita_id`.

### Esquema
```sql
CREATE TABLE cita (cita_id TEXT PRIMARY KEY, estado TEXT NOT NULL);
CREATE TABLE pago (pago_id TEXT PRIMARY KEY, cita_id TEXT REFERENCES cita(cita_id), monto INTEGER NOT NULL);
```
### Datos
```sql
INSERT INTO cita VALUES ('C-1', 'atendida'), ('C-2', 'atendida'), ('C-3', 'agendada'), ('C-4', 'atendida');
INSERT INTO pago VALUES ('G-1', 'C-1', 500), ('G-2', 'C-4', 200);
```
### Fixtures
```sql
-- fixture: sin-anticipos
UPDATE pago SET monto = monto WHERE pago_id = 'G-1';
```
```sql
-- fixture: con-anticipo
INSERT INTO pago VALUES ('G-9', NULL, 1000);
```
### Solución
```sql
SELECT c.cita_id
FROM cita c
WHERE c.estado = 'atendida'
  AND NOT EXISTS (SELECT 1 FROM pago g WHERE g.cita_id = c.cita_id)
```
### Ingenua
```sql
SELECT c.cita_id
FROM cita c
WHERE c.estado = 'atendida'
  AND c.cita_id NOT IN (SELECT g.cita_id FROM pago g)
```

## El índice que nadie usa
type: multiple_choice
id: s1-02-choice-indice
rol: recuperacion

Sin volver al libro: se creó un índice B-tree sobre `cita(estado)`. El 80 % de las filas tiene `estado = 'atendida'`. La consulta `SELECT * FROM cita WHERE estado = 'atendida'` sigue igual de lenta y el plan muestra un recorrido secuencial. ¿Por qué?

### Opciones
- [x] El predicado es poco selectivo: deja pasar casi toda la tabla, y leerla en orden cuesta menos que saltar fila por fila desde el índice; el planificador lo ignora con razón.
- El índice está corrupto y hay que reconstruirlo.
- Los índices B-tree sólo sirven para columnas numéricas.
- El planificador nunca usa índices sobre columnas de texto si no se le obliga con una pista.
### Justificación
Un índice paga cuando descarta la mayoría de las filas. Con el 80 % de coincidencias, recorrer el índice obliga a visitar casi todas las páginas de la tabla en orden aleatorio, y un recorrido secuencial es más barato. Nada indica corrupción; un B-tree ordena texto igual que números, y el planificador usa índices sobre texto cuando el predicado es selectivo. El remedio está en otra parte: la lentitud del reporte venía del join que multiplicaba filas.

## Un LIKE que empieza con comodín
type: prediccion
id: s1-02-pred-like
rol: prediccion

Existe un índice B-tree sobre `paciente(apellido)`. Predice cuál de estas consultas **no** puede aprovechar el orden del índice para encontrar las filas.

### Opciones
- [x] `WHERE apellido LIKE '%ruiz'`
- `WHERE apellido = 'Ruiz'`
- `WHERE apellido >= 'R' AND apellido < 'S'`
- `WHERE apellido BETWEEN 'Ra' AND 'Rz'`
### Justificación
Un B-tree ordena por el valor completo desde el primer carácter. Igualdad y rangos sobre el prefijo se resuelven bajando por el árbol. Un patrón que empieza con comodín no fija ningún prefijo, así que no hay rango del árbol que recorrer: hay que revisar todas las entradas. (Si el motor tiene un índice especializado para texto, la historia cambia; con un B-tree sobre la columna, no.)

## Registrar dos planes para un colega
type: production
id: s1-02-prod-planes

Escribe la nota que dejarías en el registro del proyecto tras comparar la consulta que une y luego agrega con la que agrega y luego une, ejecutadas sobre 200 y 20,000 pacientes. Debe permitir que otra persona repita la medición y entienda la conclusión.

### Modelo
Fecha y motor (versión). Datos: 200 y 20,000 pacientes generados con la misma semilla; en el grande, crónicos con hasta 12 citas y 6 pagos. Consulta A (une y agrega): en el grande, el nodo del segundo join produce la suma de citas × pagos por paciente y su estimación queda muy por debajo de las filas reales; además los totales salen inflados. Consulta B (agrega y une): cada rama agrega una tabla y el join final une una fila por paciente; estimación y realidad coinciden. Conclusión: A es incorrecta con datos realistas, no sólo lenta; B es correcta y su costo crece con el tamaño de cada tabla. Siguiente experimento: repetir con un paciente institucional de 50,000 citas.
### Regla
Un plan registrado lleva consulta, tamaño y distribución de los datos, versión del motor y fecha, y compara filas estimadas frente a reales en el nodo que importa. Sin eso no se puede comparar con la próxima medición.
### Rúbrica
- Declara motor, versión, fecha y tamaño de los datos.
- Nombra el nodo donde la estimación se aleja de la realidad y por qué (el producto del join).
- Separa corrección (totales inflados) de rendimiento.
- Propone un siguiente experimento verificable.

## Giro: un paciente con 50,000 citas
