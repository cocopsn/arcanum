## Antes de leer: diez segundos de silencio
type: prediccion
id: prediccion-worker-silencioso
rol: prediccion
tiempo: 2

Un coordinador de MapReduce asignó una tarea map hace diez segundos y el worker no ha respondido. ¿Qué es lo correcto?

### Opciones
- [x] Reasignar la tarea a otro worker, suponiendo que el primero quizá todavía la termine, y diseñar las tareas para que ejecutarlas dos veces no haga daño.
- Esperar indefinidamente, porque reasignar puede producir resultados duplicados.
- Marcar el trabajo completo como fallido, porque un worker caído invalida la ejecución.
- Reasignarla y descartar cualquier resultado que llegue después del primer worker, porque ya está muerto.
### Justificación
El coordinador no puede saber si el worker se cayó, está lento o terminó y su aviso se perdió. Esperar para siempre deja el trabajo colgado si se cayó; fallar todo desperdicia el resto. La salida es reasignar y hacer que la re-ejecución sea segura. Descartar al primer worker por «muerto» es suponer algo que no se sabe: puede terminar primero, y su resultado es tan válido como el del segundo si las tareas son deterministas y sus salidas aparecen de forma atómica.

## El coordinador de tareas
type: code
id: codigo-coordinador
tiempo: 20

Implementa la lógica de asignación del coordinador como una función pura que procesa eventos en orden de tiempo y devuelve la respuesta a cada uno.

### Especificación
`coordinador(n, plazo, eventos)`:
- Hay `n` tareas con ids `0 … n − 1`, todas libres al empezar. `plazo` es un entero en segundos.
- Cada evento es `{ "t", "tipo": "pedir", "w" }` o `{ "t", "tipo": "fin", "w", "tarea" }`, en orden no decreciente de `t`.
- **pedir:** si todas las tareas están hechas, responde `"salir"`. Si no, asigna al worker `w` la tarea **libre** de menor id; si no hay libres, la tarea **en curso** de menor id cuya última asignación fue en un instante `inicio` con `inicio + plazo ≤ t` (se reasigna y su `inicio` pasa a ser `t`). Responde el id asignado. Si no hay ninguna, responde `"esperar"`.
- **fin:** si la tarea existe, no está hecha y se le asignó alguna vez a `w`, queda hecha y responde `"ok"`. En cualquier otro caso (tarea ya hecha, id inexistente o worker al que nunca se le asignó) responde `"ignorado"`.
- Devuelve la lista de respuestas, en orden.

### Solución
```javascript
function coordinador(n, plazo, eventos) {
  const tareas = Array.from({ length: n }, () => ({ fase: "libre", inicio: 0, workers: new Set() }));
  const salida = [];
  for (const e of eventos) {
    if (e.tipo === "pedir") {
      if (tareas.every((s) => s.fase === "hecha")) {
        salida.push("salir");
        continue;
      }
      let i = tareas.findIndex((s) => s.fase === "libre");
      if (i === -1) i = tareas.findIndex((s) => s.fase === "en-curso" && s.inicio + plazo <= e.t);
      if (i === -1) {
        salida.push("esperar");
        continue;
      }
      tareas[i].fase = "en-curso";
      tareas[i].inicio = e.t;
      tareas[i].workers.add(e.w);
      salida.push(i);
    } else {
      const s = Number.isInteger(e.tarea) && e.tarea >= 0 && e.tarea < n ? tareas[e.tarea] : null;
      if (!s || s.fase === "hecha" || !s.workers.has(e.w)) {
        salida.push("ignorado");
        continue;
      }
      s.fase = "hecha";
      salida.push("ok");
    }
  }
  return salida;
}
```

def coordinador(n, plazo, eventos):
    tareas = [{"fase": "libre", "inicio": 0, "workers": set()} for _ in range(n)]
    salida = []
    for e in eventos:
        if e["tipo"] == "pedir":

                salida.append("salir")
                continue
            i = next((k for k, s in enumerate(tareas) if s["fase"] == "libre"), -1)
            if i == -1:
                i = next((k for k, s in enumerate(tareas) if s["fase"] == "en-curso" and s["inicio"] + plazo <= e["t"]), -1)
            if i == -1:
                salida.append("esperar")
                continue
            tareas[i]["fase"] = "en-curso"
            tareas[i]["inicio"] = e["t"]
            tareas[i]["workers"].add(e["w"])
            salida.append(i)
        else:
            k = e.get("tarea")
            valido = isinstance(k, int) and not isinstance(k, bool) and 0 <= k < n
            s = tareas[k] if valido else None
            if s is None or s["fase"] == "hecha" or e["w"] not in s["workers"]:
                salida.append("ignorado")
                continue
            s["fase"] = "hecha"
            salida.append("ok")
    return salida

### Pistas
- Una tarea libre siempre tiene prioridad sobre una reasignación: reasignar duplica trabajo.
- El plazo se cuenta desde la **última** asignación de la tarea, no desde la primera.
- El aviso de un worker lento que llega primero es tan válido como el del reemplazo; el segundo aviso de una tarea hecha se ignora.

## Por qué renombrar
type: multiple_choice
id: por-que-renombrar
tiempo: 3

En el laboratorio, cada worker escribe su salida en un archivo temporal y al final lo renombra al nombre definitivo. ¿Qué problema evita esa técnica?

### Opciones
- [x] Que un lector vea un archivo a medio escribir por un worker que se cayó, o la mezcla de dos ejecuciones de la misma tarea: el renombrado hace que el archivo final contenga una ejecución completa o no exista.
- Que dos workers usen el mismo nombre de archivo temporal, porque el sistema operativo no lo permite.
- Que el sistema de archivos se llene, porque los temporales se borran solos.
- Que el coordinador asigne dos veces la misma tarea.
### Justificación
Renombrar dentro de un mismo sistema de archivos es una operación atómica: el nombre definitivo apunta al archivo viejo o al nuevo, nunca a uno a medias. Si un worker muere a mitad de la escritura, sólo queda un temporal huérfano; si dos ejecuciones terminan, la segunda reemplaza a la primera con el mismo contenido, siempre que la tarea sea determinista. No evita que el coordinador reasigne (eso es intencional), no tiene que ver con el espacio en disco y cada worker crea su propio temporal con un nombre único.

## La función map que tira los dados
type: multiple_choice
id: map-no-determinista
tiempo: 3

Para acelerar un trabajo, alguien cambia la función map para que procese sólo una muestra aleatoria del 10 % de cada archivo. Una tarea map se ejecuta dos veces por una reasignación, y los dos workers terminan. ¿Cuál es el problema?

### Opciones
- [x] Las dos ejecuciones producen archivos intermedios distintos y cada reduce puede leer la versión de una ejecución diferente; la salida global mezcla dos muestras y no corresponde a ninguna ejecución del trabajo.
- Ninguno: el renombrado atómico garantiza que sólo una ejecución gana.
- Sólo que el resultado es aproximado, lo cual es aceptable porque es una muestra.
- Que el coordinador detecta la diferencia y marca la tarea como fallida.
### Justificación
El renombrado es atómico por archivo, no por tarea: cada partición intermedia (`mr-X-0`, `mr-X-1`) se renombra por separado, así que el reduce 0 puede leer la partición de la primera ejecución y el reduce 1 la de la segunda, o una partición puede quedar reemplazada después de que un reduce ya la leyó. Con una función determinista eso no importa, porque las dos versiones son iguales; con una aleatoria, la salida combina muestras distintas. Que sea aproximado no lo hace consistente, y el coordinador no compara contenidos.

## El paper de GFS con el protocolo de cinco preguntas
type: production
id: produccion-paper-gfs
tiempo: 20

Lee The Google File System y responde el protocolo de cinco preguntas del programa: problema, supuesto esencial, mecanismo, fallo que evita y costo que introduce. Agrega, como trabajo propio de la sección 08, un supuesto del paper que **no** se aplica a un servicio tuyo y qué cambiarías por eso.

### Modelo
*Problema:* almacenar archivos muy grandes, sobre todo escritos agregando al final y leídos en recorridos largos, sobre miles de máquinas baratas, para cargas de procesamiento por lotes.
*Supuesto esencial:* la falla de componentes es la norma; las cargas son de archivos grandes, escrituras por agregado y lecturas secuenciales, con más interés en el ancho de banda sostenido que en la latencia de una operación.
*Mecanismo:* un maestro único con los metadatos y servidores de trozos con los datos, de modo que los clientes hablan con el maestro sólo para ubicar y con los servidores para leer y escribir; trozos grandes replicados en varias máquinas; arrendamientos para ordenar las escrituras en cada trozo; y agregado de registros con garantía de al menos una vez.
*Fallo que evita:* que la caída de discos o máquinas pierda datos o detenga el sistema; la réplica y la re-replicación automática mantienen los datos disponibles.
*Costo:* el maestro único es un límite de escala y un punto delicado de disponibilidad; la consistencia relajada traslada a las aplicaciones la tarea de tolerar duplicados y relleno; y el diseño es malo para muchos archivos pequeños o escrituras aleatorias.
*Supuesto que no aplica (trabajo propio):* mi servicio de reservas hace escrituras pequeñas, aleatorias y sensibles a la latencia, y no tolera registros duplicados; no usaría su modelo de agregado al menos una vez sin claves de idempotencia en cada registro, ni trozos grandes.

### Regla
Un paper se lee con cinco preguntas (problema, supuesto esencial, mecanismo, fallo que evita y costo que introduce), y sus propiedades no se extrapolan a servicios modernos ni a cargas que no comparten sus supuestos.

### Rúbrica
- Responde las cinco preguntas por separado y con palabras propias.
- El supuesto esencial nombra las fallas como norma y el tipo de carga para el que se diseñó.
- El mecanismo incluye la separación entre metadatos y datos, la réplica de trozos y la garantía de agregado al menos una vez.
- El costo incluye la consistencia relajada que deben tolerar las aplicaciones.
- Identifica un supuesto concreto que no aplica a un servicio propio y dice qué cambiaría.
