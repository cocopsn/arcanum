## Antes de leer: dos threads y un contador
type: prediccion
id: prediccion-contador
rol: prediccion
tiempo: 2

Dos threads ejecutan, cada uno, 1,000 veces `contador = contador + 1` sobre la misma variable compartida, sin ningún lock. El contador empieza en 0. ¿Qué puedes afirmar del valor final?

### Opciones
- [x] Que no pasará de 2,000 y que puede ser menor, porque la línea es leer, sumar y escribir, y dos threads pueden leer el mismo valor antes de que cualquiera escriba.
- Que siempre será exactamente 2,000, porque cada thread hace sus 1,000 sumas completas.
- Que siempre será 1,000, porque los dos threads se pisan en cada suma.
- Que puede ser mayor que 2,000 si el planificador intercala mal las instrucciones.
### Justificación
Cada incremento son tres pasos. Si A lee 41, B lee 41, A escribe 42 y B escribe 42, se perdió una suma. Cuántas se pierden depende de la intercalación, que cambia en cada corrida, así que no hay un valor fijo: puede salir 2,000 en una prueba y menos en producción. Nunca pasa de 2,000, porque cada escritura vale a lo sumo uno más que algún valor leído. Que se pisen en todas las sumas es un caso extremo posible, no una garantía.

## Una cola acotada como modelo secuencial
type: code
id: codigo-cola-secuencial
tiempo: 15

Antes de sincronizar una cola concurrente hay que fijar su contrato secuencial: qué responde cada operación si se ejecutan de una en una. Implementa ese modelo, en su versión que no bloquea (en lugar de esperar, responde `"llena"` o `"vacia"`).

### Especificación
`colaSecuencial(cap, operaciones)`:
- `cap` es un entero ≥ 1; `operaciones` es una lista de `["poner", x]`, `["sacar"]` o `["cerrar"]`.
- `poner`: si la cola está cerrada responde `"cerrada"`; si tiene `cap` elementos responde `"llena"`; si no, agrega `x` al final y responde `"ok"`.
- `sacar`: si hay elementos, quita el primero y lo responde; si está vacía y cerrada responde `"cerrada"`; si está vacía y abierta responde `"vacia"`.
- `cerrar`: marca la cola como cerrada y responde `"ok"`; cerrar una cola ya cerrada también responde `"ok"`.
- Los elementos que había al cerrar se siguen entregando en orden.
- Devuelve la lista de respuestas, en orden.

### Solución
```javascript
function colaSecuencial(cap, operaciones) {
  const elementos = [];
  let cerrada = false;
  const salida = [];
  for (const op of operaciones) {
    if (op[0] === "poner") {
      if (cerrada) salida.push("cerrada");
      else if (elementos.length === cap) salida.push("llena");
      else {
        elementos.push(op[1]);
        salida.push("ok");
      }
    } else if (op[0] === "sacar") {
      if (elementos.length > 0) salida.push(elementos.shift());
      else salida.push(cerrada ? "cerrada" : "vacia");
    } else {
      cerrada = true;
      salida.push("ok");
    }
  }
  return salida;
}
```
```python
def cola_secuencial(cap, operaciones):
    elementos = []
    cerrada = False
    salida = []
    for op in operaciones:
        if op[0] == "poner":
            if cerrada:
                salida.append("cerrada")
            elif len(elementos) == cap:
                salida.append("llena")
            else:
                elementos.append(op[1])
                salida.append("ok")
        elif op[0] == "sacar":
            if elementos:
                salida.append(elementos.pop(0))
            else:
                salida.append("cerrada" if cerrada else "vacia")
        else:
            cerrada = True
            salida.append("ok")
    return salida
```

### Pistas
- `sacar` revisa primero si hay elementos: el cierre no borra lo que ya estaba en la cola.
- `poner` revisa primero el cierre: una cola cerrada responde `"cerrada"` aunque tenga lugar.
- Este modelo es el oráculo contra el que se compara la versión concurrente (SW1-03).

## ¿if o while?
type: multiple_choice
id: if-o-while
tiempo: 3

En la cola acotada del libro, un compañero cambia `mientras len(elementos) == 0 y no cerrada: esperar(no_vacia, m)` por `si len(elementos) == 0 y no cerrada: esperar(no_vacia, m)`. Hay dos consumidores y un productor. ¿Qué puede pasar?

### Opciones
- [x] Un consumidor despierta por el aviso del productor, pero otro consumidor saca el elemento antes de que el primero recupere el lock; el primero no vuelve a revisar y saca de una cola vacía.
- Nada: con el lock tomado, la condición no puede cambiar entre el aviso y el momento en que el consumidor despierto continúa.
- Sólo se vuelve más lenta, porque `if` evalúa la condición una vez en lugar de varias.
- Se produce un bloqueo mutuo entre los dos consumidores.
### Justificación
`esperar` suelta el lock mientras duerme y lo vuelve a pedir al despertar. Entre el aviso y la recuperación del lock, otro thread puede entrar y cambiar el estado, y además existen despertares sin aviso. Por eso la condición se revisa otra vez en un `while`. Con `if`, el consumidor continúa con una revisión vieja: es «revisar y luego actuar» otra vez. No es un tema de velocidad, y tampoco hay bloqueo mutuo: hay una operación sobre una cola vacía.

## El argumento de seguridad ante threads
type: production
id: produccion-seguridad-threads
tiempo: 12

Escribe el argumento de seguridad ante threads de la cola acotada del libro, como se lo presentarías a un revisor: qué estrategia usas, qué invariante proteges, qué variables protege el lock y por qué ningún thread queda dormido para siempre después de `cerrar()`.

### Modelo
*Estrategia:* sincronización con un solo lock `m` y dos variables de condición (`no_llena`, `no_vacia`); el estado no se comparte de ninguna otra forma.
*Invariante:* `0 ≤ len(elementos) ≤ cap`, y si `cerrada` es verdadero nunca vuelve a ser falso.
*Qué protege el lock:* `elementos` y `cerrada` sólo se leen y escriben con `m` tomado; ninguna referencia a `elementos` sale de la clase.
*Por qué se preserva el invariante:* `poner` agrega sólo tras ver `len < cap` con el lock tomado, y nada cambia entre esa revisión y la escritura; `sacar` quita sólo tras ver `len > 0`. Las esperas están en `while`, así que toda acción se basa en una revisión hecha con el lock en la mano.
*Progreso tras cerrar:* `cerrar()` pone `cerrada` y difunde en las dos variables; todo productor dormido despierta, ve `cerrada` y devuelve `"cerrada"`; todo consumidor dormido despierta, entrega lo que quede y, con la cola vacía y cerrada, devuelve `"cerrada"`. Ningún thread vuelve a dormir, porque las dos condiciones de espera exigen `no cerrada`.

### Regla
Un argumento de seguridad ante threads nombra la estrategia, el invariante, qué variables protege cada lock y por qué toda acción se basa en una revisión hecha con el lock tomado; si hay esperas, también por qué todo thread que espera termina despertando.

### Rúbrica
- Nombra una estrategia concreta (confinamiento, inmutabilidad, tipo seguro o sincronización) y la usa de forma consistente.
- Escribe el invariante y dice qué variables protege el lock.
- Explica por qué la revisión y la acción de `poner` y `sacar` son indivisibles.
- Justifica las esperas en `while`.
- Argumenta que nadie queda dormido después de `cerrar()`, distinguiendo productores y consumidores.

## Giro: el consumidor lento y el cierre con plazo

id: giro-cierre-con-plazo
rol: transferencia

La cola alimenta a un consumidor que tarda hasta 30 segundos por elemento (llama a un servicio externo). Producto pide que, al apagar el proceso, `cerrar()` haga que los productores dejen de esperar de inmediato, que los elementos ya aceptados no se pierdan y que el apagado completo no tarde más de 60 segundos. Rediseña el cierre: qué cambia en el contrato, qué se preserva, qué haces con los elementos que no alcanzan a procesarse y qué no debe ocurrir con el lock tomado.

### Rúbrica
- Mantiene que el lock nunca se sostiene durante la llamada lenta del consumidor (se saca el elemento con el lock y se procesa fuera).
- Separa dos fases explícitas, por ejemplo dejar de aceptar (los productores reciben `cerrada` de inmediato) y drenar con plazo.
- Decide qué pasa con los elementos no procesados al vencer el plazo (persistirlos, devolverlos al origen o registrarlos como pendientes) y no los descarta en silencio.
- Declara el cambio de contrato de `cerrar()` (por ejemplo, un plazo como parámetro y un resultado que dice cuántos quedaron pendientes).
- Propone una prueba con un consumidor lento simulado que demuestre el plazo y la ausencia de pérdidas.
