## ¿Hace falta el link de regreso?
type: prediccion
id: link-de-regreso
rol: prediccion
tiempo: 2

Definiste el tipo de link «orden asignada a técnica» entre OrdenTrabajo y Tecnica. Un compañero dice que, para poder ver desde una técnica todas sus órdenes, hay que crear un segundo tipo de link de Tecnica a OrdenTrabajo. Predice qué pasa si no lo creas.

### Opciones
- [x] Nada se pierde: un tipo de link es bidireccional, tiene dos lados y se recorre desde la técnica hacia sus órdenes con el mismo tipo de link.
- Desde la técnica no se pueden ver sus órdenes hasta que crees el link de regreso.
- La Ontology crea el link de regreso automáticamente como un segundo tipo de link.
- Hay que crear el link de regreso y además una propiedad lista con las órdenes en la técnica.
### Justificación
La documentación de tipos de link explica que cada tipo de link tiene dos lados, uno por cada tipo de objeto, y que se recorre en ambas direcciones; crear un tipo de link no crea un segundo tipo de link inverso, porque no hace falta. Un segundo tipo de link entre los mismos tipos de objeto representaría otra relación del mundo, no la dirección contraria.

### Solución
```javascript
function agrupar_identidades(registros, coincidencias) {
  const padre = new Map(registros.map((r) => [r, r]));
  const raiz = (x) => {
    while (padre.get(x) !== x) {
      padre.set(x, padre.get(padre.get(x)));
      x = padre.get(x);
    }
    return x;
  };
  for (const [a, b] of coincidencias) {
    const ra = raiz(a);
    const rb = raiz(b);
    if (ra !== rb) padre.set(ra, rb);
  }
  const grupos = new Map();
  for (const r of registros) {
    const k = raiz(r);
    if (!grupos.has(k)) grupos.set(k, []);
    grupos.get(k).push(r);
  }
  const out = [...grupos.values()].map((g) => g.sort());
  out.sort((g1, g2) => (g1[0] < g2[0] ? -1 : g1[0] > g2[0] ? 1 : 0));
  return out;
}
```
```python
def agrupar_identidades(registros, coincidencias):
    padre = {r: r for r in registros}
    def raiz(x):
        while padre[x] != x:
            padre[x] = padre[padre[x]]
            x = padre[x]
        return x
    for a, b in coincidencias:
        ra, rb = raiz(a), raiz(b)
        if ra != rb:
            padre[ra] = rb
    grupos = {}
    for r in registros:
        grupos.setdefault(raiz(r), []).append(r)
    return sorted((sorted(g) for g in grupos.values()), key=lambda g: g[0])
```

- Ordena cada grupo y después ordena los grupos por su primer elemento.

## Una relación con datos propios
type: multiple_choice
id: relacion-con-datos
tiempo: 2

Cada vez que una orden de trabajo interviene un activo hay que registrar la fecha y el resultado («ajustado», «reemplazado», «sin falla»). ¿Cómo lo modelas?

### Opciones
- [x] Con un objeto Intervención que tiene fecha y resultado y dos links N:1, uno a la orden y otro al activo.
- Con un link muchos a muchos entre orden y activo, y la fecha y el resultado como propiedades de la orden.
- Con una propiedad lista en la orden: `activos: "A-12:ajustado, A-14:reemplazado"`.
- Con un link muchos a muchos y un campo de texto libre en el activo con el historial.
### Justificación
Un link dice que dos cosas están relacionadas; si la relación tiene atributos que la decisión usa, esos atributos necesitan un lugar propio, y ese lugar es un objeto intermedio. Así el muchos a muchos conserva su historia y se puede recorrer desde la orden y desde el activo. Una propiedad lista o un texto libre no se pueden recorrer ni validar.

## Unir duplicados sin perder historia
type: multiple_choice
id: unir-sin-perder
tiempo: 2

Descubres que `mx-77` del sistema de mantenimiento y `rh-551` de recursos humanos son la misma técnica. Hay 40 órdenes cerradas con `mx-77`. ¿Qué diseño une las identidades sin perder historia y permite deshacerlo?

### Opciones
- [x] Una identidad canónica propia con dos alias (uno por registro de origen) que apuntan a ella, y la unión registrada con su evidencia; las órdenes siguen apuntando a su registro de origen.
- Reemplazar `mx-77` por `rh-551` en las 40 órdenes y borrar el registro `mx-77`.
- Usar el nombre normalizado como llave de la técnica, para que los dos registros coincidan solos.
- Dejar los dos registros como técnicas distintas y avisar a los usuarios que son la misma.
### Justificación
Sobrescribir llaves de origen destruye la historia y hace irreversible un error de unión. El nombre no es una llave (dos personas pueden llamarse igual). Dejar dos técnicas obliga a cada usuario a recordarlo. La identidad canónica con alias registrados conserva todo y se deshace moviendo un alias.

## Diseño de alias para activos
type: production
id: alias-activos
tiempo: 12

Los activos del hospital ficticio aparecen en el inventario (`inv-A12`), en el sistema de mantenimiento (`EQ-0012`) y en las etiquetas de los sensores (`SNS-12-B`). Además, cuando un equipo se reemplaza, el nuevo hereda la etiqueta del sensor. Diseña la identidad de Activo: llave canónica, objeto de alias con sus propiedades, cómo se registra una unión, cómo se deshace y cómo evitas que el reemplazo de un equipo funda dos activos distintos.

### Modelo
- **Llave canónica:** `activo_id` propio (por ejemplo `ACT-000123`), estable y sin significado; ninguna llave de origen se usa como canónica.
- **Alias:** objeto con `alias_id`, `sistema` (inventario, mantenimiento, sensores), `id_origen`, `vigente_desde`, `vigente_hasta`; link Alias → Activo N:1.
- **Unión:** acción que mueve un alias a un activo con evidencia requerida (número de serie, ubicación, fecha) y registra quién y cuándo.
- **Deshacer:** la misma acción hacia la identidad correcta; el registro anterior queda en el historial.
- **Reemplazo:** la etiqueta del sensor es un alias **con vigencia**: al reemplazar el equipo, se cierra la vigencia del alias en el activo viejo y se abre un alias nuevo en el activo nuevo. Así la etiqueta no funde dos equipos.
### Regla
La identidad se modela con una llave canónica propia y alias de origen con vigencia; unir y deshacer son operaciones registradas con evidencia; ninguna llave de origen se sobrescribe. Un identificador que se reutiliza en el tiempo se trata con vigencia, no como identidad permanente.
### Rúbrica
- Propone una llave canónica propia y alias con sistema e id de origen.
- Registra unión y deshacer con evidencia.
- Trata la etiqueta reutilizada con vigencia para no fundir dos equipos.
- Mantiene las intervenciones apuntando a su activo correcto en el tiempo.
