## Antes de leer: ¿qué número sube?
type: prediccion
id: prediccion-semver
rol: prediccion
tiempo: 2

Tu biblioteca está en la versión 2.3.1. Para simplificar, quitas un parámetro opcional de `reservar` que, según tus métricas, casi nadie usa. ¿Qué versión publicas?

### Opciones
- [x] 3.0.0, porque quitar algo de la API rompe a quien lo usa, aunque sean pocos.
- 2.4.0, porque es una mejora de la API.
- 2.3.2, porque el parámetro casi no se usaba.
- 2.3.1 otra vez, porque el comportamiento por omisión no cambia.
### Justificación
El versionado semántico clasifica el cambio por lo que le hace al contrato, no por cuántos lo notan. Quitar un parámetro hace que el código que lo pasa deje de funcionar: es un cambio que rompe, así que sube el número mayor. Que casi nadie lo use es un argumento para hacerlo, con guía de migración, no para esconderlo en una versión menor o de parche. Republicar el mismo número con otro contenido es lo peor: dos artefactos distintos con la misma identidad.

## La siguiente versión
type: code
id: codigo-siguiente-version
tiempo: 15

Implementa el cálculo de la siguiente versión semántica a partir de la versión actual y la lista de cambios de una entrega.

### Especificación
`siguienteVersion(actual, cambios)`:
- `actual` es una cadena `"MAYOR.MENOR.PARCHE"` de tres enteros no negativos sin ceros a la izquierda (`0` vale; `01` no). Si no cumple ese formato, devuelve `"error"`.
- `cambios` es una lista de tipos de cambio: `"rompe"`, `"agrega"`, `"corrige"` o `"docs"`. Si aparece otro tipo, devuelve `"error"`.
- Con `MAYOR ≥ 1`: si hay algún `"rompe"`, sube MAYOR y pone MENOR y PARCHE en 0; si no, y hay algún `"agrega"`, sube MENOR y pone PARCHE en 0; si no, y hay algún `"corrige"`, sube PARCHE.
- Con `MAYOR = 0` (desarrollo inicial, convención de esta biblioteca): `"rompe"` sube MENOR y pone PARCHE en 0; `"agrega"` o `"corrige"` suben PARCHE.
- `"docs"` no cambia la versión. Sin cambios, devuelve la misma versión.

### Solución
```javascript
function siguienteVersion(actual, cambios) {
  const m = /^(0|[1-9]\d*)\.(0|[1-9]\d*)\.(0|[1-9]\d*)$/.exec(actual);
  if (!m) return "error";
  const tipos = ["rompe", "agrega", "corrige", "docs"];
  if (cambios.some((c) => !tipos.includes(c))) return "error";
  let [mayor, menor, parche] = [Number(m[1]), Number(m[2]), Number(m[3])];
  const rompe = cambios.includes("rompe");
  const agrega = cambios.includes("agrega");
  const corrige = cambios.includes("corrige");
  if (mayor >= 1) {
    if (rompe) [mayor, menor, parche] = [mayor + 1, 0, 0];
    else if (agrega) [menor, parche] = [menor + 1, 0];
    else if (corrige) parche += 1;
  } else {
    if (rompe) [menor, parche] = [menor + 1, 0];
    else if (agrega || corrige) parche += 1;
  }
  return `${mayor}.${menor}.${parche}`;
}
```
```python
import re

def siguiente_version(actual, cambios):
    m = re.fullmatch(r"(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)", actual)
    if not m:
        return "error"
    tipos = {"rompe", "agrega", "corrige", "docs"}
    if any(c not in tipos for c in cambios):
        return "error"
    mayor, menor, parche = int(m.group(1)), int(m.group(2)), int(m.group(3))
    rompe = "rompe" in cambios
    agrega = "agrega" in cambios
    corrige = "corrige" in cambios
    if mayor >= 1:
        if rompe:
            mayor, menor, parche = mayor + 1, 0, 0
        elif agrega:
            menor, parche = menor + 1, 0
        elif corrige:
            parche += 1
    else:
        if rompe:
            menor, parche = menor + 1, 0
        elif agrega or corrige:
            parche += 1
    return f"{mayor}.{menor}.{parche}"
```

### Pistas
- Valida el formato completo antes de calcular: `"1.2"`, `"1.02.3"` y `"v1.2.3"` no son versiones.
- Gana el cambio de mayor impacto de la lista; varios del mismo tipo suben el número una sola vez.
- La regla para `MAYOR = 0` es distinta y está escrita en la especificación: léela otra vez antes de programarla.

## La comparación de versiones como texto

### Firma

### Precondición
```javascript
function pre(instalada, minima) {
  const ok = (v) => typeof v === "string" && /^[1-9]\d{0,2}\.(0|[1-9]\d{0,2})\.(0|[1-9]\d{0,2})$/.test(v);
  return ok(instalada) && ok(minima);
}
```

### Casi correcta
```javascript
function satisface(instalada, minima) {
  return instalada.split(".")[0] === minima.split(".")[0] && instalada >= minima;
}
```

### Referencia
```javascript
function satisface(instalada, minima) {
  const a = instalada.split(".").map(Number);
  const b = minima.split(".").map(Number);
  if (a[0] !== b[0]) return false;
  if (a[1] !== b[1]) return a[1] > b[1];
  return a[2] >= b[2];
}
```

## El mensaje que se volvió contrato
type: multiple_choice
id: errores-estables
tiempo: 3

Tu biblioteca lanza `Error("La sala ya está ocupada de 10:00 a 11:00 (traslape)")`. Descubres que tres equipos detectan el traslape buscando la palabra «ocupada» en el mensaje. Quieres mejorar la redacción. ¿Qué haces?

### Opciones
- [x] Agregar un código estable y datos estructurados al error (`codigo: "traslape"`, `inicio`, `fin`), documentar que el mensaje es texto para humanos sin formato garantizado, avisar a los tres equipos y cambiar la redacción sólo en una versión mayor con guía de migración.
- Cambiar la redacción en una versión de parche: el mensaje no es parte de la API porque no está en la firma de la función.
- No cambiarla nunca: una vez publicado, todo mensaje es permanente.
- Cambiarla y pedir a los tres equipos que actualicen su búsqueda de texto.
### Justificación
Los consumidores sólo podían decidir leyendo el texto, así que el texto se volvió parte del contrato aunque nadie lo haya decidido. La salida es darles una forma estable de decidir (el código y los datos), declarar el mensaje como no garantizado y, como el cambio rompe a quien depende del texto, publicarlo como versión mayor con migración. Tratarlo como parche ignora el uso real. Congelar los mensajes para siempre impide mejorar y no corrige la causa. Pedir otra búsqueda de texto repite el mismo error.

## Lo que decides no abstraer
type: multiple_choice
id: no-abstraer
tiempo: 3

`agenda-core` sólo reserva salas de un día. Un compañero propone generalizarla ya a «cualquier recurso, en cualquier rango de fechas, con reglas configurables», porque «algún día alguien lo va a pedir». Hoy hay un solo consumidor. ¿Cuál es la mejor respuesta?

### Opciones
- [x] Mantener el alcance, declararlo en el README («sólo salas de un día») y generalizar cuando haya tres usos reales distintos que muestren qué varía; una extensión compatible se puede publicar después como versión menor.
- Generalizar ahora: es más barato diseñar lo general desde el principio que cambiarlo después.
- Generalizar sólo los nombres (`recurso` en lugar de `sala`) para estar listos, sin cambiar el comportamiento.
- Rechazar cualquier extensión futura para mantener la biblioteca simple para siempre.
### Justificación
Con un solo consumidor no hay evidencia de qué va a variar, así que toda generalización es una apuesta que agrega superficie, combinaciones que probar y soporte. Declarar el alcance evita que alguien suponga lo que no existe, y una operación o un tipo nuevo se pueden agregar sin romper, como versión menor, cuando haya usos reales. Cambiar sólo los nombres promete una generalidad que el código no tiene. Cerrarse para siempre es la decisión opuesta, igual de poco fundada.

## La guía de migración a 2.0.0
type: production
id: produccion-guia-migracion
tiempo: 12

Escribe la guía de migración de `agenda-core` de 1.x a 2.0.0 para el cambio del libro: el código `traslape` se divide en `traslape-reserva` y `traslape-bloqueo`. Incluye qué cambió, por qué, qué debe hacer cada consumidor según cómo use hoy el error, cuánto tiempo recibe soporte la 1.x y cómo comprueba el consumidor que migró bien.

### Modelo
*Qué cambió:* el error `traslape` ya no existe; en su lugar hay `traslape-reserva` (choca con otra reserva) y `traslape-bloqueo` (choca con un bloqueo de mantenimiento). El resto de la API no cambia.
*Por qué:* el producto necesita mostrar mensajes y acciones distintas en cada caso; con un solo código, los consumidores no podían distinguirlos sin leer el mensaje.
*Qué hacer:* si manejabas `traslape`, maneja los dos códigos nuevos (o los dos con la misma rama si no te importa la diferencia). Si desde la 1.2.0 ya leías el campo `motivo`, el cambio es mecánico: `motivo: "reserva"` pasa a `traslape-reserva` y `motivo: "bloqueo"` a `traslape-bloqueo`.
*Soporte:* la 1.x recibe correcciones de seguridad durante seis meses desde la publicación de la 2.0.0.
*Comprobación:* los ejemplos de `ejemplos/manejar-traslape` muestran los dos casos; ejecuta tus pruebas contra la 2.0.0 con una agenda que tenga una reserva y un bloqueo, y verifica que tu código distingue los dos códigos.

### Regla
Una versión mayor se publica con una guía que dice qué cambió, por qué, qué tiene que hacer cada tipo de consumidor, cuánto dura el soporte de la versión anterior y cómo se comprueba la migración.

### Rúbrica
- Nombra exactamente qué se quitó y qué lo reemplaza.
- Explica el motivo en términos del consumidor, no de la implementación.
- Da instrucciones distintas según cómo use hoy el consumidor el error, incluido quien ya leía `motivo`.
- Declara un periodo de soporte de la versión anterior.
- Incluye una forma concreta de comprobar la migración (un ejemplo o una prueba).
