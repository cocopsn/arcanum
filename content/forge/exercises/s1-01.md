# S1-01 · Modelo relacional y dominio

Banco de la celda: predecir qué rompe una llave mal elegida, resolver identidad entre dos sistemas con SQL comprobado en tu dispositivo, separar registro de objeto y transferir el modelo a una fusión de clínicas. Los datos son sintéticos.

## Una cita que se mueve de hora
type: prediccion
id: s1-01-pred-hora-llave
rol: prediccion
escala: 50 70 90

La tabla `cita` usa como llave primaria `(paciente_id, inicio)`. Recepción reprograma la cita de Ana de las 09:00 a las 11:00 con un `UPDATE` sobre `inicio`. Antes de leer la justificación, predice qué pasa con la identidad de esa cita y con tu confianza.

### Opciones
- [x] La base acepta el cambio, pero la identidad de la cita cambió: toda referencia guardada fuera con la llave vieja (un recordatorio enviado, una línea de facturación) ya no la encuentra, y un segundo estudio de Ana a las 11:00 ese día chocaría con ella.
- Nada relevante: una llave compuesta se actualiza en cascada en todos los sistemas que la usan.
- La base rechaza el `UPDATE` porque una llave primaria nunca se puede modificar.
- Queda igual que con `cita_id`, porque la combinación paciente y hora es única de todos modos.
### Justificación
La hora describe la cita; no la identifica. Si forma parte de la llave, mover la cita es, para cualquier consumidor externo, borrar una y crear otra. La cascada sólo existe dentro de la misma base y sólo si se declaró; los sistemas de recordatorios o facturación guardan copias de la llave y no se enteran. SQL sí permite actualizar una llave primaria (no hay prohibición general), y la combinación paciente-hora deja de ser única en cuanto un paciente tiene dos estudios el mismo día. Una llave emitida por la agenda (`cita_id`) sobrevive a la reprogramación.

## ¿DISTINCT arregla los homónimos?
type: prediccion
id: s1-01-pred-distinct
rol: prediccion

El reporte de agenda une pacientes por nombre y cada cita de un homónimo sale dos veces. Un compañero propone `SELECT DISTINCT` para «quitar los duplicados». ¿Qué predices?

### Opciones
- [x] Oculta el síntoma y crea una falla nueva: elimina las filas repetidas idénticas, pero sigue atribuyendo citas al paciente equivocado y fusionaría dos citas reales que coincidan en todas las columnas mostradas.
- Lo resuelve, porque cada fila duplicada es una copia exacta y `DISTINCT` deja una por cita.
- Lo resuelve sólo si además se ordena por nombre.
- No cambia nada, porque `DISTINCT` no actúa sobre resultados de un `JOIN`.
### Justificación
El join por nombre produce filas **distintas** para cada homónimo (con el nacimiento o el id del otro paciente), así que `DISTINCT` no siempre las colapsa y, cuando lo hace, es porque las columnas visibles no bastan para distinguir hechos distintos. El problema es de identidad: dos personas compartieron llave. `DISTINCT` sí actúa sobre el resultado de un join y el orden no cambia qué filas son iguales. La corrección es unir por `paciente_id`.

## Resolver identidad al importar órdenes
type: sql
id: s1-01-sql-resolver-identidad
orden: no

El sistema anterior exportó `orden_importada` sin `paciente_id`: sólo trae nombre y fecha de nacimiento. Escribe una consulta que devuelva `orden_id` y `paciente_id` **sólo** para las órdenes importadas que corresponden a exactamente un paciente con el mismo nombre y la misma fecha de nacimiento. Las órdenes sin correspondencia, o con más de una, no deben aparecer: se revisan a mano. Dos columnas: `orden_id`, `paciente_id`.

### Esquema
```sql
CREATE TABLE paciente (
  paciente_id TEXT PRIMARY KEY,
  nombre      TEXT NOT NULL,
  nacimiento  TEXT NOT NULL
);
CREATE TABLE orden_importada (
  orden_id        TEXT PRIMARY KEY,
  paciente_nombre TEXT NOT NULL,
  nacimiento      TEXT NOT NULL,
  estudio         TEXT NOT NULL
);
```
### Datos
```sql
INSERT INTO paciente VALUES
  ('P-001', 'Ana López', '1990-03-14'),
  ('P-002', 'Luis Pérez', '1985-07-02'),
  ('P-003', 'Marta Ruiz', '1979-11-23');
INSERT INTO orden_importada VALUES
  ('L-1', 'Ana López', '1990-03-14', 'RM hombro'),
  ('L-2', 'Marta Ruiz', '1979-11-23', 'TC cráneo'),
  ('L-3', 'Pedro Gil', '2001-01-30', 'RM rodilla');
```
### Fixtures
```sql
-- fixture: base
UPDATE paciente SET nombre = nombre WHERE paciente_id = 'P-001';
```
```sql
-- fixture: homonimo-con-otra-fecha
INSERT INTO paciente VALUES ('P-004', 'Ana López', '1994-08-09');
```
```sql
-- fixture: homonimo-total
INSERT INTO paciente VALUES ('P-005', 'Marta Ruiz', '1979-11-23');
```
### Solución
```sql
SELECT i.orden_id, MIN(p.paciente_id) AS paciente_id
FROM orden_importada i
JOIN paciente p
  ON p.nombre = i.paciente_nombre AND p.nacimiento = i.nacimiento
GROUP BY i.orden_id
HAVING COUNT(*) = 1
```
### Ingenua
```sql
SELECT i.orden_id, p.paciente_id
FROM orden_importada i
JOIN paciente p ON p.nombre = i.paciente_nombre
```

## Órdenes pendientes de agendar
type: sql
id: s1-01-sql-pendientes
orden: no

Una orden está **pendiente de agendar** si no tiene ninguna cita en estado `agendada` o `atendida` (puede no tener citas, o tener sólo canceladas). Devuelve una fila por orden pendiente, con una columna: `orden_id`. Ojo: la condición es sobre la orden completa, no sobre cada fila de cita.

### Esquema
```sql
CREATE TABLE orden_estudio (
  orden_id    TEXT PRIMARY KEY,
  paciente_id TEXT NOT NULL,
  estudio     TEXT NOT NULL
);
CREATE TABLE cita (
  cita_id   TEXT PRIMARY KEY,
  orden_id  TEXT NOT NULL REFERENCES orden_estudio(orden_id),
  equipo_id TEXT NOT NULL,
  inicio    TEXT NOT NULL,
  estado    TEXT NOT NULL CHECK (estado IN ('agendada', 'atendida', 'cancelada'))
);
```
### Datos
```sql
INSERT INTO orden_estudio VALUES
  ('O-10', 'P-001', 'RM rodilla'),
  ('O-11', 'P-002', 'TC tórax'),
  ('O-12', 'P-003', 'RM columna'),
  ('O-13', 'P-001', 'TC abdomen');
INSERT INTO cita VALUES
  ('C-100', 'O-10', 'RM-2', '2026-11-10T09:00', 'agendada'),
  ('C-101', 'O-11', 'TC-1', '2026-11-10T10:00', 'atendida');
```
### Fixtures
```sql
-- fixture: base
UPDATE cita SET estado = estado WHERE cita_id = 'C-100';
```
```sql
-- fixture: reprogramada
INSERT INTO cita VALUES
  ('C-102', 'O-12', 'RM-2', '2026-11-11T08:00', 'cancelada'),
  ('C-103', 'O-12', 'RM-2', '2026-11-12T08:00', 'agendada');
```
```sql
-- fixture: dos-canceladas
INSERT INTO cita VALUES
  ('C-104', 'O-13', 'TC-1', '2026-11-11T12:00', 'cancelada'),
  ('C-105', 'O-13', 'TC-1', '2026-11-12T12:00', 'cancelada');
```
### Solución
```sql
SELECT o.orden_id
FROM orden_estudio o
WHERE NOT EXISTS (
  SELECT 1 FROM cita c
  WHERE c.orden_id = o.orden_id AND c.estado IN ('agendada', 'atendida')
)
```
### Ingenua
```sql
SELECT o.orden_id
FROM orden_estudio o
LEFT JOIN cita c ON c.orden_id = o.orden_id
WHERE c.cita_id IS NULL OR c.estado = 'cancelada'
```

## Dos «órdenes» en la misma clínica
type: multiple_choice
id: s1-01-choice-orden
rol: recuperacion

Sin volver al libro: en la clínica, radiología llama «orden» a lo que pide un médico y biomédica llama «orden» a lo que se abre cuando un equipo falla. Hoy viven en la misma tabla `orden` con una columna `tipo`. ¿Cuál es el mejor modelo?

### Opciones
- [x] Dos entidades, `OrdenEstudio` y `OrdenMantenimiento`, cada una con su llave y su ciclo de vida; si alguien necesita la lista conjunta, se construye una vista encima.
- Una sola tabla `orden` con `tipo`, porque comparten la palabra y así hay menos tablas.
- Una sola tabla con todas las columnas de ambas, dejando en `NULL` las que no aplican.
- Una tabla por sede, porque las órdenes se atienden por sede.
### Justificación
La prueba es el ciclo de vida: una nace cuando un médico pide un estudio y termina cuando se informa; la otra nace con una falla y termina con la reparación. Tienen estados, responsables y reglas distintos. Juntarlas obliga a llenar columnas de una con `NULL` en la otra y a que cada regla empiece con «si `tipo` es…». Compartir la palabra no es compartir identidad. La sede es un atributo, no una entidad.

## Registro de agenda frente a objeto Cita
type: production
id: s1-01-prod-registro-objeto

El sistema de agenda exporta `agenda_eventos(evento_id, cita_id, tipo, inicio, registrado_en)`, con una fila por creación, reprogramación o cancelación. Explica en un párrafo por qué esa tabla no es el objeto operacional `Cita`, cómo construirías `Cita` a partir de ella y qué decisión del operador necesita cada una.

### Modelo
`agenda_eventos` es un registro: guarda cada cambio con su propia llave (`evento_id`) y sirve para auditar qué pasó y cuándo. El operador no decide sobre eventos: decide sobre citas («¿confirmo la de mañana?», «¿muevo la del RM-2?»). `Cita` se construye tomando, por cada `cita_id`, el último evento según `registrado_en` (y marcándola cancelada si ese evento es una cancelación). Su llave es `cita_id`, no `evento_id`. El registro responde «¿quién la movió?»; el objeto responde «¿qué hay agendado?».
### Regla
Separa el esquema de almacenamiento del modelo operacional: un registro de cambios se audita, un objeto se decide. La llave del objeto es la de la cosa del mundo, no la de la fila que la menciona.
### Rúbrica
- Distingue registro (cambios) de objeto (estado actual de la cosa).
- Construye `Cita` como la última versión por `cita_id`, con un criterio de orden explícito.
- Nombra la llave de cada uno y por qué son distintas.
- Asocia cada estructura a una decisión o pregunta del operador.

## Una orden, una cita… por ahora
type: prediccion
id: s1-01-pred-cardinalidad
rol: recuperacion

En los datos de hoy, cada orden de estudio tiene exactamente una cita. Un compañero propone declarar la relación orden→cita como 1:1 y guardar la cita dentro de la orden. Sin volver al libro, predice qué pasa cuando un estudio se repite porque el paciente se movió.

### Opciones
- [x] El modelo no tiene dónde poner la segunda cita: hay que sobrescribir la primera (y perder su historia) o cambiar el esquema en caliente; la cardinalidad debió declararse 1:N por la regla del negocio, no por los datos de hoy.
- Nada: una relación 1:1 admite una segunda fila si la primera se cancela.
- La base crea sola una segunda orden para la cita repetida.
- Sólo cambia el reporte, porque la cardinalidad no afecta al almacenamiento.
### Justificación
La cardinalidad se declara a partir de lo que el negocio permite, no de lo que los datos muestran hoy. Repetir un estudio es una operación normal de la clínica, así que una orden puede necesitar varias citas: 1:N. Con 1:1, la segunda cita no cabe sin destruir la primera o rehacer el esquema. Una base no crea órdenes por su cuenta, y la cardinalidad sí decide dónde y cómo se guarda cada hecho.

## Giro: dos clínicas, dos identificadores
