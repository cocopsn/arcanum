## Antes de leer: el recorrido que vacía la caché
type: prediccion
id: prediccion-inundacion
rol: prediccion
tiempo: 2

Un buffer pool de 1,000 marcos con política LRU tiene en memoria las 200 páginas de un índice que todas las consultas usan. Llega una consulta que recorre una tabla de 50,000 páginas, cada una una sola vez. ¿Qué pasa con las páginas del índice?

### Opciones
- [x] Salen del pool: el recorrido trae 50,000 páginas «recientes» que expulsan a todas las demás, aunque no se vuelvan a usar; después, las consultas normales vuelven a leer el índice del disco.
- Se quedan, porque LRU reconoce que se usan con frecuencia.
- Se quedan, porque el recorrido usa marcos aparte.
- El recorrido falla, porque no cabe en el pool.
### Justificación
LRU sólo mira el último acceso. Cada página del recorrido es, al llegar, la más reciente, así que las páginas del índice, aunque se usen muy seguido, acaban siendo las menos recientes y salen. Es la inundación secuencial. LRU no guarda frecuencia; para eso existen políticas como LRU-K, que ven que cada página del recorrido tuvo un solo acceso. Un recorrido no necesita caber en el pool: pasa página por página.

## Simula LRU-K
type: code
id: codigo-lru-k
tiempo: 20

Implementa la política de reemplazo LRU-K de un buffer pool, con las reglas de desempate escritas abajo, y devuelve las páginas expulsadas en orden.

### Especificación
`lruk(capacidad, k, accesos)`:
- `capacidad ≥ 1` marcos; `k ≥ 1`; `accesos` es la lista de páginas pedidas (enteros). El instante de cada acceso es su posición en la lista (0, 1, 2…). Ninguna página queda fijada entre accesos.
- Cada página en el pool guarda el historial de sus instantes de acceso desde que entró. Si se pide una página que está en el pool, se agrega el instante a su historial.
- Si se pide una página que no está y el pool está lleno, se expulsa una víctima: la de mayor **distancia k**, que es `ahora − (instante de su k-ésimo acceso más reciente)`. Una página con menos de `k` accesos tiene distancia **infinita**.
- Si varias tienen distancia infinita, sale la que tiene el acceso registrado más antiguo (el primero de su historial).
- Al expulsar una página se borra su historial; si vuelve, empieza de cero.
- Devuelve la lista de páginas expulsadas, en orden.

### Solución
```javascript
function lruk(capacidad, k, accesos) {
  const historial = new Map();
  const expulsadas = [];
  accesos.forEach((pagina, ahora) => {
    if (!historial.has(pagina)) {
      if (historial.size >= capacidad) {
        let victima = null;
        let mejor = null;
        for (const [p, h] of historial) {
          const clave = h.length < k ? [1, -h[0]] : [0, ahora - h[h.length - k]];
          if (mejor === null || clave[0] > mejor[0] || (clave[0] === mejor[0] && clave[1] > mejor[1])) {
            mejor = clave;
            victima = p;
          }
        }
        historial.delete(victima);
        expulsadas.push(victima);
      }
      historial.set(pagina, []);
    }
    historial.get(pagina).push(ahora);
  });
  return expulsadas;
}
```
```python
def lruk(capacidad, k, accesos):
    historial = {}
    expulsadas = []
    for ahora, pagina in enumerate(accesos):
        if pagina not in historial:
            if len(historial) >= capacidad:
                victima = None
                mejor = None
                for p, h in historial.items():
                    clave = (1, -h[0]) if len(h) < k else (0, ahora - h[len(h) - k])
                    if mejor is None or clave > mejor:
                        mejor = clave
                        victima = p
                del historial[victima]
                expulsadas.append(victima)
            historial[pagina] = []
        historial[pagina].append(ahora)
    return expulsadas
```

### Pistas
- Con `k = 1`, LRU-K es LRU: la distancia es el tiempo desde el último acceso.
- Una página con menos de `k` accesos siempre gana a una con distancia finita como víctima.
- Entre dos páginas con distancia infinita, sale la que entró hace más tiempo según su primer acceso registrado.

## La página fijada
type: multiple_choice
id: pagina-fijada
tiempo: 3

Un pool de 3 marcos tiene las páginas 4, 7 y 9, las tres fijadas por consultas en curso. Llega un pedido de la página 12. ¿Qué debe hacer el pool?

### Opciones
- [x] No expulsar ninguna y devolver un fallo explícito (o hacer esperar al pedido hasta que alguna se suelte), porque expulsar una página fijada dejaría a su usuario leyendo memoria que ya contiene otra página.
- Expulsar la menos reciente, porque la política de reemplazo manda sobre la fijación.
- Expulsar la que tenga menos fijaciones, porque es la que menos daño hace.
- Leer la página 12 en un marco nuevo fuera del pool.
### Justificación
Fijar una página es la promesa de que su marco no cambiará mientras alguien la usa; romperla convierte un puntero válido en uno que apunta a otra página, sin ningún error visible. Ninguna política de reemplazo puede elegir entre páginas fijadas, tengan una o diez fijaciones. Salirse del pool rompe el límite de memoria que el pool existe para respetar. Lo honesto es fallar o esperar, y que quien llama lo maneje.

## La página sucia que sale
type: trace
id: traza-pagina-sucia
tiempo: 3

La página 9 se modificó en memoria y se soltó marcándola como sucia. Después se vuelve la víctima de una expulsión para cargar la página 12. ¿En qué orden deben ocurrir las cosas?

### Opciones
- [x] Escribir la página 9 al disco, después reutilizar el marco leyendo la página 12 y actualizar la tabla de páginas para que la 12 apunte a ese marco y la 9 ya no esté.
- Leer la página 12 en el marco y después escribir el marco al disco como página 9.
- Reutilizar el marco y marcar la página 9 para escribirla más tarde, cuando el disco esté libre.
- Descartar los cambios de la 9, porque al soltarla ya se dio por terminada.
### Justificación
Mientras la 9 esté sucia, el marco es la única copia de sus cambios. Si se sobrescribe antes de escribirla, los cambios se pierden; si se escribe el marco después de cargar la 12, se escribe la 12 con el nombre de la 9. Dejarla «para más tarde» es imposible: el marco ya tiene otra página. Soltar una página no la guarda; sólo dice que ya no se usa y si cambió.

## Un límite que las pruebas no prueban
type: production
id: produccion-limite-pruebas
tiempo: 12

La defensa de esta celda pide mostrar las pruebas de la edición y un límite que esas pruebas no cubren. Elige un límite concreto del buffer pool (de concurrencia, de reemplazo o de persistencia), explica por qué las pruebas habituales no lo ejercitan y describe una prueba propia, pequeña y determinista, que lo demostraría.

### Modelo
*Límite elegido:* entrada y salida de disco hecha con el latch global tomado. Las pruebas funcionales verifican que las páginas correctas estén en memoria y que las sucias se escriban, pero con un disco simulado instantáneo nunca miden que un thread con su página ya en memoria espere a otro que está leyendo del disco.
*Por qué escapa:* el resultado es correcto; lo que falla es la concurrencia, y sólo se nota con un disco lento y varios threads.
*Prueba propia:* un disco simulado cuya lectura de la página 50 se bloquea hasta que la prueba la libera. Thread A pide la 50 (se queda esperando en el disco). Thread B pide la página 3, que ya está en el pool. La prueba exige que B obtenga su página antes de liberar la lectura de A. Con el latch global tomado durante la lectura, B se bloquea y la prueba falla por tiempo; con la carga fuera del latch, pasa.
*Lo que sigue sin cubrir:* el rendimiento bajo contención real con muchos threads, que se mide con una carga, no con una prueba unitaria.

### Regla
Una defensa honesta muestra qué prueban las pruebas existentes y nombra un límite que no prueban, con una prueba propia pequeña y determinista que lo haría visible, y declara lo que todavía queda sin cubrir.

### Rúbrica
- Nombra un límite concreto, no una categoría vaga.
- Explica por qué las pruebas habituales no lo ejercitan.
- La prueba propuesta es determinista (controla el disco o el orden de los threads) y no depende de tiempos al azar.
- La prueba distingue la implementación correcta de la incorrecta.
- Declara lo que sigue sin cubrir.

El mismo pool ahora atiende dos cargas a la vez: reportes nocturnos que recorren tablas enteras y consultas puntuales de la app que usan siempre las mismas páginas de índice.
