# F0-05 · Banco de evaluación

Banco anclado al libro `forge-f0-05`. El ejercicio de mutantes corre en tu dispositivo: escribes casos, la referencia los valida y cada mutante muere si alguno de tus casos válidos lo hace fallar. Las opciones se comprueban localmente; misión y defensa se comparan con un modelo y una rúbrica. Datos sintéticos.

## Predicción: cien por ciento de cobertura
type: prediccion
id: prediccion-cobertura
rol: prediccion
Una suite alcanza 100 % de cobertura de líneas sobre la función `seTraslapan`. Antes de mirar las pruebas, ¿qué puedes afirmar?
### Opciones
- Que la función no tiene bugs.
- Que todo cambio pequeño en la función haría fallar alguna prueba.
- [x] Sólo que cada línea se ejecutó al menos una vez durante las pruebas.
- Que las pruebas cubren todos los bordes, como citas contiguas.
### Justificación
La cobertura mide ejecución, no verificación: una prueba que llama a la función sin comparar el resultado suma cobertura y no detecta nada. Por eso dos funciones distintas, una correcta y otra con `<=` en lugar de `<`, pueden tener la misma cobertura con la misma suite. Para saber si la suite detecta errores pequeños hay que sembrarlos (mutantes) y ver si alguna prueba falla.

## Mata a los mutantes del traslape
type: mutantes
id: mutantes-traslape
minimo: 4
La función `seTraslapan(ai, af, bi, bf)` decide si dos citas del mismo consultorio se empalman. Hay cinco versiones con un error sembrado que no ves. Escribe casos de prueba que maten al menos 4, incluidos los dos críticos. Un caso cuyo valor esperado no coincide con la referencia se rechaza como «expectativa errónea» y no cuenta.
### Firma
```javascript
function seTraslapan(ai, af, bi, bf) {
}
```
### Referencia
```javascript
function seTraslapan(ai, af, bi, bf) {
  return ai < bf && bi < af;
}
```
### Mutantes
#### m-bordes-cerrados · crítico
```javascript
function seTraslapan(ai, af, bi, bf) {
  return ai <= bf && bi <= af;
}
```
#### m-un-solo-lado · crítico
```javascript
function seTraslapan(ai, af, bi, bf) {
  return ai < bf;
}
```
#### m-solo-contencion
```javascript
function seTraslapan(ai, af, bi, bf) {
  return (ai >= bi && af <= bf) || (bi >= ai && bf <= af);
}
```
#### m-valida-en-vez-de-cruzar
```javascript
function seTraslapan(ai, af, bi, bf) {
  return ai < af && bi < bf;
}
```
#### m-corrimiento-de-un-minuto
```javascript
function seTraslapan(ai, af, bi, bf) {
  return ai < bf - 1 && bi < af - 1;
}
```
### Casos dorados
```json
[
  {"input": [600, 660, 660, 720], "expected": false},
  {"input": [600, 660, 700, 760], "expected": false},
  {"input": [700, 760, 600, 650], "expected": false},
  {"input": [600, 660, 630, 700], "expected": true},
  {"input": [600, 720, 630, 660], "expected": true},
  {"input": [600, 660, 659, 720], "expected": true}
]
```
### Formato de casos
Cada caso es `{ "input": [ai, af, bi, bf], "expected": true o false }`. Los cuatro números son minutos desde la medianoche, enteros, con `0 ≤ inicio < fin ≤ 1440`. Los intervalos son semiabiertos `[inicio, fin)`: una cita que termina a las 11:00 (660) no se empalma con otra que empieza a las 11:00. Puedes escribir hasta 50 casos.

## Bisect, sin calculadora
type: multiple_choice
id: bisect-pasos
Entre la última versión buena y la primera mala hay 64 commits. Usas `git bisect` y cada prueba te dice si un commit es bueno o malo. ¿Cuántas pruebas necesitas como máximo para encontrar el commit que introdujo el bug?
### Opciones
- 64, una por commit.
- 32, la mitad.
- [x] 6, porque cada prueba descarta la mitad de los candidatos.
- 1, porque bisect compara la primera y la última versión.
### Justificación
`git bisect` hace búsqueda binaria sobre el historial: cada respuesta (bueno o malo) parte el rango a la mitad. Con 64 candidatos, 2⁶ = 64, así que bastan 6 pruebas. Esto sólo funciona si la prueba es confiable y el bug se reproduce siempre igual; con un bug intermitente, bisect puede señalar el commit equivocado.

## Por qué verla fallar, sin mirar
type: multiple_choice
id: recuperar-ver-fallar
rol: recuperacion
Sin volver al libro: escribiste una prueba para el bug de citas contiguas y pasa en verde a la primera, antes de corregir nada. ¿Qué significa?
### Opciones
- Que el bug ya estaba corregido y puedes cerrar el reporte.
- [x] Que la prueba no reproduce el bug: compara mal, no llega a la línea o no usa el caso que falla, y hay que revisarla antes de corregir.
- Que la suite es buena, porque detecta el caso.
- Que hay que borrar la prueba porque no aporta nada.
### Justificación
Una prueba de un bug debe fallar con el código que tiene el bug, y por la razón correcta. Si pasa antes de corregir, no está midiendo el bug. Puede que el reporte esté mal y no haya bug, pero eso se demuestra reproduciendo el caso del reporte, no con una prueba verde que nunca falló.

## Misión: corrección mínima con revisión
type: production
id: mision-correccion-minima
Toma un bug real de un proyecto tuyo (o el de citas contiguas). Entrega: el caso que lo reproduce, la salida de la prueba fallando con su mensaje, el diff mínimo de la corrección, la salida con todo en verde y una revisión de cambios de cinco líneas que responda las cuatro preguntas del libro.
### Modelo
Caso: `seTraslapan(600, 660, 660, 720)` debe ser `false`. Falla antes: «citas contiguas se marcaron como traslapadas: esperado false, obtenido true». Diff: una línea, `<=` → `<` en las dos comparaciones. Después: 7 pruebas en verde. Revisión: (1) la prueba nueva falla sin la corrección, verificado; (2) el diff toca una sola línea; (3) el reporte de ocupación contaba contiguas como conflicto y su cifra va a bajar, aviso a quien lo usa; (4) no se probó el cruce de medianoche, queda como pendiente; (5) mensaje del commit: «fix: citas contiguas no se traslapan (intervalos semiabiertos)».
### Regla
La corrección empieza con un caso que falla por la razón correcta, cambia lo mínimo y termina con una revisión que nombra el efecto en otros llamadores y lo que no se probó.
### Rúbrica
- Hay un caso mínimo que reproduce el bug.
- Se muestra la prueba fallando antes de corregir, con un mensaje que nombra el bug.
- El diff es mínimo y no mezcla otros cambios.
- Se muestra todo en verde después.
- La revisión responde las cuatro preguntas (falla sin la corrección, diff chico, otros llamadores, lo no probado).

## Defensa: por qué tu prueba detecta el bug
type: production
id: defensa-por-que-detecta
Explica por qué tu prueba detecta el bug y no sólo pasa. Señala qué mutante de la función mataría y uno que no mataría, y qué caso agregarías para matarlo.
### Modelo
«Mi caso usa dos citas contiguas, que es exactamente el borde donde `<=` y `<` difieren; con `<=` el resultado es `true` y la prueba exige `false`, así que falla por la razón del reporte. Mataría al mutante de bordes cerrados. No mataría al que sólo detecta contención (una cita dentro de la otra), porque con citas contiguas también da `false`; para matarlo agrego un traslape parcial, `[600, 660, 630, 700]`, que espera `true` y ese mutante da `false`.»
### Regla
Una prueba detecta un bug cuando ejercita el borde donde la versión correcta y la defectuosa difieren. Defenderla es nombrar ese borde y los errores que todavía no mira.
### Rúbrica
- Nombra el borde exacto que el caso ejercita.
- Explica por qué la versión defectuosa da otro resultado en ese borde.
- Identifica un mutante que su suite no mata.
- Propone un caso concreto que lo mataría, con su valor esperado.

## Giro: citas que cruzan la medianoche

id: giro-medianoche
rol: transferencia
