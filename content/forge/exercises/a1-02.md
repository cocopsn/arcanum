# A1-02 · Arrays, hashing y dos punteros

Banco ligero de la ruta A1. La misión: deduplicar y conciliar eventos sin perder multiplicidades, y distinguir identidad de
igualdad. La teoría de tablas hash está en ITC C3 y la de dos punteros en CP1.

## Antes de leer: el set que deduplica ventas
type: prediccion
id: a1-02-pred-set
rol: prediccion

Llegan tres registros: (e1, SKU-A, 2), (e2, SKU-A, 2) y otra vez (e2, SKU-A, 2) por un reintento de red. El pipeline
deduplica metiendo las tuplas (sku, unidades) en un set y luego suma. ¿Cuántas unidades de SKU-A reporta?

### Opciones
- [x] 2
- 4
- 6
- 0, porque el set descarta todo lo repetido

### Justificación
El set compara por igualdad de contenido: las tres tuplas son (SKU-A, 2) y queda una sola, así que reporta 2. La verdad
son 4, porque e1 y e2 son dos ventas y sólo el tercer registro es un reintento. 6 sería no deduplicar nada, y el set nunca
deja el conjunto vacío si hubo al menos un elemento.

## Faltantes desvanecidos: multiconjunto con diccionario
type: desvanecido
id: a1-02-desv-faltantes
lang: javascript

Completa `faltantes(esperados, recibidos)`: devuelve, ordenadas, las unidades esperadas que no llegaron, respetando
repeticiones. Las listas no vienen ordenadas.

### Pasos
1. Cuenta cuántas veces llegó cada SKU: el multiconjunto de recibidos en un Map.
2. Por cada esperado, consume una unidad del conteo; si ya no queda, es faltante.
3. Ordena la salida para que sea determinista.
4. Explica por qué un Set en lugar del Map daría una respuesta incorrecta.

### Plantilla
```javascript
function faltantes(esperados, recibidos) {
  // <paso 1>
  const cuenta = new Map();
  for (const r of recibidos) cuenta.set(r, (cuenta.get(r) || 0) + 1);
  // </paso 1>
  const falta = [];
  for (const e of esperados) {
    // <paso 2>
    const c = cuenta.get(e) || 0;
    if (c > 0) cuenta.set(e, c - 1);
    else falta.push(e);
    // </paso 2>
  }
  // <paso 3>
  falta.sort();
  // </paso 3>
  return falta;
}
```

## El pipeline que pierde ventas
type: forense
id: a1-02-forense-dedupe
corte: 2026-11-01T00:00:00Z

El reporte diario de unidades por SKU «pasa»: corre sin errores y nadie se queja. Pero finanzas dice que faltan unidades.
Localiza el paso donde nace la mentira y escribe un control SQL que devuelva filas cuando el reporte no conserva las unidades
de la fuente.

### Pipeline
```sql

  SELECT DISTINCT sku, unidades FROM eventos;
-- paso: resumen
CREATE VIEW resumen AS
  SELECT sku, SUM(unidades) AS unidades FROM limpio GROUP BY sku;
```

### Invariantes
```json

  { "id": "unidades-conservadas", "tipo": "suma", "sobre": "resumen", "columnas": ["unidades"], "esperado": 21, "tolerancia": 0 }
]
```

### Mentiras
```json

  { "id": "m-dedupe-contenido", "paso": "limpio", "tipo": "dedupe-pierde", "invariante": "unidades-conservadas" }

```

### Corrección
```sql
-- paso: limpio
CREATE VIEW limpio AS
  SELECT event_id, MIN(sku) AS sku, MIN(unidades) AS unidades
  FROM eventos
  GROUP BY event_id;
-- paso: resumen
CREATE VIEW resumen AS
  SELECT sku, SUM(unidades) AS unidades FROM limpio GROUP BY sku;
```

### Control de referencia
```sql
SELECT r.total AS reportado, f.total AS fuente
FROM (SELECT SUM(unidades) AS total FROM resumen) AS r,
     (SELECT SUM(u) AS total
        FROM (SELECT event_id, MIN(unidades) AS u FROM eventos GROUP BY event_id)) AS f
WHERE r.total <> f.total;
```

## Conciliar dos listas ordenadas con dos punteros
type: code
id: a1-02-code-conciliar
tiempo: 12

Recibes `a` (lo esperado) y `b` (lo recibido), dos arreglos de enteros **ordenados** y con repetidos. Devuelve
`[soloEnA, soloEnB]`: la diferencia de multiconjuntos en cada sentido, en orden. Hazlo en O(n + m) sin diccionarios.

### Especificación
Dos índices i y j. Si a[i] === b[j], avanzan los dos. Si a[i] < b[j], a[i] ya no puede emparejar y va a soloEnA. Si no, b[j]
va a soloEnB. Al final, lo que quede de cada lado se agrega a su lista.

### Firma
```javascript

  // tu código
}
```
```python
def diferencias_ordenadas(a, b):
    # tu código
    pass
```

### Casos
```json
[
  { "input": [[], []], "expected": [[], []] },
  { "input": [[1, 2, 2, 3], [2, 3, 3]], "expected": [[1, 2], [3]] },
  { "input": [[5, 5, 5], [5]], "expected": [[5, 5], []] },
  { "input": [[1, 4], [2, 3]], "expected": [[1, 4], [2, 3]] },
  { "input": [[2, 2], [2, 2]], "expected": [[], []] },
  { "input": [[0], []], "expected": [[0], []] },
  { "input": [[], [7, 7]], "expected": [[], [7, 7]] }
]
```

### Solución
```javascript
function diferenciasOrdenadas(a, b) {
  const soloA = [];
  const soloB = [];
  let i = 0;
  let j = 0;
  while (i < a.length && j < b.length) {
    if (a[i] === b[j]) { i++; j++; }
    else if (a[i] < b[j]) soloA.push(a[i++]);
    else soloB.push(b[j++]);
  }
  while (i < a.length) soloA.push(a[i++]);
  while (j < b.length) soloB.push(b[j++]);
  return [soloA, soloB];
}
```
```python
def diferencias_ordenadas(a, b):
    solo_a, solo_b = [], []
    i = j = 0
    while i < len(a) and j < len(b):
        if a[i] == b[j]:
            i += 1
            j += 1
        elif a[i] < b[j]:
            solo_a.append(a[i])
            i += 1
        else:
            solo_b.append(b[j])
            j += 1
    solo_a.extend(a[i:])
    solo_b.extend(b[j:])
    return [solo_a, solo_b]
```

### Pistas
- Si a[i] < b[j], ningún elemento posterior de b puede valer a[i]: b está ordenado.
- Cada vuelta avanza al menos un puntero; ese es tu argumento de costo.

## Costo esperado contra peor caso
type: multiple_choice
id: a1-02-mc-costo
rol: recuperacion

Sin volver al libro: deduplicas n eventos insertando su event_id en un diccionario. ¿Qué afirmación es correcta?

### Opciones
- Cuesta O(1) por operación en el peor caso, siempre.
- [x] Cuesta O(1) esperado por operación si el hash reparte bien las llaves; con llaves que colisionan a propósito una consulta puede costar O(n).
- Cuesta O(log n) por operación, porque el diccionario mantiene las llaves ordenadas.
- Cuesta O(n) por operación, porque cada inserción recorre la tabla completa.

### Justificación
La garantía de una tabla hash es de costo esperado y depende de que las llaves se repartan; si todas caen en la misma zona,
una búsqueda recorre muchas llaves. Por eso «O(1) siempre» es falso. Un diccionario no mantiene las llaves ordenadas por
valor (eso sería un árbol de búsqueda, O(log n)), y en el caso normal no recorre toda la tabla.

## Identidad contra igualdad, por escrito
type: production
id: a1-02-prod-identidad

Explica, con un ejemplo de eventos de ventas, cuándo dos eventos con el mismo contenido son dos hechos distintos y cuándo
dos registros son el mismo hecho. Termina con la llave que usarías para deduplicar.

### Modelo
Dos ventas de 2 unidades de SKU-A a las 10:05 tienen el mismo contenido, pero si traen event_id distintos (e1 y e2) son dos
hechos y deben sumar 4. Un reintento de red reenvía el registro de e2 con el mismo event_id: es el mismo hecho y debe contar
una vez. La igualdad de contenido no prueba identidad, y un contenido distinto con el mismo id es un conflicto que hay que
reportar. Deduplico por event_id y concilio unidades contra la fuente.

### Regla
Se deduplica por identidad (la llave que el origen asigna una vez) y se compara por contenido sólo para detectar conflictos;
deduplicar por contenido borra multiplicidades reales.

### Rúbrica
- Da un caso de contenido igual con identidad distinta, y dice que cuenta dos veces.
- Da un caso de identidad igual (reintento) que cuenta una vez.
- Nombra la llave de deduplicación y qué hacer si el mismo id llega con contenido distinto.

## Listas ordenadas y poca memoria
type: multiple_choice
id: a1-02-mc-memoria

Tienes que conciliar dos listas de un millón de identificadores cada una. Las dos ya vienen ordenadas y la memoria extra
disponible es mínima. ¿Qué enfoque eliges?

### Opciones
- Un diccionario con la primera lista y una pasada por la segunda
- [x] Dos punteros sobre las listas ordenadas: O(n + m) de tiempo y memoria extra constante, además de la salida
- Ordenar las dos listas de nuevo y luego usar un diccionario
- Comparar cada identificador de una lista contra todos los de la otra

### Justificación
El diccionario cuesta O(n) de memoria extra, que es justo lo que falta. Con las listas ya ordenadas, dos punteros recorren cada
una una vez sin guardar nada más que los índices. Volver a ordenar gasta O(n log n) sin necesidad, y comparar todo contra todo
es cuadrático.
