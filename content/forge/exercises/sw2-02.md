## Antes de leer: esperar antes de leer
type: prediccion
id: prediccion-esperar-leer
rol: prediccion
tiempo: 2

Un lanzador conecta la salida de un hijo a una tubería, llama a `esperar(hijo)` y, cuando vuelve, lee toda la salida. El hijo escribe 5 MB. ¿Qué pasa?

### Opciones
- [x] Lo más probable es que los dos queden bloqueados: el hijo se detiene al llenar el búfer de la tubería, esperando que alguien lea, y el padre espera que el hijo termine.
- Funciona: la tubería guarda los 5 MB hasta que el padre los lea.
- El hijo termina con un error de tubería rota y el padre lee lo que haya.
- El sistema operativo detecta el bloqueo y mata al hijo.
### Justificación
El búfer de una tubería es pequeño comparado con 5 MB; cuando se llena, la escritura del hijo se bloquea hasta que alguien lea. Como el padre no lee hasta que el hijo termine, ninguno avanza: un bloqueo mutuo sin error ni consumo de CPU. La tubería no se rompe porque el padre sigue teniéndola abierta, y el sistema no detecta este tipo de espera. Con salidas pequeñas el error no aparece, por eso pasa las pruebas.

## Clasifica cómo terminó cada trabajo
type: code
id: codigo-clasificar-trabajos
tiempo: 12

Implementa la clasificación del registro del lanzador: cómo terminó cada trabajo, con una precedencia fija.

### Especificación
`clasificar(trabajos, plazoMs, maxBytes)`:
- Cada trabajo es `{ "codigo", "senal", "ms", "bytes" }`: el código de salida (entero, o `null` si lo terminó una señal), la señal (texto como `"SIGKILL"`, o `null`), la duración y los bytes de salida.


### Solución
```javascript
function clasificar(trabajos, plazoMs, maxBytes) {
  return trabajos.map((t) => {
    if (t.ms > plazoMs) return "plazo";
    if (t.bytes > maxBytes) return "salida-excedida";
    if (t.senal !== null) return "senal:" + t.senal;
    if (t.codigo !== 0) return "fallo:" + t.codigo;
    return "ok";
  });
}
```
```python
def clasificar(trabajos, plazo_ms, max_bytes):
    salida = []
    for t in trabajos:
        if t["ms"] > plazo_ms:
            salida.append("plazo")
        elif t["bytes"] > max_bytes:
            salida.append("salida-excedida")
        elif t["senal"] is not None:
            salida.append("senal:" + t["senal"])
        elif t["codigo"] != 0:
            salida.append("fallo:" + str(t["codigo"]))
        else:
            salida.append("ok")
    return salida
```

### Pistas
- La precedencia está escrita: un trabajo que pasó el plazo se registra como `plazo` aunque el lanzador lo haya terminado con una señal.
- Igual al límite no es exceder: `ms` igual al plazo y `bytes` igual al máximo son válidos.
- Un código distinto de 0 sin señal es un fallo del propio trabajo.

## Los zombis
type: multiple_choice
id: zombis
tiempo: 3

Un lanzador arranca miles de trabajos al día y nunca llama a `esperar()` sobre sus hijos; sólo revisa si su salida terminó. Al cabo de unos días, no puede crear más procesos. ¿Por qué?

### Opciones
- [x] Cada hijo terminado y no esperado queda como zombi, ocupando una entrada de la tabla de procesos; acumulados, agotan las entradas y el sistema no puede crear procesos nuevos.
- Los hijos siguen corriendo en segundo plano y consumen toda la CPU.
- El sistema operativo bloquea a los lanzadores que crean muchos procesos.
- Las tuberías abiertas consumen toda la memoria.
### Justificación
Un proceso que terminó deja su estado de salida para que el padre lo recoja con `esperar()`; mientras nadie lo recoge, sigue ocupando su entrada como zombi, aunque ya no corra ni use CPU. Miles al día terminan llenando la tabla. No es un problema de CPU porque los zombis no ejecutan nada. Las tuberías sin cerrar son otra fuga posible, pero no explican la imposibilidad de crear procesos. La corrección es esperar siempre a cada hijo, también a los que se terminan por plazo.

## La terminación en dos pasos
type: trace
id: traza-terminacion
tiempo: 3

El lanzador tiene un plazo de 30 s por trabajo y un periodo de gracia de 5 s. Un hijo arranca en t = 0 y nunca termina por su cuenta; atiende la señal amable a los 2 s de recibirla, cerrando sus archivos y saliendo. ¿Qué ocurre y cuándo?

### Opciones
- [x] En t = 30 s recibe la señal amable; en t = 32 s termina limpiando sus archivos; el lanzador lo espera, registra `plazo` y no necesita la señal final.
- En t = 30 s recibe la señal que no se puede ignorar y termina sin limpiar.
- En t = 35 s recibe la señal final, aunque ya haya terminado.
- Nada: un hijo que atiende señales no puede ser terminado por el lanzador.
### Justificación
El procedimiento empieza con la señal amable al vencer el plazo, para darle al hijo la oportunidad de limpiar. Este hijo la atiende y sale a los 2 s, dentro del periodo de gracia, así que la señal final de t = 35 s ya no hace falta: el lanzador sólo la envía si el hijo sigue vivo. Mandar de entrada la señal final le quita la oportunidad de limpiar. Que el hijo atienda señales no lo protege: si no saliera, la señal final lo terminaría.

## Recursos, limpieza y límites
type: production
id: produccion-defensa-lanzador
tiempo: 12

Escribe la defensa del lanzador de la misión que pide la ficha: qué recursos crea por trabajo, dónde y cuándo los libera, cómo observa cada forma de fallo (código, señal, plazo, salida excesiva) y cuáles son los límites del aislamiento que ofrece.

### Modelo
*Recursos por trabajo:* el proceso hijo, una tubería para su salida (y otra para errores), un directorio temporal de trabajo y un temporizador de plazo.
*Liberación:* la tubería se lee mientras el hijo corre y se cierra al terminar; el hijo siempre se espera, también si se mató por plazo, para no dejar zombis; el directorio temporal se borra en un bloque que corre pase lo que pase; el temporizador se cancela al terminar el hijo.
*Observación del fallo:* el estado de `esperar()` da el código de salida o la señal; el temporizador marca el plazo; el contador de bytes leídos marca la salida excesiva; cada trabajo deja un registro con su clasificación, su duración y sus bytes, sin copiar contenido sensible de la salida.
*Límites del aislamiento:* el hijo corre con el mismo usuario y permisos que el lanzador; comparte el sistema de archivos, la red y la CPU; un hijo malicioso o defectuoso puede borrar archivos accesibles, consumir disco o abrir conexiones. Para código no confiable harían falta otro usuario, límites de recursos y un entorno aislado (por ejemplo, un contenedor sin red).

### Regla
Un lanzador se defiende nombrando cada recurso que crea por trabajo con el lugar donde se libera en todos los caminos, la señal que observa cada forma de fallo y los límites de lo que el aislamiento entre procesos protege.

### Rúbrica
- Enumera los recursos por trabajo y dónde se libera cada uno, incluidos los caminos de error y plazo.
- Espera siempre a los hijos y explica por qué.
- Distingue código de salida, señal, plazo y salida excesiva como observaciones distintas.
- Lee la salida mientras el hijo corre o la manda a un archivo, y la limita.
- Declara al menos tres límites del aislamiento.
