## El reinicio a mitad de aplicar
type: prediccion
id: reinicio-a-mitad
rol: prediccion
tiempo: 2

Un agente guarda en la memoria de su proceso la lista de reasignaciones que ya aplicó. Aplicó 3 de 6 aprobadas cuando el proceso se reinicia; al reanudar, recorre otra vez las 6 aprobaciones. Predice el resultado.

### Opciones
- [x] Aplica de nuevo las 3 primeras (duplicadas) y las 3 que faltaban: la memoria del proceso se perdió y nada identifica las acciones ya hechas.
- Aplica sólo las 3 que faltaban, porque la plataforma recuerda lo que hizo el proceso.
- No aplica ninguna, porque un reinicio cancela la sesión.
- Aplica las 6 una sola vez, porque las aprobaciones son únicas.
### Justificación
La continuidad tiene que estar en un registro durable (el historial de la sesión o el registro de la acción), con un identificador estable por acción guardado antes de ejecutarla, y un manejo idempotente que consulte ese registro antes de aplicar. La memoria de un proceso no sobrevive a su reinicio.

## Reanudar sin duplicar
type: code
id: reanudar-sin-duplicar
tiempo: 15

Escribe `reanudar(eventos)`. Cada evento tiene `tipo` y, salvo `interrupcion`, un `accion` (identificador de la acción): `propuesta`, `aprobada`, `aplicada` (el agente aplicó y registró) y `reintento` (alguien vuelve a pedir que se aplique). Procesa en orden: un `reintento` aplica la acción **sólo si** está aprobada y todavía no aplicada (y entonces cuenta como aplicada en ese momento); si ya estaba aplicada, cuenta un **duplicado evitado**; si no estaba aprobada, se **ignora**. ### Solución
```javascript
function reanudar(eventos) {
  const propuestas = new Set();
  const aprobadas = new Set();
  const hechas = new Set();
  const aplicadas = [];
  let duplicados = 0;
  let ignorados = 0;
  for (const e of eventos) {
    if (e.tipo === "propuesta") propuestas.add(e.accion);
    else if (e.tipo === "aprobada") aprobadas.add(e.accion);
    else if (e.tipo === "aplicada" || e.tipo === "reintento") {
      if (hechas.has(e.accion)) duplicados += 1;
      else if (e.tipo === "aplicada" || aprobadas.has(e.accion)) {
        hechas.add(e.accion);
        aplicadas.push(e.accion);
      } else ignorados += 1;
    }
  }
  const pendientes = [...propuestas].filter((a) => !hechas.has(a)).sort();
  return { aplicadas, duplicados_evitados: duplicados, ignorados, pendientes };
}
```
```python
def reanudar(eventos):
    propuestas = set()
    aprobadas = set()
    hechas = set()
    aplicadas = []
    duplicados = 0
    ignorados = 0
    for e in eventos:
        t = e["tipo"]
        if t == "propuesta":
            propuestas.add(e["accion"])
        elif t == "aprobada":
            aprobadas.add(e["accion"])
        elif t in ("aplicada", "reintento"):
            if e["accion"] in hechas:
                duplicados += 1
            elif t == "aplicada" or e["accion"] in aprobadas:
                hechas.add(e["accion"])
                aplicadas.append(e["accion"])
            else:
                ignorados += 1
    pendientes = sorted(a for a in propuestas if a not in hechas)
    return {"aplicadas": aplicadas, "duplicados_evitados": duplicados, "ignorados": ignorados, "pendientes": pendientes}
```
### Pistas
- Lleva tres conjuntos: propuestas, aprobadas y hechas.
- Antes de aplicar, consulta si ya está hecha: eso es lo que evita el duplicado.
- Un reintento de algo no aprobado no se aplica nunca.

## Qué guarda una sesión

## La aprobación como evento
type: multiple_choice
id: aprobacion-evento
tiempo: 2

¿Por qué la aprobación de la coordinadora debe ser un evento con autor en la sesión y no un mensaje cualquiera en el chat?

### Opciones
- [x] Porque así es una transición de estado verificable: el agente sólo aplica cuando existe el evento de aprobación de quien tiene la autoridad, y el historial muestra quién aprobó qué y cuándo.
- Porque los mensajes del chat no se guardan nunca.
- Porque el modelo no puede leer los mensajes del chat.
- No importa: un «sí, dale» en el chat es equivalente.
### Justificación
Un mensaje libre se interpreta; un evento con autor y tipo se verifica. La revisión humana sólo protege si aplicar exige ese evento concreto. Además deja el registro que la defensa necesita.

## Diseña la sesión
type: production
id: disenar-sesion
tiempo: 12

Diseña la sesión de un agente sintético que prepara pedidos urgentes de farmacia para que la jefatura los apruebe: elementos de contexto tipados, estados y eventos (con su autor), identificador de cada acción, cómo se reanuda tras una interrupción y el ensayo que demuestra que no duplica pedidos.

### Modelo
- **Contexto tipado:** `PropuestaPedido { accion_id, insumo_id, cantidad, evidencia (stock, mínimo, próxima entrega) }`.
- **Estados:** preparando → en_revision → aplicando → cerrada (y rechazada → cerrada).
- **Eventos:** `propuesta` (agente), `aprobada` o `rechazada` (jefatura), `aplicada` (agente, tras crear el pedido con la acción), `reintento` (sistema).
- **Identificador:** `pedido:<insumo_id>:<fecha>` guardado en el contexto antes de crear el pedido.
- **Reanudación:** recorrer el historial; para cada aprobada sin `aplicada`, consultar si el pedido con ese identificador ya existe; si existe, registrar «ya aplicada»; si no, crearlo una vez.
- **Ensayo:** 4 propuestas aprobadas; interrumpir tras crear 2; reanudar y entregar un `reintento` repetido; el historial debe mostrar 4 pedidos, 0 duplicados y los reintentos marcados.
### Regla
Una sesión de agente con revisión humana guarda contexto tipado, estados y eventos con autor; cada acción con efecto tiene un identificador estable guardado antes de ejecutarla y un manejo idempotente que consulta el registro antes de aplicar; la continuidad se demuestra con un ensayo de interrupción.
### Rúbrica
- Define contexto tipado, estados y eventos con autor.
- Usa un identificador estable por acción, guardado antes de ejecutar.
- Describe la reanudación consultando el registro.
- Incluye un ensayo de interrupción con el resultado esperado.
