# P2-04 · Indexación y frescura

Banco de la celda P2-04. El camino de un cambio desde la fuente hasta la lectura, y la diferencia entre persistir, indexar, materializar y leer. Caso sintético de una clínica ficticia.

## Hidratación en curso
type: prediccion
id: hidratacion-en-curso
rol: prediccion
tiempo: 2

Un cambio de estado de una cita ya pasó por changelog, fusión e indexación en un pipeline por lotes de Funnel; la hidratación sigue en curso. Una aplicación consulta el objeto en ese momento. Predice qué recibe.

### Opciones
- [x] El valor anterior: el tipo de objeto queda listo para consultas cuando termina la hidratación, así que la lectura sigue sirviendo el índice previo.
- El valor nuevo, porque ya está indexado.
- Un error, porque el objeto está bloqueado mientras se hidrata.
- El valor nuevo, porque las lecturas consultan directamente el dataset de la fuente.
### Justificación
La página de Funnel batch pipelines describe la hidratación como el último paso: la base de objetos descarga los archivos de índice a sus nodos de búsqueda y sólo al terminar el tipo de objeto está listo para consultarse. Indexado no es lo mismo que legible, y las lecturas no van al dataset de origen sino al servicio de lectura de objetos.

### Solución
```javascript
function rastrear_cambio(marcas) {
  const etapas = ["fuente", "changelog", "fusion", "indexacion", "hidratacion"];
  let ultima = null;
  let en_curso = null;
  const demoras = [];
  let previa = null;
  for (const e of etapas) {
    const t = marcas[e];
    if (t === null || t === undefined) {
      en_curso = e;
      break;
    }
    if (previa !== null) demoras.push({ etapa: e, segundos: t - previa });
    previa = t;
    ultima = e;
  }
  return { ultima, en_curso, legible: ultima === "hidratacion", demoras };
}
```


## Cuatro palabras
type: multiple_choice
id: cuatro-palabras
tiempo: 3

Una técnica corrige con una acción el estado de una cita. Según la documentación de Funnel batch pipelines, las ediciones de usuario se aplican de inmediato a los índices, y los pipelines vivos las persisten en el paso de fusión al correr (cada seis horas si no hay cambios en la fuente). Un minuto después de la edición, ¿cuál es la descripción correcta?

### Opciones
- [x] La edición ya se puede leer, pero todavía no está persistida en el dataset de cambios fusionados de Funnel.
- La edición está persistida y materializada, pero no se puede leer hasta dentro de seis horas.
- La edición no existe en ningún lado hasta que corra el pipeline vivo.
- Persistida, indexada, materializada y leída son lo mismo: la edición está completa.
### Justificación
La página distingue los dos momentos: las ediciones se aplican a los índices de inmediato (legibles) y se guardan de forma persistente cuando el pipeline vivo pasa por la fusión de cambios. Para una auditoría, «la vi en pantalla» y «quedó persistida» son afirmaciones distintas.

## Plan para rastrear un cambio
type: production
id: plan-rastreo
tiempo: 10

Escribe el procedimiento que seguiría una persona de guardia cuando un usuario dice «corregí el dato y no lo veo». Incluye qué pregunta hace primero, en qué orden revisa las etapas, qué evidencia busca en cada una, cómo distingue un cambio de fuente de una edición de usuario y qué le responde al usuario mientras tanto.

### Modelo
1. **Pregunta primero:** ¿el cambio se hizo en la fuente (dataset) o con una acción (edición de usuario)? ¿A qué hora?
2. **Si fue en la fuente:** revisa en orden la transacción de la fuente, el changelog, la fusión de cambios, la indexación y la hidratación del pipeline del tipo de objeto; ubica la primera etapa sin terminar o fallida.
3. **Si fue una edición:** comprueba que la acción se envió y se aplicó; si ya se lee, explica que su persistencia ocurre al correr el pipeline vivo.
4. **Cambio de esquema:** si el cambio es una propiedad nueva, revisa si hay un pipeline de reemplazo en curso.
5. **Respuesta al usuario:** «el cambio está en la etapa X desde las HH:MM; se verá cuando termine Y»; si la decisión no puede esperar, se indica la antigüedad del dato o se usa un camino de menor latencia.
### Regla
Un cambio que «no se ve» se ubica por etapas, en orden, distinguiendo su origen (fuente o edición), y la respuesta al usuario nombra la etapa en la que está. Volver a correr builds sin ubicarlo agrega trabajo en la cola sin resolver nada.
### Rúbrica
- Pregunta por el origen del cambio y la hora antes de actuar.
- Revisa las etapas en el orden del pipeline.
- Distingue fuente, edición de usuario y cambio de esquema.
- Da al usuario una respuesta con la etapa y una expectativa honesta.
