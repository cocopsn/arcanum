## Lo que lee una acción por lotes
type: prediccion
id: p206-pred-lotes
rol: prediccion

Una función respalda una acción con escrituras por lotes, el modo por omisión. La función pone `estado = "cerrado"` en un Ticket y, dos líneas después, vuelve a leer ese mismo Ticket para decidir si manda un aviso de cierre. Antes de ver la respuesta, predice qué valor de `estado` lee esa segunda lectura.

### Opciones
- [x] El valor anterior al edit: en escrituras por lotes la acción no ve sus propios edits hasta el commit.
- `"cerrado"`: toda lectura posterior a un edit dentro de la misma ejecución lo ve.
- Depende del nivel de aislamiento: bajo instantánea ve `"cerrado"` y bajo legado el valor anterior.
- Ninguno: leer un objeto ya editado en la misma ejecución lanza un error de conflicto.

### Justificación
La página de consistencia distingue dos modos de escritura. Por lotes, los edits se juntan y se confirman al final, y las lecturas de la propia acción devuelven el estado sin esos edits. Sólo con escrituras escalonadas la acción ve lo que ya editó. El nivel de aislamiento decide qué foto ve la acción del resto del mundo y qué conflictos la hacen fallar, no si ve sus propios edits. Leer lo que uno editó no es un conflicto: el conflicto es entre dos acciones que escriben el mismo objeto.

## Dos acciones, un objeto, propiedades distintas
type: prediccion
id: p206-pred-mismo-objeto
rol: prediccion

Bajo aislamiento de instantánea, la acción A cambia la `prioridad` de un Ticket y la acción B, al mismo tiempo, cambia su `asignado`. Ninguna toca la propiedad de la otra. Predice qué pasa.

### Opciones
- [x] Una de las dos falla con error de conflicto y pierde su edit completo: el conflicto se detecta por objeto, no por propiedad.
- Las dos confirman y el Ticket conserva ambos cambios, porque no hay propiedades en común.
- Las dos confirman y gana la última en todas las propiedades del Ticket.
- Las dos fallan, porque la instantánea aborta toda escritura concurrente.

### Justificación
Según la página de consistencia, la detección escritura-escritura es a nivel de objeto y aplica aunque las acciones escriban propiedades distintas; la que falla descarta su edit entero. El escenario «las dos confirman y se conservan ambos cambios» es el comportamiento descrito para lectura confirmada, no para instantánea. Nada indica que fallen las dos: falla la que llega a confirmar con un objeto que otro ya cambió.

## Reservar sin tocar el recurso
type: prediccion
id: p206-pred-write-skew
rol: prediccion

Para evitar conflictos, alguien cambió la acción «Reservar»: ya no escribe el objeto Sala; cuenta las Reservas existentes de la sala y, si hay lugar, crea una Reserva nueva. Sala con capacidad 1 y ninguna reserva. Dos usuarios reservan a la vez bajo instantánea. Predice el resultado.

### Opciones
- [x] Las dos acciones confirman y quedan dos reservas: escriben objetos nuevos y distintos, y la instantánea no comprueba lo que sólo se leyó.
- Una falla por conflicto, porque las dos leyeron el mismo conjunto de reservas.
- Una falla por la restricción de capacidad, que la Ontology comprueba al confirmar.
- Las dos fallan, porque crear objetos en la misma sala es una escritura concurrente sobre la sala.

### Justificación
Es write skew. La página explica que la instantánea sólo comprueba conflictos sobre objetos escritos, así que dos acciones pueden leer datos que se solapan, escribir objetos distintos y confirmar las dos. La consistencia de la Ontology cubre restricciones como tipos de valor y propiedades requeridas, no una regla de capacidad entre objetos que tú no conviertes en escritura. El remedio que propone la página es expresar el invariante como una escritura sobre un objeto compartido, por ejemplo un contador en la Sala.

## Writeback que sale bien, commit que no
type: prediccion
id: p206-pred-writeback
rol: prediccion

Una acción tiene un webhook configurado como writeback hacia el sistema de reservas del proveedor, y el modo de reintento por omisión. El proveedor responde 200 y registra la reserva; después, el commit de la acción en Foundry falla por un conflicto. Predice el estado final.

### Opciones
- [x] El proveedor tiene la reserva y Foundry no; la plataforma no reejecuta sola la acción porque tiene una llamada externa, así que hace falta reconciliar.
- Ninguno tiene la reserva: el writeback forma parte de la transacción y se deshace con ella.
- Los dos la tienen: la plataforma reintenta la acción hasta 5 veces y termina por confirmarla.
- Foundry tiene la reserva y el proveedor no, porque el writeback corre después de los edits.

### Justificación
La página de webhooks en acciones dice que el writeback corre antes de las demás reglas y que, si falla, la Ontology no cambia; también admite que la petición externa puede salir bien y los cambios en la Ontology fallar. La atomicidad de la acción no alcanza al sistema externo. Y la página de consistencia indica que, por omisión, sólo se reintentan solas las acciones sin llamadas externas, porque reejecutar repetiría el efecto. El writeback no corre después de los edits: ese es el efecto secundario.

## Ejemplo desvanecido · reservar con versión
type: desvanecido
id: p206-desv-version
lang: javascript

Completa una reserva optimista sobre un recurso con versión. La acción trae la versión que leyó y la cantidad que pide. Si alguien confirmó antes, la versión cambió y hay que rechazar por conflicto; si no hay cupo, rechazar sin tocar nada; si todo va bien, devolver un recurso nuevo con la ocupación y la versión actualizadas. Cada nivel oculta un paso más. El último paso es de prosa y se autoverifica.

### Pasos
1. Rechaza con `motivo: "conflicto"` si la versión leída no es la actual, y devuelve el recurso sin cambios.
2. Rechaza con `motivo: "sin-cupo"` si la cantidad pedida no cabe en la capacidad, y devuelve el recurso sin cambios.
3. Devuelve `ok: true`, `motivo: "aplicada"` y un recurso nuevo con `ocupadas` sumada y `version` incrementada en uno.
4. Explica en dos o tres frases por qué el paso 3 tiene que escribir el recurso, y no sólo crear la reserva, para que dos solicitudes concurrentes choquen.

### Plantilla
```javascript
function reservarConVersion(recurso, solicitud) {
  // <paso 1>
  if (solicitud.leida !== recurso.version) {
    return { ok: false, motivo: "conflicto", recurso };
  }
  // </paso 1>
  // <paso 2>
  if (recurso.ocupadas + solicitud.cantidad > recurso.capacidad) {
    return { ok: false, motivo: "sin-cupo", recurso };
  }
  // </paso 2>
  // <paso 3>
  const nuevo = { ...recurso, ocupadas: recurso.ocupadas + solicitud.cantidad, version: recurso.version + 1 };
  return { ok: true, motivo: "aplicada", recurso: nuevo };
  // </paso 3>
}
```

### Casos
```json

  { "input": [{ "version": 1, "capacidad": 2, "ocupadas": 1 }, { "leida": 1, "cantidad": 1 }], "expected": { "ok": true, "motivo": "aplicada", "recurso": { "version": 2, "capacidad": 2, "ocupadas": 2 } } },
  { "input": [{ "version": 2, "capacidad": 2, "ocupadas": 1 }, { "leida": 1, "cantidad": 1 }], "expected": { "ok": false, "motivo": "conflicto", "recurso": { "version": 2, "capacidad": 2, "ocupadas": 1 } } },
  { "input": [{ "version": 4, "capacidad": 3, "ocupadas": 2 }, { "leida": 4, "cantidad": 2 }], "expected": { "ok": false, "motivo": "sin-cupo", "recurso": { "version": 4, "capacidad": 3, "ocupadas": 2 } } },
  { "input": [{ "version": 7, "capacidad": 5, "ocupadas": 0 }, { "leida": 7, "cantidad": 5 }], "expected": { "ok": true, "motivo": "aplicada", "recurso": { "version": 8, "capacidad": 5, "ocupadas": 5 } } },
  { "input": [{ "version": 3, "capacidad": 1, "ocupadas": 1 }, { "leida": 2, "cantidad": 1 }], "expected": { "ok": false, "motivo": "conflicto", "recurso": { "version": 3, "capacidad": 1, "ocupadas": 1 } } }

```

### Niveles
- 1: 3
- 2: 2, 3
- 3: 1, 2, 3, 4

### Rúbrica
- Dice que el conflicto se detecta sobre objetos escritos: si la reserva sólo crea objetos nuevos, dos solicitudes no escriben nada en común.
- Nombra el resultado sin la escritura del recurso: las dos confirman y la capacidad se excede (write skew).
- Reconoce el costo: el recurso se vuelve un punto de contención y habrá más conflictos o reintentos.

## Bug sembrado 1 · la versión que no sube
type: code
id: p206-bug-version
rol: practica

Este procesador aplica acciones en el orden en que llegan, con comprobación optimista **por objeto**: cada acción trae la versión del objeto que leyó y sólo se aplica si esa versión sigue siendo la actual; si no, es un conflicto y se descarta entera. El código de la firma tiene un bug sembrado: en ciertos órdenes deja pasar una actualización perdida. Reprodúcelo con un caso, encuentra la línea y corrige con el parche mínimo.

### Especificación
`aplicarEnOrden(objetos, acciones)`:
- `objetos`: mapa id → `{ version, ...propiedades }`. No lo modifiques: trabaja sobre una copia.
- `acciones`: lista de `{ id, objeto, leida, cambios }`, en orden de llegada.
- Si el objeto no existe → `"rechazada"`. Si `leida` no es la versión actual → `"conflicto"` y no se aplica nada de esa acción. Si coincide → se aplican los `cambios` y la versión sube en uno → `"aplicada"`.
- Devuelve `{ objetos, resultados }` con el estado final y un resultado por acción, en orden.
- Igual que en la plataforma, dos acciones que tocan propiedades distintas del mismo objeto también chocan.

### Firma
```javascript
function aplicarEnOrden(objetos, acciones) {
  const estado = JSON.parse(JSON.stringify(objetos));
  const resultados = [];
  for (const a of acciones) {
    const obj = estado[a.objeto];
    if (!obj) { resultados.push("rechazada"); continue; }
    if (a.leida !== obj.version) { resultados.push("conflicto"); continue; }
    Object.assign(obj, a.cambios);
    resultados.push("aplicada");
  }
  return { objetos: estado, resultados };
}
```

### Casos
```json

  { "name": "sin acciones", "input": [{ "sala": { "version": 5, "libres": 1 } }, []], "expected": { "objetos": { "sala": { "version": 5, "libres": 1 } }, "resultados": [] } }
```

### Solución
```javascript
function aplicarEnOrden(objetos, acciones) {
  const estado = JSON.parse(JSON.stringify(objetos));
  const resultados = [];
  for (const a of acciones) {
    const obj = estado[a.objeto];
    if (!obj) { resultados.push("rechazada"); continue; }
    if (a.leida !== obj.version) { resultados.push("conflicto"); continue; }
    Object.assign(obj, a.cambios);
    obj.version += 1; // sin esto, la segunda lectura de la misma versión también se aplica
    resultados.push("aplicada");
  }
  return { objetos: estado, resultados };
}
```

### Pistas
- Corre el primer caso a mano: después de aplicar A, ¿qué versión ve la comprobación de B?
- La comprobación es correcta; lo que falta es lo que hace que la próxima comprobación sepa que alguien escribió.

## Bug sembrado 2 · el writeback que se creyó parte de la transacción
type: code

Esta función modela una acción con un webhook writeback hacia un sistema externo. Recibe el resultado del webhook (`"ok"`, `"error"` o `"timeout"`) y el del commit en la Ontology (`"ok"` o `"conflicto"`). El código de la firma tiene un bug sembrado de diseño: trata la escritura externa como si viviera dentro de la transacción. Corrígelo según la semántica del libro.

### Especificación
`aplicarConWriteback(objetos, edit, webhook, commit)`:
- `edit`: `{ objeto, cambios }`. No modifiques `objetos`: trabaja sobre una copia.
- El writeback corre **antes** de los edits. `"error"` → no se aplica nada y el resultado es `"rechazada"`.
- `"timeout"` → no se aplica nada en la Ontology y el resultado es `"desconocida"`: el sistema externo pudo o no aplicar.
- `"ok"` y commit `"ok"` → se aplican los cambios y el resultado es `"aplicada"`.
- `"ok"` y commit `"conflicto"` → no se aplica nada en la Ontology y el resultado es `"reconciliar"`: afuera sí quedó.
- Devuelve `{ objetos, resultado }`.

### Firma
```javascript
function aplicarConWriteback(objetos, edit, webhook, commit) {
  const estado = JSON.parse(JSON.stringify(objetos));
  Object.assign(estado[edit.objeto], edit.cambios);
  if (webhook === "ok") return { objetos: estado, resultado: "aplicada" };
  return { objetos: estado, resultado: "rechazada" };
}
```

### Casos
```json

  { "name": "todo bien", "input": [{ "r": { "estado": "pendiente" } }, { "objeto": "r", "cambios": { "estado": "confirmada" } }, "ok", "ok"], "expected": { "objetos": { "r": { "estado": "confirmada" } }, "resultado": "aplicada" } },

  { "name": "afuera sí, adentro conflicto", "input": [{ "r": { "estado": "pendiente" } }, { "objeto": "r", "cambios": { "estado": "confirmada" } }, "ok", "conflicto"], "expected": { "objetos": { "r": { "estado": "pendiente" } }, "resultado": "reconciliar" } },

]
```

### Solución
```javascript
function aplicarConWriteback(objetos, edit, webhook, commit) {
  const estado = JSON.parse(JSON.stringify(objetos));
  if (webhook === "error") return { objetos: estado, resultado: "rechazada" };
  if (webhook === "timeout") return { objetos: estado, resultado: "desconocida" };
  if (commit !== "ok") return { objetos: estado, resultado: "reconciliar" };
  Object.assign(estado[edit.objeto], edit.cambios);
  return { objetos: estado, resultado: "aplicada" };
}
```

### Pistas
- ¿En qué orden corren el writeback y los edits? El código de la firma los invierte.
- Un timeout no es un rechazo: no sabes qué pasó afuera.
- Que el externo diga 200 no garantiza que el commit de adentro salga bien.

## Retención a 21 días · timeout con resultado desconocido
type: retencion
id: p206-ret-timeout
rol: recuperacion
dias: 21
variante_de: p206-bug-writeback
forma: codigo

Repaso a las 3 semanas (intervalo: propuesta del programa, ajustable). Una acción llamó varias veces a un sistema externo con la **misma** clave de idempotencia. Tienes los resultados de cada intento y, a veces, una consulta por clave hecha después del plazo. Diagnostica el estado de la operación sin inventar certeza.

`diagnosticar(intentos, consulta)`:
- `intentos`: lista de `"ok"`, `"error"` (rechazo definitivo) o `"timeout"`.
- `consulta`: `null` si no se pudo consultar, o `{ encontrada: true | false }`.
- Algún `"ok"` → `"aplicada"`. Si no, con consulta → `"aplicada"` o `"no-aplicada"` según `encontrada`. Sin consulta: si ningún intento fue timeout → `"no-aplicada"`; si alguno lo fue → `"desconocida"`.

### Firma
```javascript
function diagnosticar(intentos, consulta) {
  // devuelve "aplicada", "no-aplicada" o "desconocida"
}
```

### Casos
```json
[
  { "input": [["timeout"], null], "expected": "desconocida" },
  { "input": [["timeout", "timeout"], { "encontrada": true }], "expected": "aplicada" },
  { "input": [["timeout"], { "encontrada": false }], "expected": "no-aplicada" },
  { "input": [["error", "error"], null], "expected": "no-aplicada" },
  { "input": [["timeout", "ok"], null], "expected": "aplicada" },
  { "input": [["error", "timeout"], null], "expected": "desconocida" },
  { "input": [[], null], "expected": "no-aplicada" }
]
```

### Solución
```javascript
function diagnosticar(intentos, consulta) {
  if (intentos.includes("ok")) return "aplicada";
  if (consulta !== null) return consulta.encontrada ? "aplicada" : "no-aplicada";
  return intentos.includes("timeout") ? "desconocida" : "no-aplicada";
}
```
