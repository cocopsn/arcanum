# S1-07 · Pruebas por riesgo

Banco de la celda: predecir qué mide la cobertura, escribir casos que maten mutantes de una función de traslapes, reconocer la falla que sobrevive a los mocks, hacer reproducible un recorrido crítico, convertir riesgos en pruebas y transferir la suite a una dependencia que no puedes ejecutar.

## Cien por ciento de cobertura
type: prediccion
id: s1-07-pred-cobertura
rol: prediccion
escala: 50 70 90

El módulo de exportación tiene 100 % de cobertura de líneas y todas sus pruebas pasan. Predice qué garantiza eso.

### Opciones
- [x] Que cada línea se ejecutó al menos una vez durante las pruebas; nada sobre si los resultados se verificaron ni sobre los casos que las pruebas no imaginaron.
- Que el módulo no tiene errores en los caminos cubiertos.
- Que cada rama de cada condición se probó con valores verdaderos y falsos.
- Que el módulo funciona con la API real, porque todas sus llamadas se ejecutaron.
### Justificación
La cobertura de líneas registra ejecución, no verificación: una prueba sin aserciones útiles cubre igual que una buena. No implica cobertura de ramas (una línea con `a && b` se ejecuta sin probar ambos lados) y, si las llamadas a la API pasan por un mock, ejecutarlas dice cómo responde el mock, no la API. Para medir la calidad de la suite sirven las pruebas de mutación.

## Matar mutantes del traslape
type: mutantes
id: s1-07-mut-traslape
minimo: 4

`seTraslapan(a, b)` decide si dos citas del mismo equipo chocan. Cada cita es un intervalo semiabierto `[inicio, fin)` en minutos: dos citas contiguas (una termina a las 09:30 y la otra empieza a las 09:30) **no** se traslapan. Escribe casos que maten a los mutantes; la referencia calcula el resultado esperado de tus entradas y un caso con una expectativa errónea no cuenta.

### Firma
```javascript
function seTraslapan(a, b) {
  // a, b: { inicio, fin } en minutos, con inicio < fin
}
```
### Referencia
```javascript
function seTraslapan(a, b) {
  return a.inicio < b.fin && b.inicio < a.fin;
}
```
### Mutantes
#### menor-o-igual-inicio · crítico
```javascript
function seTraslapan(a, b) {
  return a.inicio <= b.fin && b.inicio < a.fin;
}
```
#### menor-o-igual-fin
```javascript
function seTraslapan(a, b) {
  return a.inicio < b.fin && b.inicio <= a.fin;
}
```
#### o-en-vez-de-y · crítico
```javascript
function seTraslapan(a, b) {
  return a.inicio < b.fin || b.inicio < a.fin;
}
```
#### solo-un-lado
```javascript
function seTraslapan(a, b) {
  return a.inicio < b.fin;
}
```
#### solo-contencion
```javascript
function seTraslapan(a, b) {
  return a.inicio <= b.inicio && b.fin <= a.fin;
}
```
#### extremos-cerrados
```javascript
function seTraslapan(a, b) {
  return a.inicio <= b.fin && b.inicio <= a.fin;
}
```
### Casos dorados
```json
[
  { "input": [{ "inicio": 0, "fin": 30 }, { "inicio": 60, "fin": 90 }], "expected": false },
  { "input": [{ "inicio": 0, "fin": 60 }, { "inicio": 30, "fin": 90 }], "expected": true },
  { "input": [{ "inicio": 0, "fin": 90 }, { "inicio": 30, "fin": 60 }], "expected": true },
  { "input": [{ "inicio": 0, "fin": 30 }, { "inicio": 30, "fin": 60 }], "expected": false },
  { "input": [{ "inicio": 30, "fin": 60 }, { "inicio": 0, "fin": 30 }], "expected": false },
  { "input": [{ "inicio": 60, "fin": 90 }, { "inicio": 0, "fin": 30 }], "expected": false },
  { "input": [{ "inicio": 10, "fin": 20 }, { "inicio": 10, "fin": 20 }], "expected": true }
]
```
### Formato de casos
Cada caso es un objeto `{ "input": [a, b], "expected": true | false }`, donde `a` y `b` son `{ "inicio": N, "fin": M }` en minutos desde las 00:00, con `inicio < fin`. Piensa en los bordes de la agenda real: citas contiguas en los dos órdenes, una cita dentro de otra y una cita después de la otra.

## La falla que el mock no ve
type: multiple_choice
id: s1-07-choice-mock
rol: recuperacion

Sin volver al libro: la exportación a facturación usa un cliente de la API simulado en todas las pruebas. ¿Cuál de estas fallas reales puede pasar todas esas pruebas?

### Opciones
- [x] Que la API real entregue páginas de 100 con un cursor y el código nunca pida la segunda página.
- Que el código sume mal los montos de las órdenes que recibe.
- Que una orden sin informe se exporte por un `if` invertido.
- Que el código lance un error con una lista vacía.
### Justificación
Un mock es una suposición escrita sobre la dependencia. Si el mock devuelve todo de una vez, ninguna prueba con ese mock puede ver que el código ignora la paginación real: la falla vive exactamente en la suposición. Las otras tres son errores de lógica propia que una buena prueba unitaria con el mock sí detecta. La defensa es una prueba de integración con un doble que pagine como la API (o respuestas grabadas de la API real).

## Un recorrido crítico reproducible
type: multiple_choice
id: s1-07-choice-reproducible

El recorrido «reservar → atender → informar → exportar» pasa en tu máquina y falla una de cada cinco veces en la integración continua. ¿Qué cambio lo vuelve reproducible?

### Opciones
- [x] Fijar los datos sintéticos de partida, el reloj y la semilla de todo lo aleatorio, y crear los datos en un espacio aislado por corrida.
- Reintentar el recorrido hasta tres veces y aceptar el primer verde.
- Correrlo sólo en tu máquina, que es donde pasa.
- Agregar pausas de 5 segundos entre pasos.
### Justificación
Una prueba que falla a veces depende de algo que no controla: datos compartidos con otras corridas, la hora actual (citas «de mañana» que cambian de día), valores aleatorios o la zona horaria. Fijar esas entradas hace que la misma corrida dé el mismo resultado. Reintentar esconde la falla y deja de medir; correrla en una sola máquina no la arregla; las pausas sólo cambian la frecuencia de una carrera, no la eliminan.

## El mock que entregaba todo de una vez
type: prediccion
id: s1-07-pred-paginas
rol: prediccion

El mock del cliente de la API devuelve las 4,000 órdenes del día en una respuesta. La API real devuelve 100 por página con `siguiente`. El código hace una sola llamada y exporta lo que recibe. Predice qué exporta en producción.

### Opciones
- [x] Las primeras 100 órdenes, sin ningún error.
- Las 4,000, porque la API real detecta que el cliente no pagina y devuelve todo.
- Ninguna: la API real rechaza a un cliente que no envía `cursor`.
- Un error de tiempo de espera por el tamaño de la respuesta.
### Justificación
Con la API real, la primera llamada sin cursor devuelve la primera página y un cursor que el código ignora. La exportación «termina bien» con 100 órdenes: es la peor falla posible, porque es silenciosa. Ninguna API adivina que el cliente no pagina, y la primera página no requiere cursor.

## De riesgos a pruebas
type: production
id: s1-07-prod-riesgos

Para la exportación de órdenes informadas a facturación, escribe una tabla corta de cuatro riesgos con su daño y la prueba más barata que detectaría cada uno, indicando el nivel (unidad, integración o recorrido crítico). Termina señalando una falla real que podría sobrevivir a todas tus pruebas.

### Modelo
1. Exportar órdenes no informadas: factura algo que no se atendió; unidad con todos los estados. 2. Exportación incompleta por paginación: facturación pierde dinero; integración con un doble que pagina como la API (o respuestas grabadas). 3. Montos en la moneda o el redondeo equivocado: facturas rechazadas; unidad con casos de redondeo y moneda. 4. Exportar dos veces la misma orden tras un reintento: cobro doble; integración que repite la exportación y verifica idempotencia por `orden_id`. Falla que puede sobrevivir: un cambio de permisos en la cuenta de servicio que la deja sin acceso a una sede; la exportación sigue «exitosa» con menos órdenes. La detecta un monitoreo en producción que compare el conteo exportado con el conteo de informadas del día.
### Regla
La prioridad de una prueba sale del daño y de la probabilidad del riesgo; cada riesgo se asigna a la prueba más barata que lo detecta, y lo que ninguna prueba ve se vigila en producción.
### Rúbrica
- Cuatro riesgos con daño concreto.
- Cada uno asignado a un nivel con una prueba específica.
- Al menos un riesgo que exige una dependencia real o un doble fiel.
- Nombra una falla que sobrevive a las pruebas y cómo se detectaría en producción.

## Giro: la agenda pasa a un servicio externo
type: giro
id: s1-07-giro
rol: transferencia

La clínica reemplaza su agenda propia por un servicio externo de agendas. No puedes ejecutar ese servicio en tus pruebas, sólo tiene un entorno de pruebas compartido con otros clientes y cambia su API con dos semanas de aviso. ¿Cómo cambia tu suite? Explica qué pruebas conservas, cuáles reemplazas y cómo detectas que el servicio cambió antes de que falle la operación.

### Rúbrica
- Conserva las pruebas de unidad de la lógica propia, que no dependen del servicio.
- Introduce pruebas de contrato con respuestas grabadas del servicio y un proceso para refrescarlas cuando cambie.
- Usa el entorno de pruebas compartido con datos aislados por corrida y sin depender de su estado previo.
- Agrega un monitoreo sintético en producción del recorrido crítico (una reserva de prueba controlada).
- Reconoce qué riesgos ya no puede cubrir en pruebas y cómo los acota.
