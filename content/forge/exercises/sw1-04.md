## Antes de leer: dos objetos iguales en un Set
type: prediccion
id: prediccion-set-objetos
rol: prediccion
tiempo: 2

En JavaScript, ¿qué valor tiene `new Set([{ id: 1 }, { id: 1 }]).size`?

### Opciones
- [x] 2, porque `Set` compara objetos por identidad y son dos objetos distintos aunque tengan el mismo contenido.
- 1, porque los dos objetos tienen exactamente las mismas propiedades con los mismos valores.
- 1, porque `Set` convierte cada objeto a texto antes de compararlo.
- Lanza un error, porque los objetos no se pueden guardar en un `Set`.
### Justificación
`Set` y `Map` usan la igualdad SameValueZero, que para objetos es identidad de referencia. Los dos literales crean dos objetos distintos, así que el conjunto tiene dos elementos. Nada convierte los objetos a texto: si quieres igualdad de valor, tienes que construir tú una llave canónica. Los objetos sí se pueden guardar en un `Set`; el problema es qué cuenta como «el mismo».

## Igualdad redefinida, hash olvidado
type: multiple_choice
id: hash-inconsistente
tiempo: 3

En un lenguaje con mapas hash, un equipo redefine la igualdad de `Dinero` para comparar `centavos` y `moneda`, pero deja el hash por omisión, que depende de la identidad del objeto. Guardan `m.put(Dinero(100, "MXN"), "caja 1")` y después preguntan `m.get(Dinero(100, "MXN"))` con un objeto nuevo. ¿Qué es lo más probable?

### Opciones
- [x] Devuelve vacío casi siempre: los dos objetos son iguales, pero sus hashes difieren, así que la búsqueda va a otra cubeta y nunca llega a comparar con el guardado.
- Devuelve «caja 1», porque el mapa siempre usa la igualdad redefinida para buscar.
- Lanza una excepción por llave duplicada.
- Devuelve «caja 1» sólo si el mapa tiene más de 16 cubetas.
### Justificación
Un mapa hash elige la cubeta con el hash y sólo después compara con la igualdad dentro de esa cubeta. Si objetos iguales tienen hashes distintos, la búsqueda mira una cubeta donde la llave no está; la igualdad redefinida nunca se llega a usar. La regla es que objetos iguales deben tener el mismo hash. No hay excepción por duplicado: el mapa ni siquiera sabe que son iguales. El número de cubetas no arregla nada; a lo sumo hace la falla intermitente.

## Una clave canónica para valores JSON

- Números, cadenas, booleanos y `null` se escriben como en JSON.
- Dos objetos con las mismas propiedades y valores, creados en distinto orden, dan la misma cadena.

}

### Casos
```json
[
  { "input": [{ "b": 2, "a": 1 }], "expected": "{\"a\":1,\"b\":2}" },
  { "input": [{ "a": 1, "b": 2 }], "expected": "{\"a\":1,\"b\":2}" },
  { "input": [{ "sala": "B", "fin": 600, "inicio": 540 }], "expected": "{\"fin\":600,\"inicio\":540,\"sala\":\"B\"}" },
  { "input": [{ "z": { "y": 1, "x": [3, { "q": true, "p": null }] } }], "expected": "{\"z\":{\"x\":[3,{\"p\":null,\"q\":true}],\"y\":1}}" },
  { "input": [[2, 1]], "expected": "[2,1]" },
  { "input": [[]], "expected": "[]" },
  { "input": [{}], "expected": "{}" },
  { "input": ["texto"], "expected": "\"texto\"" },
  { "input": [null], "expected": "null" },
  { "input": [false], "expected": "false" },
  { "input": [{ "monto": 2.5, "moneda": "MXN" }], "expected": "{\"moneda\":\"MXN\",\"monto\":2.5}", "hint": true }
]
```

### Solución
```javascript
function claveCanonica(valor) {
  if (valor === null || typeof valor !== "object") return JSON.stringify(valor);
  if (Array.isArray(valor)) return "[" + valor.map(claveCanonica).join(",") + "]";
  const llaves = Object.keys(valor).sort();
  return "{" + llaves.map((k) => JSON.stringify(k) + ":" + claveCanonica(valor[k])).join(",") + "}";
}
```
```python
import json

def clave_canonica(valor):
    return json.dumps(valor, sort_keys=True, separators=(",", ":"), ensure_ascii=False)
```

### Pistas
- Los casos base son los valores que no son objeto ni arreglo: ahí basta la serialización JSON de siempre.
- Un arreglo conserva su orden; sólo las llaves de los objetos se ordenan.
- La recursión tiene que llegar a los objetos dentro de arreglos dentro de objetos.

## ¿Qué cambio es compatible?
type: multiple_choice
id: cambio-compatible
tiempo: 3

El evento `ReservaCreada` lo consumen tres servicios que no puedes actualizar este mes. ¿Cuál de estos cambios es compatible en las dos direcciones (consumidores viejos con eventos nuevos y consumidores nuevos con eventos viejos)?

### Opciones
- [x] Agregar el campo opcional `prioridad`, con valor por omisión `"normal"` cuando falta, y que los consumidores ignoren los campos que no conocen.
- Cambiar `inicio` de minutos a segundos, conservando el nombre del campo.
- Renombrar `paciente` a `pacienteId` para que sea más claro.
- Volver opcional el campo `sala`, que hoy es obligatorio, para soportar reservas sin sala asignada.
### Justificación
Agregar un campo opcional con valor por omisión fortalece lo que el evento promete sin exigir nada nuevo: el consumidor viejo lo ignora y el nuevo lee los eventos viejos con el valor por omisión. Cambiar las unidades conservando el nombre es el cambio más peligroso, porque nada falla de inmediato: el consumidor viejo calcula horarios equivocados. Renombrar rompe a todo consumidor que lee el campo. Volver opcional un campo obligatorio debilita la promesa: el consumidor viejo supone que `sala` siempre está y falla con los eventos nuevos.

## Identidad, valor y contrato de una reserva
type: production
id: produccion-identidad-reserva
tiempo: 12

Para el tipo `Reserva` de la clínica, decide y justifica: qué la identifica, cuándo dos reservas son iguales, qué hash usarías y cómo agregarías el campo `prioridad` sin romper a los consumidores actuales. Distingue explícitamente identidad, igualdad de valor y compatibilidad.

### Modelo
*Identidad:* la reserva es una entidad con ciclo de vida (se crea, se reprograma, se cancela), así que se identifica por un `reservaId` estable asignado al crearla, no por su contenido: una reserva cancelada y otra nueva en el mismo hueco tienen el mismo contenido y son reservas distintas, y una reserva reprogramada cambia de contenido y sigue siendo la misma.
*Igualdad:* por identidad, comparando `reservaId`; el hash usa sólo `reservaId`, que nunca cambia, así que reprogramar no mueve la reserva de cubeta.
*Igualdad de valor auxiliar:* para deduplicar solicitudes repetidas antes de crear la reserva, se usa un valor inmutable `SolicitudReserva(sala, inicio, fin, paciente)` con igualdad por campos normalizados y una clave canónica.
*Compatibilidad:* `prioridad` entra como campo opcional con omisión `"normal"`; los consumidores viejos lo ignoran y los nuevos leen los eventos viejos como `"normal"`. No se reutiliza ningún nombre con otro significado.

### Regla
Las entidades mutables se comparan por identidad estable; los valores inmutables, por igualdad de valor con hash consistente; y un cambio de tipo es compatible si la especificación nueva es igual o más fuerte que la anterior para cada consumidor.

### Rúbrica
- Separa identidad, igualdad de valor y compatibilidad sin usarlas como sinónimos.
- Elige una identidad estable y explica por qué el contenido no sirve como identidad de una entidad mutable.
- El hash es consistente con la igualdad elegida y no depende de campos que cambian.
- El campo nuevo es opcional, con omisión declarada, y se justifica en las dos direcciones de compatibilidad.
- Menciona cómo se deduplican solicitudes repetidas sin confundirlas con la identidad de la reserva.
