## Una negación con un token reducido
type: prediccion
id: negacion-token
rol: prediccion
tiempo: 3

Una acción tiene el criterio «el usuario actual NO pertenece al grupo técnicos» para que sólo supervisión reasigne órdenes urgentes. Un técnico ejecuta la acción desde un servicio que usa un token de alcance reducido, que no trae sus atributos de grupo. Predice qué pasa con el criterio.

### Opciones
- [x] Puede pasar: si el token no trae la pertenencia al grupo, la negación se evalúa como «no pertenece» y concede más acceso del previsto.
- Falla siempre, porque un token reducido nunca puede ejecutar acciones.
- Pasa sólo si el técnico también pertenece a supervisión.
- La plataforma convierte automáticamente la negación en una condición positiva.
### Justificación
La documentación de criterios de envío advierte que usar `NOT` con pertenencia a grupos, markings u organizaciones es una mala configuración, porque los tokens de alcance reducido pueden no traer el atributo y la condición pasaría. La forma robusta es la positiva: «pertenece a supervisión» o, combinada, «pertenece a supervisión o la orden no es urgente».

## Evaluar criterios de envío
type: code
id: evaluar-criterios
tiempo: 15

Escribe `evaluar_criterios(criterio, contexto)`. Un `criterio` es una condición o una combinación: `{ "todos": [criterios] }` (todas deben cumplirse) o `{ "alguno": [criterios] }` (al menos una). Una condición tiene `id` y `tipo`:

- `grupo` con `grupo`: se cumple si `contexto.usuario.grupos` incluye ese grupo;
- `igual` con `parametro` y `valor`: se cumple si `contexto.parametros[parametro] === valor`;
- `en` con `parametro` y `valores`: se cumple si el parámetro está en la lista.

Devuelve `{ permitido, fallan }`: `permitido` dice si el criterio raíz se cumple, y `fallan` es la lista ordenada (sin repetidos) de los `id` de condiciones que explican el rechazo: en un `todos`, las de los hijos que no se cumplen; en un `alguno` que no se cumple, las de todos sus hijos; en un `alguno` que se cumple, ninguna. Si `permitido` es verdadero, `fallan` es vacía.

```javascript
function evaluar_criterios(criterio, contexto) {
  function ev(c) {
    if (c.todos) {
      const rs = c.todos.map(ev);
      const ok = rs.every((r) => r.ok);
      return { ok, fallan: ok ? [] : rs.flatMap((r) => r.fallan) };
    }
    if (c.alguno) {
      const rs = c.alguno.map(ev);
      const ok = rs.some((r) => r.ok);
      return { ok, fallan: ok ? [] : rs.flatMap((r) => r.fallan) };
    }
    let ok = false;
    if (c.tipo === "grupo") ok = (contexto.usuario.grupos || []).includes(c.grupo);
    else if (c.tipo === "igual") ok = contexto.parametros[c.parametro] === c.valor;
    else if (c.tipo === "en") ok = c.valores.includes(contexto.parametros[c.parametro]);
    return { ok, fallan: ok ? [] : [c.id] };
  }
  const r = ev(criterio);
  return { permitido: r.ok, fallan: [...new Set(r.fallan)].sort() };
}
```

### Modelo
| Criterio | Mensaje de rechazo |

**Prueba desde otra superficie:** ejecutar la acción desde una segunda aplicación (o desde código) con un usuario de farmacia que no es jefatura, y con el creador del pedido; ambos intentos deben rechazarse con su mensaje. Inventario: ninguna otra acción cambia el estado del pedido sin estos criterios.
### Regla
Las reglas de negocio de una acción se escriben como criterios de envío en positivo, cada uno con un rechazo que dice qué falló y qué hacer; se prueban desde otra superficie y se revisa toda acción que modifica las mismas propiedades.
### Rúbrica
- Todas las reglas aparecen como criterios, ninguna como visibilidad de un botón.
- La pertenencia a grupo está en positivo.
- La regla del motivo usa un operador «alguno» o equivalente.
- Cada criterio tiene un mensaje accionable.
- Incluye la prueba desde otra superficie y el inventario de acciones.
