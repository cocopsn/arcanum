## Antes de leer: cambiar un número en la URL
type: prediccion
id: prediccion-cambiar-id
rol: prediccion
tiempo: 2

Ana inició sesión y ve su reserva en `GET /reservas/4471`. El servidor busca la reserva por el id de la URL y la devuelve si el token es válido. Ana cambia la URL a `/reservas/4472`. ¿Qué es lo más probable?

### Opciones
- [x] Ve la reserva de otra persona: el servidor comprobó quién es Ana, pero no si esa reserva es suya.
- Recibe 401, porque su token sólo vale para la reserva 4471.
- Recibe 403, porque el navegador detecta que la URL fue modificada a mano.
- Ve su propia reserva otra vez, porque el servidor ignora el id y usa el del token.
### Justificación
El servidor hizo la autenticación (el token es válido) y se saltó la autorización (¿es de Ana la reserva 4472?). Un token identifica a la persona, no a cada recurso que puede tocar, y el navegador no impide nada: el id de la URL es un dato que el cliente controla. Usar el id del token en lugar del de la URL sería otra API distinta, no lo que hace este servidor. Es una falla horizontal de manual.

### Solución
```javascript
function puede(usuario, operacion, recurso) {
  const ops = ["ver", "editar", "cancelar", "exportar"];
  if (!usuario || typeof usuario !== "object" || !recurso || typeof recurso !== "object") return false;
  if (!ops.includes(operacion)) return false;
  const tieneId = typeof usuario.id === "string";
  switch (usuario.rol) {
    case "administracion":
      return true;
    case "paciente":
      return (operacion === "ver" || operacion === "cancelar") && tieneId && recurso.paciente === usuario.id;
    case "recepcion":
      return operacion !== "exportar" && typeof usuario.sede === "string" && recurso.sede === usuario.sede;
    case "medico":
      return operacion === "ver" && tieneId && recurso.medico === usuario.id;
    default:
      return false;
  }
}
```

## 401, 403 o 404
type: multiple_choice
id: codigo-de-estado
tiempo: 3

Un usuario autenticado de recepción de la sede norte pide `PATCH /reservas/4471`, una reserva de la sede sur que sí existe. La política no le permite editarla. ¿Qué respuesta es coherente con el libro?

### Opciones
- [x] 404 (o 403 si la API decide revelar que existe), sin modificar nada, y un registro de auditoría del intento: la identidad es válida, pero la operación no está autorizada sobre ese recurso.
- 401, porque el usuario no tiene permiso.
- 200 con el cuerpo vacío, para no dar pistas.
- 500, porque la petición provocó una excepción de permisos.
### Justificación
`401` es para cuando falla la autenticación: aquí se sabe quién es. La operación no está autorizada, así que la respuesta es `403`, o `404` si la API prefiere no confirmar que el recurso existe; en cualquier caso, nada cambia y el intento queda registrado. Un `200` miente: dice que el cambio se aplicó. Un `500` describe una falla del servidor, no una decisión de la política, y confunde el monitoreo.

## ¿Qué tipo de falla es?
type: multiple_choice
id: tipo-de-falla
tiempo: 3

En una revisión encuentras que `POST /reservas/{id}/confirmar` no revisa si la reserva pasó por la validación de horario, porque «el formulario siempre la llama antes». Un usuario manda la confirmación directamente con una reserva que nunca se validó. ¿Qué tipo de falla de control de acceso es?

### Opciones
- [x] Dependiente del contexto: el paso de confirmación confía en que el paso anterior ocurrió, y el usuario lo salta.
- Horizontal: el usuario accede a la reserva de otro usuario.
- Vertical: el usuario usa una función de administración.
- No es una falla de control de acceso, porque el usuario es el dueño de la reserva.
### Justificación
La reserva es del propio usuario y la función no es de administración, así que no es horizontal ni vertical. El problema es que la autorización de «confirmar» depende de un estado previo («ya se validó el horario») que el servidor no comprueba: el flujo está protegido sólo por el orden en que la interfaz llama a los endpoints. Que el usuario sea el dueño no lo autoriza a saltarse un paso que la política exige.

## Las pruebas negativas de un endpoint

### Modelo
*Negativas:* (1) paciente `u-91` cancela la reserva de `u-90` → 404 y la reserva sigue activa; (2) médico `u-31` cancela una reserva suya → 404 y sigue activa; (3) recepción de la sede norte cancela una reserva del sur → 404 y sigue activa; (4) sin token → 401 y sigue activa; (5) paciente `u-90` manda `"rol": "administracion"` en el cuerpo para cancelar la reserva de otro → 404 y sigue activa (el rol sale del token, nunca del cuerpo).
*Positivas:* (6) paciente `u-90` cancela su reserva → 200 y la reserva queda cancelada; (7) recepción del sur cancela una reserva del sur → 200 y queda cancelada.
*Además del código:* en cada negativa se vuelve a leer la reserva desde la base y se comprueba que no cambió, y que el intento quedó en la auditoría sin datos clínicos.

### Regla
Cada operación protegida lleva pruebas negativas por rol y por relación con el recurso, y cada prueba comprueba el estado del recurso además del código de estado; los datos de identidad salen del token verificado, nunca de la petición.

### Rúbrica
- Incluye al menos cuatro pruebas negativas que cubren falla horizontal, rol sin permiso, otra sede y ausencia de autenticación.
- Incluye una prueba que manda datos de identidad o de rol en el cuerpo y espera que se ignoren.
- Cada prueba negativa comprueba que el recurso no cambió.
- Incluye pruebas positivas que demuestran que la regla no niega de más.
- Distingue 401 de 403 o 404 según la causa.
