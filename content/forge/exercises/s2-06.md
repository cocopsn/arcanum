# S2-06 · Consenso y transacciones distribuidas

Banco de la celda: predecir qué lado de una partición puede escribir, calcular el índice comprometido de un líder con la regla del término actual, separar elección, replicación y commit, anticipar el bloqueo de dos fases, leer Raft y Spanner con el protocolo de cinco preguntas y transferir el clúster a tres regiones.

## Cinco nodos partidos en dos
type: prediccion
id: s2-06-pred-particion
rol: prediccion
escala: 50 70 90

Un clúster Raft de 5 nodos tiene como líder a `A`. La red se parte en `{A, B}` y `{C, D, E}`. Predice qué pasa con las escrituras de cada lado durante la partición.

### Opciones
- [x] `{C, D, E}` elige un líder nuevo en un término mayor y compromete escrituras; `A` puede aceptar escrituras pero nunca las compromete, porque sólo llega a 2 de 5.
- Los dos lados siguen escribiendo y se reconcilian al sanar la red.
- Ningún lado escribe hasta que la red sane.
- `{A, B}` sigue escribiendo porque ahí está el líder; `{C, D, E}` espera.
### Justificación
Comprometer exige una mayoría del clúster completo: 3 de 5. El lado de tres nodos puede elegir líder (3 votos) y comprometer; el de dos no llega nunca. `A` puede seguir creyéndose líder hasta que vea un término mayor, pero sus entradas nuevas no se comprometen y deben quedar como resultado desconocido para sus clientes. No hay reconciliación de dos historias porque sólo una se comprometió; y no es cierto que nadie escriba: el lado mayoritario sí puede.

## El índice comprometido del líder
type: code
id: s2-06-code-commit

Implementa `indiceComprometido(match, terminos, terminoActual)`, la regla con la que un líder de Raft avanza su índice de commit. `match[i]` es el índice más alto que el nodo `i` tiene replicado (incluido el propio líder; los índices empiezan en 1). `terminos[k]` es el término de la entrada de índice `k + 1` en el registro del líder. Devuelve el mayor `N` tal que **más de la mitad** de los nodos tienen `match ≥ N` **y** la entrada `N` es del `terminoActual`. Si no existe, devuelve `0`.

### Firma
```javascript
function indiceComprometido(match, terminos, terminoActual) {
  // mayor N con mayoría y terminos[N - 1] === terminoActual, o 0
}
```
### Casos
```json
[
  { "input": [[5, 5, 5, 3, 2], [1, 1, 2, 2, 3], 3], "expected": 5 },
  { "input": [[5, 5, 4, 3, 2], [1, 1, 2, 2, 3], 3], "expected": 0 },
  { "input": [[3, 3, 1], [1, 2, 2], 2], "expected": 3 },
  { "input": [[4, 1, 1], [1, 1, 1, 1], 1], "expected": 1 },
  { "input": [[0, 0, 0], [], 1], "expected": 0 },
  { "input": [[2, 2, 1, 1], [1, 1], 1], "expected": 1 },
  { "input": [[6, 6, 6, 1, 1], [1, 1, 2, 3, 3, 3], 3], "expected": 6 }
]
```
### Solución
```javascript
function indiceComprometido(match, terminos, terminoActual) {
  for (let n = terminos.length; n >= 1; n--) {
    const copias = match.filter((m) => m >= n).length;
    if (copias * 2 > match.length && terminos[n - 1] === terminoActual) return n;
  }
  return 0;
}
```
### Pistas
- «Más de la mitad» con 4 nodos son 3, no 2.
- Una entrada de un término anterior replicada en la mayoría no se compromete por conteo: espera a una entrada del término actual.

## Tres pasos que no son uno
type: multiple_choice
id: s2-06-choice-pasos
rol: recuperacion

Sin volver al libro: un servicio responde «listo» al cliente en cuanto el líder escribe la entrada en su propio disco. ¿Qué paso se saltó y qué puede pasar?

### Opciones
- [x] Se saltó el commit: la entrada no está en una mayoría; si el líder cae ahora, un líder nuevo puede no tenerla y la escritura «lista» desaparece.
- Se saltó la elección: el líder no fue elegido por mayoría.
- Ninguno: escribir en el disco del líder hace durable la entrada.
- Se saltó la aplicación, que es lo único que importa al cliente.
### Justificación
Elección, replicación y commit son pasos distintos. El líder fue elegido correctamente, pero una entrada sólo en su disco no sobrevive a su caída: el siguiente líder sale de una mayoría que puede no tenerla y la reemplaza. Durabilidad en un disco no es durabilidad del sistema. Aplicar después de comprometer está bien; responder antes de comprometer es prometer algo que el sistema no garantiza.

## El coordinador que cae
type: prediccion
id: s2-06-pred-dos-fases
rol: prediccion

Una transacción de dos fases reserva un quirófano (base de agenda) y descuenta un kit quirúrgico (base de inventario). Ambos participantes votaron «sí» y retienen sus candados. El coordinador cae antes de anunciar el resultado y tarda 20 minutos en volver. Predice qué pasa en esos 20 minutos.

### Opciones
- [x] Los dos participantes quedan en duda: no pueden confirmar ni abortar por su cuenta, y el quirófano y el kit siguen bloqueados para otras transacciones.
- Cada participante confirma solo, porque ya votó que sí.
- Cada participante aborta solo pasado un tiempo de espera.
- El participante que votó primero decide por los dos.
### Justificación
Al votar «sí», un participante promete poder confirmar si el coordinador lo decide, y no sabe si otro votó «no». Si confirmara solo, podría confirmar algo que el coordinador abortó; si abortara solo, podría deshacer algo ya confirmado en el otro. Por eso espera con sus candados tomados. Este bloqueo es el costo clásico de dos fases; replicar el coordinador por consenso (como en Spanner) es la forma de evitar que su caída lo detenga todo.

## Lectura de §08: Raft
type: production
id: s2-06-prod-paper-raft

Lee el [laboratorio de Raft de MIT 6.5840](https://pdos.csail.mit.edu/6.5840/labs/lab-raft1.html) y el paper que enlaza con el protocolo de cinco preguntas: problema, supuesto esencial, mecanismo, fallo que evita y costo que introduce. Después haz el trabajo propio de §08: escribe el historial de una falla para tu simulación de elección (cinco nodos, una partición y una caída) y analiza qué se compromete y qué se pierde.

### Modelo
Problema: mantener un registro replicado y ordenado en varias máquinas que fallan, de forma que se pueda razonar sobre él. Supuesto esencial: nodos que se detienen o se reinician con su disco intacto, sin mentir, y una mayoría que eventualmente se comunica. Mecanismo: términos con a lo sumo un líder (elección por mayoría con tiempos aleatorios), replicación con comprobación del registro anterior y commit por mayoría de entradas del término actual. Fallo que evita: dos líderes a la vez y la pérdida de entradas comprometidas tras caídas. Costo: sin mayoría no hay escrituras; cada escritura paga un viaje a la mayoría; la implementación correcta es sutil (persistencia antes de responder, regla del término actual). Trabajo propio: t0 líder A (término 2); t1 la red se parte {A, B} | {C, D, E}; t2 A acepta x=7, guardado en A y B (2/5, no comprometido); t3 D gana el término 3 con C, D y E y compromete y=9; t4 cae E: D se queda con C y D (2 de 5) y deja de comprometer, y sus clientes reciben tiempo agotado; t5 la red sana: A ve el término 3, se vuelve seguidor, x=7 se reemplaza por el registro de D y D vuelve a comprometer con A, B, C y D. Resultado: y=9 comprometido y preservado; x=7 perdido, respondido como resultado desconocido; entre t4 y t5 el sistema no aceptó escrituras, que es lo correcto sin mayoría.
### Regla
Cada lectura se reduce a cinco preguntas (problema, supuesto esencial, mecanismo, fallo que evita, costo que introduce) y se cierra con un artefacto propio; las propiedades de un protocolo valen sólo bajo su modelo de fallas, que se escribe.

- El historial tiene tiempos, términos y líderes de cada lado.
- Distingue qué se comprometió, qué se aplicó y qué se respondió a cada cliente.
- Declara el modelo de fallas bajo el que su conclusión es válida.

## Lectura de §08: Spanner
type: production
id: s2-06-prod-paper-spanner

Lee el [paper de Spanner](https://research.google/pubs/spanner-googles-globally-distributed-database-2/) con el protocolo de cinco preguntas. Después haz el trabajo propio de §08: explica qué garantiza cada mecanismo (replicación por consenso de cada fragmento, dos fases entre fragmentos y el reloj con incertidumbre acotada) y qué **no** puede suponerse en una aplicación ordinaria que use una base de datos replicada cualquiera.

### Modelo
Problema: una base de datos distribuida globalmente con transacciones cuyo orden respete el tiempo real, a escala de muchos centros de datos. Supuesto esencial: un servicio de tiempo con incertidumbre acotada y conocida (relojes atómicos y GPS en la infraestructura). Mecanismo: cada fragmento es un grupo replicado por consenso con un líder; las transacciones entre fragmentos usan dos fases con participantes que son esos grupos; las marcas de tiempo de commit se asignan con el reloj y se espera a que pase la incertidumbre antes de hacer visible el resultado. Fallo que evita: que la caída de un participante bloquee las transacciones y que dos transacciones se vean en un orden distinto del real. Costo: infraestructura de tiempo especializada, latencia de la espera de commit y de los viajes entre regiones. Qué no puede suponerse en una app ordinaria: que los relojes de sus servidores tengan una incertidumbre acotada y conocida (sin eso, ordenar por marca de tiempo no respeta el orden real), ni que una base «distribuida» cualquiera dé dos fases sin bloqueo o consistencia externa; hay que leer qué garantiza su documentación, bajo qué fallas.
### Regla
Cada lectura se reduce a cinco preguntas (problema, supuesto esencial, mecanismo, fallo que evita, costo que introduce) y se cierra con un artefacto propio; las propiedades de un paper no se extrapolan a servicios que compartan nombre o parezcan similares.
### Rúbrica

- Asigna a cada mecanismo la garantía que aporta.
- Nombra al menos dos cosas que no pueden suponerse en una aplicación ordinaria.
