## Predicción: la aserción que no revisa
type: prediccion
id: prediccion-asercion
rol: prediccion
Una API devuelve el texto `{"id":"o-17","lineas":[{"sku":"A-1","cantidad":"3"}]}`. Tu código hace `const orden = JSON.parse(texto) as Orden;`, donde `Orden` declara `cantidad: number`. ¿Qué pasa en esa línea al ejecutarse?
### Opciones
- Lanza un error de tipo porque `"3"` no es `number`.
- TypeScript convierte `"3"` a `3` automáticamente.
- [x] Nada: la aserción no existe en tiempo de ejecución y `cantidad` sigue siendo la cadena `"3"`.
- El compilador no deja compilar la línea.
### Justificación
Los tipos se borran al compilar: `as Orden` sólo le dice al compilador que confíe en ti, y no genera ninguna comprobación. `JSON.parse` devuelve lo que trae el texto, así que `cantidad` es una cadena y el error aparece después, por ejemplo cuando una suma concatena en lugar de sumar. El compilador acepta la línea porque `JSON.parse` devuelve `any`, que se puede afirmar como cualquier tipo.

## Predicción: un estado nuevo
type: prediccion
id: prediccion-estado-nuevo
rol: prediccion
Tu unión `Orden` tiene los estados `borrador`, `confirmada`, `enviada` y `cancelada`, y en un `switch (orden.estado)` la rama `default` hace `const nunca: never = orden;`. Un compañero agrega el estado `devuelta` a la unión y no toca el `switch`. ¿Qué pasa?
### Opciones
- Nada hasta que llegue una orden devuelta; entonces cae en `default` y sigue.
- [x] El código deja de compilar en la rama `default`, porque una orden `devuelta` no se puede asignar a `never`.
- El compilador agrega la rama que falta.
- Compila, pero muestra una advertencia que se puede ignorar.
### Justificación
En la rama `default` el compilador ya descartó los cuatro estados tratados; si queda alguno sin tratar, `orden` no es `never` y la asignación falla. Así un cambio en el modelo te obliga a revisar cada lugar que decide por estado, antes de que una orden devuelta caiga en silencio en un camino pensado para otra cosa. Es una garantía del compilador, y por eso sólo protege el código que compila contra esa unión: no valida datos que llegan de fuera.

## Validador de frontera de líneas
type: code
id: code-validar-lineas
Escribe `validarLineas(x)`. Recibe cualquier valor y devuelve `{ ok: true, valor }` con la lista de líneas `{ sku, cantidad }` (el `sku` sin espacios a los lados) o `{ ok: false, errores }` con **todos** los errores `{ campo, motivo }`. Reglas: si `x` no es una lista, un único error `{ campo: "lineas", motivo: "debe ser una lista" }`; si es una lista vacía, un único error `{ campo: "lineas", motivo: "al menos una línea" }`; en cada línea `i`, si el `sku` no es una cadena no vacía, `{ campo: "lineas[i].sku", motivo: "requerido" }`, y si la `cantidad` no es un entero positivo de tipo número, `{ campo: "lineas[i].cantidad", motivo: "debe ser entero positivo" }`, en ese orden. Una cadena como `"3"` no es una cantidad válida. Si hay algún error, no se devuelve ninguna línea.
### Firma
```javascript
function validarLineas(x) {
}
```
### Casos

```json
  {"name": "línea nula", "input": [[null]], "expected": {"ok": false, "errores": [{"campo": "lineas[0].sku", "motivo": "requerido"}, {"campo": "lineas[0].cantidad", "motivo": "debe ser entero positivo"}]}}

```
### Solución
```javascript
function validarLineas(x) {
  if (!Array.isArray(x)) return { ok: false, errores: [{ campo: "lineas", motivo: "debe ser una lista" }] };
  if (x.length === 0) return { ok: false, errores: [{ campo: "lineas", motivo: "al menos una línea" }] };
  const errores = [];
  const valor = [];
  x.forEach((l, i) => {
    const sku = l && typeof l === "object" ? l.sku : undefined;
    const cantidad = l && typeof l === "object" ? l.cantidad : undefined;
    const skuOk = typeof sku === "string" && sku.trim() !== "";
    const cantOk = typeof cantidad === "number" && Number.isInteger(cantidad) && cantidad > 0;
    if (!skuOk) errores.push({ campo: "lineas[" + i + "].sku", motivo: "requerido" });
    if (!cantOk) errores.push({ campo: "lineas[" + i + "].cantidad", motivo: "debe ser entero positivo" });
    if (skuOk && cantOk) valor.push({ sku: sku.trim(), cantidad: cantidad });
  });
  return errores.length ? { ok: false, errores: errores } : { ok: true, valor: valor };
}
```
### Pistas
- Primero decide la forma (`Array.isArray`), después cada campo.
- `Number.isInteger("3")` es `false`: no conviertas, rechaza.
- Junta los errores en una lista y decide al final.

## Compilador o frontera
type: multiple_choice
id: compilador-o-frontera
¿Cuál de estas garantías **sí** te la da el compilador de TypeScript sin que escribas validación en tiempo de ejecución?
### Opciones
- Que la respuesta de la API traiga el campo `lineas`.
- Que la cantidad de cada línea sea un entero positivo.
- [x] Que tu código no lea `orden.guia` en una rama donde el tipo dice que la orden está cancelada.
- Que una fecha recibida como texto corresponda a un día que existe.
### Justificación
El compilador razona sobre tu código y los tipos declarados: en la rama `cancelada` de una unión discriminada no existe `guia`, y leerla es un error de compilación. Todo lo que depende de datos que llegan de fuera (que exista un campo, que un número sea entero y positivo, que una fecha sea real) sólo se sabe al ejecutar, y por eso se valida en la frontera.

## La frontera, sin mirar
type: multiple_choice
id: recuperar-frontera
rol: recuperacion
Sin volver al libro: ¿cuál es la regla de la frontera?
### Opciones
- Validar cada dato en cada función que lo usa, por seguridad.
- Confiar en los tipos generados y no validar nada.
- [x] Validar una vez donde el dato entra, devolver todos los errores o un valor de tipo confiable, y no volver a revisarlo dentro.
- Validar sólo en la interfaz de usuario, porque es donde el usuario escribe.
### Justificación
Validar en todas partes dispersa las reglas y las contradice; no validar deja pasar lo que los tipos no pueden ver; validar sólo en la interfaz olvida las otras entradas (archivos, colas, otras API). La frontera es el único lugar donde el dato cambia de «texto de fuera» a «valor del dominio».

## Defensa: runtime frente a compilador
type: production
id: defensa-runtime-compilador
Demuestra con tu propio código cómo separas la validación en tiempo de ejecución de las garantías del compilador. Señala una línea donde confías en el compilador, una donde validas en la frontera y una regla de negocio que ningún tipo puede expresar.
### Modelo
«En `parseOrden(x: unknown): Resultado<Orden>` valido forma y reglas: `Array.isArray(x.lineas)`, `Number.isInteger(cantidad) && cantidad > 0` y que el total declarado sea la suma de las líneas. Esa es la frontera: todo lo que entra por la API pasa por ahí. Dentro, `function enviar(o: Extract<Orden, { estado: "confirmada" }>)` confía en el compilador: nadie puede llamarla con una orden cancelada sin que el código deje de compilar. La regla que ningún tipo expresa es que el total cuadre con las líneas; la reviso en la frontera y mi prueba la cubre con un total alterado.»
### Regla
El compilador garantiza la coherencia del código con sus tipos; la frontera garantiza que los datos tienen esa forma y cumplen las reglas de negocio. Una defensa muestra las dos con líneas concretas.
### Rúbrica
- Señala una línea concreta donde confía en el compilador y explica qué error previene.
- Señala la función de frontera y qué valida de forma y de negocio.
- Nombra una regla que ningún tipo puede expresar y dónde la valida.
- No usa aserciones (`as`) para convertir datos de fuera en tipos del dominio.
