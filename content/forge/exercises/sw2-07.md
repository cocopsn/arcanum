## Antes de leer: diez veces más rápida
type: prediccion
id: prediccion-amdahl
rol: prediccion
tiempo: 2

Una función ocupa el 20 % del tiempo de una petición. La reescribes y queda 10 veces más rápida. ¿Cuánto más rápida queda la petición completa?

### Opciones
- [x] Alrededor de 1.22 veces: el 80 % que no cambió sigue ahí, así que el total pasa de 1 a 0.8 + 0.02 = 0.82.
- 10 veces, porque la función es 10 veces más rápida.
- 2 veces, porque el 20 % se reduce a la mitad.
- 1.2 veces exactas, porque 20 % de mejora es 1.2.
### Justificación
Por la ley de Amdahl, la aceleración total es `1 / ((1 − p) + p / s)` = `1 / (0.8 + 0.02)` ≈ 1.22. La parte que no se tocó pone el techo: aunque la función costara cero, la petición sólo mejoraría 1.25 veces. Multiplicar por 10 ignora el 80 % restante. Ni «la mitad» ni «20 %» salen de la fórmula: el resultado es 0.82 del tiempo original.

## Percentiles por rango más cercano

Implementa los percentiles 50, 95 y 99 de una lista de latencias con el método del rango más cercano, usando sólo aritmética entera para el rango.

### Especificación
`percentiles(muestras)`:
- `muestras` es una lista de enteros (milisegundos), en cualquier orden.
- Se ordenan de menor a mayor. Para el percentil `p` (50, 95 o 99) con `n` muestras, el rango es `⌈p · n / 100⌉`, calculado como `⌊(p · n + 99) / 100⌋`, y el percentil es la muestra en esa posición (contando desde 1).

### Solución
```javascript
function percentiles(muestras) {
  if (muestras.length === 0) return { p50: null, p95: null, p99: null };
  const orden = [...muestras].sort((a, b) => a - b);
  const n = orden.length;
  const valor = (p) => orden[Math.floor((p * n + 99) / 100) - 1];
  return { p50: valor(50), p95: valor(95), p99: valor(99) };
}
```
```python
def percentiles(muestras):
    if not muestras:
        return {"p50": None, "p95": None, "p99": None}
    orden = sorted(muestras)
    n = len(orden)

    def valor(p):
        return orden[(p * n + 99) // 100 - 1]

    return {"p50": valor(50), "p95": valor(95), "p99": valor(99)}
```

### Pistas
- Ordena una copia: la lista original no es tuya.
- El rango es un número entre 1 y `n`; resta 1 para convertirlo en índice.
- Con pocas muestras, el percentil 99 suele ser el máximo: es una advertencia sobre cuántas muestras necesitas, no un error.

## Lo que dice el perfil
type: trace
id: traza-perfil
tiempo: 4

Un perfilador por muestreo tomó 2,000 muestras de una petición lenta: `seTraslapa` aparece en 1,700, `ordenarSalida` en 200 y `formatearHora` en 100. La petición tarda 800 ms y el objetivo es 200 ms. ¿Cuál es la mejor conclusión?

### Opciones
- [x] `seTraslapa` ocupa alrededor del 85 % del tiempo; aun si costara cero, la petición bajaría a unos 120 ms, así que es el único lugar donde una optimización puede alcanzar el objetivo, y hay que revisar si su algoritmo (no sólo su código) es el problema.
- Optimizar `formatearHora`, porque es la más fácil de mejorar.
- Optimizar las tres por igual, porque todas aparecen en el perfil.
- Optimizar `ordenarSalida`, porque ordenar siempre es lo más caro.
### Justificación
Las muestras estiman la fracción del tiempo: 1,700 de 2,000 es 85 %, unos 680 de los 800 ms. Sin ella quedarían unos 120 ms, debajo del objetivo; con cualquiera de las otras dos, el techo no lo alcanza (`formatearHora` es el 5 %, 40 ms). La facilidad del cambio no decide nada si el techo no llega al objetivo. Repartir el esfuerzo por igual ignora el perfil. Ordenar no es «siempre» lo más caro: aquí es el 10 %.

## Una comparación que se pueda creer
type: multiple_choice
id: experimento-creible
tiempo: 3

Comparas la versión vieja y la nueva de `huecosLibres`. ¿Cuál de estos experimentos es defendible?

### Opciones
- [x] La misma carga generada con una semilla fija para las dos versiones, en la misma máquina, descartando una corrida de calentamiento, con cinco repeticiones y reportando percentiles 50 y 99 con su variación.
- Una corrida de cada versión con una agenda inventada a mano, comparando el tiempo total.
- La versión vieja medida la semana pasada en el portátil y la nueva hoy en el servidor.
- Diez corridas de la versión nueva y una de la vieja, para tener más datos de la que importa.
### Justificación
Para atribuir la diferencia al cambio, todo lo demás debe ser igual: la carga, la máquina y el tratamiento del calentamiento, con repeticiones suficientes para ver si la diferencia supera la variación. Una sola corrida con datos a mano no dice nada del caso general. Medir en máquinas y fechas distintas mezcla el cambio con todo lo demás. Medir más una versión que la otra no hace más justa la comparación.

## Defiende el experimento
type: production
id: produccion-defensa-experimento
tiempo: 12

Defiende la optimización del ejemplo del libro como pide la ficha: describe el experimento (carga, línea base, perfil, cambio, equivalencia y medición), cuantifica la mejora y describe un escenario concreto en el que la optimización deja de ayudar.

### Modelo
*Carga:* 200 agendas de 5,000 bloques desordenados generadas con una semilla fija, duración de 30 minutos; misma máquina y configuración para las dos versiones.
*Línea base:* cinco repeticiones descartando la primera; percentil 50 de 620 ms y percentil 99 de 900 ms, frente a un objetivo de 100 ms.
*Perfil:* el 88 % de las muestras en `seTraslapa` dentro de un ciclo doble; techo de Amdahl de unas 8 veces, insuficiente acelerando sólo la función, así que se cambia el algoritmo.
*Cambio:* ordenar una vez por inicio y recorrer buscando huecos entre bloques consecutivos (de O(n²) a O(n log n)).
*Equivalencia:* la versión vieja como referencia contra 10,000 agendas generadas, incluidas vacías, de un bloque y con bloques que se tocan; resultados idénticos.
*Medición:* misma carga y procedimiento; percentil 50 de 9 ms y percentil 99 de 14 ms.
*Dónde deja de ayudar:* con agendas de pocas decenas de bloques las dos versiones tardan menos de un milisegundo; y si la agenda llega de un servicio remoto que tarda 300 ms, el tiempo que ve el usuario lo domina la red y la mejora de CPU no se nota.

### Regla
Una optimización se defiende con una carga reproducible, una línea base con percentiles y repeticiones, un perfil que justifica qué se cambió y su techo, una prueba de equivalencia contra la versión anterior y una medición con la misma carga, más los límites fuera de los que la mejora deja de valer.

### Rúbrica
- Describe la carga con semilla, tamaño y distribución.
- Reporta percentiles (no sólo promedio) antes y después, con repeticiones.
- Usa el perfil y el techo de Amdahl para justificar qué se cambió.
- Incluye una prueba de equivalencia contra la versión vieja con casos de borde.
- Describe un escenario concreto donde la mejora deja de ayudar.
