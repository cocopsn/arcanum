## Antes de leer: el tiempo de espera vencido
type: prediccion
id: prediccion-timeout
rol: prediccion
tiempo: 2

Tu servicio llama al ERP para crear una orden y, a los 5 segundos, vence el tiempo de espera sin respuesta. ¿Qué sabes con certeza sobre la orden?

### Opciones
- [x] Nada: la petición pudo no llegar, pudo fallar o pudo aplicarse y perder la respuesta; hace falta una forma de averiguarlo o de reintentar sin duplicar.
- Que no se creó, porque si se hubiera creado el ERP habría respondido.
- Que se creó, porque el ERP sólo tarda cuando está procesando.
- Que falló, así que lo correcto es mostrar un error al usuario y no reintentar.
### Justificación
Un tiempo de espera vencido es el tercer resultado de una llamada por red: «no sé». La respuesta pudo perderse después de que el ERP aplicó el cambio, o la petición pudo no llegar nunca. Suponer cualquiera de los dos lleva a un error: si supones que no se creó y reintentas sin protección, puedes duplicarla; si supones que falló y avisas al usuario, puede que la orden sí exista. La salida es reintentar con una clave de idempotencia o reconciliar consultando al ERP.

## Un registro de claves de idempotencia
type: code
id: codigo-registro-claves
tiempo: 18

Simula el registro de claves de idempotencia de un servicio: procesa una secuencia de solicitudes en orden y devuelve la respuesta a cada una.

### Especificación
`responder(solicitudes)`:
- `solicitudes` es una lista de objetos `{ clave, cuerpo }`; `cuerpo` es un valor JSON (objetos anidados permitidos).
- Si `clave` no es una cadena no vacía, la respuesta es `"rechazada"` y no se registra nada.
- Si la clave no se ha visto, se aplica el efecto: un contador de efectos empieza en 0 y sube en 1; la respuesta es `"aplicada:N"`, con `N` el valor del contador tras aplicar.
- Si la clave ya se vio con un cuerpo **igual** (igualdad de valor: el orden de las propiedades de los objetos no importa), no se aplica nada y la respuesta es `"repetida:N"`, con el `N` de la primera vez.
- Si la clave ya se vio con un cuerpo **distinto**, no se aplica nada y la respuesta es `"conflicto"`; el registro de esa clave no cambia.
- Devuelve la lista de respuestas, en orden.

### Solución
```javascript
function responder(solicitudes) {
  const canon = (v) => {
    if (v === null || typeof v !== "object") return JSON.stringify(v);
    if (Array.isArray(v)) return "[" + v.map(canon).join(",") + "]";
    return "{" + Object.keys(v).sort().map((k) => JSON.stringify(k) + ":" + canon(v[k])).join(",") + "}";
  };
  const registro = new Map();
  let efectos = 0;
  const salida = [];
  for (const s of solicitudes) {
    if (typeof s.clave !== "string" || s.clave === "") {
      salida.push("rechazada");
      continue;
    }
    const huella = canon(s.cuerpo);
    const previa = registro.get(s.clave);
    if (!previa) {
      efectos += 1;
      registro.set(s.clave, { huella, n: efectos });
      salida.push("aplicada:" + efectos);
    } else if (previa.huella === huella) {
      salida.push("repetida:" + previa.n);
    } else {
      salida.push("conflicto");
    }
  }
  return salida;
}
```
```python
import json

def responder(solicitudes):
    registro = {}
    efectos = 0
    salida = []
    for s in solicitudes:
        clave = s.get("clave")
        if not isinstance(clave, str) or clave == "":
            salida.append("rechazada")
            continue
        huella = json.dumps(s.get("cuerpo"), sort_keys=True, separators=(",", ":"), ensure_ascii=False)
        previa = registro.get(clave)
        if previa is None:
            efectos += 1
            registro[clave] = (huella, efectos)
            salida.append("aplicada:" + str(efectos))
        elif previa[0] == huella:
            salida.append("repetida:" + str(previa[1]))
        else:
            salida.append("conflicto")
    return salida
```

### Pistas
- Guarda por clave la huella del cuerpo y el número de efecto de la primera vez.
- La huella debe ser canónica: dos objetos iguales con propiedades en distinto orden dan la misma huella; dos arreglos con distinto orden no.
- Un conflicto no reemplaza el registro: la siguiente solicitud con el cuerpo original sigue siendo una repetición.

## La multiplicación de reintentos
type: trace
id: traza-amplificacion
tiempo: 3

Una petición del usuario pasa por tres capas: la app llama al servicio de órdenes, que llama al servicio de inventario, que llama a la base de datos. Cada capa reintenta hasta 3 veces (4 intentos en total) cuando la capa de abajo falla. La base de datos está caída y falla siempre. ¿Cuántas peticiones recibe la base de datos por una sola petición del usuario?

### Opciones
- [x] 64, porque cada uno de los 4 intentos de la app produce 4 intentos de órdenes, y cada uno de esos produce 4 intentos de inventario: 4 × 4 × 4.
- 12, porque son 4 intentos en cada una de las 3 capas.
- 9, porque son 3 reintentos en cada una de las 3 capas.
- 4, porque sólo la capa más cercana a la base de datos la llama.
### Justificación
Los reintentos se multiplican entre capas, no se suman. Inventario hace 4 intentos contra la base por cada vez que lo llaman; órdenes lo llama 4 veces por cada intento de la app; la app lo intenta 4 veces. En total, 4³ = 64 peticiones a una base que ya está caída. Sumar (12 o 9) ignora que cada capa reintenta cada fallo de la de abajo. Que sólo inventario llame a la base es cierto, pero lo llaman 16 veces. Por eso conviene reintentar en una sola capa y que las demás fallen rápido.

## Guardar la clave antes o después
type: multiple_choice
id: clave-antes-despues
tiempo: 3

Tu servicio crea órdenes en un ERP externo que acepta una referencia del cliente y la usa para rechazar duplicados. El proceso puede caer en cualquier punto. ¿Qué diseño evita la orden duplicada cuando el proceso cae justo después de que el ERP aplicó el cambio y antes de responder?

### Opciones
- [x] Registrar la clave como `en-curso` con una inserción única antes de llamar al ERP, pasar la clave como referencia al ERP y, ante un `en-curso` viejo, reconciliar consultando al ERP por esa referencia en lugar de volver a crear.
- Llamar al ERP y guardar la clave al recibir la respuesta, porque así sólo se registran operaciones exitosas.
- Guardar la clave en memoria del proceso, porque es más rápido que la base de datos.
- No guardar claves: si el ERP tarda, el cliente debe esperar más antes de reintentar.
### Justificación
Si la clave se guarda después del efecto, una caída entre las dos líneas deja el efecto aplicado y la clave sin registrar: el reintento la busca, no la encuentra y repite. Registrar antes, con una operación atómica que falle si la clave existe, también evita que dos reintentos concurrentes ejecuten ambos. Pasar la clave al ERP extiende la protección al sistema externo, y la reconciliación resuelve el `en-curso` sin adivinar. La memoria del proceso desaparece justo en la caída. Esperar más reduce la probabilidad, pero no elimina el resultado desconocido.

## Declara dónde termina tu garantía
type: production
id: produccion-limite-garantia
tiempo: 12

Tu servicio de cobros usa claves de idempotencia, pero el proveedor de pagos **no** acepta referencias del cliente ni deduplica. Escribe la declaración de garantía que publicarías para los equipos que llaman a tu servicio: qué garantizas, en qué caso no puedes garantizarlo, qué estado ven mientras tanto y cómo se resuelve ese estado.

### Modelo
*Garantía:* para una misma clave de idempotencia, el servicio llama al proveedor a lo sumo una vez mientras su registro esté disponible, devuelve el mismo resultado a todos los reintentos con el mismo cuerpo y responde `conflicto` si llega la misma clave con otro cuerpo.
*Límite:* si el proceso cae o vence la espera después de llamar al proveedor y antes de registrar su respuesta, el servicio no sabe si el cobro ocurrió. El proveedor no permite deduplicar, así que el servicio **no** vuelve a cobrar automáticamente.
*Estado visible:* la operación queda `pendiente-de-confirmar`; quien llama recibe ese estado, no un éxito ni un fallo, y no debe reintentar con una clave nueva.
*Resolución:* un reconciliador consulta los movimientos del proveedor por cliente, monto y ventana de tiempo; si encuentra exactamente un cargo que coincide, marca `completada` con ese cargo; si no encuentra ninguno tras la ventana de asentamiento del proveedor, marca `fallida` y se puede reintentar; si encuentra más de uno o la coincidencia es ambigua, pasa a revisión humana.
*Lo que no prometemos:* exactamente una vez de punta a punta con este proveedor.

### Regla
La idempotencia protege lo que tu servicio controla. Cuando el efecto ocurre en un sistema que no deduplica, la garantía termina en tu frontera, y el caso desconocido se expone como un estado propio y se resuelve con reconciliación, nunca adivinando.

### Rúbrica
- Distingue lo que el servicio garantiza de lo que no puede garantizar con este proveedor.
- Nombra el caso exacto en que la garantía falla (efecto aplicado y respuesta perdida).
- Expone un estado intermedio explícito y dice qué debe hacer quien llama mientras dura.
- Describe una reconciliación con criterio para coincidencia única, ninguna y ambigua.
- No promete «exactamente una vez» de punta a punta.

## Giro: el reintento que llega un día después
type: giro
id: giro-reintento-tardio
rol: transferencia
tiempo: 15

Las claves de idempotencia se guardan 24 horas. Una app móvil sin conexión acumula órdenes y las reenvía al recuperar la red, a veces dos días después, con sus claves originales. Además, el ERP ahora cobra por cada llamada de consulta, así que reconciliar todo cuesta dinero. Rediseña: qué haces con un reintento cuya clave ya expiró, cómo cambias la retención de claves y qué parte de la garantía se conserva o se pierde.

### Rúbrica
- Reconoce que una clave expirada convierte un reintento tardío en una operación aparentemente nueva y que eso puede duplicar la orden.
- Propone una retención de claves ligada al tiempo máximo real de reenvío (o a la vida de la operación), con su costo de almacenamiento estimado.
- Usa información que viaja con la solicitud (por ejemplo, la fecha de creación en el dispositivo) para detectar reintentos más viejos que la retención y tratarlos como `pendiente-de-confirmar` en lugar de aplicarlos.
- Limita el costo de reconciliar (por ejemplo, sólo para claves expiradas o `en-curso` viejos) y lo justifica con números.
- Declara explícitamente qué garantía cambia para los clientes y cómo se les comunica.
