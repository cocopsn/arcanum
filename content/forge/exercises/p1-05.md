### Solución
```javascript
function evaluar_expectativas(filas, expectativas) {
  const nulo = (v) => v === null || v === undefined;
  const fallan = [];
  for (const e of expectativas) {
    let ok = true;
    if (e.tipo === "llave") {
      const vistos = new Set();
      for (const f of filas) {
        const partes = e.columnas.map((c) => f[c]);
        if (partes.some(nulo)) { ok = false; break; }
        const k = JSON.stringify(partes);
        if (vistos.has(k)) { ok = false; break; }
        vistos.add(k);
      }
    } else if (e.tipo === "conteo") {
      const n = filas.length;
      if ((e.min !== undefined && n < e.min) || (e.max !== undefined && n > e.max)) ok = false;
    } else if (e.tipo === "lista") {
      const col = e.columnas[0];
      ok = filas.every((f) => !nulo(f[col]) && e.valores.includes(f[col]));
    } else if (e.tipo === "no_nulo") {
      const col = e.columnas[0];
      ok = filas.every((f) => !nulo(f[col]));
    }
    if (!ok) fallan.push(e.id);
  }
  return fallan.sort();
}
```

```python
def evaluar_expectativas(filas, expectativas):
    fallan = []
    for e in expectativas:
        ok = True
        t = e["tipo"]
        if t == "llave":
            vistos = set()
            for f in filas:
                partes = tuple(f.get(c) for c in e["columnas"])
                if any(p is None for p in partes) or partes in vistos:
                    ok = False
                    break
                vistos.add(partes)
        elif t == "conteo":
            n = len(filas)
            if ("min" in e and n < e["min"]) or ("max" in e and n > e["max"]):
                ok = False
        elif t == "lista":
            col = e["columnas"][0]
            ok = all(f.get(col) is not None and f.get(col) in e["valores"] for f in filas)
        elif t == "no_nulo":
            col = e["columnas"][0]
            ok = all(f.get(col) is not None for f in filas)
        if not ok:
            fallan.append(e["id"])
    return sorted(fallan)
```

- Sobre un lote vacío, las reglas «para toda fila» se cumplen; el conteo mínimo no.

## ¿Qué dice un check de estado de job?
type: multiple_choice
id: estado-de-job
tiempo: 2

Un schedule construye `cobros_vigentes` y después `resumen`. Hoy `cobros_vigentes` se construyó bien y `resumen` falló. Tienes un check de estado de job sólo sobre `cobros_vigentes`. ¿Qué muestra?

### Opciones
- [x] Verde: el check de estado de job tiene éxito si su dataset objetivo se construyó bien, aunque el build falle más abajo; para ver la falla del schedule completo hace falta un check de estado de schedule.
- Rojo, porque el schedule del que forma parte falló.
- Cancelado, porque cualquier falla en el schedule cancela todos sus checks.
- No se evalúa hasta que el schedule completo termine bien.
### Justificación
La página de tipos de checks de Data Health define que el estado de job se evalúa sobre el dataset en el que está instalado y que tiene éxito aunque el build falle aguas abajo; si la falla ocurre antes de llegar a ese dataset, el job queda cancelado y el check no se evalúa. Por eso la misma documentación recomienda un check de estado de schedule para cada schedule.

## ¿Detener el build o alertar?
type: multiple_choice
id: detener-o-alertar
tiempo: 3

Tienes dos checks nuevos para el panel de cobros: (a) la llave `folio` debe ser única en `cobros_vigentes`; (b) el máximo de `ts` debe estar a menos de 2 días del corte. La decisión del panel se toma cada mañana. ¿Cómo los configuras?

### Opciones
- [x] (a) como expectativa de datos que detiene el build, porque un folio duplicado infla los cobros y haría actuar mal; (b) como health check de frescura que alerta a quien responde, porque el dato viejo hace actuar tarde y la persona puede decidir esperar o usar el panel con la advertencia.
- Los dos como alertas, para no detener nunca un build.
- Los dos como expectativas que detienen el build, porque todo check debe ser estricto.
- Ninguno: el build en verde ya garantiza llaves únicas y datos de hoy.
### Justificación
La regla del libro: detiene lo que haría actuar mal; alerta lo que haría actuar tarde. Un duplicado propaga un número falso aguas abajo; la falta de frescura no cambia los números existentes, pero los vuelve viejos, y alguien con contexto debe decidir. El build en verde no garantiza ninguna de las dos cosas.

## Matriz de fallas sembradas
type: production
id: fallas-sembradas
tiempo: 12

Para el dataset sintético `inventario_diario` (una fila por `insumo_id` y `sucursal_id` por día, con `stock` entero ≥ 0, `actualizado_en` y `unidad` en una lista cerrada), escribe cinco checks y, para cada uno, la falla que sembrarías para verlo en rojo y el mensaje que esperas. Incluye al menos uno de frescura y uno de coherencia con otra tabla.

### Modelo
| Check | Falla sembrada | Mensaje esperado |
|---|---|---|
| Llave primaria (`insumo_id`, `sucursal_id`, `dia`) | Repetir la fila de un insumo | «llave duplicada: (I-07, SUC-2, 2026-03-04)» |
| Por fila `stock >= 0` | Insertar un stock de −3 | «stock negativo en I-12» |
| Valor en lista para `unidad` | Escribir `pieza` en lugar de `pza` | «unidad no permitida: pieza» |
| Frescura del contenido: `MAX(actualizado_en)` a menos de 1 día del corte | Dejar el pipeline leyendo el corte de ayer | «inventario con más de 1 día» |
| Coherencia: insumos con consumo en citas ⊆ insumos en inventario | Borrar un insumo del inventario | «I-03 se consume y no tiene inventario» |
### Regla
Cada check corresponde a una promesa escrita y se demuestra viéndolo fallar por la razón correcta: el mensaje del fallo nombra lo que protege. Si una falla sembrada no lo dispara, el check no mide esa promesa.
### Rúbrica
- Cinco checks, cada uno ligado a una promesa (llave, rango, lista, frescura, coherencia).
- Cada check tiene su falla sembrada concreta.
- Cada mensaje esperado nombra lo que protege, con el dato que lo disparó.
- La frescura usa la marca de tiempo del contenido contra un corte, no el tiempo desde la última transacción.
- La coherencia compara con otra tabla.
