## El segundo evento del mismo clic
type: prediccion
id: segundo-evento
rol: prediccion
tiempo: 3

Un botón tiene dos eventos en este orden: (1) fijar `$alertaSel` a la alerta A-211; (2) enviar una acción con el parámetro `medico = $sugerido`, donde `$sugerido` es una variable derivada de la propiedad «sugerido» de `$alertaSel`. Antes del clic, `$alertaSel` era A-207 (sugerido «Soto»); el sugerido de A-211 es «Vega». Predice qué médico recibe la acción.

### Opciones
- [x] Puede recibir «Soto»: el evento 1 deja `$alertaSel` al día, pero la derivada `$sugerido` no está garantizada al día cuando corre el evento 2.
- «Vega», porque los eventos esperan a que se recalculen las variables dependientes.
- Ninguno: Workshop bloquea el segundo evento hasta que el usuario vuelva a hacer clic.
- «Vega», porque las variables derivadas se recalculan antes de cada evento.
### Justificación
La documentación de eventos de Workshop indica que los eventos corren en secuencia, que la variable fijada queda al día para el siguiente evento, pero que las variables que dependen de ella no lo están antes de que corra el siguiente, y que no hay forma de forzar la espera. Por eso se separan los gestos o la acción calcula y valida el valor ella misma.

## Detectar lecturas viejas en una cadena de eventos
type: code
id: lecturas-viejas
tiempo: 15

Escribe `lecturas_viejas(derivadas, eventos)`. `derivadas` es un objeto `variable → lista de variables de las que depende` (las que no aparecen como llave son variables base; una derivada puede depender de otra derivada). `eventos` es la lista ordenada de una cadena, cada uno `{ id, lee: [variables], escribe: variable | null }`; sólo se escriben variables base. ### Solución
```javascript
function lecturas_viejas(derivadas, eventos) {
  const escritas = new Set();
  const vieja = (v, visto = new Set()) => {
    if (!(v in derivadas)) return false;
    if (visto.has(v)) return false;
    visto.add(v);
    return derivadas[v].some((d) => escritas.has(d) || vieja(d, visto));
  };
  const out = [];
  for (const e of eventos) {
    for (const v of e.lee) if (vieja(v)) out.push({ evento: e.id, variable: v });
    if (e.escribe) escritas.add(e.escribe);
  }
  return out;
}
```
```python
def lecturas_viejas(derivadas, eventos):
    escritas = set()
    def vieja(v, visto=None):
        visto = visto if visto is not None else set()
        if v not in derivadas or v in visto:
            return False
        visto.add(v)
        return any(d in escritas or vieja(d, visto) for d in derivadas[v])
    out = []
    for e in eventos:
        for v in e["lee"]:
            if vieja(v):
                out.append({"evento": e["id"], "variable": v})
        if e.get("escribe"):
            escritas.add(e["escribe"])
    return out
```
### Pistas
- Lleva el conjunto de variables base escritas por eventos anteriores de la cadena.
- Una derivada es vieja si alguna de sus dependencias, directa o transitiva, está en ese conjunto.
- Revisa las lecturas de un evento antes de registrar lo que ese evento escribe.

## La corrección que no corrige
type: multiple_choice
id: evento-vacio
tiempo: 2

Para que la acción reciba el sugerido correcto, alguien agrega un tercer evento vacío entre «fijar la selección» y «enviar la acción», «para dar tiempo». ¿Qué pasa?

### Opciones
- [x] Nada cambia: los eventos corren en secuencia sin esperar a los cálculos dependientes, así que un evento intermedio no garantiza que la derivada esté al día.
- Funciona, porque cada evento adicional espera un ciclo de recálculo.
- Funciona sólo si el evento vacío es de tipo «abrir capa».
- Rompe el botón, porque Workshop no admite eventos vacíos.
### Justificación
La documentación indica que no se puede forzar a los eventos a esperar la propagación completa y recomienda separar los eventos en varias acciones del usuario. Las correcciones reales son dos gestos o una acción que reciba la alerta y calcule y valide el sugerido.

## Selección por llave
type: multiple_choice
id: seleccion-llave
tiempo: 2

Mientras la coordinadora revisa la tabla, llega una actualización y la lista de alertas se reordena. Tu módulo guardaba la selección como «la fila 3». ¿Qué riesgo hay y cómo se evita?

### Opciones
- [x] La fila 3 ahora es otra alerta y la acción se enviaría sobre ella; la selección debe guardar la llave del objeto (A-211), no su posición.
- Ninguno, porque la tabla bloquea las actualizaciones mientras hay una fila seleccionada.
- Se evita refrescando la página antes de cada acción.
- Se evita ordenando la tabla por fecha de creación para que no cambie.
### Justificación
Cuando los datos cambian mientras el usuario trabaja, la posición deja de identificar al objeto. La llave del objeto sí lo identifica. Además, la acción debe validar con sus criterios de envío que la alerta sigue abierta y que el valor tiene sentido.

## Guion de reproducción
type: production
id: guion-reproduccion
tiempo: 12

Escribe el guion para **reproducir** un cambio de selección durante una actualización de datos en la bandeja de alertas: estado inicial, pasos exactos, qué observas con el defecto, cómo provocas la actualización a mitad del flujo, qué corrección aplicas y cómo demuestras con el mismo guion que quedó corregido.

### Modelo
1. **Estado inicial:** alerta A-207 seleccionada (sugerido «Soto»); lista filtrada por sede Norte con 4 alertas.
2. **Defecto:** clic en la fila de A-211 y, en el mismo clic, «Reasignar» (botón con dos eventos: fijar selección y enviar con el sugerido).
3. **Observación con defecto:** la acción recibe «Soto» en lugar de «Vega»; se registra el parámetro enviado.
4. **Actualización a mitad del flujo:** con la alerta A-211 seleccionada, llega un cambio que agrega una alerta urgente y reordena la tabla; se verifica a qué alerta apunta la selección.
5. **Corrección:** la selección se fija al elegir la fila y guarda la llave; «Reasignar» sólo envía y la acción recibe la alerta como parámetro, calcula el sugerido y su criterio de envío rechaza un médico que no corresponde.
6. **Demostración:** repetir los pasos 2 a 4: la acción recibe «Vega» y la selección sigue en A-211 tras el reordenamiento; un intento con un sugerido inválido se rechaza con su mensaje.
### Regla
Un estado inconsistente se demuestra corregido reproduciéndolo: mismo guion antes y después, con la actualización de datos provocada a mitad del flujo, y con la acción como última defensa.
### Rúbrica
- Parte de un estado inicial conocido y pasos exactos.
- Observa y registra el valor que recibe la acción con el defecto.
- Provoca la actualización de datos a mitad del flujo y revisa la selección.
- Aplica una corrección basada en lo que la plataforma garantiza (gestos separados, llave, validación en la acción).
- Repite el mismo guion para demostrar la corrección.
