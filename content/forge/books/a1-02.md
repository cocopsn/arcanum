> Dos ventas idénticas del mismo producto en el mismo minuto: ¿son un evento repetido o dos ventas?

Libro ligero. Las tablas hash por dentro están en [el libro de ITC C3](#libro:itc-c3) y los dos punteros en
[CP1](#libro:cp1). Aquí está lo propio de la misión de A1-02: deduplicar y conciliar eventos **sin perder multiplicidades**, y
defender la diferencia entre identidad e igualdad.

## Identidad no es igualdad

Un evento tiene **identidad** (quién es: su `event_id`, asignado una vez en el origen) y **contenido** (qué dice: producto,
unidades, hora). Dos preguntas distintas salen de ahí:

- **¿Es el mismo evento?** Se responde con la identidad. Un reintento de red reenvía el mismo `event_id` y debe contarse una
  vez.
- **¿Dicen lo mismo?** Se responde con el contenido. Dos ventas reales de dos unidades del mismo producto tienen contenido
  igual y son dos hechos.

Deduplicar por contenido (meter tuplas en un `set`) confunde las dos preguntas y borra ventas reales. Deduplicar por
identidad conserva la multiplicidad. El tutorial de
[estructuras de datos de Python](https://docs.python.org/3/tutorial/datastructures.html) muestra los dos materiales de esta
misión: el `set` descarta repetidos por igualdad y el diccionario asocia una llave a un valor, que aquí es un conteo o el
evento elegido para esa identidad.

## Costo esperado y peor caso

Con un diccionario, deduplicar `n` eventos cuesta `O(n)` **esperado**: cada inserción y cada consulta cuestan `O(1)` en
promedio si la función hash reparte bien las llaves. Ese «si» importa: con llaves que colisionan a propósito, una consulta
puede recorrer muchas llaves y el total degrada hacia `O(n²)`. La unidad de hashing de
[MIT 6.006](https://www.ocw.mit.edu/courses/6-006-introduction-to-algorithms-spring-2020/pages/lecture-notes/) separa esas
dos garantías. Si necesitas un costo que no dependa de la suerte, ordena las dos listas (`O(n log n)`) y concílialas con dos
punteros en `O(n + m)`: el peor caso queda fijo y el resultado sale ordenado.

## Ejemplo trabajado

Conciliar lo que el almacén esperaba contra lo que llegó, como multiconjuntos ordenados:

```javascript
function diferenciasOrdenadas(a, b) {        // a y b ordenados, con repetidos
  const soloA = [], soloB = [];
  let i = 0, j = 0;
  while (i < a.length && j < b.length) {
    if (a[i] === b[j]) { i++; j++; }          // una unidad de cada lado se cancela
    else if (a[i] < b[j]) soloA.push(a[i++]); // a[i] ya no puede emparejar
    else soloB.push(b[j++]);
  }
  while (i < a.length) soloA.push(a[i++]);
  while (j < b.length) soloB.push(b[j++]);
  return [soloA, soloB];
}
```

Con `a = [1, 2, 2, 3]` y `b = [2, 3, 3]` sale `[[1, 2], [3]]`: sobra un 2 de lo esperado y un 3 de lo recibido. El argumento
de correctitud es que, si `a[i] < b[j]`, ningún elemento posterior de `b` puede valer `a[i]`, porque `b` está ordenado. Cada
paso avanza al menos un puntero, así que el lazo hace a lo sumo `n + m` vueltas.

## Contraejemplo

```python
eventos = [("e1", "SKU-A", 2), ("e2", "SKU-A", 2), ("e2", "SKU-A", 2)]
unicos = {(sku, u) for (_id, sku, u) in eventos}   # {("SKU-A", 2)}
```

El reporte dice 2 unidades. La verdad son 4: `e1` y `e2` son dos ventas y sólo el tercer registro es un reintento. Ningún
error lo delata, porque el `set` hizo exactamente lo que se le pidió. La llave correcta es `event_id`.

## Diagrama

```text
 llegan:   e1 A×2   e2 A×2   e2 A×2 (reintento)   e3 B×1
              |        |        |                    |
 por contenido: {(A,2), (B,1)}          -> A=2  B=1   (miente)
 por identidad: {e1:(A,2), e2:(A,2), e3:(B,1)} -> A=4  B=1
                         ^ el reintento cae sobre la misma llave
```
