# S1-07 · Pruebas por riesgo

> **Pregunta raíz.** Tu suite tiene 100 % de cobertura y todas las pruebas pasan. El viernes, la exportación de órdenes a facturación procesa 100 órdenes de 4,000. ¿Qué medía tu suite, y qué prueba habría visto la falla?

## 1. Probar por riesgo, no por cobertura

La cobertura dice qué líneas se **ejecutaron** durante las pruebas; no dice qué comportamiento se **verificó**. Una prueba sin aserciones útiles cubre igual que una buena. La lectura de pruebas de [MIT 6.005](https://www.ocw.mit.edu/ans7870/6/6.005/s16/classes/03-testing/index.html) presenta la cobertura (de sentencias, de ramas, de caminos) junto a la elección de casos por particiones del espacio de entradas; la segunda es la que decide qué se verifica. Probar por riesgo empieza por otra pregunta: **¿qué puede salir mal, cuánto daña y cuál es la prueba más barata que lo detectaría?**

Para el sistema de órdenes de la clínica, una lista de riesgos se ve así:

| Riesgo | Daño | Prueba más barata que lo detecta |
|---|---|---|
| Transición prohibida aceptada | Informe huérfano, facturación rechazada | Unidad: todos los pares (estado, evento) inválidos |
| Doble reserva bajo concurrencia | Paciente sin atender | Integración: dos transacciones reales contra la base |
| Exportación incompleta por paginación | Facturación incompleta | Integración contra la API real (o un doble que pagina igual) |
| Fechas en otra zona horaria | Citas a la hora equivocada | Unidad con reloj y zona fijados |
| Recorrido completo roto tras un despliegue | La clínica no opera | Recorrido crítico reproducible |

La prioridad sale del daño y de la probabilidad, no de lo fácil que es escribir la prueba.

## 2. Tres niveles con propósito

- **Unidad:** lógica pura con entradas controladas (la tabla de transiciones, el cálculo de traslapes, el cursor de paginación). Rápida, precisa y ciega a todo lo que está fuera de la función.
- **Integración:** la lógica con sus dependencias reales o con dobles que se comportan como ellas (la base con sus restricciones, el SQL real, la serialización, la paginación de la API). Más lenta; ve lo que la unidad no ve.
- **Recorrido crítico:** el camino que, si se rompe, detiene la operación (reservar → atender → informar → facturar), ejecutado de punta a punta con datos sintéticos fijos, reloj fijo y semilla fija para que el resultado sea **reproducible**: la misma corrida da el mismo resultado hoy y dentro de un mes.

Las plataformas traen herramientas para cada nivel. La documentación de Foundry describe [pruebas unitarias en repositorios de transformaciones Python](https://www.palantir.com/docs/foundry/transforms-python/unit-tests), que aplican a pipelines por lotes y no a pipelines de streaming, y un paquete experimental para [probar código TypeScript del OSDK](https://www.palantir.com/docs/foundry/ontology-sdk/typescript-osdk-testing) con objetos y links simulados y llamadas del cliente reemplazadas por respuestas fijas. Saber qué nivel cubre cada herramienta es parte de la decisión.

## 3. Lo que sobrevive a los mocks

Un mock es una **suposición escrita**: «la API responde así». Si la suposición es falsa, la prueba pasa y el sistema falla. Las fallas reales que suelen sobrevivir a una suite de mocks:

- **Paginación y límites:** el mock devuelve todo de una vez; la API real entrega páginas de 100.
- **Esquema que deriva:** el mock conserva un campo que la API real renombró.
- **Permisos:** el mock no tiene permisos; la cuenta de servicio real no puede leer una sede.
- **Tiempo y zona:** el mock usa la zona de tu máquina; producción, la del servidor.
- **Concurrencia y volumen:** el mock atiende una petición a la vez y con 10 filas.

Dos defensas. **Pruebas de contrato:** respuestas grabadas de la dependencia real que el doble debe reproducir, revisadas cuando la dependencia cambia. **Pruebas de mutación:** se introducen errores pequeños y deliberados en el código (un `<` por `<=`, una condición omitida) y se mide cuántos «mata» la suite. Un mutante que sobrevive señala un comportamiento que ninguna prueba verifica. Es la forma honesta de medir la calidad de una suite, y es el tipo de ejercicio que trae esta celda. El [paquete de pruebas del OSDK](https://www.palantir.com/docs/foundry/ontology-sdk/typescript-osdk-testing) simula el cliente; precisamente por eso no puede, solo, demostrar que la API real pagina como el doble.

## Ejemplo trabajado

**Encargo.** Diseña pruebas unitarias, de integración y un recorrido crítico reproducible para la reserva de citas, y mide su calidad con mutantes.

**Paso 1 · La función bajo prueba.** Dos citas del mismo equipo se traslapan si sus intervalos semiabiertos `[inicio, fin)` se cruzan:

```javascript
function seTraslapan(a, b) {
  return a.inicio < b.fin && b.inicio < a.fin;
}
```

**Paso 2 · Una primera suite, débil.** Tres casos: `[0, 30)` con `[60, 90)` (no), `[0, 60)` con `[30, 90)` (sí), `[0, 90)` con `[30, 60)` (sí). Todas pasan.

**Paso 3 · Mutantes.** Cambia `<` por `<=` en la primera comparación: las tres pruebas siguen pasando. El mutante sobrevive porque ninguna prueba usa citas **contiguas** (`[0, 30)` y `[30, 60)`), que en la agenda real son lo más común. Cambia `&&` por `||`: muere con el primer caso. Agrega los dos órdenes de citas contiguas y un caso con el primer intervalo después del segundo: ahora mueren todos los mutantes de la lista.

**Paso 4 · Integración.** Contra una base real: dos transacciones simultáneas que reservan el mismo horario (la historia de S1-04). La prueba pasa sólo si una de las dos queda rechazada.

**Paso 5 · Recorrido crítico.** Datos sintéticos fijos (3 pacientes, 2 equipos), reloj fijo en `2026-11-10T08:00`, semilla fija: reservar, atender, informar y exportar a facturación con la paginación real. La aserción final: la exportación contiene exactamente las órdenes informadas del día, ni una más ni una menos.

## Contraejemplo

Un equipo tenía 100 % de cobertura en el módulo de exportación. El cliente de la API estaba simulado y el mock devolvía las 4,000 órdenes en una sola respuesta. La API real devuelve 100 por página con un cursor `siguiente`, y el código nunca pedía la segunda página. Ninguna prueba unitaria podía fallar, porque todas usaban el mock; la falla vivía exactamente en la suposición que el mock codificaba. Una prueba de integración con un doble que pagina como la API real (o con respuestas grabadas de la API) la habría detectado en la primera corrida.
