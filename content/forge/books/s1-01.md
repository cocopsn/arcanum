# S1-01 · Modelo relacional y dominio

> **Pregunta raíz.** Una clínica te pide «la tabla de citas». Antes de escribir un `CREATE TABLE`, ¿qué cosa del mundo representa cada fila, qué la identifica y quién decide que dos filas hablan de la misma cosa?

## 1. Una relación es un conjunto de hechos con identidad

El modelo relacional guarda **hechos**: cada fila de una relación afirma algo del mundo («la cita C-104 usa el equipo RM-2 de 09:00 a 09:40»). Una relación es un conjunto, así que dos filas idénticas no aportan dos hechos: aportan el mismo hecho dos veces. Por eso toda relación necesita una **llave**: el conjunto mínimo de atributos que distingue un hecho de otro. La llave primaria es la candidata que eliges como identidad estable; las llaves foráneas son la forma de decir «este hecho habla de aquel otro» sin copiar sus datos.

El formalismo (álgebra relacional, dependencias, normalización) está en las primeras unidades del curso de bases de datos de CMU, [CMU 15-445/645](https://15445.courses.cs.cmu.edu/fall2026/schedule.html). Aquí lo usamos como herramienta de diseño, con tres reglas de trabajo:

1. **Una llave por cada cosa que el negocio cuenta.** Si recepción cuenta citas y facturación cuenta estudios, son dos cosas, aunque hoy coincidan uno a uno.
2. **La llave sobrevive al sistema de origen.** Un número de fila, una posición en un Excel o un nombre no sobreviven a una migración. Un identificador emitido por quien crea el hecho, sí.
3. **La cardinalidad se declara, no se deduce de los datos de hoy.** Que hoy cada orden tenga una sola cita no significa que la regla sea 1:1.

## 2. Esquema de almacenamiento frente a modelo operacional

El esquema de almacenamiento responde a «¿cómo guardo esto sin contradicciones y lo consulto rápido?». El modelo operacional responde a «¿sobre qué cosas decide la gente y qué acciones toma?». Se parecen, pero no son lo mismo. La documentación de Foundry presenta su capa operacional, la [Ontology](https://www.palantir.com/docs/foundry/ontology/overview), como tipos de objeto y de link, tipos de acción, funciones e interfaces, y su página de [conceptos básicos](https://www.palantir.com/docs/foundry/ontology/core-concepts) define cada una de esas piezas. Lo útil para este curso es la separación: los datasets guardan filas; los objetos representan las cosas sobre las que alguien decide.

Un ejemplo de la diferencia: el sistema de agenda exporta `agenda_eventos`, con una fila por cada **cambio** de horario (creación, reprogramación, cancelación). Esa tabla es un buen registro de almacenamiento y un mal objeto operacional: el operador no decide sobre «eventos de agenda», decide sobre **citas**. El objeto `Cita` se construye a partir del registro (la última versión por `cita_id`), y su llave es la de la cita, no la del evento.

La documentación de diseño de la Ontology dedica páginas a [buenas prácticas](https://www.palantir.com/docs/foundry/ontology/ontology-best-practices) y a [antipatrones](https://www.palantir.com/docs/foundry/ontology/ontology-anti-patterns); léelas después de hacer tu propio modelo, como contraste y no como receta.

## 3. Entidades ambiguas: cómo se detectan antes de que cuesten

Una entidad es ambigua cuando dos personas del negocio usan la misma palabra para cosas distintas, o palabras distintas para la misma cosa. Tres preguntas la delatan, y caben en una entrevista corta con los usuarios del caso; el [ciclo de vida de un caso de uso](https://www.palantir.com/docs/foundry/use-case-life-cycle/overview) en la documentación de Foundry es un buen marco para ubicar esa conversación:

- **¿Qué evento la crea y cuál la termina?** «Orden» en radiología nace cuando un médico pide un estudio; «orden» en biomédica nace cuando un equipo falla. Dos ciclos de vida, dos entidades: `OrdenEstudio` y `OrdenMantenimiento`.
- **¿Cuántas hay?** Si recepción dice «hoy tuvimos 40 citas» y el sistema dice 52 filas, hay reprogramaciones contadas como citas o citas de dos sedes mezcladas. La diferencia de conteo es la evidencia.
- **¿Qué pasa con su identidad si cambia un atributo?** Si una cita se mueve de las 9 a las 11, ¿sigue siendo la misma cita? Para el paciente, sí. Entonces la hora no puede ser parte de la llave.

## Ejemplo trabajado

**Encargo.** Modela pacientes sintéticos, citas, equipos y órdenes con llaves explícitas para una clínica de imagen con dos sedes.

**Paso 1 · Lista las cosas que se cuentan.** Paciente, orden de estudio (lo que el médico pide), cita (cuándo y con qué equipo se atiende) y equipo (el resonador RM-2, el tomógrafo TC-1).

**Paso 2 · Elige identidad para cada una.** `paciente_id` emitido por el registro de la clínica (nunca el nombre); `orden_id` del sistema que emite la orden; `cita_id` de la agenda; `equipo_id` del inventario biomédico.

**Paso 3 · Declara las relaciones y su cardinalidad.** Un paciente tiene muchas órdenes (1:N). Una orden puede necesitar más de una cita, por ejemplo cuando el estudio se repite por movimiento del paciente (1:N). Un equipo atiende muchas citas (1:N). La cita **no** guarda `paciente_id`: lo obtiene por la orden, así no pueden contradecirse.

```sql
CREATE TABLE paciente (
  paciente_id TEXT PRIMARY KEY,
  nombre      TEXT NOT NULL,
  nacimiento  TEXT NOT NULL
);
CREATE TABLE equipo (
  equipo_id TEXT PRIMARY KEY,
  tipo      TEXT NOT NULL,
  sede      TEXT NOT NULL
);
CREATE TABLE orden_estudio (
  orden_id    TEXT PRIMARY KEY,
  paciente_id TEXT NOT NULL REFERENCES paciente(paciente_id),
  estudio     TEXT NOT NULL,
  emitida     TEXT NOT NULL
);
CREATE TABLE cita (
  cita_id   TEXT PRIMARY KEY,
  orden_id  TEXT NOT NULL REFERENCES orden_estudio(orden_id),
  equipo_id TEXT NOT NULL REFERENCES equipo(equipo_id),
  inicio    TEXT NOT NULL,
  fin       TEXT NOT NULL,
  estado    TEXT NOT NULL CHECK (estado IN ('agendada', 'atendida', 'cancelada'))
);
```

**Paso 4 · Pruébalo con una pregunta real.** «Agenda de mañana del RM-2 con el nombre del paciente»: `cita` → `orden_estudio` → `paciente`, siempre por llaves. Si para contestar tuvieras que unir por nombre, el modelo está incompleto.

**Paso 5 · Escribe lo que el esquema todavía no protege.** Nada impide aún que el RM-2 tenga dos citas a la misma hora. Esa regla es un invariante entre filas y se trabaja en S1-04 y S1-05. Anotarla aquí evita creer que las llaves lo resuelven todo.

## Contraejemplo

Un equipo con prisa usa `nombre` como llave de paciente «porque en la clínica todos se conocen». Con 3,000 pacientes sintéticos generados con nombres frecuentes aparecen 41 nombres repetidos. La consulta de agenda une `orden_estudio` con `paciente` por nombre y cada cita de un homónimo sale dos veces, una por cada «Ana López». El reporte muestra 46 citas donde hay 40, y nadie lo nota porque los números «se ven razonables».

La falla no está en el `JOIN`: está en el modelo, que permitió que dos hechos distintos (dos personas) compartieran identidad. Tampoco se arregla con `DISTINCT`, porque `DISTINCT` también fusionaría a dos pacientes reales que se atienden a la misma hora. La corrección es una llave emitida por el registro y una regla escrita: **nunca se une por un atributo descriptivo**.

## Diagrama

```text
  PACIENTE (paciente_id)
     │ 1
     │            N
     └──────────────< ORDEN_ESTUDIO (orden_id)
                          │ 1
                          │            N
                          └──────────────< CITA (cita_id) >────────────── 1  EQUIPO (equipo_id)
                                               │                              N:1
                                               └ estado ∈ {agendada, atendida, cancelada}

  Regla de identidad:  se une sólo por *_id;  nombre, hora y sede describen, no identifican.
  Pendiente (S1-04):   dos CITA del mismo EQUIPO no se traslapan.
```

## Conexiones

- **Hashing e identidad.** Una llave primaria es lo que una tabla hash usa para encontrar una fila; revisa [el libro de hashing de ITC](#libro:itc-c3-hashing) para ver por qué una llave mal elegida concentra colisiones.
- **SQL con propósito.** [El libro de SQL de OA](#libro:oa-11-sql) entrena agregaciones; aquí la pregunta previa es si lo que agregas está bien identificado.
- **Datos industriales.** En [Fundamentos de datos industriales](#libro:fred-s1-datos-industriales) un sensor y una lectura son dos entidades con ciclos de vida distintos; es el mismo razonamiento que separa `Cita` de `agenda_eventos`.
- **Hacia la plataforma.** En P2-01 pasarás de este esquema a objetos de la [Ontology](https://www.palantir.com/docs/foundry/ontology/core-concepts) justificados por decisiones; S1-02 mide qué pasa cuando un join multiplica filas.
