# P3-03 · Funciones de dominio

> **Pregunta raíz.** La regla «¿puede este médico tomar esta cita?» vive hoy en tres lugares: una columna calculada en la bandeja, un `if` dentro de un botón y la memoria de la coordinadora. Cada uno dice algo un poco distinto. ¿Cómo la conviertes en **una** función con entradas claras, errores con nombre y pruebas, y en qué lenguaje la escribes si mañana la tiene que usar también un pipeline?

La misión de esta celda es implementar una regla no trivial con entradas, errores y pruebas claras. La defensa pide comparar alternativas de lenguaje y runtime **según el soporte real**. Las dos mitades se sostienen mutuamente: una regla bien especificada se puede escribir en cualquier lenguaje; la elección del lenguaje depende de dónde se va a usar y de lo que la plataforma soporta en cada uno.

## 1. Qué es una función y dónde se usa

La documentación de [funciones](https://www.palantir.com/docs/foundry/functions/overview) las presenta como lógica que se ejecuta rápido en contextos operativos (paneles y aplicaciones para decidir), del lado del servidor y en un entorno aislado, con soporte de primera clase para la Ontology: leer propiedades, recorrer links y hacer ediciones. Entre los usos que enumera:

- devolver conjuntos de objetos o valores de variables para Workshop, o columnas calculadas en una tabla de objetos;
- agregaciones para gráficos;
- expresar una edición compleja de la Ontology como **acción respaldada por función**;
- consultar sistemas externos, o transmitir resultados de modelos de lenguaje;
- usar funciones de Python como contenedor auxiliar en Pipeline Builder.

Los lenguajes soportados son TypeScript y Python. La consecuencia para la pregunta raíz: la regla de disponibilidad puede ser **una** función que usan la columna de la bandeja, la acción de reasignar y, si se escribe en el lenguaje adecuado, un pipeline.

## 2. Especificar la regla: entradas, salida y errores con nombre

Antes del código, la especificación (es la disciplina de SW1-01 aplicada a una [función](https://www.palantir.com/docs/foundry/functions/overview) de dominio):

- **Entradas:** la cita (estado, especialidad requerida, franja), el médico destino (especialidad, si está activo), su agenda y sus ausencias en la franja.
- **Salida:** `{ ok: true }` o `{ ok: false, error: CODIGO }`.
- **Errores con nombre, en un orden fijo:** `ENTRADA_INVALIDA`, `CITA_NO_PROGRAMADA`, `MEDICO_INACTIVO`, `ESPECIALIDAD_DISTINTA`, `MEDICO_AUSENTE`, `MEDICO_OCUPADO`.
- **Definiciones:** dos franjas chocan si una empieza antes de que la otra termine y viceversa; franjas contiguas (una termina justo cuando la otra empieza) **no** chocan.

El orden de los errores importa: si la cita ya no está programada, decirle a la coordinadora que el médico está ocupado es una respuesta verdadera e inútil. Y los nombres importan: un código estable permite que la bandeja muestre un mensaje claro y que una prueba compruebe **cuál** error salió, no sólo que «falló».

## 3. Elegir lenguaje y runtime según el soporte real

La página de [soporte de funcionalidades por lenguaje](https://www.palantir.com/docs/foundry/functions/language-feature-support) es una tabla que conviene leer antes de escribir una línea. Algunas filas que deciden casos frecuentes:

| Necesidad | Qué dice la tabla |
|---|---|
| Leer y editar interfaces de la Ontology | Sólo TypeScript v2 |
| Llamar la función desde Pipeline Builder | Sólo Python |
| Integración con modelos de lenguaje | TypeScript v2 y Python |
| Ejecución desplegada (recursos dedicados) | TypeScript v2 y Python |
| Escrituras por etapas (beta) para garantías de lectura tras escritura | TypeScript v2 y Python |
| Llamar webhooks directamente | TypeScript v1; en v2 y Python, publicándolos como función de webhook |
| Medios (OCR de documentos, transcripción) | Completo en TypeScript v1; parcial en v2 y Python |

La tabla también incluye a AIP Logic como una columna más. La lección para la defensa: **la costumbre no es un criterio**. Si la regla tiene que correr dentro de un pipeline de Pipeline Builder y además en la bandeja, Python cubre las dos; si tiene que trabajar sobre una interfaz (P2-03), hoy sólo TypeScript v2 lo hace. Y una fila con «beta» o «parcial» es un riesgo que se anota en el diseño, como en P5-02.

## 4. Pruebas de una función de dominio

Una prueba de esta regla no es «devuelve algo»: es una tabla de casos con el error **exacto** que debe salir, y al menos uno por cada código:

- un caso feliz;
- cada error, en aislamiento (sólo esa condición falla);
- **combinaciones** que prueban el orden (cita cancelada *y* médico ocupado → `CITA_NO_PROGRAMADA`);
- bordes: franjas contiguas, agenda vacía, entrada incompleta.

Como en P1-03, la regla se escribe como núcleo puro (recibe datos, devuelve datos) y la función de la plataforma es el adaptador que lee los objetos y llama al núcleo. Así las pruebas no necesitan una instancia, y la misma especificación vale para la versión TypeScript y para la Python. Las [funciones](https://www.palantir.com/docs/foundry/functions/overview) que se ejecutan del lado del servidor dan además un lugar único donde vive la regla, en vez de tres copias divergentes.

## Ejemplo trabajado

La regla, como núcleo puro (es el ejercicio de código del banco, en JavaScript y Python):

```text
validar_reasignacion(entrada):
  si falta cita o medico, o cita.inicio >= cita.fin        → ENTRADA_INVALIDA
  si cita.estado ≠ "programada"                            → CITA_NO_PROGRAMADA
  si no medico.activo                                      → MEDICO_INACTIVO
  si medico.especialidad ≠ cita.especialidad               → ESPECIALIDAD_DISTINTA
  si alguna ausencia choca con [cita.inicio, cita.fin)     → MEDICO_AUSENTE
  si alguna cita de la agenda choca con la franja          → MEDICO_OCUPADO
  si no                                                     → ok
choca(a, b) = a.inicio < b.fin  y  b.inicio < a.fin
```

Casos que la definen (franjas en minutos desde medianoche):

| Caso | Resultado |
|---|---|
| Cita 480–510, Soto activa, misma especialidad, agenda 510–540 (contigua) | ok |
| La misma cita, pero cancelada, y Soto con agenda 480–510 | `CITA_NO_PROGRAMADA` (manda el orden) |
| Médico de otra especialidad | `ESPECIALIDAD_DISTINTA` |
| Ausencia 450–490 | `MEDICO_AUSENTE` |
| Cita con inicio 510 y fin 480 | `ENTRADA_INVALIDA` |

Elección de lenguaje para esta clínica: la regla la usan la bandeja (Workshop), la acción de reasignar y un pipeline nocturno que precalcula sugerencias. Por la fila «usable en Pipeline Builder» de la [tabla de soporte](https://www.palantir.com/docs/foundry/functions/language-feature-support), la versión compartida va en Python; si la acción necesitara además escrituras por etapas, TypeScript v2 y Python las soportan (en beta), y eso se anota.

## Contraejemplo

La versión que existía:

- La columna de la bandeja comprueba la especialidad, pero no las ausencias.
- El botón comprueba las ausencias, pero trata franjas contiguas como choque.
- Ninguna devuelve un error con nombre: la bandeja muestra «No disponible» en todos los casos.
- No hay pruebas; «funciona» porque nadie se ha quejado.

Tres copias de la regla con tres respuestas distintas para la misma pregunta. La corrección es una sola función con especificación, errores con nombre y pruebas, escrita en el lenguaje que la [tabla de soporte](https://www.palantir.com/docs/foundry/functions/language-feature-support) permite usar en todos los lugares donde se necesita.
