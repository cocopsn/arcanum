# HTTP, concurrencia y límites

> **Pregunta raíz.** Tu programa llama a un servicio ajeno 500 veces. Un día ese servicio no falla: simplemente deja de contestar. ¿Cuánto tarda tu programa en darse cuenta, qué hace con las otras 499 llamadas y qué le dice a quien esperaba el resultado?

## Tres límites que todo consumidor necesita

Un consumidor de una dependencia externa necesita tres límites explícitos. Sin ellos, el comportamiento lo decide la dependencia, no tú.

- **Plazo (timeout).** Cuánto estás dispuesto a esperar una respuesta. Sin plazo, una dependencia congelada te congela a ti.
- **Cancelación.** Qué pasa con el trabajo en curso cuando ya no lo necesitas: porque venció el plazo, porque el usuario se fue o porque otra parte falló. Cancelar bien es liberar recursos y dejar el estado consistente.
- **Concurrencia acotada.** Cuántas llamadas haces a la vez. Sin tope, 500 llamadas simultáneas pueden tumbar a la dependencia, agotar tus conexiones o activar su límite de tasa.

En Python, la página de [corrutinas y tareas de asyncio](https://docs.python.org/3/library/asyncio-task.html) documenta las piezas para los tres: `asyncio.timeout()` como contexto con plazo, la cancelación de tareas y `asyncio.TaskGroup` para lanzar varias tareas y esperarlas juntas. Dos detalles de esa página cambian cómo se escribe un consumidor:

1. Cuando una tarea de un `TaskGroup` falla, el grupo cancela las demás. En cambio, con `asyncio.gather` y su opción por omisión, la primera excepción llega a quien espera pero **las otras tareas siguen corriendo**, sin que nadie las espere.
2. Las herramientas de concurrencia estructurada (`TaskGroup`, `timeout`) usan la cancelación por dentro. Una corrutina que atrapa `CancelledError` y no la vuelve a lanzar puede hacer que se comporten mal. Limpia en un `finally` y deja que la cancelación siga.

## La dependencia que se congela y la que responde a medias

Las dos fallas más caras no son los errores, que llegan rápido y con un código. Son las respuestas que no llegan y las que llegan incompletas.

**Congelada.** Con concurrencia acotada a 5 y sin plazo, basta con que 5 llamadas se congelen para que las 495 restantes esperen para siempre detrás de ellas. El tope de concurrencia, que te protegía, ahora amplifica la falla. Por eso plazo y tope van juntos: el plazo garantiza que cada lugar del tope se libera.

**Parcial.** La dependencia contesta `200` con una página de 100 resultados cuando había 340, o con una lista vacía porque su base no respondió. Para tu programa, «vacío», «parcial» y «error» deben ser tres resultados distintos. Un consumidor honesto reporta cuántas consultas salieron bien, cuántas vencieron el plazo y cuántas fallaron, y no presenta un total como completo si no lo es.

**Resultado desconocido.** Si una llamada que **escribe** (crear una orden, enviar un pago) vence el plazo, no sabes si el servidor la procesó. Repetirla a ciegas puede duplicar el efecto. El plazo resolvió tu espera, no la incertidumbre; esa se resuelve con idempotencia o consultando el estado, y vuelve con detalle en S2-02.

El mismo problema aparece del otro lado cuando tu plataforma es la que llama. La documentación de [webhooks de Data Connection](https://www.palantir.com/docs/foundry/data-connection/webhooks-overview) describe cómo configurar llamadas desde la plataforma hacia sistemas externos: el sistema externo es entonces la dependencia, y sus plazos, sus respuestas parciales y sus reintentos son tu responsabilidad de diseño.

## Lo que dice cada respuesta HTTP

Un consumidor no trata igual todas las fallas. Una clasificación mínima, útil para decidir si reintentar:

| Respuesta | Qué suele significar | ¿Reintentar? |
|---|---|---|
| `2xx` | La operación se hizo; revisa que el cuerpo esté completo | No |
| `400`, `401`, `403`, `404`, `422` | Tu pedido está mal o no tienes permiso | No: el mismo pedido fallará igual |
| `408`, `429` | Plazo del servidor o límite de tasa | Sí, con espera; respeta `Retry-After` si viene |
| `5xx` | Falla del servidor | Quizá, con espera creciente y tope, y sólo si la operación es segura de repetir |
| Plazo vencido en tu lado | No sabes qué pasó | Sólo si la operación es idempotente o puedes consultar el estado |

La tabla es una regla de partida, no una ley: cada API documenta sus códigos, y un `404` puede ser temporal en un sistema con réplicas atrasadas. Lo que no cambia es la pregunta: **¿repetir este pedido puede hacer daño?** Las herramientas para escribir esa lógica en Python están en la misma página de [corrutinas y tareas](https://docs.python.org/3/library/asyncio-task.html).

## Ejemplo trabajado

Un consumidor que consulta 12 pedidos con a lo sumo 5 llamadas a la vez y 200 ms de plazo por llamada. La dependencia es simulada: dos pedidos se congelan y uno devuelve error.

```python
import asyncio

async def consumir(ids, consultar, limite=5, plazo=0.2):
    sem = asyncio.Semaphore(limite)
    resultados = {}

    async def uno(id_):
        async with sem:
            try:
                async with asyncio.timeout(plazo):
                    resultados[id_] = ("ok", await consultar(id_))
            except TimeoutError:
                resultados[id_] = ("tiempo", None)
            except RuntimeError as e:
                resultados[id_] = ("error", str(e))

    async with asyncio.TaskGroup() as tg:
        for i in ids:
            tg.create_task(uno(i))
    return resultados
```

Corrido contra la dependencia simulada, el reporte es: 9 `ok`, 2 `tiempo` y 1 `error`, y el programa termina en menos de un segundo aunque dos llamadas nunca contestaron. Fíjate en tres decisiones:

- El plazo está **dentro** del semáforo: mide la llamada, no la espera por un lugar libre. Si estuviera afuera, las tareas que esperan turno vencerían sin haber llamado.
- Cada resultado queda clasificado; ninguno se pierde ni se convierte en «vacío».
- Las fallas esperadas se atrapan dentro de `uno`, así que el `TaskGroup` no cancela a las demás por un error de un pedido. Una falla inesperada (un bug) sí cancela el grupo y se ve.

## Contraejemplo

```python
async def consumir_ingenuo(ids, consultar):
    respuestas = await asyncio.gather(*(consultar(i) for i in ids))
    return [r for r in respuestas if r]
```

Contra la misma dependencia:

- Sin plazo, las dos llamadas congeladas hacen que `gather` no termine nunca.
- Sin tope, con 500 ids se lanzan 500 llamadas a la vez.
- Si una llamada lanza excepción, `gather` la propaga y las demás tareas siguen corriendo huérfanas: nadie recoge su resultado ni sus errores.
- El filtro `if r` mezcla «no había datos» con «la llamada falló», y el reporte final parece completo.

## Diagrama

```text

                    │  el plazo libera el lugar                       └─▶ error    ─┘     (ok · tiempo · error)
```
