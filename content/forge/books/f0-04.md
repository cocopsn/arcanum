# TypeScript y contratos

> **Pregunta raíz.** Tu código compila sin un solo error y aun así se cae en producción con `Cannot read properties of null`. ¿Qué te prometió el compilador, qué no te prometió, y dónde tenías que haber revisado tú?

## Lo que el compilador garantiza y lo que no

TypeScript revisa tu programa **antes** de que corra y después borra los tipos: el JavaScript que se ejecuta no lleva ninguna anotación. De ahí sale la regla que organiza esta celda:

- **El compilador garantiza** que tu código es coherente con los tipos que declaraste: que no llamas a una propiedad que el tipo no tiene, que cubres todos los casos de una unión, que no pasas una cadena donde va un número.
- **El compilador no garantiza** que los datos que llegan de fuera tengan esa forma. Una respuesta HTTP, un archivo, un mensaje de una cola o un formulario llegan como texto, y su tipo real es «no sé»: `unknown`.

Una aserción como `datos as Orden` no comprueba nada: le pide al compilador que te crea. Si los datos no tienen esa forma, el error aparece lejos, en otra función, cuando ya nadie recuerda de dónde vinieron.

Cuando el cliente es generado a partir de un modelo de datos, como el [TypeScript OSDK de Palantir](https://www.palantir.com/docs/foundry/ontology-sdk/typescript-osdk), cuya documentación usa como ejemplo un objeto `Restaurant` con sus acciones y consultas, los tipos que ves en el editor vienen de ese modelo. Eso ayuda mucho dentro de la frontera del SDK. No te exime de validar lo que entra a tu sistema por otro lado (un formulario, un archivo, otra API), ni de decidir qué haces cuando un valor permitido por el tipo es inválido para tu negocio.

La [visión general de la cadena de herramientas para desarrolladores](https://www.palantir.com/docs/foundry/dev-toolchain/overview) ubica al OSDK entre las APIs y los SDK principales de la plataforma, junto a entornos de desarrollo, servidores MCP, módulos de cómputo y endpoints propios. Cada una de esas piezas es una frontera distinta, con su propia forma de recibir datos.

## Tipos que cuentan la verdad: estados y errores

Un buen tipo hace imposible representar un estado que el negocio no permite. Dos herramientas bastan para casi todo:

**Uniones discriminadas para estados.** Una orden no es «un objeto con muchos campos opcionales». Es una de varias formas, cada una con lo que le corresponde:

```typescript
type Orden =
  | { estado: "borrador"; id: string; lineas: Linea[] }
  | { estado: "confirmada"; id: string; lineas: Linea[]; confirmadaEn: string }
  | { estado: "enviada"; id: string; lineas: Linea[]; guia: string }
  | { estado: "cancelada"; id: string; motivo: string };
```

Una orden cancelada no tiene guía; una enviada siempre la tiene. Con `switch (orden.estado)` el compilador sabe qué campos existen en cada rama, y con una rama `default` que asigna a `never` te avisa si alguien agrega un estado y olvida tratarlo.

**Resultados explícitos para errores.** Un validador que lanza excepciones esconde en su firma que puede fallar. Uno que devuelve `{ ok: true; valor } | { ok: false; errores }` obliga a quien lo llama a decidir qué hacer con la falla. Los errores también son tipos: `{ campo: "lineas[2].cantidad"; motivo: "debe ser entero positivo" }` se puede mostrar, contar y probar.

Las [Functions de Palantir](https://www.palantir.com/docs/foundry/functions/overview) se presentan como lógica escrita por desarrolladores que se ejecuta rápido en contextos operativos, como tableros y aplicaciones. Ese es el lugar donde una regla de negocio mal tipada se convierte en una decisión mal tomada, así que la disciplina de este libro aplica igual allí.

## Validar en la frontera, una sola vez

La frontera es el punto donde un dato deja de ser «texto de fuera» y pasa a ser «un valor de tu dominio». La regla es: **valida en la frontera, una vez, y devuelve un tipo que ya no necesite revisarse**.

- La función de frontera recibe `unknown` y devuelve un resultado: o una `Orden` válida, o la lista completa de errores (todos, no sólo el primero, para que quien corrige no tenga que reenviar diez veces).
- Dentro del sistema, el resto del código recibe `Orden` y confía en el tipo. Si cada función vuelve a revisar todo, la validación se dispersa y se contradice.
- Las reglas que el tipo no puede expresar (cantidad entera y positiva, fecha que existe, total que cuadra con las líneas) también se revisan en la frontera, y su resultado queda dicho en el tipo devuelto.

En el lado del SDK, la documentación del [TypeScript OSDK](https://www.palantir.com/docs/foundry/ontology-sdk/typescript-osdk) dedica secciones a cargar objetos, paginar, filtrar y recorrer links; cada una de esas llamadas es también una frontera: lo que vuelve de la red puede faltar o venir paginado, y tu código debe decir qué hace en ese caso.

## Ejemplo trabajado

Validador de frontera para una línea de orden. El objetivo es que el resto del sistema nunca vea una cantidad que no es entero positivo.

```typescript
type Linea = { sku: string; cantidad: number };
type ErrorCampo = { campo: string; motivo: string };
type Resultado<T> = { ok: true; valor: T } | { ok: false; errores: ErrorCampo[] };

function parseLineas(x: unknown): Resultado<Linea[]> {
  if (!Array.isArray(x)) return { ok: false, errores: [{ campo: "lineas", motivo: "debe ser una lista" }] };
  const errores: ErrorCampo[] = [];
  const lineas: Linea[] = [];
  x.forEach((l, i) => {
    const sku = (l as { sku?: unknown })?.sku;
    const cantidad = (l as { cantidad?: unknown })?.cantidad;
    if (typeof sku !== "string" || sku.trim() === "") errores.push({ campo: `lineas[${i}].sku`, motivo: "requerido" });
    if (typeof cantidad !== "number" || !Number.isInteger(cantidad) || cantidad <= 0)
      errores.push({ campo: `lineas[${i}].cantidad`, motivo: "debe ser entero positivo" });
    if (typeof sku === "string" && sku.trim() !== "" && typeof cantidad === "number" && Number.isInteger(cantidad) && cantidad > 0)
      lineas.push({ sku: sku.trim(), cantidad });
  });
  if (x.length === 0) errores.push({ campo: "lineas", motivo: "al menos una línea" });
  return errores.length ? { ok: false, errores } : { ok: true, valor: lineas };
}
```

Con `[{ sku: "A-1", cantidad: 2 }, { sku: "", cantidad: "3" }]` devuelve dos errores, uno por campo de la segunda línea, y ninguna línea a medias. Observa que `"3"` (cadena) se rechaza aunque «parezca» un número: convertirlo en silencio es decidir por el usuario.

## Contraejemplo

```typescript
async function cargarOrden(id: string): Promise<Orden> {
  const res = await fetch(`/api/ordenes/${id}`);
  return (await res.json()) as Orden;
}

const orden = await cargarOrden("o-17");
const total = orden.lineas.reduce((s, l) => s + l.cantidad, 0);
```

Compila sin errores. En producción, una orden cancelada llega sin `lineas` y el `reduce` revienta; otra llega con `cantidad: "3"` y la suma deja de ser un número (`0 + "3"` da la cadena `"03"`), que luego se muestra como total. Ninguno de los dos errores ocurre en `cargarOrden`, que es donde estaba la frontera; aparecen después, en código que «confiaba en el tipo». Además, `res.ok` nunca se revisa: un 404 con un cuerpo de error también se convierte en una «orden».

```text

  ┌────────────────────┐      ┌─────────────────────────┐      ┌──────────────────────────────┐

  │ cola · formulario  │      │  forma + reglas negocio │      │ switch exhaustivo · never    │
  └────────────────────┘      └───────────┬─────────────┘      └──────────────────────────────┘
                                          │ errores[] (todos)
                                          ▼
                               respuesta clara al emisor
   compilador: coherencia DENTRO          runtime: verdad de lo que CRUZA la frontera
```
