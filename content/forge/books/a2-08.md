> ¿Aprobaste el simulacro, o aprobaste el problema que ya conocías?

**Formato de práctica propio; no es el proceso oficial de contratación.** El proceso real lo describe la empresa en su
propia página; este simulacro es un ejercicio de Arcanum para integrar lo de A1 y A2.

Libro ligero. Cada pieza del simulacro tiene su celda: el set mixto de [A2-01](#libro:forge-a2-01), el SQL de
[A2-04](#libro:forge-a2-04), el debug de [A2-06](#libro:forge-a2-06) y la comunicación de [A2-07](#libro:forge-a2-07). Aquí
va lo propio de A2-08: completar una sesión con coding, SQL, debug y preguntas de transferencia, y aprobar **corrección,
defensa y manejo del tiempo en tres sets independientes**.

## El formato del simulacro

Un set dura 75 minutos y trae cuatro piezas: un problema de código (25 min), una consulta SQL (20), un bug sembrado (20) y dos
preguntas de transferencia (10), en las que se cambia una restricción de lo que acabas de resolver. Antes de empezar se
escribe el **plan de tiempo**; al terminar, el **registro real**. Los problemas salen de bancos que no hayas visto, como el
[índice comunitario de OA](https://github.com/perixtar/Tech-OA-Interview-Questions) (reportes de la comunidad, no un temario
oficial). Para saber cómo contrata Palantir de verdad, la fuente es su página de
[carreras, Getting Hired](https://www.palantir.com/careers/getting-hired); este formato no la reproduce ni la sustituye.

## Cómo se aprueba: tres criterios, tres sets

Cada set se califica con tres criterios, y los tres tienen que pasar **en el mismo set**:

- **Corrección:** el código pasa sus pruebas, la consulta devuelve el conjunto correcto en los casos de borde y el bug queda
  cerrado con reproducción y prueba.
- **Defensa:** las dos preguntas de transferencia se responden con un argumento (qué cambia, qué se conserva, cuánto cuesta),
  no con una solución recordada.
- **Tiempo:** cada pieza termina, o se corta con lo que falta anotado, dentro de su bloque más un margen de 5 minutos.

Un set fuerte no compensa a uno débil. Los tres se hacen en días distintos, con problemas distintos y sin ver las soluciones
de un set antes del siguiente: si no son **independientes**, aprobar dos veces el mismo set sólo mide memoria. Los
enunciados del [índice comunitario](https://github.com/perixtar/Tech-OA-Interview-Questions) sirven para armar los tres sin
repetir.

## Ejemplo trabajado

Registro de un set:

| pieza | plan | real | resultado | nota |
|---|---|---|---|---|
| código (k más frecuentes) | 25 | 22 | 7/7 casos | desempate por valor preguntado al inicio |
| SQL (total por categoría) | 20 | 26 | correcto | 6 min perdidos en un INNER JOIN que borraba categorías sin ventas |
| debug (mediana) | 20 | 14 | cerrado | reproducción: longitud par; prueba con vacío |
| transferencia | 10 | 10 | 2/2 argumentadas | flujo con memoria acotada |

Corrección: pasa. Defensa: pasa. Tiempo: el SQL se pasó 6 minutos, dentro del margen de 5 no; el set queda **no aprobado en
tiempo** aunque todo esté correcto, y la nota dice qué practicar: la lectura de «incluir categorías sin ventas».

## Contraejemplo

Un candidato hace el mismo set tres veces en una tarde hasta resolverlo en 60 minutos y declara el simulacro aprobado. Los
tres «sets» no son independientes: a partir del segundo ya conocía los problemas, así que el tiempo y la corrección miden
memoria. Otro caso: resolver perfecto el código y dejar el SQL y el debug en blanco. Sin las otras piezas el set no se
aprueba, por bueno que sea el código.

## Diagrama

```text
 set (75 min)   [código 25][SQL 20][debug 20][transferencia 10]
                plan ──────────────────────────────► registro real
 criterios por set:  corrección ✓   defensa ✓   tiempo ✓   (los tres en el mismo set)
 simulacro:  set A (día 1) · set B (día 3) · set C (día 5)   problemas distintos, sin ver soluciones
 aprobado  ⇔  A, B y C aprobados por separado
```
