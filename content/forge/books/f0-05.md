# Git, pruebas y depuración

> **Pregunta raíz.** Corregiste un bug y todas las pruebas pasan. ¿Cómo sabes que alguna de ellas habría fallado antes de tu corrección? Si ninguna fallaba, no probaste la corrección: probaste que el resto del código sigue igual.

## Reproducir antes de corregir

La secuencia de esta celda es fija y tiene una razón para cada paso:

1. **Escribir un caso que reproduce el bug** con los datos más chicos posibles.
2. **Verlo fallar** con el código actual, por la razón correcta: el mensaje de la falla nombra lo que está mal.
3. **Corregir lo mínimo** para que ese caso pase.
4. **Ver pasar todo**: el caso nuevo y los anteriores.
5. **Revisar el cambio** antes de integrarlo.

El paso 2 es el que más se salta y el que más vale. Una prueba que nunca viste fallar puede estar pasando por accidente: compara contra el valor equivocado, no llega a la línea del bug o no comprueba nada. Verla fallar primero demuestra que la prueba mide lo que crees que mide.

En la documentación de Palantir sobre [pruebas unitarias de transforms en Python](https://www.palantir.com/docs/foundry/transforms-python/unit-tests), las secciones cubren escribir pruebas, correrlas en local, ver su salida y medir cobertura como parte de los chequeos del repositorio. La página advierte además que esas pruebas aplican a pipelines por lotes y no a los de streaming: un límite que conviene saber antes de suponer que tu prueba cubre cualquier pipeline.

## Una prueba buena es la que mata al bug

¿Cómo se mide si una suite de pruebas es buena? La cobertura dice qué líneas se ejecutaron, no si alguna aserción las revisó. Una prueba que llama a la función y no compara nada da 100 % de cobertura y no detecta ningún error.

Una medida más honesta es preguntar: **si alguien introduce un error pequeño y plausible, ¿alguna prueba falla?** A esas versiones con un error sembrado se les llama *mutantes*: cambiar un `<` por `<=`, invertir una condición, olvidar un caso. Una suite «mata» un mutante cuando al menos una prueba falla con él. Si un mutante sobrevive, hay un comportamiento que nadie está mirando.

![Chequeo de cobertura de pruebas que falla en un repositorio de transforms](https://www.palantir.com/docs/resources/foundry/transforms-python/coverage.png "figura https://www.palantir.com/docs/foundry/transforms-python/unit-tests")

La figura viene de la misma página de [pruebas unitarias](https://www.palantir.com/docs/foundry/transforms-python/unit-tests): un chequeo de cobertura puede detener una integración. Es útil como piso; no reemplaza la pregunta de los mutantes. El banco de esta celda te pide justamente eso: escribir casos que maten mutantes de una función de traslape de horarios, sin que te digamos cuáles son.

## Dobles de prueba en la frontera

Muchas funciones de dominio llaman a algo de fuera: una base, una API, un SDK. Para probarlas sin esa dependencia se usa un **doble**: un objeto que responde como la dependencia, con datos que tú controlas, incluidas las fallas.

La documentación del [paquete de pruebas del TypeScript OSDK](https://www.palantir.com/docs/foundry/ontology-sdk/typescript-osdk-testing) describe cómo simular objetos, links y llamadas del cliente, incluidos casos como un link que falla al cargarse o que no existe. También dice que el paquete es experimental y se publica bajo una ruta `/experimental`: si lo usas, fija la versión y espera cambios.

Dos reglas para que un doble no mienta:

- **Simula las fallas, no sólo el camino feliz.** Si el doble nunca devuelve un error, tu prueba nunca ejercita el manejo de errores.
- **No simules lo que estás probando.** El doble reemplaza a la dependencia, nunca a la lógica que quieres comprobar.

## Corrección mínima y revisión con Git

Una corrección mínima cambia lo necesario para que el caso pase y nada más. Un diff chico se revisa entero; uno grande se revisa por encima. Si mientras corriges ves otra cosa que mejorar, anótala y hazla en otro commit.

Herramientas de Git que sostienen este oficio (el [Missing Semester del MIT](https://missing.csail.mit.edu/2020/index.html), apoyo de esta ruta, tiene una clase dedicada a control de versiones y otra a depuración):

- `git bisect` encuentra el commit que introdujo un bug con búsqueda binaria: entre 64 commits, a lo sumo 6 pruebas.
- `git diff --staged` muestra exactamente lo que vas a integrar, no lo que crees que cambiaste.
- Un mensaje de commit que dice qué fallaba, por qué y cómo se comprobó, convierte el historial en documentación.

La revisión de cambios responde cuatro preguntas: ¿la prueba nueva falla sin la corrección? ¿El diff toca sólo lo necesario? ¿Qué otro llamador de esta función podría notar el cambio? ¿Qué no se probó?

## Ejemplo trabajado

**Reporte.** «Una cita de 10:00 a 11:00 y otra de 11:00 a 12:00 en el mismo consultorio se marcan como empalmadas.»

```javascript
// minutos desde medianoche; intervalos semiabiertos [inicio, fin)
function seTraslapan(ai, af, bi, bf) {
  return ai <= bf && bi <= af;   // código actual
}
```

1. *Reproducir.* Caso mínimo: `seTraslapan(600, 660, 660, 720)` debe ser `false`, porque una cita termina justo cuando empieza la otra.
2. *Ver fallar.* Con el código actual devuelve `true`. El mensaje de la prueba: «citas contiguas se marcaron como traslapadas».
3. *Corregir lo mínimo.* Cambiar `<=` por `<` en las dos comparaciones: `return ai < bf && bi < af;`.
4. *Ver pasar todo.* El caso nuevo pasa; los anteriores (traslape parcial, contención, disjuntos) siguen pasando.
5. *Revisar.* El diff es de una línea. Otro llamador, el reporte de ocupación, contaba las citas contiguas como conflicto: su número va a bajar y hay que avisarlo. No se probó el caso de citas que cruzan la medianoche; queda anotado.

## Contraejemplo

Un alumno recibe el mismo reporte, cambia `<=` por `<`, corre la suite y todo pasa. Entrega.

Qué falta: ninguna prueba de la suite tenía citas contiguas, así que **también pasaba antes** de la corrección. La suite no detecta el bug ni detectaría su regreso. Además, en el mismo commit reordenó parámetros «para que se lean mejor», y el revisor ya no puede ver de un vistazo cuál cambio arregló el bug. Si dentro de seis meses alguien vuelve a poner `<=`, nada lo detiene.

## Diagrama

```text
   reporte ──▶ caso mínimo ──▶ ¿FALLA con el código actual? ──no──▶ el caso no reproduce: revisar
                                        │ sí (mensaje nombra el bug)
                                        ▼
                                corrección mínima ──▶ ¿pasa todo? ──no──▶ ajustar
                                                          │ sí
                                                          ▼
                     revisión: diff chico · otros llamadores · lo no probado ──▶ commit con el porqué

   calidad de la suite:  mutante sembrado ──▶ ¿alguna prueba falla?  sí = muerto · no = punto ciego
```
