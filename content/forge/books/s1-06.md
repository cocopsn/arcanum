# S1-06 · API y evolución de contratos

> **Pregunta raíz.** Renombras un campo de tu API porque el nombre viejo confundía. Tus pruebas pasan, tu interfaz funciona y a la mañana siguiente el tablero de un hospital socio está vacío. ¿A quién le prometiste qué, y cómo se cambia una promesa sin romperla?

## 1. Un contrato es una promesa a consumidores que no ves

Una API de operaciones tiene consumidores que no controlas: tu interfaz, scripts de soporte, integraciones de socios y clientes generados a partir de su descripción. En Foundry, la [Developer Console](https://www.palantir.com/docs/foundry/developer-console/overview) administra aplicaciones con sus clientes de autorización y sus SDK, y el [Ontology SDK](https://www.palantir.com/docs/foundry/ontology-sdk) da acceso a la Ontology desde el entorno de desarrollo con un cliente tipado. Un cliente tipado hace el contrato más explícito, y también más frágil: un cambio de tipo que un humano ignoraría rompe la compilación de otro equipo.

El contrato no es sólo la lista de campos. Incluye:

- **Forma:** recursos, campos, tipos, obligatorios y opcionales.
- **Semántica:** qué significa cada campo y cada estado (un `estado: cancelada` que antes incluía reprogramadas y ahora no es un cambio de contrato aunque el JSON sea idéntico).
- **Orden y paginación:** en qué orden llegan las filas y cómo se pide la siguiente página.
- **Errores:** qué códigos existen, cuáles se pueden reintentar.
- **Límites:** tamaño de página, cuotas, tiempos.

## 2. Paginación que no miente

La paginación por **desplazamiento** (`?offset=100&limit=50`) es sencilla y falla bajo escrituras: si entra una orden nueva antes de la posición 100 mientras el cliente pagina, la página siguiente repite una fila; si se borra una, se salta otra. Un cliente que exporta «todas las órdenes» termina con duplicados y huecos, sin ningún error.

La paginación por **cursor** (o por llave) pide «las siguientes 50 después de este punto» con un orden total y estable, por ejemplo `(emitida, orden_id)`: el `orden_id` desempata filas con la misma fecha. El cursor se entrega **opaco** (un token que el cliente devuelve tal cual), de modo que puedas cambiar su contenido sin romper a nadie. La referencia de la API de Foundry dedica páginas a la [paginación](https://www.palantir.com/docs/foundry/api/general/overview/paging) y a los [límites](https://www.palantir.com/docs/foundry/api/general/overview/limits); compáralas con tu diseño.

## 3. Errores que el cliente puede usar

Un error útil responde tres preguntas sin leer el texto: **qué** pasó (un código estable, como `ORDEN_NO_ENCONTRADA`), **de quién** es la culpa (argumento inválido, permiso, conflicto, falla transitoria del servidor) y **si conviene reintentar**. El mensaje legible es para personas y puede cambiar; el código es parte del contrato y no.

Dos reglas que evitan incidentes: un error de validación nunca se reintenta solo, y un error transitorio después de una escritura no dice si la escritura ocurrió (eso se trabaja en S2-02 con idempotencia). La referencia de la API de Foundry también tiene una página de [errores](https://www.palantir.com/docs/foundry/api/general/overview/errors); úsala como contraste, no como plantilla.

## 4. Evolucionar sin romper

Un cambio es **compatible** si todo consumidor que funcionaba sigue funcionando sin tocar su código. Agregar un campo opcional en la respuesta suele serlo. No lo son: quitar o renombrar un campo, cambiar su tipo, volver obligatorio un parámetro, endurecer una validación, cambiar el orden por omisión y cambiar el significado de un valor. Agregar un valor a un enumerado de la respuesta es una zona gris: rompe a todo cliente que haga una enumeración exhaustiva.

Los cambios incompatibles se hacen en **paralelo** (expandir y contraer):

1. **Expandir:** publica lo nuevo junto a lo viejo (el campo `paciente_id` junto a `paciente`).
2. **Migrar:** avisa con fecha, mide quién sigue leyendo lo viejo.
3. **Contraer:** cuando la medición dice cero (o la fecha venció con aviso), quita lo viejo.

Cuando el cambio no admite convivencia en la misma versión, se publica otra versión y ambas conviven un tiempo declarado. La referencia de la API de Foundry explica su propio esquema de [versionado](https://www.palantir.com/docs/foundry/api/general/overview/versioning).

## Ejemplo trabajado

**Encargo.** Diseña paginación, errores y compatibilidad de la API de órdenes de la clínica.

**Paso 1 · Lectura paginada.** `GET /v1/ordenes?estado=agendada&tamano=50&cursor=<token>`. Orden total: `(emitida, orden_id)` ascendente. Respuesta:

```json
{
  "datos": [{ "orden_id": "O-10", "paciente_id": "P-001", "estado": "agendada", "emitida": "2026-11-02" }],
  "siguiente": "eyJlIjoiMjAyNi0xMS0wMiIsImkiOiJPLTEwIn0"
}
```

`siguiente` es `null` en la última página. `tamano` acepta de 1 a 200; fuera de rango es un error de validación, no un recorte silencioso.

**Paso 2 · Errores.**

```json
{ "error": { "codigo": "CURSOR_INVALIDO", "categoria": "argumento", "reintentable": false } }
```

Categorías cerradas: `argumento`, `permiso`, `no_encontrado`, `conflicto`, `transitorio`. Sólo `transitorio` es reintentable, y para escrituras exige clave de idempotencia.

**Paso 3 · El cambio.** El campo `paciente` (que traía el nombre) confunde, y se quiere `paciente_id`. Plan: (a) versión 1.4 agrega `paciente_id` y marca `paciente` como obsoleto en la documentación y en una cabecera de aviso; (b) se registra, por cliente, cada lectura de `paciente`; (c) a los 90 días, con cero lecturas en las últimas 4 semanas o con aviso cumplido a quien queda, `paciente` se elimina. El cambio se considera terminado cuando la métrica de uso del campo viejo llega a cero, no cuando se publica el nuevo.

**Paso 4 · Prueba de contrato.** Un conjunto de respuestas grabadas de la versión anterior se reproduce contra la nueva: ningún campo que existía desaparece ni cambia de tipo mientras dure la expansión.

## Contraejemplo

Un equipo agrega el estado `en_revision` a las órdenes. Es «sólo un valor nuevo», no rompe el JSON y sus pruebas pasan. El cliente generado de un socio tenía un `switch` exhaustivo sobre `estado` que lanzaba un error ante un valor desconocido; su tablero se cae con la primera orden en revisión. El cambio era incompatible para ese consumidor. Lo que faltó: declarar en el contrato si los enumerados pueden crecer (y exigir a los clientes un caso «desconocido»), y publicar el valor nuevo detrás de un aviso con fecha.
