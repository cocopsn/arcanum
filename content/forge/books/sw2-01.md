# Memoria y vida útil

> **Pregunta raíz.** Un programa libera un bloque de memoria y, un rato después, otra parte del código todavía guarda un puntero a él y escribe ahí. A veces no pasa nada. A veces corrompe datos de otro objeto que ya ocupa ese lugar. Nunca avisa. ¿Cómo se diseña un componente para que ese error sea imposible o, al menos, se detecte en el acto? Empieza por poder decir, de cada dato, dónde vive, cuánto vive y quién puede tocarlo.

## Dónde vive cada dato

Un programa tiene, a grandes rasgos, tres lugares para sus datos, que el capítulo de la API de memoria de [OSTEP](https://pages.cs.wisc.edu/~remzi/OSTEP/) presenta desde el espacio de direcciones de un proceso:

- **la pila:** variables locales de una función; nacen al entrar y mueren al salir, sin que nadie las libere;
- **el montón (heap):** memoria pedida explícitamente (`malloc`, `new`); vive hasta que alguien la libera (o hasta que el recolector de basura decide que nadie la alcanza);
- **la zona estática:** datos globales que viven todo el programa.

El error más clásico mezcla dos de ellas: una función devuelve la dirección de una variable local. La variable murió al salir; la dirección sigue ahí, apuntando a una pila que la próxima llamada va a reutilizar. [CS61C](https://cs61c.org/fa26/) trabaja estos errores en C, donde nada los impide.

## Propiedad y vida útil

En el montón, cada bloque necesita un **dueño**: la parte del código responsable de liberarlo exactamente una vez. Tres errores salen de no tener uno claro:

- **fuga:** nadie lo libera y la memoria se acaba poco a poco;
- **doble liberación:** dos partes lo liberan, y el asignador queda en un estado inconsistente;
- **uso después de liberar:** alguien usa un puntero a un bloque ya liberado, quizá reasignado a otro objeto.

Los lenguajes con recolector de basura eliminan la doble liberación y el uso después de liberar de memoria, pero no el problema de fondo: un archivo cerrado, una conexión devuelta al pool o una página soltada del buffer pool (SW4-01) siguen teniendo vida útil, y usarlos después de su fin es el mismo error con otro nombre. La disciplina que [OSTEP](https://pages.cs.wisc.edu/~remzi/OSTEP/) pide para la memoria vale para todo recurso.

## Fuera de rango y alias

Dos errores más completan la variante de la ficha:

- **acceso fuera de rango:** leer o escribir más allá del bloque pedido. En C no hay comprobación: se pisa lo que esté al lado. Un componente seguro comprueba los límites en su frontera, como una precondición convertida en error declarado (SW1-01).
- **alias:** dos referencias al mismo dato. Si una lo cambia, la otra ve el cambio; si una lo libera, la otra queda colgando. Es la exposición de la representación de SW1-02 llevada a la memoria.

Reconstruir «dónde vive cada dato y quién puede modificarlo», que es la defensa de esta celda, es hacer explícitos los dueños y los alias. Los laboratorios de [CS61C](https://cs61c.org/fa26/) entrenan esa lectura con herramientas que detectan accesos inválidos.

## Un componente con errores detectables

El capítulo de gestión del espacio libre de [OSTEP](https://pages.cs.wisc.edu/~remzi/OSTEP/) explica cómo un asignador lleva la cuenta de los bloques libres; aquí se agrega una pieza para detectar errores. Una forma de hacer detectable el uso después de liberar es no entregar punteros crudos sino **manijas con generación**. Un pool de bloques de tamaño fijo guarda, por cada bloque, si está ocupado y un **contador de generación** que sube cada vez que se libera. La manija que se entrega es el par «índice, generación»:

- `asignar` toma el bloque libre de menor índice y entrega `índice:generación`;
- `liberar(m)` comprueba que el bloque esté ocupado y que la generación de la manija coincida; si no, es una doble liberación o una manija vieja, y se rechaza;
- `leer(m)` hace la misma comprobación antes de dar acceso.

Una manija vieja queda **inválida para siempre**, aunque el bloque se reutilice, porque la generación ya cambió. El error se detecta en el acto, en la operación que lo comete, y no tres llamadas después.

## Ejemplo trabajado

**Pool de 2 bloques.**

| Operación | Respuesta | Estado del pool |
|---|---|---|
| asignar | `0:0` | bloque 0 ocupado (gen 0) |
| asignar | `1:0` | bloque 1 ocupado (gen 0) |
| asignar | `lleno` | — |
| liberar `0:0` | ok | bloque 0 libre, gen 1 |
| leer `0:0` | **inválido** (manija vieja) | — |
| asignar | `0:1` | bloque 0 ocupado (gen 1) |
| leer `0:0` | **inválido**: el bloque está ocupado, pero por otro dueño | — |
| liberar `0:0` | **inválido** (doble liberación con manija vieja) | — |
| leer `0:1` | ok | — |

Sin generación, el `leer 0:0` de la séptima fila habría devuelto los datos del nuevo dueño del bloque 0: un uso después de liberar silencioso. Con generación, falla con un error que nombra la manija.

## Contraejemplo

Un pool entrega el índice del bloque como manija, sin generación:

```text
a = asignar()      // a = 0
liberar(a)         // bloque 0 libre
b = asignar()      // b = 0: el mismo bloque, ahora de otro dueño
escribir(a, "x")   // el código viejo todavía tiene a = 0: escribe en el bloque de b
```

`escribir(a, ...)` no falla: el bloque 0 está ocupado y la manija apunta a él. El dueño de `b` encuentra datos que no escribió, y el error aparece lejos, en otra parte del programa, mucho después. Las pruebas que asignan y liberan en orden nunca lo ven. La generación convierte este caso en un rechazo inmediato.

## Diagrama

```text
   espacio de direcciones de un proceso
   ┌──────────────┐  código y datos estáticos   ← viven todo el programa
   ├──────────────┤  montón ↓                    ← viven hasta que su dueño los libera
   │      …       │
   ├──────────────┤  pila ↑                      ← viven mientras la función está activa
   └──────────────┘

   pool con manijas de generación:
     bloque:      [ 0 ][ 1 ]
     ocupado:     [ sí][ sí]
     generación:  [ 1 ][ 0 ]
     manija válida  ⇔  ocupado[i]  y  generación[i] == generación de la manija
     manija vieja "0:0" → inválida para siempre (el bloque 0 ya va en la generación 1)
```
