## El 401 que nunca llega
type: multiple_choice
tiempo: 3

El test falla: `expected 401 "Authentication required", got 200`. El middleware es:

```javascript
function requireAuth(req, res, next) {
  if (req.user !== undefined) {
    return res.status(401).json({ error: "Authentication required" });
  }
  next();
}
```

¿Dónde está el bug y cuál es el parche mínimo?

### Opciones
- [x] La comparación está INVERTIDA: `req.user !== undefined` dispara el 401 justo cuando el usuario SÍ está autenticado, y deja pasar al anónimo. Parche mínimo: `if (req.user === undefined)` — una negación, cero líneas nuevas. Es el bug de catálogo «comparación invertida»: el código se lee plausible porque la ESTRUCTURA es correcta; solo el operador está volteado.
- Falta un `else` antes del `next()`: sin él, la función siempre continúa aunque haya respondido 401.
- El status correcto es 403, no 401, y por eso el test no encuentra el mensaje.
- `req.user` nunca existe en Express; hay que leer `req.headers.authorization` y decodificar el token aquí mismo.
### Justificación
El test dice exactamente qué esperaba (401 para el no-autenticado) y qué obtuvo (200): el anónimo pasó — la condición trata al autenticado como intruso. El `else` es innecesario: el `return` ya corta la ejecución antes de `next()` (ese distractor «arregla» una rama que no está rota). 403 vs 401 es una confusión real del catálogo pero AQUÍ el test pide 401 y el handler ya responde 401 — el contrato no es el problema, el operador sí. Y reescribir el middleware para decodificar tokens es la regeneración que el libro prohíbe: cambio grande, riesgo nuevo, cuando el parche era un carácter. Bajo reloj: leer el test PRIMERO te dice qué rama está al revés.

## El comentario que se guarda pero no aparece
type: multiple_choice
tiempo: 4

Test: `GET /issues/7/comments → expected [ { body: "hola" } ], got []`. El handler de creación:

```javascript
async function createComment(req, res) {
  const issue = await Issue.findById(req.params.issueId);
  if (!issue) return res.status(404).json({ error: "Issue not found" });
  const comment = new Comment({ body: req.body.body, author: req.user.id });
  await comment.save();
  return res.status(201).json(comment);
}
```

El POST devuelve 201 y el comentario existe en la colección `comments`. ¿Cuál es el bug?

### Opciones
- [x] El comentario se guarda pero NUNCA SE VINCULA a su issue: nadie hizo `issue.comments.push(comment._id)` + `await issue.save()` (ni `Comment` guarda `issueId` que el GET pueda consultar). Es el bug de catálogo «objeto guardado nunca escrito de vuelta / nunca vinculado»: cada pieza funciona aislada — el 201 es real, el documento existe — pero la RELACIÓN que el GET recorre quedó sin escribir.
- El `new Comment(...)` está mal: en Mongoose los documentos solo se crean con `Comment.create()`.
- Falta `{ new: true }` en el `findById` para que devuelva el issue actualizado.
- El `status(201)` debería ser `status(200)`: por eso el GET posterior no ve el comentario.
### Justificación
La firma del bug es que el POST luce sano (201, documento en su colección) y el sistema «olvida» el dato al leerlo por la ruta relacional — el libro lo llama el clásico de la plataforma tipo Jira, y la corrección toca DOS escrituras (guardar el comentario Y escribir el vínculo en el issue, o guardar el issueId en el comentario, según el esquema que el GET consulte). `new` + `save()` es exactamente equivalente a `create()` — ese distractor es superstición de API. `{ new: true }` es un modificador de findByIdAndUpdate (aquí no hay update que devolver). Y el código de status de un POST no altera lo que un GET posterior encuentra — confunde síntoma con transporte.

## La página 2 que repite al último de la página 1
type: multiple_choice
tiempo: 3

Test: `GET /products?page=2&size=10 → expected product 11 first, got product 10`. El servicio (páginas 1-indexadas):

```javascript
async function listProducts(page, size) {
  const skip = (page - 1) * size - 1;
  return Product.find().sort({ id: 1 }).skip(Math.max(0, skip)).limit(size);
}
```

¿Cuál es el diagnóstico?

### Opciones
- [x] Off-by-one en el cálculo de `skip`: para `page=2, size=10` da `(2-1)*10 - 1 = 9`, así que la página 2 arranca en el elemento 10 (repite el último de la página 1). El `- 1` sobra: `skip = (page - 1) * size` es la fórmula completa para páginas 1-indexadas. El `Math.max(0, …)` era un parche cosmético que además ESCONDE el mismo error en la página 1 (skip −1 → 0 por accidente feliz).
- El bug es el `sort({ id: 1 })`: paginar exige orden descendente para que el skip cuente desde el final.
- `limit(size)` debe ser `limit(size + 1)` para compensar el elemento que falta.
- El error está en el test: pedir `page=2` con 10 elementos por página DEBE devolver el producto 10 primero.
### Justificación
La aritmética es el diagnóstico completo: páginas 1-indexadas → saltas `(page-1)*size` elementos exactos; el `-1` corre TODA página una posición hacia atrás, y el `Math.max` disfraza el caso page=1 (−1 → 0), que es justo por qué «funcionaba» en la primera pantalla — el patrón de off-by-one del libro: sano en el caso chico, roto a partir del segundo. El orden del sort es ortogonal al desplazamiento (asc/desc cambia QUÉ ves, no la matemática del skip). `limit(size+1)` entregaría 11 elementos — cambiar un bug de frontera por otro. Y el test tiene razón: elementos 1..10 son página 1; el 11 abre la página 2 — desconfiar del test antes que del código viola la regla del libro: el test ES el contrato.

## La edición que devuelve el documento viejo
type: multiple_choice
tiempo: 3

Test: `PATCH /reviews/5 { rating: 4 } → expected body.rating 4, got 2`. La base de datos SÍ queda con rating 4 después de la llamada. El handler:

```javascript
async function updateReview(req, res) {
  const review = await Review.findByIdAndUpdate(req.params.id, { rating: req.body.rating });
  return res.status(200).json(review);
}
```

¿Qué está pasando?

### Opciones
- [x] `findByIdAndUpdate` sin opciones devuelve el documento ANTERIOR a la actualización (así está diseñado): la escritura sí ocurre — por eso la base queda bien — pero la respuesta serializa el objeto viejo. Parche mínimo: `findByIdAndUpdate(id, cambios, { new: true })`. Es el bug de catálogo donde el estado y la respuesta divergen: los tests de API comparan el CUERPO, no la base.
- El PATCH nunca escribió: falta un `await review.save()` después del findByIdAndUpdate.
- `rating` es un subdocumento anidado y falta `review.markModified("rating")` antes de responder.
- Mongoose cachea las lecturas: hay que llamar `Review.findById` dos veces para invalidar el caché.
### Justificación
El dato que discrimina está EN el enunciado: la base queda con 4 — la escritura ocurrió, así que todo distractor que «arregla la escritura» ataca un problema inexistente. `findByIdAndUpdate` ejecuta el update él mismo (un `save()` extra no aplica: no hubo mutación local del documento) y su contrato de retorno por defecto es el documento PRE-update — el `{ new: true }` existe exactamente para esto y el libro lo lista como bug 2.6. `markModified` es para mutaciones profundas ANTES de un save(), otra familia (bug 2.5) — aquí no hay ni subdocumento ni save. Y el «caché de lecturas» de Mongoose no existe en esa forma: cada query va al motor. La lección del libro: los tests verifican status Y cuerpo — devolver lo viejo con 200 falla igual que no escribir.

## El tercer strike que no marca
type: multiple_choice
tiempo: 4

Sistema de moderación con strikes (las reglas del cuaderno F1): cada violación incrementa el contador; al ACUMULAR 3, el usuario queda `isFlagged = true`; un usuario marcado queda bloqueado en todo intento posterior. El test `third violation flags the user` falla: tras la tercera violación, `isFlagged` sigue `false`. El servicio:

```javascript
async function registerViolation(user) {
  user.violations = user.violations + 1;
  if (user.violations > 3) {
    user.isFlagged = true;
  }
  await user.save();
  return user;
}
```

¿Dónde está el bug?

### Opciones
- [x] El umbral está corrido: `> 3` marca al usuario hasta la CUARTA violación, y la regla dice «tras 3 acumuladas» — el parche mínimo es `>= 3`. Es un off-by-one de REGLA DE NEGOCIO (no de índice): la estructura persiste bien (save() está), pero la frontera del umbral traiciona la especificación exacta que el test verifica.
- Falta `markModified("violations")`: los contadores numéricos no se persisten sin él.
- El `user.save()` debe ir ANTES del `if`, para que el contador ya esté en la base al evaluar el umbral.
- El bug es que `violations` arranca en `undefined` y `undefined + 1` es `NaN`, así que el contador nunca llega a 3.
### Justificación
La regla dice «tras 3 violaciones acumuladas» y el test dispara la tercera: con `> 3` la condición evalúa `3 > 3` = false — un carácter (`>=`) cierra el caso. Es la variante de frontera que el libro agrupa con off-by-one: no en un índice, sino en el umbral de una regla. `markModified` aplica a rutas anidadas/mixed, no a un campo numérico plano (Mongoose rastrea esa asignación sola). Mover el save() antes del if no cambia la evaluación (el if lee la variable local, no la base) — solo reordena sin efecto. Y si `violations` fuera undefined→NaN el contador jamás sería 1 ni 2 y OTROS tests (primera/segunda violación) habrían fallado antes — el enunciado dice que solo falla el del tercer strike: la evidencia acota el bug a la frontera.

## La paginación corrida — parchea
type: code
tiempo: 12

Starter con el off-by-one de paginación sembrado (el bug 2.3 del libro, el mismo que viste arriba en el snippet de Express). Páginas 1-indexadas. Corre, mira qué elemento abre la página 2, y corrige la aritmética del salto — nada más.

### Especificación
`paginar(items, pagina, porPagina)`:
- Páginas 1-indexadas: la página 1 son los primeros `porPagina` elementos; la página 2 los siguientes; etc.
- Devuelve el arreglo (posiblemente más corto) de esa página; página fuera de rango → `[]`.
- `pagina < 1` o `porPagina < 1` → `[]` (entrada inválida, fail-closed).

### Firma
```javascript
function paginar(items, pagina, porPagina) {
  // BUG SEMBRADO: la aritmetica del salto esta corrida en uno. Parcha MINIMO.
  if (pagina < 1 || porPagina < 1) return [];
  const desde = (pagina - 1) * porPagina - 1;
  const inicio = Math.max(0, desde);
  return items.slice(inicio, inicio + porPagina);
}
```

## Los strikes del moderador — parchea la frontera
type: code
tiempo: 12

Las reglas de moderación del cuaderno (F1), como función pura de servicio. El starter trae el umbral corrido (la frontera `> / >=` del snippet de arriba, ahora con los casos cazándola). Reglas EXACTAS en la especificación — táchalas una por una contra el código, como manda el cuaderno.

### Especificación
`moderarIntento(strikesPrevios, violaEstaVez)` devuelve `[status, strikesFinales]`:
- Usuario ya marcado (strikesPrevios >= 3): SIEMPRE `[403, strikesPrevios]` — bloqueado sin importar el contenido, y un bloqueado no acumula strikes nuevos.
- No marcado y `violaEstaVez` true: incrementa (`strikesPrevios + 1`) y devuelve `[403, nuevos]` (la reseña violatoria no se publica).
- No marcado y sin violación: `[201, strikesPrevios]` (se publica).
- `strikesPrevios` negativo se trata como 0.

### Firma
```javascript
function moderarIntento(strikesPrevios, violaEstaVez) {
  // BUG SEMBRADO: una frontera de umbral esta corrida. Parcha MINIMO.
  const previos = Math.max(0, strikesPrevios);
  if (previos > 3) {
    return [403, previos];
  }
  if (violaEstaVez) {
    return [403, previos + 1];
  }
  return [201, previos];
}
```

## El protocolo del Problema 2, de memoria
type: production
tiempo: 8

Sin mirar el libro: escribe tu protocolo completo del Problema 2 — fases con sus topes de tiempo, el ciclo por prueba, la plantilla de prompt para el asistente, y las dos reglas de cierre. Es la hoja mental que ejecutarás el día del examen.

### Modelo
1. Exploración ≤ 10 min: README (el contrato de la API) + correr la suite + anotar cada test fallido con su mensaje. Al minuto 10, se ataca.
2. Por CADA prueba fallida: pegar el output del test + el archivo relevante al asistente con la plantilla «Here is the failing test output and the relevant file; identify the bug and propose the smallest patch» → el asistente LOCALIZA (archivo → función → líneas) → leo YO el código → decido el parche mínimo → corro la suite → siguiente.
3. Cambios quirúrgicos siempre: nunca regenerar un archivo completo; el diff se lee antes de aceptar.
4. Una prueba atorada > 15 min → se abandona y se regresa al final: verde parcial (4/6) avanza candidatos; un solo bug perfecto no.
5. Cierre: dejar ≥ 5 min para la corrida final completa en el sandbox — lo que pasa local todavía tiene que pasar allá.
6. Recordatorio de contrato: los tests verifican STATUS y MENSAJE de la API — el fix va en handler Y service, jamás solo en el frontend.

### Regla
El protocolo existe porque los dos sumideros documentados del Problema 2 son navegación sin tope y regeneración a ciegas: acotar la exploración convierte el repo desconocido en una lista de contratos rotos, y usar la IA como LOCALIZADOR (no como autor) mantiene al ingeniero responsable de la corrección — que es exactamente lo que Amazon está midiendo con el panel de IA disponible.

### Rúbrica
- Las fases llevan TOPES numéricos (10 min exploración, 15 min por prueba atorada, 5 min de corrida final).
- La plantilla de prompt pide LOCALIZACIÓN (archivo → función → líneas), no la solución ni el archivo regenerado.
- El ciclo corre la suite DESPUÉS de cada parche (nunca acumular cambios sin verificar).
- Está la regla del verde parcial (4/6 avanza) y la del handler+service (los tests miran la API, no la pantalla).
- Lo escribiste completo de memoria, en ≤ 8 minutos.
