## Caja de pagos con denominaciones ilimitadas — por qué el cajero greedy falla
type: multiple_choice
tiempo: 3

Un kiosko de devoluciones entrega reembolsos en efectivo con denominaciones `[1, 3, 4]` (existencias ilimitadas de cada una) y debe entregar el monto EXACTO con el mínimo número de billetes; si un monto no se puede formar, reporta -1. Para un reembolso de 6, el cajero «greedy» (tomar siempre la denominación más grande que quepa) entrega 4+1+1 = tres billetes. ¿Cuál es el diagnóstico correcto?

### Opciones
- [x] El greedy es subóptimo y el problema pide DP: la respuesta correcta para 6 es DOS billetes (3+3), que el greedy nunca ve porque comprometerse con el 4 deja un residuo de 2 que solo se cubre con unos. El estado es `dp[m]` = mínimo de billetes para formar exactamente `m`, la transición es `dp[m] = min(dp[m - d] + 1)` sobre las denominaciones que caben, el caso base es `dp[0] = 0`, y un `dp[monto]` que queda en infinito se reporta como -1. Con denominaciones arbitrarias no hay prueba de intercambio que sostenga al greedy — y sin esa prueba, los contraejemplos son cuestión de tiempo.
- El greedy es correcto y 4+1+1 es óptimo: tomar la denominación más grande minimiza billetes por construcción, como con las monedas de uso corriente.
- El problema es de backtracking puro: hay que explorar todas las combinaciones de billetes recursivamente, y como los montos del OA son pequeños, la exponencial pasa.
- El estado correcto necesita dos dimensiones, `dp[m][d]` = mínimo de billetes para el monto `m` usando solo las primeras `d` denominaciones, porque sin esa segunda dimensión no se puede controlar qué denominación se usó.
### Justificación
Es el Coin Change del libro (el «knapsack disfrazado de cambio de monedas») con su tripleta exacta: estado `dp[m]`, transición con el mínimo sobre denominaciones que caben, base `dp[0] = 0`, e imposible → -1 cuando el infinito sobrevive. La trampa del libro «hacer greedy donde se necesita DP» aplica literal: el greedy por denominación mayor funciona con sistemas de monedas canónicos, pero `[1, 3, 4]` con monto 6 es el contraejemplo mínimo — si sigues encontrando contraejemplos a tu greedy, esa es la señal de que el problema genuinamente necesita DP, no un ajuste más. El backtracking puro recalcula el mismo subproblema (¿mínimo para el monto m?) por caminos distintos — subproblemas superpuestos es exactamente la condición que hace a la recursión ingenua exponencial y a la memoización necesaria. Y la segunda dimensión sobra en el knapsack NO acotado: como cada denominación se puede reusar, no hay que recordar cuáles «quedan disponibles»; `dp[m]` unidimensional con el bucle hacia adelante ya permite la reutilización — esa dimensión extra pertenece al 0/1, no a este problema.

## Cupones de un solo uso — la dirección del bucle decide qué cuentas
type: multiple_choice
tiempo: 3

Dos promociones sobre el mismo esqueleto de código con arreglo 1D: (A) reembolso con DENOMINACIONES ilimitadas (cada valor se puede usar las veces que sea), y (B) carrito con CUPONES de un solo uso (cada cupón se aplica a lo más una vez). Ambas llenan `dp[0..monto]`. ¿Qué decide la dirección del bucle interno sobre el monto, y cuál corresponde a cada promoción?

### Opciones
- [x] La dirección controla si un mismo elemento puede volver a usarse dentro de la misma pasada: hacia ADELANTE, `dp[m - valor]` ya pudo haber incorporado ese mismo valor antes en esta pasada — reutilización permitida, correcto para las denominaciones ilimitadas (A). Hacia ATRÁS, `dp[m - valor]` todavía es el resultado de ANTES de considerar este elemento — cada cupón cuenta a lo más una vez, correcto para los cupones (B). Confundir la dirección reintroduce o excluye la reutilización incorrectamente, y el bug no truena: entrega números plausibles pero mal contados.
- La dirección es una preferencia de estilo: adelante y atrás recorren las mismas celdas, así que producen la misma tabla en ambos problemas.
- Hacia atrás es solo una optimización de memoria para no copiar la fila anterior; la corrección no depende de la dirección sino de inicializar bien `dp[0]`.
- La dirección depende de si el problema pide mínimo o máximo: los mínimos se llenan hacia adelante y los máximos hacia atrás.
### Justificación
Es la nota central de la sección de Coin Change y la trampa «orden de evaluación incorrecto» del libro: en el knapsack no acotado el bucle va hacia adelante — permitiendo que `dp[m - moneda]` ya haya incorporado esa misma moneda en esta misma pasada —, mientras el 0/1 recorre el monto hacia atrás precisamente para que cada elemento se use a lo más una vez. Esa diferencia de dirección «es exactamente el tipo de detalle que decide si tu solución cuenta correctamente o repite/excluye elementos incorrectamente», y la pregunta previa del libro es siempre la misma: ¿el problema permite reutilizar el elemento? «Preferencia de estilo» es falso: las celdas visitadas son las mismas pero el CONTENIDO de `dp[m - valor]` al momento de leerlo cambia — antes o después de incorporar el elemento actual, y ahí vive toda la semántica. Lo de la memoria confunde el porqué: el bucle hacia atrás en el 0/1 no es un truco de espacio, es lo que preserva la semántica «sin este elemento» al comprimir la tabla a una dimensión. Y mínimo/máximo es irrelevante para la dirección: ambos operadores funcionan en ambas direcciones; lo que la dirección gobierna es la reutilización, no la función objetivo.

## Campañas en slots consecutivos — la adyacencia prohibida
type: multiple_choice
tiempo: 3

Una parrilla de promociones tiene N slots consecutivos, cada uno con un ingreso proyectado no negativo. Activar dos slots ADYACENTES canibaliza la conversión, así que está prohibido. Hay que maximizar el ingreso total. Con N hasta 10⁵, ¿cuál es el plan y su tripleta?

### Opciones
- [x] DP lineal con la recurrencia de adyacencia: estado `dp[i]` = máximo ingreso considerando los primeros `i` slots; transición `dp[i] = max(dp[i-1], dp[i-2] + valor[i])` — o activas el slot actual (sumando el mejor de hace DOS posiciones, porque el inmediato anterior queda excluido) o no lo activas (heredando el mejor hasta el anterior); base: cero slots dan 0. Como cada paso solo mira las dos posiciones previas, dos variables rodantes bastan: O(n) tiempo y O(1) espacio.
- Greedy: ordenar los slots por ingreso descendente y activar el mayor disponible marcando sus dos vecinos como bloqueados, hasta agotar candidatos.
- Separar los slots en posiciones pares e impares, sumar cada grupo completo y quedarse con el mayor de los dos totales: como dos pares nunca son adyacentes, esa partición ya es óptima.
- Ventana deslizante de tamaño 2: mantener la mejor suma de cada par de slots no adyacentes y avanzar la ventana acumulando.
### Justificación
Es House Robber, que el libro presenta como «el DP lineal más simple posible con una restricción de adyacencia» y pide tener como reflejo absoluto: la disyuntiva por slot es binaria (activar → excluyes al vecino inmediato, por eso sumas sobre `dp[i-2]`; no activar → heredas `dp[i-1]`), y la implementación de dos variables rodantes es O(n)/O(1). El greedy de «mayor primero bloqueando vecinos» falla con contraejemplos pequeños — con ingresos [5, 6, 5], toma el 6, bloquea ambos 5 y entrega 6 cuando el óptimo es 10 — porque comprometerse con un máximo local no considera lo que ese bloqueo cuesta. La partición pares/impares también falla: con [4, 1, 1, 4] los pares suman 5 y los impares 5, pero el óptimo es 8 (primero y último) — la solución óptima puede mezclar paridades mientras no tome dos consecutivos, y esa mezcla es justo lo que la DP explora. Y la «ventana deslizante de tamaño 2» ni siquiera modela el problema: la decisión en el slot `i` depende del acumulado óptimo global hasta `i-2`, no de una ventana local de dos elementos — es vocabulario de otro patrón pegado a la fuerza.

## Etiquetas de picking concatenadas — de «¿se puede?» a «¿cuánto cuesta?»
type: multiple_choice
tiempo: 4

Un escáner recibe una cadena sin separadores (por ejemplo `"catsanddog"`) que debe segmentarse por completo en tokens de un catálogo; cada token del catálogo tiene un costo de procesamiento. Hay que reportar el costo MÍNIMO de segmentar la cadena completa, o -1 si ninguna segmentación total existe. Ya conoces la versión booleana («¿se puede segmentar?»). ¿Qué cambia y qué no?

### Opciones
- [x] El estado y la estructura NO cambian; solo cambia qué combinas en cada paso: `dp[i]` pasa de ser un booleano («¿los primeros i caracteres se pueden segmentar?») a ser un número («costo mínimo de segmentar los primeros i caracteres»), la transición pasa de OR sobre los cortes a MIN — `dp[i] = min(dp[j] + costo(s[j:i]))` sobre las `j` donde `s[j:i]` es token del catálogo y `dp[j]` es alcanzable —, la base sigue siendo `dp[0] = 0` (prefijo vacío, costo cero), y el imposible se reporta como -1 cuando `dp[n]` queda en infinito. Reconocer esta equivalencia estructural es exactamente lo que la variante examina.
- Greedy sobre el catálogo: en cada posición consumir el token MÁS LARGO que empate y avanzar; si el costo importa, consumir el token más barato que empate.
- El estado necesita crecer a `dp[i][ultimo_token]`, porque el costo mínimo hasta `i` depende de qué token cerró la segmentación anterior.
- Backtracking con poda: enumerar todas las segmentaciones válidas acumulando costos y quedarse con la mínima; el catálogo acota las ramas lo suficiente para que la enumeración pase.
### Justificación
Es la sección Word Break del libro con su moraleja explícita: la única diferencia real entre la versión booleana y la de costo es que `dp[i]` pasa de bool a número que minimizas — «la lógica de revisar todos los cortes posibles j antes de i, y combinar con lo que ya sabes de dp[j], es idéntica» — y esa es «exactamente la señal que este módulo quiere que interiorices»: cuando Amazon convierte un clásico de sí/no en costo mínimo, casi siempre el estado y la recurrencia no cambian, solo el operador (OR booleano → MIN numérico). El greedy por token más largo (o más barato) falla porque un empate local puede bloquear la única segmentación total o encarecerla — con catálogo {"cat", "cats", "and", "sand", "dog"}, consumir "cats" deja "anddog", que aún segmenta, pero consumir siempre-el-más-largo no garantiza ni completar la cadena ni el costo mínimo; sin prueba de intercambio, es una apuesta. La dimensión `ultimo_token` sobra: el costo es aditivo por token y no hay ninguna regla que acople un token con el siguiente, así que el prefijo `i` captura toda la información necesaria — inflar el estado sin necesidad es el error simétrico al de no capturar suficiente. Y el backtracking enumera un número de segmentaciones que crece exponencialmente con los cortes válidos, recalculando el mismo sufijo una y otra vez — subproblemas superpuestos: la definición de cuándo memoizar deja de ser opcional.

## Demanda estrictamente creciente — ¿cuadrático o patience?
type: multiple_choice
tiempo: 4

Auditoría de una cadena de picking: dada la secuencia de pesos de n paquetes en orden de llegada, reporta la longitud de la subsecuencia más larga con pesos ESTRICTAMENTE crecientes. Caso (A): n ≤ 2,000. Caso (B): n = 2×10⁵. ¿Qué implementación corresponde a cada caso?

### Opciones
- [x] En (A) el O(n²) clásico basta y es la jugada correcta bajo reloj: `dp[i]` = LIS que termina en la posición `i`, doble bucle, unos 4×10⁶ pasos — trivial para cualquier límite de tiempo y más rápido de escribir sin errores. En (B) el cuadrático son 4×10¹⁰ pasos — no cabe — y toca la técnica O(n log n) de `tails`/patience: mantener el menor valor final posible para cada longitud de subsecuencia y colocar cada elemento con binary search. La restricción de tamaño DECIDE la implementación; escribir patience para n = 2,000 es tiempo de examen regalado, y escribir el cuadrático para 2×10⁵ es un TLE seguro.
- El O(n²) sirve en ambos casos: sigue siendo polinomial, y los jueces de OA aceptan cualquier solución polinomial sin fijarse en la constante.
- Patience/`tails` sirve para ambos y también para cualquier variante: si mañana agregan la restricción «pesos consecutivos de la subsecuencia difieren en a lo más K», el mismo arreglo de tails la absorbe con un ajuste en el binary search.
- Ordenar una copia de los pesos y calcular la subsecuencia común más larga entre el original y la copia: esa reducción a LCS es la vía estándar y corre en O(n log n).
### Justificación
El libro da las dos mitades: la LIS clásica O(n log n) con `tails` viene de `cp7-dp-competitivo` (mantener el menor valor final por longitud), y la decisión por restricciones es el pan del OA cronometrado — con n ≤ 2,000 el cuadrático (~4×10⁶ operaciones) entra holgado y minimiza el riesgo de bug, con 2×10⁵ el cuadrático (~4×10¹⁰) excede por órdenes de magnitud cualquier presupuesto razonable de tiempo, así que patience deja de ser opcional. «Polinomial luego pasa» es falso: los límites del OA están calibrados para separar exponentes — n² con n = 2×10⁵ no termina a tiempo aunque sea polinomial. La tercera opción contradice la sección 5.2 del libro palabra por palabra: con la restricción de salto máximo K, `tails` YA NO aplica directamente, porque necesitas el máximo de longitudes sobre un RANGO de valores (`[x-K, x-1]`), no el menor final por longitud — el estado se redefine sobre valores y la consulta exige un segment tree/BIT de máximo de rango; creer que tails «absorbe» esa variante es exactamente el error que la sección existe para prevenir. Y la reducción a LCS es real pero el LCS clásico es O(n²) — venderla como O(n log n) es falso, y aun como cuadrático es un rodeo que solo re-obtiene lo que el `dp[i]` directo ya da.

## Bonos en el organigrama — el par incluyo/no-incluyo
type: multiple_choice
tiempo: 4

Un organigrama es un árbol: cada empleado tiene a lo más un jefe directo y cada nodo trae el monto de un bono. Política: no se puede premiar a un empleado Y a su jefe directo (arista padre-hijo); empleados del mismo nivel o abuelo-nieto sí pueden coincidir. Maximiza la suma de bonos. ¿Cuál es el plan correcto?

### Opciones
- [x] DP en árbol con un PAR de valores por nodo, calculado en post-orden: `incluyo(nodo)` = bono del nodo + suma de `no_incluyo(hijo)` sobre sus hijos (premiarlo excluye a TODOS sus reportes directos), y `no_incluyo(nodo)` = suma de `max(incluyo(hijo), no_incluyo(hijo))` (no premiarlo deja a cada hijo libre de tomar su mejor rama). La respuesta es el máximo del par en la raíz. Es House Robber con la adyacencia definida por aristas del árbol en vez de vecindad en el arreglo — la misma disyuntiva incluir-excluye-al-vecino, aplicada sobre la recursión del árbol.
- Alternar niveles: premiar todos los niveles pares del organigrama, luego todos los impares, y quedarse con la mayor de las dos sumas — como dos nodos del mismo nivel nunca son jefe y reporte, cada suma es válida y una de las dos es óptima.
- Greedy por monto: ordenar los bonos descendente y premiar al de mayor bono disponible, descartando a su jefe y a sus reportes directos, hasta agotar candidatos.
- Aplanar el árbol con un recorrido BFS a un arreglo y correr el House Robber lineal `dp[i] = max(dp[i-1], dp[i-2] + v[i])` sobre ese arreglo: el orden por niveles preserva las relaciones jefe-reporte como adyacencias del arreglo.
### Justificación
Es la conexión que el libro señala dos veces: House Robber III «es, literalmente, House Robber aplicado sobre la recursión de un árbol», con el par incluir/no-incluir por nodo — y reconocer esa conexión «te da la mitad del trabajo gratis». El par es necesario porque el padre necesita AMBAS respuestas de cada hijo: si se incluye, necesita `no_incluyo(hijo)`; si no, el mejor de los dos — devolver un solo máximo por subárbol pierde la información para decidir arriba. Alternar niveles es válido pero no óptimo: en una cadena jefe→reporte→reporte→reporte con bonos 4, 1, 1, 4, los niveles pares suman 5 y los impares 5, pero el óptimo es 8 (los dos extremos) — la solución óptima mezcla niveles mientras respete las aristas, igual que en la versión lineal mezcla paridades. El greedy por monto máximo repite el fallo clásico: un bono grande cuyo descarte de vecinos cuesta más de lo que aporta (jefe de 6 entre dos reportes de 5) lo hunde, y no hay argumento de intercambio que lo salve. Y aplanar por BFS destruye la estructura: dos posiciones consecutivas del arreglo BFS suelen ser HERMANOS (que sí pueden coincidir) y un jefe-reporte real puede quedar a distancia arbitraria — la restricción vive en las aristas del árbol, no en la vecindad del arreglo aplanado.

## Dos variables que ruedan — trace de House Robber
type: trace
tiempo: 4

La versión O(1) de espacio del maximizador con adyacencia prohibida, tal como la da el libro:

```python
def maximo_botin(valores):
    anterior2, anterior1 = 0, 0
    for v in valores:
        actual = max(anterior1, anterior2 + v)
        anterior2, anterior1 = anterior1, actual
    return anterior1
```

Con `valores = [2, 7, 9, 3, 1]`, ¿qué devuelve la función?

### Opciones
- [x] Devuelve 12. La corrida, paso a paso con el par (anterior2, anterior1): arranca en (0, 0); v=2 → actual = max(0, 0+2) = 2, par (0, 2); v=7 → actual = max(2, 0+7) = 7, par (2, 7); v=9 → actual = max(7, 2+9) = 11, par (7, 11); v=3 → actual = max(11, 7+3) = 11, par (11, 11); v=1 → actual = max(11, 11+1) = 12, par (11, 12). El 12 corresponde a tomar los valores 2, 9 y 1 — ninguno adyacente a otro.
- Devuelve 16: los dos valores más grandes son 7 y 9, y el máximo botín es simplemente su suma.
- Devuelve 11: tras procesar v=3 el par queda en (11, 11), el empate indica que el óptimo ya se alcanzó y las iteraciones restantes no pueden mejorarlo.
- Devuelve 10: la corrida óptima alterna posiciones impares y toma 7 + 3.
### Justificación
Verificada a mano arriba, iteración por iteración: el resultado es 12 = 2 + 9 + 1, el conjunto óptimo sin dos adyacentes. La recurrencia es la del libro — o tomas el valor actual sumándolo al mejor de hace dos posiciones (`anterior2 + v`, porque el inmediato anterior queda excluido) o heredas el mejor anterior (`anterior1`) — y solo se necesitan las dos posiciones previas, por eso el par rodante. «16 = 7 + 9» viola la restricción: 7 y 9 son adyacentes en el arreglo, exactamente lo que el problema prohíbe — la suma de los dos mayores no es un candidato válido. «11» malinterpreta el empate: (11, 11) tras v=3 solo dice que tomar o no tomar el 3 da lo mismo HASTA AHÍ; `anterior2` subió a 11, y eso es lo que habilita que el 1 final sume 11 + 1 = 12 — detener la lectura antes de la última iteración es el clásico error de trace. Y «10 = 7 + 3» asume que el óptimo alterna paridades fijas: el conjunto óptimo real (posiciones 0, 2, 4) está en las PARES aquí, y en general puede mezclar, como muestra cualquier caso tipo [4, 1, 1, 4] donde el óptimo son los extremos.

## El precio de la tabla — monto por denominaciones
type: complexity
tiempo: 3

El kiosko de reembolsos llena `dp[0..M]` para un monto M con k denominaciones, con la doble anidación estándar del Coin Change (bucle externo sobre el monto, interno sobre las denominaciones). ¿Cuál es la complejidad, y qué implica para los límites del OA?

### Opciones
- [x] O(M · k) de tiempo y O(M) de espacio: la tabla tiene M+1 estados y calcular cada uno consulta las k denominaciones; el espacio es la tabla misma. La implicación de examen: el costo crece con el VALOR del monto, no con su número de dígitos — con M = 10⁴ y k = 12 son ~10⁵ pasos (trivial), pero un enunciado con montos de 10⁹ está gritando que esta tabla ya no es el camino y hay que buscar otra estructura para el problema.
- O(k log k): lo dominante es ordenar las denominaciones de mayor a menor; con las denominaciones ordenadas, la tabla se llena en tiempo constante por celda.
- O(2^k): cada denominación se usa o no se usa, así que el algoritmo explora los subconjuntos de denominaciones.
- O(M + k): el bucle externo toca M celdas y el interno toca k denominaciones, y dos bucles se suman.
### Justificación
El libro anota la complejidad literal en el docstring de `monedas_minimas`: O(objetivo × len(monedas)) — cada una de las M+1 celdas evalúa las k denominaciones, y son bucles ANIDADOS, no consecutivos, así que multiplican. La nota de examen importa porque el tamaño de la tabla depende del valor numérico de M (no de cuántos bits ocupa), y los límites del enunciado te dicen si la tabla cabe: es el reflejo de leer restricciones antes de comprometerte con un plan. «Ordenar las denominaciones» pertenece al cajero greedy — que este mismo banco ya mostró subóptimo con [1, 3, 4] — y ningún orden hace constante el llenado de una celda: el mínimo sobre k opciones cuesta k. «2^k subconjuntos» confunde el modelo: en el knapsack NO acotado no se decide un subconjunto de denominaciones (cada una puede usarse cero, una o muchas veces); la DP existe precisamente para no enumerar combinaciones. Y «M + k» suma lo que la anidación multiplica: el bucle interno corre completo POR CADA celda del externo — confundir composición con concatenación de bucles es el error de conteo más básico que el OA castiga en las preguntas de complejidad.

### Solución
```javascript
function monedasMinimas(monedas, monto) {
  const INF = Number.POSITIVE_INFINITY;
  const dp = new Array(monto + 1).fill(INF);
  dp[0] = 0;                                   // caso base: 0 monedas para formar 0
  for (let m = 1; m <= monto; m++) {
    for (const moneda of monedas) {
      if (moneda <= m && dp[m - moneda] + 1 < dp[m]) {
        dp[m] = dp[m - moneda] + 1;
      }
    }
  }
  return dp[monto] === INF ? -1 : dp[monto];
}

### Pistas
- El estado en una frase antes de teclear: `dp[m]` = mínimo de monedas para formar EXACTAMENTE `m`; la base `dp[0] = 0` resuelve gratis los bordes de monto cero.
- Reutilización ilimitada → el bucle del monto va hacia ADELANTE: `dp[m - moneda]` ya pudo haber usado esa misma moneda en esta pasada, y eso es exactamente lo que quieres.
- El imposible no se adivina: inicializa en infinito y traduce a -1 SOLO al final — si conviertes a -1 dentro de la tabla, el mínimo lo elige como si fuera el mejor valor.

## Drill: robarCasas
type: code

El drill del DP lineal con adyacencia prohibida: maximiza la suma activando slots de una parrilla sin tomar dos consecutivos. Validado localmente contra los casos de abajo — no es el juez del OA. function robarCasas(valores) {
  let anterior2 = 0;
  let anterior1 = 0;
  for (const v of valores) {
    const actual = Math.max(anterior1, anterior2 + v);   // tomar v excluye al vecino inmediato
    anterior2 = anterior1;
    anterior1 = actual;
  }
  return anterior1;
}
```

### Pistas
- La disyuntiva por slot es binaria: tomarlo (sumas sobre el mejor de hace DOS posiciones) o no (heredas el mejor de la posición anterior) — `max(anterior1, anterior2 + v)`.
- Arrancar el par en (0, 0) resuelve gratis el arreglo vacío y el de un elemento: no necesitas casos especiales si el estado inicial es honesto.
- El caso [2, 1, 1, 2] delata al greedy y a las paridades fijas: el óptimo (2 + 2) toma los extremos, saltándose DOS posiciones de en medio — la recurrencia lo encuentra sola.
